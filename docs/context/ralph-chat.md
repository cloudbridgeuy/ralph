# ralph chat Command

`ralph chat` is a single long-running chat with one persistent memory. Messages run on one persistent `claude -p` process that chat resets under a policy (see [Process reset](#process-reset)). The model sees a compressed view of the whole chat and can open details through a private MCP server. Bare `ralph` (no subcommand) runs `ralph chat`.

## CLI

```bash
ralph chat [--skill <PATH>]... [--permission-mode <MODE>] [--worktree-dir <DIR>] [--no-inbox-sound] [--no-inbox-notification]
ralph                      # same as ralph chat with defaults
```

- `--skill <PATH>` (repeatable) adds a skill directory. See Skills.
- `--permission-mode <MODE>` sets the claude permission mode for turns and claude workers. Precedence: flag, `RALPH_CHAT_PERMISSION_MODE`, `[chat] permission_mode` in the ralph config, then `auto`. Resolved once at chat start. `ralph ask` has its own setting.
- `--worktree-dir <DIR>` sets where spawned workers get their worktrees. Precedence: flag, `RALPH_WORKTREE_DIR`, `[chat] worktree_dir`, then `.worktrees`. A leading `~` expands to home; a relative path resolves against the repo root of each spawn, not the chat's cwd. The chat process resolves the rest on each spawn and close.
- `--wrap-width <N>` caps the wrap width of rendered replies, worker reports and the prompt area (status line, draft, footer). Precedence: flag, `RALPH_WRAP_WIDTH`, `[chat] wrap_width`; `0` or unset = terminal width. The smaller of the cap and the terminal width wins, read at each render. A value that is not a whole number stops chat start with an error. See [configuration](../configuration.md).
- `--no-inbox-sound` and `--no-inbox-notification` turn off the inbox alert parts (see Inbox alerts).
- `--store <DIR>` sets the store path. Precedence: `--store`, then `RALPH_CHAT_STORE`, then `~/.ralph/chat`; an empty `RALPH_CHAT_STORE` counts as unset, and a missing home directory is an error when neither is set. A relative path resolves against the cwd at startup. The directory is created at startup. Parallel chat instances need separate stores; otherwise they share the log, `history.txt`, `editor.md`, and `inbox/`.
- Hidden subcommands: `ralph chat-mcp --store <DIR> --socket <PATH>` and `ralph chat-nap --store <DIR> [--timeout 600]` (`NAP_TIMEOUT_SECS`). Both are spawned by ralph itself.
- Input is a reedline editor on the main thread with prompt `>>> `. Enter sends; Alt-Enter or Ctrl-J inserts a newline; Ctrl-G opens `[chat] editor` (an argv list such as `["nvim", "-c", "normal! Go", "-c", "startinsert"]`; the file path is appended as the last arg; an empty list warns and falls back), else `$VISUAL`, `$EDITOR`, or `vi` (one program, no splitting), on `<store>/editor.md`, prefilled with the last assistant reply, a `──── write below ────` line, and the draft; the text below the last separator line replaces the draft (never sent; an empty result keeps the old draft). Ctrl-V pastes a clipboard image as `[Image #N: path]` (see [Images](#images)). Esc Esc clears the whole draft (Ctrl-Z undoes it, Ctrl-O redoes). With `[chat] edit_mode = "vi"` the editor uses reedline's vi insert and normal keymaps: Esc leaves insert mode, so Esc Esc does not clear; Ctrl-U clears the whole draft in insert and normal mode instead. The insert keymap keeps Alt-Enter, Ctrl-J, Ctrl-V, Ctrl-G and Ctrl-O; normal mode keeps Ctrl-G. Visual mode is off: when a key (`v`) enters it, the edit-mode wrapper switches straight back to normal mode before reedline paints, so no selection starts; `fv`, `tv` and `rv` still work. The prompt indicator is `>>> ` in insert mode and `::: ` in normal mode. The pure `chat_edit_mode` core module resolves the key and the indicator. Up/Down and Ctrl-R use the history file `<store>/history.txt` (1000 entries). Ctrl-D or Ctrl-C at the prompt quits; an empty message does nothing unless reports are unread (see Worker inbox); `[chat] empty_submit` and `empty_prompt` change this (see [configuration](../configuration.md)). A turn has no time limit. Ctrl-C during a turn cancels that turn (nothing is stored) and returns to the prompt with the message restored as the draft; SIGTERM and SIGHUP end the chat. While a turn runs, chat keeps a `<store>/turn` marker (`user` or `worker`, removed when the turn ends); the chat socket server reads it so `spawn_worker`, `close_worker` and `watch` work only in a user-started turn (`reply` also in a worker turn).
- A dark-gray full-width rule (the shared termimad skin's `---`, default gray(6) `―`) prints before the turn and after the reply.

## Turn loop

1. A launch (`Store::load_after_nap`) first waits for a running nap, then `Store::load_settled` takes a shared `LOCK`, then reads log and tree. It waits only while an append or a nap commit holds `LOCK` (one fsynced line each), not for curator calls. Nodes that are still pending show as described in [Pending summaries](#pending-summaries).
2. `split_view(entries, tree, VIEW_LINES, recent_history_tokens)` builds the memory view in two parts. The cut snaps down to a multiple of `OLDER_VIEW_STEP` (32 entries). The older part is the view (`VIEW_LINES`, 200 lines) of every entry before the cut. So the older view stays byte-identical across respawns until the step boundary moves or nap adds summaries. The tail starts at the cut. Entries between the cut and the verbatim run show as summaries. The rest is the verbatim run: the newest entries within the recent-history budget (see [Recent history](#recent-history)). The two cover every entry once. The view is built only when the turn needs a new `claude` process (step 4); a turn on a live process does not use it.
3. For a worker turn, one `worker` entry per report is appended to the log. The user message waits for step 6.
4. One `claude` process serves the whole chat. The first turn (and any turn after the process died or a turn failed) runs `build_chat_command`: a fresh `claude --verbose --permission-mode <MODE>` (the chat's resolved mode) with isolation args, `--append-system-prompt <system prompt + older view>` (`turn_system_prompt(custom, older)`: the built-in text, or with `[chat] prompt_file` the file text in place of the behaviour rules and with the tool contract kept, then each `append_prompt_files` text, then the older view; just the prompt while the older part is empty; files are read once at chat start into `CustomPrompt`), the MCP args, `--settings` with `autoCompactEnabled` false (merged with the CLAUDE.md exclude), `--input-format stream-json --output-format stream-json` and `-p`. Memory is injected at process start only: the first message is the tail lines, a blank line, `New message:`, then the message. Later turns send the message text only, as one stream-json `user` line (`ralph_core::stream::user_line`); the process keeps the conversation. The command starts with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, so claude starts no background tasks and the process stays alive after each `result`. The `Session` owns the piped stdin and the stdout/stderr reader threads for its whole life, and `Session::turn` can be called many times. A turn ends at the top-level `result` event (parsed with `ralph_core::stream::result_is_error`, not text-matched); if claude exits mid-turn ralph reads its remaining lines for up to 3 s (`EXIT_GRACE`) before it finishes; chat turns have no time limit (`timeout_secs` is not used). The process stays up and the next turn reuses it. The session is dead, and the next turn respawns it from the store, when the process exits, stdout closes before `result`, or a turn is killed. Before each turn chat polls the child with `waitid` and `WNOWAIT`, which does not reap it, so a process that exited while idle is dropped and respawned. Before it sends the message, `Session::drive` discards the stdout lines that the process wrote after the last `result`. If one of them is a `result`, the turn fails with `LeftoverResult` and chat respawns the process, as for a process that exited while idle. A line that arrives after this check still goes into the turn: stream-json lines carry no turn id. A turn that exits non-zero, has no reply, or errors drops the session too, as does a reset (see [Process reset](#process-reset)). On cancel or SIGINT the session writes one `control_request` `interrupt` line (`interrupt_line`) and keeps reading until `result`. With no `result` within 3s it kills the process group and the session is dead. Dropping the `Session` closes stdin, waits, and kills after 3s. On every chat exit, a lost terminal included (`watch_input` drops the session before `exit`), ralph kills the claude process group before it reaps claude and never signals the group after that (`group_signal_safe`); nap and inbox-alert helpers start through `spawn_detached`, which reaps them on a thread. There is no `--resume` and no `--agent`. Worker triggers use the same path.
5. Output goes through the spinner subprocess runner and `StreamProcessor`, as in `ralph ask`.
6. On exit code 0 with response text, the user message (if any) and then the reply are appended verbatim and a detached `ralph chat-nap` is spawned (stdio null; spawn failure only warns). Otherwise a warning `chat turn failed (exit N)` prints and the loop continues. Only the subprocess call is wrapped in `retry_on_outage`: a non-zero exit whose stderr or response text matches an outage marker, waits 2s then 8s and respawns the process from the store with the first-message form and runs the turn again (at most 2 retries), warning `chat turn hit an outage (<kind>); retrying in Ns (k/2)`. The wait polls the cancel flag every 100ms, so Ctrl-C ends the turn as a cancel; SIGTERM and SIGHUP end it too. Cancel and interrupt are never retried. If the first stdin write to a reused process fails (it died after the check), the turn starts a fresh process from the store once and sends the first-message form; the dead process never got the message, so it is sent once, and this is not an outage retry. After the retries run out, or for any non-outage failure, the warnings and draft restore below apply unchanged. Only the final attempt writes a usage record, and only the first turn of each process carries the view and prompt-size fields.
7. A turn that is cancelled (Ctrl-C), fails, or hits a subprocess error stores nothing for a user message, including any partial reply, and returns to the prompt with the message preloaded as the draft (`draft_after`). A cancelled turn also drops the claude process, so the next turn respawns it from the store. Worker report entries from step 3 stay in the log. SIGTERM and SIGHUP end the chat.

The system prompt tells the model that the message starts with the compressed chat, that `#<id>` lines are summaries, to use `zoom`, `recall` and `search` before guessing or asking (`read` pages a range of ids), that `[worker ...]` messages come from workers, not the person, and never to claim manual saving. On a worker message the model may `reply` only with an answer already settled in the chat (a decision the person made, approved scope, a step in an agreed plan); merges, pushes, PRs, Linear status changes, new scope and anything public go to the person, and every worker reply is listed in its next message to the person. `spawn_worker` and `close_worker` are only for what the person asked in their latest message, `abandon` only when the person said to drop the work, and `force` only when the person said to close a worker of another chat. The chat MCP server enforces this with the pure `worker::command_allowed`: in a turn the person started every worker command is allowed, in a worker-triggered turn only `reply` is, and anything else is refused. Messages that start with `[worker watch:<name> · watch]` are watch reports from the `watch` tool, not from an agent or the person; before calling `watch` the model shows the exact command and waits for approval. Its delegation rules keep turns short: the model reads inline only to scope (at most 3 tool calls per question), sends multi-file reads, broad searches and test runs to `evidence-collector`, all code edits to `implementer`, and fixing work that fell short to `reviser`, and every dispatch prompt states goal, question, known facts, owned files, output cap, stop condition and tool budget, "Report not-found, do not widen scope.", and "You are a subagent. Don't run mem." After 2 failed repair rounds it diagnoses; after a 3rd it waits for the person. It also must lead with the answer and end with one next step, call `help` first when the person asks how ralph chat itself works, show a 3-5 line plan when a request is ambiguous, treat a worker "done" as unverified until it checks the diff, tests, git and Linear, cite the `#<id>` behind facts from older chat, and say it has no erase tool when asked to forget.

## Queued messages

Ctrl-Q during a turn, or typing text, pauses the display of the turn output and opens a queue editor. Typed text seeds the editor, so no typing is lost. The turn keeps running and the output is held.

- Enter with text adds the text as a queue entry, except a read-only command (`/help`, `/workers`, `/inbox list`, `/inbox peek N`, `/watch list`, a bare `/watch`, `/schedule` and `/schedule list`, and the usage or unclosed-quote replies of `/inbox`, `/watch`, `/schedule` and `/diff`): it runs at once, prints before the held output returns, and is not queued. The turn is not cancelled. Other commands (`/inbox`, `/inbox drop N`, `/hold`, `/watch start`, `/watch stop`, `/schedule cancel`, `/diff` with a target) stay queued. Empty Enter or Ctrl-D adds nothing.
- Ctrl-Q in the editor backs out: a non-blank draft is added as the last entry, and the queue is held. The turn is not cancelled. At turn end ralph sends nothing and puts the entries, joined with a blank line, in the next prompt. Ctrl-Q during the same turn opens the editor again; the queue stays held.
- Each of these closes the editor, prints the held output, and resumes live output.
- Ctrl-C in the editor (a host command, `queue_ctrl_c`) clears a non-empty draft and the turn keeps running; on an empty draft it cancels the turn and holds the queue.
- While the editor is open, a queue block follows the mode block in the status bar: `turn running · QUEUED N`, or `turn done · QUEUED N` once the turn ended (no `· QUEUED N` part at 0 entries). Compact forms: `running · QN` / `done · QN`, then `▶ QN` / `✓ QN`. A held queue (after a back-out or an editor Ctrl-C) says `HELD` instead: `turn running · HELD N`, `running · HN`, `▶ HN`, and the `done` / `✓` forms likewise. When the bar is too narrow, the block is dropped after mail and before the mode block. The turn's end repaints the editor through its reedline repaint signal, so the block flips without a key press. The mode block keeps `NAP`, `INBOX`, `WORK` or `IDLE`.
- Nothing sends while the editor is open. A turn that ends meanwhile waits for the editor to close.
- After a normal reply, ralph joins the entries with a blank line, in typed order, and sends them as one message as if typed at the prompt. Slash commands and `!` cells behave as at the prompt.
- Only the merged text goes to `history.txt`.
- After a cancel, a failed turn, an editor Ctrl-C, or a back-out, ralph sends nothing and puts the entries, joined with a blank line, in the next prompt. A restored cancelled message comes first, then a blank line, then the entries. On exit (SIGTERM or SIGHUP) the entries and any typed text are saved to the chat history, and one line `N queued message(s) not sent; saved to history.` goes to stderr.
- Text typed during a turn opens the queue editor seeded with it (`chat_typed::typed`): all printable text of the read, before and after a Ctrl-Q, with Tab and inner line breaks kept. Control bytes, arrows and other escape sequences, Alt keys, bracketed-paste markers (the paste content stays) and invalid UTF-8 are dropped; a read with no text and no Ctrl-Q is ignored. A read that ends inside a UTF-8 character or an escape sequence waits up to two 10 ms polls for the rest. Ctrl-C and Ctrl-Z still signal (the terminal keeps ISIG). Bytes left in stdin when the turn ends are read, not flushed; their text is never sent but joins the next prompt draft, after the draft and the queue entries. If the input closes, ralph stops reading keys during the turn. Ctrl-Q at the idle prompt does nothing.

## Suggested reply

The chat-mcp tool `suggest_reply` takes one required `text`. The socket server parses it with the pure `chat_suggestion::parse_suggestion` (trimmed; empty, a line break, or more than 200 characters is a tool error that says what to fix, and the text is never cut) and stores it in an in-memory slot owned by the running chat; a later call replaces the earlier one. It has no risk marker and no turn check. The slot is cleared right before each turn starts and taken right after it ends, so a call outside a turn is dropped and a suggestion shows only in the first prompt after the turn that set it.

At turn end the pure `chat_suggestion::prefill` picks the text for the editor, through the same insert path as a restored draft, with the cursor at the end. Held or queued text always wins: a kept message, a held draft or queue entries replace the suggestion, and queued text that ralph sends by itself drops it. The suggestion fills the prompt only after a normal reply. Enter sends it, it is editable, and Ctrl-U clears it (Esc Esc too in emacs mode). Clearing it and pressing Enter follows the normal empty-submit rule. The suggestion is drawn in the `[theme.input] suggestion` color until the first edit, in emacs and vi modes alike; after that the buffer stays in the normal color even if you retype the same words. Held or queued text keeps the normal color. With `NO_COLOR` or no TTY the suggestion is not colored. A suggestion sent unchanged stays in the suggestion color in scrollback, which marks it as accepted. The system prompt and tool description tell the model to call it first, before any reply text, with the exact quoted words of its Next step line, and never to mention it; the tool result repeats that the reply comes next. ralph never parses reply text.

## Worker inbox

Worker reports never interrupt the draft. A watcher thread polls every 500 ms and repaints the prompt in place (reedline `RepaintSignal`), keeping the buffer and cursor.

- Each arriving inbox file moves into the queue `<store>/inbox.json` (oldest first, positions from 1 that shift up when a report leaves); unread is the queue length. A report leaves the queue only when sent to main or dropped, and is deleted from the file. An old file with `next_id`, `id` and `read` fields still loads; its read entries are dropped. Tmux workers have sessions named `ralph-<project>-<id>` (`<project>` = the git top-level folder name, letters, digits and dashes only, else `repo`), so the same id in two projects does not collide. Names are cosmetic: at spawn ralph tags each session with the tmux user options `@ralph_store` = the canonical store path and `@ralph_id` = the bare id, and the status line reads the id from `@ralph_id`. Only sessions tagged with this chat's store and an id are listed (sessions without both, including ones started before `@ralph_id`, are ignored; missing tmux or no server means no tmux workers). Headless Cursor and opencode workers are listed from their owner files instead (see [Headless workers](headless-workers.md)). A worker with a `blocked/<id>` marker (a pending permission request) shows `permission` whatever its reports say, and counts as working. A claude worker's state is the status of its latest report, else `running`. A `reply`, a nudge or a spawn writes the marker `<store>/sent/<id>`; while it exists a `done`, `blocked` or `question` status is ignored (a `check` status is not), so the worker shows as working until its next report, which removes the marker (`chat_status::superseded`). For opencode workers ralph asks the chat's own opencode server for `GET /api/session/active` (one call for all workers, every 5 s and after each turn or inbox read, only while an opencode worker runs): `busy` while `ses_ralph<id>` is in it, else the latest report status, else `idle`; if the call fails they fall back to the claude rule.
- Worker status: the worker-mcp tool `set_status` takes one required `text` (at most 120 characters; controls stripped, newlines become spaces, empty or longer is a tool error) and atomically appends to `<store>/status/<id>` (an entry is an RFC 3339 time line and a text line; the file keeps the last 5 entries, oldest first, through the pure `worker::append_status`; an old single-entry file still decodes). It is not a report: it writes no inbox entry or marker and costs no turn. `/workers` shows the newest entry with its age, and `/workers <id>` lists all kept entries; `close_worker` removes the file, spawn clears a leftover one for a reused id, and `set_status` is refused with `Could not set status: worker closed.` once the worker is closed. The worker prompt tells workers to set it when they start and when their activity changes.
- Spawn record: every spawn, whatever the harness, writes `<store>/spawn/<id>` atomically (JSON `SpawnRecord`: optional `ticket`, optional `tracker` of `linear` or `jira`, and `at` in epoch seconds; every field has a serde default, so a file with missing or extra fields still decodes). The pure `worker::resolve_ticket` picks the ticket: an explicit `ticket` wins and gets the tracker of the `[tickets]` key it matches as `<KEY>-<digits>` (else none, the key is kept); without one, the id must be exactly `<KEY>-<digits>` for a configured key (case-sensitive), else the worker has no ticket. Close removes the file with the status file (`close_clear_paths`), and spawn clears a leftover one before it writes the new one. `/workers <id>` reads it.
- Worker check: when `[chat] worker_check_secs` is above 0 (default 60), the watcher thread runs `Monitor::check` every that many seconds. For each running worker it reads the `ready`, `blocked`, `waiting`, `unreported` and `sent` markers (a `sent` marker means the last report is old, so the worker is never counted as reported), and the last real report (`done`, `blocked` or `question`) seen in the inbox or logged as a worker entry in the chat log at start (so a restart keeps it). Only `Claude` workers get a pane capture, skipped when blocked, waiting, or ready and reported; headless workers have no pane. The pure `worker_check::plan` classifies the observations. Markers, all in `<store>/<dir>/<id>`: `blocked` = a permission request is pending, `waiting` = the worker stopped without a report after one reminder, `unreported` = the reminder failed (the hooks and host turn logic that write and clear them are in [MCP tools](#mcp-tools)). A waiting worker gets one nudge per wait, `worker_check::NUDGE_TEXT` ("You stopped without calling report. Call the report tool now: done, blocked or question.") through `Workers::nudge`: typed into tmux or queued to the headless host. Only a report that lands after the nudge re-arms it. Each state change that needs the person posts one inbox message with status `check`, which raises the usual alert; `check` posts never count as reports. Both headless kinds report waiting without an attach hint. A Cursor permission wait posts no check message: the worker host posts its own alert for every pending request (see Cursor permissions); an opencode permission wait posts a check message with instructions to ask the person and relay the answer with `reply`.
- Heartbeat: a Cursor, opencode or Codex worker's host writes `activity/<id>` (`<epoch secs> running|idle`, rewritten only when the second or the flag changes) on every ACP request, notification, turn start and turn end (opencode: every SSE event of the worker's session, running from prompt or turn start to turn end; Codex: every app-server stdout line, with `gone/<id>` on stdout EOF or a `try_wait` exit, written once), and `gone/<id>` when the `agent acp` child exits or its connection ends without a close or chat exit (reason text; the host's 250 ms poll `try_wait`s each live child, which also reaps it, and writes `agent acp exited (<status>)` once per exit) or when the shared `opencode serve` dies without a chat exit (first line `scope server pid <n>`, then the reason). Spawn, resume and close clear both. A server-scope `gone` stays across the server restart; the monitor deletes it after it posts the Dead message, so the next server death alerts again; with `worker_check_secs = 0` no Dead message posts and the marker stays until spawn, resume or close. On each worker check the monitor feeds the markers to the pure `HeadlessState` reducer and `liveness`: a Running worker (not blocked) with no activity for `[chat] worker_quiet_secs` (default 300; measured: silences outside tool calls reached 132 s and a tool call is silent for its whole run, see [Quiet periods](headless-workers.md#quiet-periods-2026-10-22)) is Quiet and posts one `check` message `quiet <n> s; may be stuck on a prompt`; a `gone` marker makes it Dead and posts one message naming the reason. Each fires once per episode; new activity re-arms Quiet. Idle, blocked and starting workers are never Quiet. Runs on the worker check tick, so `worker_check_secs = 0` turns it off. One server death posts a single message naming the server, the reason and every affected worker (the message's worker field is the sorted comma-joined ids). Claude workers: the check remembers which Claude sessions were alive; one that vanishes while its `ready/<id>` marker remains gets `gone/<id>` (`tmux session ended`) and one Dead message. Close clears `ready/<id>` before killing the session (and restores it if the session survives), so a clean close posts nothing. A death while chat is not running posts nothing; the startup leftover hint (`orphan_hint`) lists it.
- Tmux-only check states: trust = the folder-trust dialog shows; unknown = the pane has not changed since the last check, no report came, no Claude busy marker shows in the pane footer (`esc to interrupt`, or `← N agent(s)` with N of 1 or more), and no `unreported` marker is set (that marker means `waiting` is due at the next `idle_prompt`, so the worker counts as working until then). ralph never types into a permission prompt or the trust dialog. Tmux check messages describe waiting, a permission prompt, the trust dialog or an unknown wait and end with `tmux attach -t <session>`. Unknown posts at most once per wait: flips to working (a spinner or status-line redraw) do not post it again; a report, waiting, blocked or trust state re-arms it.
- Inbox alerts: on each poll the watcher compares pending reports with the last poll (reports pending at chat start never alert). For new reports it asks tmux for focus and the pure `inbox_alert::inbox_alert` decides. Inside tmux, `tmux display -p -t $TMUX_PANE '#{pane_active} #{window_active} #{session_id}'` plus `tmux list-clients -t <session> -F '#{client_flags}'` give `Visible` when the pane and its window are active and a client has the `focused` flag, else `Hidden`. Outside tmux, no attached client, or a failed query give `Unknown`, which alerts unless `[chat] inbox_alert_unknown_focus = "silent"`. `Visible` never alerts, and nothing alerts when both `inbox_alert_sound` and `inbox_alert_notification` are off. An alert plays a sound (`afplay /System/Library/Sounds/Glass.aiff` on macOS, else a terminal bell) and, with `inbox_alert_notification`, a notification `<id> <status>, ...` (`osascript display notification` on macOS, else OSC 9, wrapped for tmux passthrough). Limits: a tmux client that never got a focus-out (background pty, terminal without focus reporting) counts as focused and suppresses the alert; focus follows the terminal app, not window visibility (minimised, other Space, second monitor). Only inbox reports alert.
- Status line: a lualine-style bar painted above the input. `status_segments::segments` builds segments from `Status`, `layout` picks which fit, and `chat_statusbar` paints them. Left: mode block (bright, bold; one of `HOLD`, `NAP`, `INBOX`, `WORK`, `IDLE`, see below), the hold block (only during `/hold`: `from <source>` or `from anyone`, then `<source>` or `anyone`; same drop priority as the queue block), the queue block (only in the queue editor; forms in [Queued messages](#queued-messages)), `📬 N unread` (soft; absent at 0 unread), the store path (last two parts). Right, soft to bright: `workers`, `watch`, the schedule cell (armed and running scheduled tasks: `sched <id> <HH:MM>` for one, `+<N>d` after a later day, `N scheduled`, `SN`; absent with none; same colors as `watch`), the thread cell (`ralph_core::chat_thread`), `$cost` (bright, bold). The thread cell has four forms, long to short: `T12/30 · ctx 62% · cache 41m! · shift ~9 msg`, `T12/30 · 62% · 41m!`, `12/30 62% 41m!`, `41m!`. `T` is the turn count on the live claude process over `reset_turns`, 0 with no live process. `ctx` is the last turn's `context_tokens` over `reset_tokens` (`–` with no live process or no `context_tokens`). `cache` is an estimate of the minutes left of the prompt cache, counted from `request_at` (the last streamed main-thread reply line of the last turn) with an assumed one-hour TTL (rounded up; `cold` with no live process, no `request_at` or 0 s left). `!` follows the minutes when the cache creation of the last turn is at least half of its input total, the sum of `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` (`restart_write`). `shift ~N msg` is the entries left until the older view moves to the next 32-entry cut (`entries_to_shift`); only the longest form shows it. On the first turn after a reset the two long forms start with `↻ tokens · `, `↻ turns · ` or `↻ restart · `. `$` is the session total (it leaves out cancelled turns, which write no usage line): the sum, over the claude processes that ran since this `ralph chat` started, of the last `cost_usd` of each process (see [Usage](#usage)). Nap cost is not included. It shows as `$4.12 (+0.31)`, then `$4.12`; the delta is the last turn's cost. It is absent when no turn has a cost. The cell is recomputed every 500 ms and the status repaints once per minute; usage and shift refresh every 5 s and after each turn or inbox read. Limit: ralph sees an idle process death only at the next turn, so until then the cell still counts the process as live. The filler runs the full width in the base background. When the bar is too wide, `layout` compacts the least important segment first, and drops segments only after every form is compact. Drop order, first to last: store, schedule, watches, workers, cost, thread (it shrinks to the cache-only form first), mail, queue; the mode block stays. Colors come only from the `[theme.status]` table (`mode_*` (including `mode_hold_fg` and `mode_hold_bg`), `store_fg`, `workers_fg`, `watches_fg` and `base_bg`, resolved by `status_theme.rs`; keys and defaults in [configuration](../configuration.md#status-line-colors-themestatus)). Segments are plain colored blocks; `[chat] status_powerline = true` adds powerline glyphs between them. With no color (`NO_COLOR` or no TTY) the bar is plain text with `│` between segments and no padding. Not shown: git branch and elapsed time, because the status data has none of them.
- Status modes: `status_mode::mode` picks the mode block, first match wins: `NAP` (a nap holds the `NAP` lock), `INBOX` (unread above 0), `WORK` (a worker is `running`, `busy` or `permission`, or any watch exists), else `IDLE`. Each mode has its own `mode_<name>_fg` / `mode_<name>_bg` keys. The queue, mail, thread and cost blocks take the active mode's colors, so the coloured ends of the bar match the mode block; blocks of the same color run together with no separator in block mode. There is no turn mode; during a turn the bar renders only in the queue editor, where the queue block shows the turn state. `Store::napping` try-locks the store `NAP` file in shared mode and releases it at once, so the probe never blocks. Limit: a nap started by another `ralph chat` on the same store also holds that lock, so the bar shows `NAP` there too.
- Footer: `footer` in `chat_status.rs` builds a hint line, painted under the input with one empty line after it, so the prompt is never the last terminal line. Stock reedline 0.52.1 erases everything below the cursor on repaint, so `vendor/reedline` carries upstream nushell/reedline plus the footer commit (`Prompt::render_prompt_footer`) and `Reedline::with_wrap_width`. The painter soft-wraps the prompt area at the capped width, or at the terminal width without a cap: draft rows break between words (UAX #14, as in replies; a word longer than a row breaks inside it) and each wrapped row starts with the `::: ` continuation prefix. The breaks and prefixes are display-only; the submitted text is what was typed. Mouse-click mapping still assumes character wrap; chat does not enable it through `[patch.crates-io]`. Bracketed paste is on, so a multi-line paste stays in the draft.

### /inbox commands

N is a position in the unread queue: oldest first, from 1, positive integer. Positions shift up after a send or a drop. An unknown N prints `No report N. /inbox list shows the queue.` and changes nothing.

| Command | Effect | Starts a turn |
| --- | --- | --- |
| `/inbox`, or Enter on an empty prompt with reports unread | Sends every queued report to main and deletes it from the queue: one `worker` log entry per report, then one turn with all reports in one message. With nothing unread, `/inbox` prints `No unread reports.` and Enter does nothing. `[chat] empty_submit = "inbox-first"` sends `empty_prompt` instead of doing nothing; `"phrase"` always sends it, so only `/inbox` opens the inbox | yes |
| `/inbox next` | Same as `/inbox` for the oldest report only (position 1). With nothing unread, prints `No unread reports.` | yes |
| `/inbox N` | Same as `/inbox` for the report at position N only. Unknown N prints the not-found message | yes, when the report exists |
| `/inbox list` | Prints one row per queued report, `#<position>  <worker>  <status>  <age>`, columns padded, oldest first (`No reports.` when empty); age is `<n>s` under a minute, `<n>m` under an hour, `<n>h` under a day, else `<n>d`, `0s` for a future time and `?` for an unparsable one (pure `inbox::list`) | no |
| `/inbox peek N` | Prints report N in full with the same header box and markdown as `/inbox`; removes nothing | no |
| `/inbox drop N` | Removes report N from the queue and prints `Dropped report N.`. Before the queue changes, appends one JSON line `{timestamp, worker, status, text}` to `<store>/inbox-drops.jsonl` (append-only, never rewritten); an unknown N logs nothing. The unread count refreshes after a drop | no |
| any other `/inbox` argument | Prints the usage string (below) | no |

Usage string: `Usage: /inbox [next | N | list | peek N | drop N]`. `/inboxfoo` is a normal message. Local commands never start a turn or call the model. Each report that `/inbox`, `next`, `N` or `peek` prints goes under a header box from the pure `frame::worker_header` (`● worker <id> · <status>`, border and status colors from the agent palette: blue border, green for done, red for blocked or failed, yellow for waiting or check by default; sized by display width and cut to the terminal width), then its text as markdown through the chat renderer with the agent `MarkdownTheme` from `[theme.agent]` (see [configuration](../configuration.md); code blocks default to the assistant theme); plain text (header `[worker <id> · <status>]`) when stdout is not a TTY or `NO_COLOR` is set. The model still gets the plain `[worker <id> · <status>]` message.

### /hold

`/hold [<worker-id> | watch:<name> | schedule:<id>]` waits for an inbox report and runs it as a normal inbox turn. ralph answers it itself; it starts no model turn. It is not a read-only command, so during a turn it is queued like `/inbox`.

- The filter is the exact sender of a report (`report.worker`, not the inbox file name): a worker id, `watch:<name>` for a watch report, or `schedule:<id>` for a scheduled task report. `schedule:<id>` also matches the reports of the scheduled worker `sched-<id>`; `/workers schedule:<id>` shows that worker. A bare `/hold` matches any report and the bar reads `from anyone`. A watch needs its `watch:` prefix: `/hold ci` waits for a worker named `ci` and does not match `watch:ci`; there is no automatic mapping. Two or more arguments make the line a normal message (`/hold a b`, `/holdfoo`). An unknown id arms the hold anyway; the bar shows the id.
- One shot. While held there is no prompt. The first matching unread report starts a turn that sends only that report (the same as `/inbox N` for its position); then the hold is off. Nothing re-arms it. Reports that do not match stay unread in the queue.
- A matching report that is already unread when `/hold` runs starts its turn at once.
- Exit keys: Ctrl-Q or Ctrl-D leave the hold and return to the prompt. Ctrl-C also leaves it (the SIGINT sets the interrupt flag, which hold clears) and does not quit the chat. A hangup (stdin closed, SIGTERM, SIGHUP) quits the chat. Hold puts the terminal in the partial mode used by the queue editor (no echo, no line buffering, Ctrl-Q arrives as a key) when stdin is a terminal.
- The status bar shows the `HOLD` mode, above `NAP` in the mode order, and the filter. It is redrawn in place (carriage return, clear line, bar, no newline) each time the status changes (for example a new unread report); one newline is printed when the hold ends, on every exit path. Hold clears a stale interrupt flag on entry. If the inbox ledger cannot be read, hold prints one warning and leaves. A nap or the store lock does not stop the hold; the turn that follows waits as any inbox turn does.
- Pure logic in `ralph_core::chat_hold` (`HoldFilter`, `first_match`, `hold_key`, `redraw`); the polling loop is `crates/ralph/src/chat/hold.rs` and the dispatch is in the chat main loop.

## Watches

A watch is a shell command (`sh -c`) that runs as a child process of `ralph chat`, in its own process group, with stdin closed. Ralph keeps only a bounded tail of its stdout and stderr.

- When the watch exits, ralph posts exactly one `watch` report to the worker inbox. The text holds the exit code (or killed or timed-out note), the output tail, and the follow-up instruction.
- The report goes through the inbox, so it never interrupts the chat channel.
- Stopping a watch posts one "stopped" report. Closing the chat kills every watch and its child processes and posts nothing.
- The runner lives in `crates/ralph/src/watches.rs`; the pure report and tail logic lives in `crates/core/src/watch.rs`.
- Persistent watches are saved as one JSON file each in `<store>/watches/` (spec, `started_at`, timeout deadline, wake deadline), written atomically before the command starts.
- On every `ralph chat` start, `Watches::restore` reruns all saved persistent watches, also after Ctrl-D. Normal records are deleted, never restored. An unreadable record warns and is deleted.
- A restart keeps the original `started_at` and deadlines. The timeout becomes the time left. A command that is exactly `sleep <N>` is rewritten to `sleep <left>` (rounded up to whole seconds). Other commands rerun unchanged.
- A watch whose wake deadline passed posts an exit-0 report right away. One whose timeout deadline passed posts a timed-out report right away (the earlier deadline wins). Neither is spawned.
- The saved record is removed when the watch exits, times out, or is stopped. Closing the chat kills the watch but keeps the record. The pure logic lives in `crates/core/src/watch_store.rs`; the file store is `crates/ralph/src/watch_store.rs`.
- The agent starts a watch with the `watch` tool (see [MCP tools](#mcp-tools)). The chat socket server queues the request by writing a file to `<store>/watch-requests/` (atomic, one JSON file per request). The file is claimed with a hard link, which fails if the name exists, so a second call for an id whose request still waits returns the error `watch <id> is already queued` and queues nothing. The chat watcher thread takes every request on each 500 ms poll, calls `Watches::start`, and deletes the file (`crates/ralph/src/watch_requests.rs`; pure parsing in `crates/core/src/watch_request.rs`). If the start fails (duplicate id, spawn error), chat posts one `watch` report with the error to the inbox.
- Every watch id is stored, reported and shown as `watch:<name>`: generated ids are `watch:w1`, `watch:w2`, ...; a `watch` tool id `foo` becomes `watch:foo`, and an id that already starts with `watch:` is not doubled (`watch_id` in `crates/core/src/watch.rs`). Worker ids allow only letters, digits and dashes, so a watch id never equals a worker id. `/watch stop` accepts `w1` or `watch:w1`.
- Watch reports show as `[worker watch:<name> · watch]`. The system prompt says they come from a watch, not from an agent or the person.
- Approval: the system prompt tells the model to show the person the exact command and wait for approval before it calls `watch`. The prompt enforces this, not the tool. The tool only refuses outside a user-started turn, like `spawn_worker`.
- `/watch` is local: it never starts a turn or calls the model. The shell side is `crates/ralph/src/chat/watch.rs`; the pure parsing and formatting is `crates/core/src/watch_command.rs`.
  - `/watch start [--persistent] <command> -- <follow-up>` starts a watch in this process (`Watches::start`). The input splits at the last ` -- `; both parts must be non-empty. The id is the lowest unused `watch:w<n>` (n from 1) among running and saved watches. It prints `Started <kind> watch <id>.`. There is no timeout flag.
  - `/watch list` prints one row per active watch: id, kind (`normal` or `persistent`), time left, command. Time left is the earlier of the wake deadline (a time-based `sleep N`) and the timeout deadline, shown as `<n>s`, `<n>m`, `<n>h` or `<n>d`, or `—` when there is none. It prints `No active watches.` when empty.
  - `/watch stop <id>` kills the watch and posts its one "stopped" report. A stopped persistent watch is removed from `<store>/watches/`, so it does not come back after a restart. This is the only way to remove a persistent watch. If the id is not running but has a saved record, the record is removed and the message says so. An unknown id prints a message, not an error.
  - Bare `/watch` or any other argument prints `Usage: /watch start [--persistent] <command> -- <follow-up> | list | stop <id>`. `/watchfoo` is a normal message.
- A restarted watch that times out reports the original timeout, not the time left.
- Status line: running watches show after the workers as `watch <id> <left>, <id>, ...` (the time left is omitted when there is none). It sheds detail as the terminal narrows: time left, then names to `<n> watches`, then `<n>wt`, then nothing. It refreshes on the same 500 ms poll, so it updates when a watch starts, ends or is stopped.
- Every watch has a timeout. A watch without its own `timeout_secs` (from the `watch` tool, `/watch start`, or an old saved record) gets `[chat] watch_timeout_secs` (default 3600, so 1 hour; `0` is a config error, resolved by `resolve_watch_timeout` in `crates/core/src/chat.rs`, same file-then-default precedence as `worker_check_secs`). `WatchSpec::with_default_timeout` applies it at start and at restore. When it passes, ralph kills the watch and posts one report that says `timed out after <n>s and was killed`, where `<n>` is the original limit.

## Scheduled tasks

The model schedules a shell command or a worker with the `schedule` tool (see [MCP tools](#mcp-tools)). A command runs as a watch when it is due; a worker runs a brief in its own worktree. Pure logic: `crates/core/src/schedule.rs`, `schedule_request.rs`, `schedule_command.rs` and `schedule_worker.rs`. Shell: `crates/ralph/src/schedule_store.rs`, `crates/ralph/src/chat/schedule.rs` and `crates/ralph/src/chat/schedule_worker.rs`.

- Tool fields: `id`, exactly one of `command` or `brief`, optional `follow_up`, `at` (a future RFC 3339 time, or local `HH:MM` for its next occurrence in the local time zone, daylight saving included) or `after` (`90s`, `10m`, `2h`, `1h30m`; give exactly one of `at` and `after`), optional `timeout_secs` (a command: else `[chat] watch_timeout_secs`; a worker: else 2 h, at most 8 h, larger is rejected). A worker takes no `follow_up`. An error: a duplicate `id`, an `id` with a space, slash or control character, an RFC 3339 `at` that is not in the future, an `HH:MM` that a daylight saving change skips.
- The tool writes the task as `proposed` to `<store>/schedule/<id>.json`. Nothing runs until you approve it.
- Approval is a y/n question at the prompt. It shows the id, the command, the time and the timeout; a worker shows `Scheduled worker <id>:`, the full brief indented, `Base: origin/main at fire time. Never pushes.`, then the time and timeout. Control characters in the command or brief show as `\x1b`, `\r`, `\n` and so on. `y` or `yes` arms the task; if the file cannot be saved it prints `Could not arm <id>: <error>` and the task stays proposed. `n`, `no` or Ctrl-C cancels it and removes the file. Any other answer asks again. The question comes before held text and before the `suggest_reply` pre-fill.
- Tasks run only while `ralph chat` is on. Each 500 ms tick starts every armed task that is due as a watch named `schedule:<id>` and marks it `running`. The watch is not persistent. Its report reaches the inbox tagged `schedule:<id>`; the task file goes when that watch ends.
- Worker kind. Each tick, `plan_worker_tick` decides from the records, the inbox reports and the live worker ids; no model turn runs. A due worker is started on a short-lived thread (`Workers::spawn` can block 20 s) as worker `sched-<id>` (`:` is not valid in a branch name) with the claude harness forced: the other harnesses have neither the scheduled prompt nor the guard. Branch `worker/sched-<id>`. Before the worktree is made, `git fetch origin` runs and the worktree is cut from `origin/main`, not HEAD. The fetch never prompts: `GIT_TERMINAL_PROMPT=0`, and `GIT_SSH_COMMAND` is `<base> -o BatchMode=yes` (pure `fetch_ssh_command`), where the base is the `GIT_SSH_COMMAND` of the chat process, else the repository `core.sshCommand`, else `ssh`, so the repository key stays. It runs in its own process group and the whole group is killed after 60 s; a timeout is a spawn failure. The stderr read waits at most 2 s after git exits, so the setup lock is held about 62 s at most. Fetch and guard setup run under one process-wide lock. The worker runs with `--permission-mode auto` whatever mode the chat uses: auto never stops to ask, a refused action is denied and the worker goes on, and the classifier still guards risky actions; `--disallowedTools` still applies. The ids `sched-*` are reserved: `spawn_worker` refuses them, `reply` refuses a `sched-<id>` worker while its schedule record exists, and a worker-kind schedule id must be letters, digits and dashes. A late worker gets `Ran late: due HH:MM, started HH:MM.` before its brief.
- Prompt rule. The scheduled worker prompt (`SCHEDULED_WORKER_PROMPT`, chosen by `SpawnArgs.scheduled`, not by brief text) says: act, never ask; never push, merge, open a PR or change Linear; commit only on your own branch; send one report (`done`, or `blocked` with the reason), then stop and never wait for an answer.
- Cap and lateness. At most 2 worker records run at once. A due worker over the cap stays `armed` and starts on a later tick; it is late when it starts more than one tick (500 ms) after its time. The running record stores a `deadline` (start plus timeout).
- Timeout. At the deadline only the harness stops (`Workers::stop_harness`). The worktree and branch stay. A `schedule:<id>` report says it timed out and whether the harness was stopped or could not be stopped (with the error), and the record is removed.
- Slow start. While the spawn thread runs, the task counts as alive (an in-flight set), so a spawn slower than the 60 s grace is not reported as vanished. The thread checks that the record is still running before it spawns and after it returns. If the record is gone (cancel, timeout), a harness that started is stopped, and a failed spawn posts no report.
- Reports. A scheduled worker report reaches the inbox as the worker (`sched-<id>`) and is not consumed or hidden: the tick reads the inbox without draining it, and keeps a copy of reports the person already drained. `done` closes the worker (`Workers::close` without abandon or force); if close refuses (commits or changes), only the harness stops and the branch stays. `blocked` and `question` remove the record and leave the worker open for you; it leaves the cap. A spawn failure posts a `schedule:<id>` report and removes the record. A running worker whose harness is gone for more than 60 s with no report gets a `schedule:<id>` report and its record is removed.
- Restart. A worker record that was running and whose worker is still alive stays `running` (no second run). If its harness is gone it goes back to `armed`, late, with no deadline, and fires again in the same worktree.
- No-push guard (scheduled worktrees only, `worker/guard.rs` plan, `workers/guard.rs` shell). Five layers: (1) claude runs with `--disallowedTools` `Bash(git push:*)`, `Bash(gh pr:*)`, `Bash(gh api:*)`; (2) the worktree gets `core.hooksPath` set in its own config (`git config --worktree`) to `<git-common-dir>/ralph-schedule-hooks`, one directory per repository; (3) that directory holds a `pre-push` that refuses, plus a forwarder for each executable hook of the repository, so the repository hooks such as `pre-commit` still run; forwarders without a matching real hook are removed, and hooks are written through unique temp files that are removed when the write fails (a sweep also removes temp files older than 60 s, `abandoned_temp_hooks`); (4) every remote of the common config gets `remote.<name>.pushurl` = `ralph-refused://<name>` in the worktree config, and every shared `remote.*.pushurl` value P gets `url.ralph-refused://.insteadOf` = P (a per-worktree pushurl only adds a value, so without the rewrite git would still push to P), so `git push --no-verify` fails; (5) `url.ralph-refused://.pushInsteadOf` has one value per prefix in the worktree config: `/`, `./`, `../`, `file://`, `ssh://`, `git@`, `git://`, `http://` and `https://`. A push to an explicit URL of those forms, with or without `--no-verify`, goes to `ralph-refused://` and fails. If a remote's fetch url starts with a shared push url P, the insteadOf rewrite would break fetching, so the task is not started: a `schedule:<id>` report names the remote and the reason and the record is removed. The plan first runs `git config --worktree --unset-all` on each of the two url keys (the shell accepts exit 5, key absent), then `--add` for each value. This removes stale values from an earlier run, so the steps are idempotent with no duplicates. The only change to the main `.git/config` is `extensions.worktreeConfig = true`.
- Known gaps. A scp-like `host:path` without a user and a bare relative path without `./` are not rewritten, so a push to them is not refused by layer 5. Linear writes through the user's MCP tools are blocked only by the prompt rule, not by a flag. A worker can unset its own worktree config, which removes layers 2 to 5. A `done` report that arrives while the chat is down, followed by a machine reboot (the harness is gone), makes the task run again: the record still says running, so it goes back to `armed`.
- A task missed while the chat was off fires at once, marked late; its follow-up says when it was due. A task that was running when the chat died or closed goes back to `armed` and fires late on restart; once shutdown starts, the tick no longer removes running tasks whose watch was stopped.
- `/schedule` (or `/schedule list`) lists every task: id, state (`cmd` or `worker`, then `proposed`, `armed`, `running`), local time (with the date when it is not today), time left, a `late` marker, the command or the first line of a worker brief (a running worker shows `sched-<id>: ` before it; control characters escaped as in the approval question). `/schedule cancel <id>` (or `schedule:<id>`) removes the file and stops the watch of a running command (cancelling a running worker task stops `sched-<id>` with `Workers::stop_harness`, which keeps its worktree and the branch `worker/sched-<id>`, and removes the record); an unknown id prints a not-found line. `/schedule` never creates a task. `/schedule list` and the usage reply run mid-turn; `cancel` is queued.
- Status cell: armed and running tasks (command and worker). One task shows `sched <id> <HH:MM>` (with `+<N>d` after the time when it is due N local days later, e.g. `09:00+1d`), several show `<N> scheduled`, the narrowest form is `S<N>`.
- Scheduling does not take the memory `LOCK`. Two chats on one `--store` are not supported.

## /help

`/help` is local: it never starts a turn or calls the model. Only the bare command (after trimming) counts: `/help x`, `/help me fix the build` and `/helpfoo` are normal messages. It prints the pure `chat_help::help_text(width)`, word-wrapped to the prompt width (the terminal width, capped by `--wrap-width`); a section whose text column would be under 30 columns puts each text under its label:

- Commands: one row per form of `/help`, `/inbox`, `/watch`, `/schedule`, `/diff`, `/workers` and `/hold`, from `Command::ALL`. `route_input` matches the same table, so a command cannot route without a help row.
- Cells: the `!` shorthand and `!<runtime>` fences.
- Keys: at the prompt, in vi mode, during a turn, and in the queue editor (`PROMPT_KEYS`, `VI_KEYS`, `TURN_KEYS`, `QUEUE_KEYS`).
- Status bar: one row per segment `Kind`, the four modes, each part of the thread cell (`T12/30`, `ctx 62%`, `cache 41m`, `!`, `shift ~9 msg`) and the `↻ tokens`, `↻ turns` and `↻ restart` marks.

The chat-mcp tool `help` gives the model the same text: no `topic` returns `help_text` unwrapped, `topic` (`diff` or `/diff`) returns that command's rows from `Command::ALL`, and an unknown topic is a tool error that lists the topics (`chat_help::help_topic`, answered by `chat-mcp` itself). Topic `config` returns the resolved `config.toml` path, the store file path (`<store>/config.toml`, which overrides the global file per key), the location, environment override and precedence text, and the section names; `config <section>` (`chat` or `[chat]`) returns that section of `docs/configuration.md`, embedded with `include_str!` and split by `chat_help::config_sections`. `handle_request` answers it as `Outcome::ConfigHelp`, and `chat/mcp.rs` fills in `config::config_path()` and the store file. Topic `images` returns how a reply shows an image (`IMAGES_HELP`). A command topic whose name matches a config section ends with `Settings: help topic "config <name>"`. `SYSTEM_PROMPT` tells the model to call it for questions about settings and for requests to change how ralph behaves or looks, to propose a code change only when no setting covers the request, to edit the global `config.toml` by default and the store file only for a store-specific setting, to copy the edited file to `config.toml.bak` first, and, after editing, to run `ralph config check --store <store>` and copy `config.toml.bak` back over the edited file if it fails (`config::check` reports unknown keys via `serde_ignored`, theme and chat-setting warnings, and the hard chat-startup errors).

Staleness tests: `chat_help` tests fail when a `Command` does not route or has no row, when `status_segments::segments` builds a segment kind with no legend, or when `status_mode::mode` returns a mode with no legend. `every_chat_binding_has_a_help_entry` in `crates/ralph/src/chat/tests.rs` builds the real emacs, vi and queue keymaps, keeps the bindings that differ from reedline's defaults, and fails when one has no key table entry. Keys handled outside reedline (Esc Esc, Ctrl-C, Ctrl-D, Ctrl-Q during a turn) are listed in the tables by hand. Another test fails when `Command::ALL`, `MODES` or `RESETS` misses a variant, and the thread legend is checked against `thread_variants` of a real cell.

## /diff

`/diff` is local: it never starts a turn or calls the model. `/difffoo` is a normal message.

| Input | Shows |
| --- | --- |
| `/diff` | the last finished chat turn (same as `/diff last 1`) |
| `/diff last N` | net changes over the last N finished chat turns (N >= 1) |
| `/diff ago N` | the single chat turn N back (N >= 1) |
| `/diff worker <id>` | that worker's changes since it spawned |
| `/diff worker <id> last N` or `ago N` | that worker's last N turns, or the turn N back |
| `/diff now` | the working tree against the index, as plain `git diff` |

The ranges use the same snapshots and rules as the `changes` tool (`last` and `ago`, rebase-aware). If snapshots are off, there is none yet, or N is larger than the finished turns, `/diff` prints one plain line and runs nothing. After an upstream change it may print the upstream note first. An empty snapshot range prints `no changes` (same wording as the `changes` tool) and runs no pager. There are no absolute turn numbers.

The words after the range keywords are git diff args: `/diff -U1 -- a` is the last chat turn with `-U1 -- a`, and `/diff worker w1 last 2 --stat` is a worker range with `--stat`. `/diff now [git diff args]` is the working-tree diff: `git diff` in the chat's working directory. Words are split on whitespace, with quotes and backslash escapes (a trailing backslash is kept; no `$` expansion or globs), and are passed after `[changes] diff_args`. In a range, the two snapshot revs come right after `diff`, before `diff_args`. An unclosed quote prints `/diff: unclosed quote` and runs nothing. A bad count, a missing worker id, or `last`, `ago` or `now` as the worker id prints a usage line and runs nothing.

```toml
[changes]
pager = "git" # git | delta | hunk
diff_args = [] # default git diff args; typed /diff args follow
```

- `pager = "git"` (default): `git diff <revs> <diff_args> <typed>`. The user's `core.pager` in git config is left untouched.
- `pager = "delta"`: `git -c core.pager=delta diff ...` for this call only.
- `pager = "hunk"`: `git -c core.pager=hunk pager diff ...`, with `core.pager=hunk pager` as one argument.
- Any other pager string warns once at chat start (`[changes] pager = "..." is unknown; using git`) and uses `git`. Loading the config still succeeds.
- ralph does not write `core.pager`. Snapshot ranges set `GIT_DIR` and the alternate object dir for the spawned git only; `/diff now` sets no environment variables.

The spawn runs only after reedline `read_line` has turned raw mode off, so a full-screen pager returns to a normal prompt. `git diff` exiting 1 (there are changes) is not a chat error. A failure to start git warns and returns to the prompt.

## /workers

`/workers` is local: it never starts a turn or calls the model. Only the bare command and `/workers <id>` (one token) count; `/workers a b` and `/workersfoo` are normal messages. Only live workers appear (`running_workers`); a Codex worker has only what its shared record gives. The shell is `crates/ralph/src/chat/workers.rs`; the pure parsing and layout is `crates/core/src/workers_view.rs`, with the detail view in `crates/core/src/workers_view/detail.rs`. The ticket and PR lookups run in background threads; `/workers` never waits for them (see [Remote lookups](#remote-lookups)).

| Column | Source |
| --- | --- |
| ID, HARNESS | the running worker record |
| STATE | the status bar state (`Monitor::status`) |
| REPORT | `<text> · <age> ago` of the worker's status when it has set one (`set_status`, see [Worker inbox](#worker-inbox)) and its time is later than the latest report's (both parsed as RFC 3339; equal or unparsable report times keep the report; no report at all shows the status), else `<status> <age> ago` of the latest real report (`done`, `blocked`, `question`): worker entries in the chat log (read only) and unread inbox reports, newest first |
| HEAD | `git log -1 --format=%h %s` in the worker worktree (`git worktree list --porcelain`, branch `worker/<id>`) |
| +/- | `+A -D Nf` over tracked changes of the worktree against `git merge-base HEAD <base>`, plus ` ?N` for untracked files, each file counted (`git status --porcelain -uall`; omitted at 0). Every git call runs with `--no-optional-locks`, so `/workers` never takes the worktree `index.lock`; binary files count as files with 0 lines; one failed git call makes the whole cell `?` |
| BEHIND | `git rev-list --count HEAD..origin/<base>` |
| TICKET | the remote state of the spawn record's ticket (see [Remote lookups](#remote-lookups)); prefixed with the key when the key is not the worker id |
| PR | the newest PR of branch `worker/<id>`: `#12 draft`, `#12 open`, `#12 approved`, `#12 changes`, `#12 merged`, `#12 closed` |

BEHIND counts against the local remote-tracking ref `origin/<base>` (base = `[chat] worker_base`, else `origin/HEAD`, else `main`), so it is stale until a fetch; no network is used, and a missing ref shows `?`. +/- uses the merge-base with `<base>`. In the table a `-` cell is wrapped in a code span (backslash escapes are not honored) so termimad does not draw a list bullet. A missing value shows `-`, a failed lookup `?`, a lookup not done yet `…`.

With no live worker it prints `No live workers.`. By default, the list is a markdown table through the chat renderer when it fits the prompt width (columns plus `cols + 1` border cells, as termimad draws them without padding); the HEAD subject is cut with `…` down to 20 characters first. Else each worker is a block, every line cut to the width. Set `[workers] view = "list"` to always use these blocks; `view = "table"` keeps the default table with a block fallback and does not change `/workers <id>`:

```
● GUZ-844 · claude · busy
  report  done 12m ago
  head    2f7f8c0 fix(chat): exact /help, width-wrapped…
  diff    +120 -40 in 3 files ?2 · 2 behind origin/main
  ticket  In Progress
  pr      #12 open
```

`/workers <id>` prints that block plus the branch, worktree path, base ref, tmux session (claude only), the set markers among `blocked`, `waiting`, `unreported`, `sent` and `gone`, and the heartbeat from `activity/<id>` (`running|idle <age>`), the `ticket` line from the spawn record (`GUZ-918 (linear) · In Progress`, or just the key when the tracker is unknown; `-` without a ticket), the `pr` line as `#12 open · <url>` (a URL that does not fit goes uncut on the next line), then one `status: <text> (<age> ago)` line for each kept status, newest first, then the last 5 reports newest first as `<status> <age>  <first line>`. The detail view always shows the status lines above the reports; the table and the REPORT cell use only the newest status. In the table the status text is cut with the HEAD subject to share the width budget, so one long status does not force the list. An id that is not live prints `No live worker <id>. /workers lists them.`

### Remote lookups

The pure model is `crates/core/src/workers_view/remote.rs`; the shell is `crates/ralph/src/chat/workers_remote.rs`. A worker has a ticket lookup only when its spawn record has a tracker (`-` otherwise, no lookup): Linear runs `mcptools linear issue get <KEY> --history-limit 0 --json` and reads `state`; Jira runs `mcptools atlassian jira get <KEY> --json` and reads `status`. The PR lookup runs `gh pr list --head worker/<id> --state all --json number,state,isDraft,url,reviewDecision` in the chat's working directory and takes the newest item; an empty list is `-`. `[workers] pr_provider = "none"` skips it. Settings are in [Configuration](../configuration.md#workers---workers-remote-lookups).

`/workers` renders from a cache held by the chat and never waits. A key that is missing or older than `cache_secs` shows `…`, and `/workers` starts one detached thread for it unless one runs already. The thread runs the command in its own process group with `lookup_timeout_ms` as a hard bound (output is read through a channel with the remaining time) and kills the whole group at the deadline, then stores the result; if the thread dies first, a guard stores `?`. `[workers]` comes from the config `/workers` reloads on each call (defaults when it fails to load). A timeout, non-zero exit or output that does not parse stores `?`, cached like a result. The next `/workers` shows the result. A result for a worker that has closed is only cached. The threads are never joined, so they do not hold the chat open.

## Process reset

The persistent `claude` process is dropped, and the next turn respawns it from the store through `Turn::launch`, when `reset_reason` (`crates/core/src/chat.rs`) returns a reason (`turns` or `tokens`) rather than none after a turn:

- Turns on this process reach `[chat] reset_turns` (default 30).
- The last assistant message's `context_tokens` reach `[chat] reset_tokens` (default 140000). No usage means no token trigger.
- The `result` event has `terminal_reason` `blocking_limit` (claude's context is full). Only the structured field counts, never the text `Prompt is too long`. The turn counts as failed: warning, `Unanswered`, no reply stored, session dropped. The usage record is still written.

Compaction stays off. A respawn waits for a running nap (`load_after_nap`: shared `NAP` try-lock, spinner while it blocks) and then loads under the shared `LOCK`; no lock is held while claude runs. A nap that is spawned but has not yet taken `NAP` when the respawn loads is not waited for: the respawn reads the committed tree and shows the nodes as pending.

## Turn snapshots

Unless `[changes] enabled = false`, every turn (user and worker-report turns) snapshots the working tree of the repo the chat started in, before and after the model call. A chat outside a git repo does nothing and prints no warning; this is decided once at start. A snapshot failure warns and never stops the turn.

- Storage: one bare git dir per repo at `<store>/snapshots/<repo-dir-name>.git`, with its own objects and no link to the repo. The repo's own refs and objects are untouched.
- Refs: `refs/ralph/chat/turn-<n>/start` and `.../end`. `<n>` continues from the highest existing number, also across restarts.
- Content: `git read-tree -m -i HEAD` into a private index at `<side>/index/chat` (skipped when the branch has no commit yet), then `git add -A`, so tracked files stay even when ignored and `.gitignore` and `info/exclude` apply to untracked files, then `write-tree` and `commit-tree`. `read-tree` runs without the side object dir; stat-clean entries reuse blobs an earlier snapshot wrote there and `add -A` rehashes the rest. Snapshot commits have no parents.
- Message: the ref name, then trailers `Ralph-Head: <sha>` (HEAD at snapshot time) and `Ralph-Base: <sha>` (merge-base of HEAD and the default branch, left out when it cannot be resolved; same default-branch rule as the worker base). Older snapshots have no trailers. Built by `snapshot_message`, read by `parse_snapshot_base`.
- Pruning: after each turn the last 20 turns stay; older start and end refs are deleted, then `git gc --auto --prune=1.hour.ago` reclaims objects.
- Code: pure logic in `crates/core/src/snapshot.rs`; git calls in `crates/ralph/src/snapshot.rs`; the turn hook in `crates/ralph/src/chat/snapshots.rs`.

### Worker snapshots and report diffstats

Claude, Cursor and opencode workers snapshot their worktree into the same side dir, keyed by the main repo name (from `git rev-parse --git-common-dir`). Snapshots come from ralph's own side dir, not from opencode's `/api/session/<sid>/diff`.

- Refs: `refs/ralph/workers/<id>/turn-<k>`, private index at `<side>/index/workers/<id>`. Turn 0 is taken at spawn; turn `k` at the end of each turn (Claude Stop hook, Cursor `run_turns`, opencode `Effect::Snapshot`, which the pure `TurnState` emits first on every `TurnEnded` from SSE or `reconcile`, resends included, but not while the chat is closing; the chat's SSE thread runs the git calls). The `/opencode.json` line that spawn adds to the repo's `info/exclude` keeps ralph's opencode config out of the snapshots unless the repo tracks that file. The last 20 stay. `close_worker` deletes the refs and the index.
- Report: the worker MCP server (`worker-mcp --worktree`) appends two `git diff --stat` blocks to the report text, rendered by `render_changes`: since spawn (merge-base of `HEAD` and the worker base branch against a fresh tree of the worktree, so untracked files count) and since the last turn snapshot (labelled turn `latest + 1`). A block that cannot be computed is left out. Output is uncapped. The since-spawn block is already rebase-safe, because it diffs from the current merge-base. The since-last-turn block is rebase-aware (see "Reading changes").
- `[changes] enabled = false` also turns off worker snapshots and report diffstats: the spawn decides once (`snapshots_enabled`), takes no turn 0, and passes no `--worktree` to the worker hooks and MCP server (opencode: `opencode.json`'s `worker-mcp` command, built by `worker_mcp_args`; the spawn handoff carries `snapshots`, and resumed opencode sessions read the config at chat start). `close_worker` still clears leftover refs and index from workers spawned while it was on.
- Code: pure helpers in `crates/core/src/snapshot.rs` and `crates/core/src/changes.rs`; git calls in `crates/ralph/src/worker_changes.rs`.

### Reading changes

The `changes` tool of `chat-mcp` lets the main thread read a diff without leaving chat. It runs `git diff` in the side dir (`--no-pager --no-color`), so the output is plain text.

- Scope: turns are counted back from the newest finished turn, so the model never needs absolute turn numbers. `last=N` and `ago=N` (1 or more, not both) are resolved by the pure `resolve_range` over the listed refs. With no `worker`, the chat repo (`chat-mcp` runs in the chat's directory); finished turns are those with an end snapshot, so the running turn never counts. `last=N` (default 1) gives the start snapshot of the Nth newest finished turn to the end snapshot of the newest; `ago=N` gives one finished turn (`ago=1` is the newest, `ago=2` the one before). With `worker`, that worker's worktree, where each step between two consecutive turn snapshots is a finished turn: no `last` or `ago` gives `turn-0` to the highest turn (since spawn); `last=N` spans the last N steps; `ago=N` is the single step N back. An N larger than the finished turns is not clamped: it is an error such as `last=5 is more than the 3 finished turns of the chat; use last 3 or less`. The removed `turn` and `since` arguments are rejected with an error that names `last` and `ago`. Other errors: `no finished chat turn snapshots yet`, `no snapshots for worker X`, `no snapshots`.
- Rebase handling: after a rebase onto a newer default branch, a plain diff would count commits pulled in from the default branch. `diff_base` compares the `Ralph-Base` of the two snapshots (the fresh `current_base` for the since-last-turn report block). Same base, or both unresolved: `Direct`, diff as is. The newer snapshot has `Ralph-Base` equal to its `Ralph-Head` (the checkout sits on the default branch, such as a chat on main): `Direct`, so a moved base is its own commits. Both bases known and different: `Rebase`, and the older snapshot is moved onto the new base with `git merge-tree --write-tree --merge-base=<old> <new> <snapshot>`, then that tree is diffed. Missing trailers or one unresolved base: `Unknown`, diff as is. Any `merge-tree` failure (git older than 2.40, a conflict, unparsable output) falls back to the unmoved diff. Every fallback and `Unknown` appends the line `note: could not separate upstream commits from these snapshots; counts may include commits pulled in by a rebase`. The rebase step never fails the call. `merge-tree` runs with `GIT_DIR` set to the side dir and the repo object dir as an alternate, so its objects land in the side dir and never in the user's repo.
- Format: `stat` is `--stat`, `files` is `--name-status`, `patch` is `--patch`. `paths` limit the diff. The first output line says what the range is, such as `changed in chat turn 3`. No changes gives `no changes`.
- Cap: output keeps whole lines from the start while the body fits in `max_bytes` (default 32768), never splits a UTF-8 character, and ends with `… <B> bytes omitted (<F> files not shown); narrow with paths or format=stat`. Body and footer together stay within `max_bytes`, except when `max_bytes` is smaller than the footer: then only the footer shows. The label line is not counted. Worker report diffstats stay uncapped.
- `[changes] enabled = false` makes the tool return an error that says snapshots are off. A chat outside a git repo, or with no snapshots yet, returns `no snapshots`.
- Limit: changes after the latest snapshot are not shown; a running turn has no end snapshot until it finishes.
- Code: pure parsing and range resolution in `crates/core/src/changes.rs`, the cap in `crates/core/src/changes/cap.rs`; rebase handling in `crates/core/src/changes/rebase.rs`; the tool call in `crates/ralph/src/chat/changes.rs`; `render_diff` and the git helpers in `crates/ralph/src/snapshot.rs`.

## Executable cells

A fenced block in a message you type whose info string is `!<runtime>` (for example ```` ```!zsh ````) is a cell. Worker reports and agent replies never run cells; a `!` fence inside another fence is not a cell. Parsing and message building are pure in `ralph_core::chat_cell`; PATH lookup, spawn and streaming are in `crates/ralph/src/chat/cell.rs`.

Shorthand: a message whose first character is `!` is the same as one `!shell` cell holding everything after the `!` (all lines; trailing newlines dropped; a longer fence when the body has backtick fences). `expand_bang_shell` in `crates/ralph/src/chat/cell.rs` rewrites it before parsing. Only the very first character counts: ` !ls` or `hi !ls` is plain text, and so is `!` alone or `!` followed only by whitespace. A failed or cancelled cell restores the draft as typed (`!ls`).

- On Enter, cells run in order, one process each, in the chat's working directory. The runtime is found by exact name on `PATH`; the code goes to its stdin. No sandbox. Stdout and stderr share one pipe. While a cell runs the terminal shows one dim line `▸ cell N · runtime`; the output is not echoed live.
- Claude gets the message with the `!` removed, then per cell: `[cell N · runtime · exit C]`, the code, and the output. A non-zero exit still sends. The store keeps this enriched message.
- After all cells ran, the terminal shows the message (the `!` removed) rendered as markdown (images: see [Rendering images](#rendering-images)). Each cell is followed by its full, untrimmed output in a ```` ```result ```` fence (longer fence if the output has backticks; none when the output is empty) and, for a non-zero exit, an `exit N` line (`core::chat_cell::display_results`). The display never reaches Claude, `log.jsonl` or memory.
- Caps shape only what Claude receives: `[chat] cell_output_limit` (200 lines, first half and last half kept) and `cell_output_bytes` (65536, head and tail kept), each with a marker in place of the cut: `… N lines trimmed …` and `… N bytes trimmed …`. For an odd limit the head keeps `limit / 2` and the tail keeps the larger rest. `0` disables a cap. See [configuration](../configuration.md).
- A missing runtime prints ``runtime `X` not found``, runs nothing, sends nothing, and puts the text back in the prompt. Ctrl-C kills the running cell and its process group, ends the turn without sending, and restores the draft.
- `!shell` runs `$SHELL -i` (`/bin/sh` when unset) and keeps state between `!shell` cells, in one message and in later messages, until ralph exits. One process per cell, no long-running shell. The stdin is a generated prologue plus the cell code. The prologue empties the prompt variables and prompt hooks, turns off verbose and xtrace, unsets `HISTFILE` (a leading space keeps the first line out of history) so no state or code reaches the history file, dumps a START snapshot to fd 3 (a pipe ralph reads into memory, never disk), restores the saved state, installs an exit hook that dumps an END snapshot to fd 3, then re-enables verbose and xtrace if they were on. The snapshot has the exported env, `$PWD`, functions and aliases. `diff(END, START)` is the saved state: new, changed and removed exports, functions and aliases, plus the end directory. START is taken before the restore, so the diff holds everything done since ralph started, and inherited env and `.zshrc` definitions are never copied. Output before the prologue's end marker (rc noise, the first prompt) is dropped from the result. Restore text and the prologue never appear in the output, in Claude's message or in the result fences.
- `!shell` state works for zsh and bash only (bash is best effort; macOS bash 3.2 untested). Any other shell runs without state and warns once. A snapshot that cannot be read (for example the cell closed fd 3) or a failed spawn warns and resets the state to clean; the message still sends. A cancelled cell (Ctrl-C) keeps the state from before that cell. Not carried: shell options, background jobs, open connections, `precmd`/`preexec` hooks (cleared inside `!shell` cells), anything outside the snapshot.
- The prompt shows the raw buffer, so the `!` stays visible while you type.

## Memory

- Log: `log.jsonl`, append-only, one `{role, at, text}` per line (`role` is `user`, `assistant` or `worker`, `at` is RFC 3339). Each append is fsynced under `LOCK`, then `log.idx` is brought up to date under the same lock (see [Index](#index)). A complete line that does not parse is kept as a placeholder entry at its position, shown as `[corrupt entry]` (role `worker`, empty `at`). The placeholder carries an explicit `corrupt` flag that only the parser sets: the flag is never written to `log.jsonl` (`#[serde(skip)]`), so a real entry with that text stays a normal entry. `parse_log` (`Store::load`: turn view, status bar, nap, check, editor) and the archive (`read`, `zoom`, `recall`, `search`) both give the placeholder the id of its line and show every later entry with the same ids. The placeholder can never be written back: the log writer takes a separate `NewEntry` type, so a loaded `Entry` (including a `[corrupt entry]` placeholder) cannot be written back, and the compiler enforces it. The turn view shows no placeholder as a message. `view` and `tail_lines` replace it with a notice line, `[#12: unreadable log line, skipped]`, and merge consecutive placeholders into one line, `[#12-14: unreadable log lines, skipped]` (`merge_notices`, pure, in `notice.rs`); ids of the other entries do not change, and a run that crosses the older view and the tail gives one notice on each side. The status bar counts the same lines and shows no entry text. `read`, `zoom`, `recall` and `search` keep the `[corrupt entry]` line per id, so a caller can still address each id. `recall` and `search` never match the placeholder. `pending` never offers a leaf or block whose range holds a placeholder, so the nap never summarizes it; the view falls back to the children of a skipped range. A trailing line without newline is ignored. `Store::append` truncates a torn last line (a crash mid-append) under the exclusive `LOCK` before it writes, so a new entry never glues onto it (`log_tail`, pure; the file reads and `set_len` are in `trim_torn_tail`), and warns with the byte offset.
- Tree: `tree.jsonl`, one `{lo, hi, text}` record per line, indexed by `tree.idx` (see [Index](#index)). Nodes are aligned power-of-two blocks `[lo, hi)` over log indexes, ids print as `5` or `4-7`. First record wins for a duplicate node; invalid records warn and are skipped. Summaries are at most `SUMMARY_BYTES` = 512 bytes, one line.
- Leaves are single messages. Outside the verbatim run (see [Recent history](#recent-history)), messages of 512 bytes or fewer stay in the view with whitespace collapsed and need no node. Longer ones get a leaf summary node. Parent nodes merge two children and exist only for complete blocks. A node is written once and never rebuilt.
- `cover(t, budget)` picks the nodes for the view: all leaves if the log fits the budget, otherwise a cover of the whole log, oldest first, tuned to use the budget. A cover node with no summary yet is shown through its halves or a marker (see [Pending summaries](#pending-summaries)).
- View line formats: message `#<i> <role> <at> <text>`; summary `#<id> <summary>`.
- `zoom` leaf lines already carry the full timestamp (`entry_line`), while range lines are summaries with no single time, so no zoom change was made for timestamps.
- This is a port of the OptMem cover, pending and tree_put design. There is no runtime dependency on `~/.optmem`.

### Index

`log.idx` and `tree.idx` let `read` and `zoom` load only the entries and summaries they show. `log.jsonl` and `tree.jsonl` stay the record; each index is a cache that is always safe to delete.

- Format (`chat_memory/index.rs`, one generic `Index<S: Slot>`): a 52-byte header (magic `RLPHLOGX` or `RLPHTREX`, version 3, `covered`, `tail`, `hash`, `skipped` line count, slot count, all little-endian), then fixed-size slots. `log.idx` has one `u64` start offset per entry; `tree.idx` has one `{lo, hi, start, end}` slot of four `u64` per valid record, in file order. `covered` ends on the newline of the last scanned line, `tail` is that line's start, and `hash` is the FNV-1a hash of the bytes `[tail, covered)`.
- Same visible content as the parsers: only complete, non-blank lines are scanned. In `log.idx` every complete line is a slot, a corrupt one too, so later entries stay visible; the line is not parsed when the index is built. Entry ids are line ordinals, so `#<id>` does not change. In `tree.idx` an invalid record is skipped (`parse_tree`), and `TreeIndex::find` returns the first slot of each node, so the first record wins.
- Freshness (`Index::freshness`, pure): a file shorter than `covered` or a tail whose hash differs means `Rebuild`; a file that ends at `covered` is `Fresh`; a longer file is `Extend`, which scans only the bytes past `covered`. A file with a bad magic, version, length, slot or offset order decodes as missing, which also means a full rebuild.
- Writes: `Store::append` updates `log.idx` under the exclusive `LOCK` after the log fsync; the nap commit updates `tree.idx` under the same lock after the record is written. `refresh` and `write_plan` decide: nothing, an in-place extend (new slots at the end, then the header at 0; a crash in between leaves a length the header does not match, so the next load rebuilds), or a full file written to a temp file and renamed over the index. The temp file is named `.<index>.<6 letters or digits>.tmp` (`index_temp_prefix`, `is_index_temp`). `check_path` rejects a symlinked or hard-linked index. A failed index write only warns: the line is already committed.
- Readers (`read`, `zoom`, `recall`, `search`, `Store::with_archive`) hold a shared `LOCK` for the whole call. They open the log and the tree and fix their lengths, read both indexes and extend or rebuild them in memory, answer, then save each index they had to extend or rebuild (`save_stale`). That save writes the whole file to a temp file and renames it, never in place: no writer runs under the shared lock, readers that hold it see the same lengths and so write the same bytes, and a concurrent reader sees the old file or the new one. No write plan is built on this path. An index for a missing file is not saved, and a store directory that does not exist reads as empty without creating anything (no directory, no `LOCK`). Summaries come from `IndexedTree`, one read per wanted node.
- Temp-file sweep: a save killed between the temp write and the rename leaves its temp file. `Store::append` removes every file whose name `is_index_temp` matches (`sweep_index_temps`) after its own index update, under the exclusive `LOCK`: no save runs then, so every match is orphaned and no age check is needed. Symlinks and other names stay. A failed sweep only warns.
- Self-healing (`Archive::retry`): a decode only checks the header, lengths and offset order, so a damaged slot can still decode. Each load checks what it reads: the log lines in a window must start at the stored offsets (the read starts one byte early to catch an offset inside a line) (a line that does not parse is not a failed check: it becomes the placeholder); a tree slot must end before `covered`, parse as a record, and name the node it is filed under. A failed check is `InvalidData`: the call rebuilds both indexes from their files, runs once more, and the reader saves the rebuilt indexes.
- Warnings (`Archive::warnings`): each call that loads a corrupt log line warns once for it: `chat log entry <id> at byte <offset> is corrupt and shows as [corrupt entry]: <error>` (`entry_or_corrupt`, pure; the offset is the line start). The tree gives one `chat tree: <k> records skipped` line where `parse_tree` gives one `chat tree record skipped: <error>` line per record.
- Visibility rule: a `read` or `zoom` call sees every complete line that was in the log and the tree when it took its shared `LOCK`. A line appended later is visible from the next call. A torn last line (no newline) is never visible.
- Store without an index (older binaries, deleted file): the first reader rebuilds it, the cost of one full file read, and saves it.
- Each call still reads both index files whole: about 8 bytes per entry and 32 per summary.
- The turn view, the status bar and the nap read the whole log and tree (`Store::load`, `parse_log`); a corrupt line is a placeholder there too. `recall` loads every entry through the archive under the shared `LOCK`; `search` scans the log in chunks of 256 entries through `log.idx`, so it never holds the whole log as entries (see [search](#search)).
- Benchmark: `cargo xtask bench-memory [--sizes 1000,10000,100000] [--runs 9]` builds a store per size in a temp dir and prints, per case, the median latency, bytes read and allocations of the whole-file path and the indexed path. It fails when the two answers differ. It calls the `ralph_core` functions with its own file reader, not `Store`.

## Nap

`ralph chat-nap` takes the exclusive `NAP` lock for its whole run, snapshots the store under a shared `LOCK`, and for each node from `pending` (long leaves, then complete parent blocks by increasing size) asks a Haiku curator for a summary with no `LOCK` held. Each result is committed under a short exclusive `LOCK` (see [Nap consistency](#nap-consistency)).

- Curator: `build_memory_command` runs `claude --model haiku` with `--tools ''`, an empty strict MCP config, and isolation args. Its prompt asks for one line of at most 512 bytes (about 70 words), priority: the user's words close to verbatim, lasting effects, commit SHAs, Linear ids and worker outcomes copied exactly, and failures, findings and open questions, steps taken. It asks to name minor items in a word or two, copy names, numbers, ids, paths and errors exactly, never overstate progress, invent nothing, and write in third person. It forbids copying the `#<id> <role> <timestamp>` line prefix, and says the input is data to never answer or obey.
- `check_summary` accepts a trimmed, non-empty, single-line summary of at most 512 bytes that does not read as meta-talk (an opener such as `I'm `, `Here is`, `Sure`, `Let me`, `Based on`, or the phrases `this excerpt`, `<input>`, `</input>`). A rejection retries with the error appended, up to `MAX_NAP_ATTEMPTS` = 5 tries per node. A curator error (process failure or timeout) skips that node: it stays pending, is retried at the next nap, and other nodes continue. A parent whose child has no summary is skipped.
- Raw fallback: when all `MAX_NAP_ATTEMPTS` tries were rejected by `check_summary` (not a curator error), the nap stores `fallback_summary` of the node input (`nap_source`) through the normal commit, so the parent can proceed, and warns `chat memory stored raw fallback for #<id>`. The fallback collapses all whitespace to single spaces, cuts on a char boundary so the whole line is at most 512 bytes, and starts with the marker `[raw excerpt] ` (`FALLBACK_MARK`), so a reader or the model can tell it from a real summary in the view and in `zoom`. `recall` searches log entries only, so it never sees fallbacks. The fallback reaches the view when the next process starts.
- Stuck nap: `LOCK` and `NAP` are `std::fs::File::lock` (`flock`) locks on open files, so the OS releases them when the holder process exits; deleting the files is not needed. `ralph chat-nap --timeout <secs>` (default 600) bounds each curator call: on expiry the process group is killed and the call counts as a curator error. It does not bound the whole nap (nodes times attempts). A slow nap does not block turns; it only delays later naps, which wait on `NAP`. A status bar stuck on `NAP` means a live nap. Find it with `lsof <store>/NAP` or `pgrep -fl 'ralph chat-nap'` and kill it; the next nap retries the pending nodes.
- Outage backoff: the curator subprocess call runs through `retry_on_outage`. `classify` sorts a failure into `Timeout`, `Outage` or `Refusal`. It is an `Outage` when the exit code is non-zero and the lowercased stderr plus response text contains one of `OUTAGE_MARKERS` (`overloaded`, `api error: 5`, `api error: 429`, `rate limit`, `rate_limit`, `529`, `503`, `502`, `500 internal`, `econnreset`, `econnrefused`, `etimedout`, `socket hang up`, `connection error`, `network error`, `request timed out`). Everything else, such as a refusal, bad output or an unknown error, is a `Refusal` and is never retried. An outage waits `OUTAGE_BACKOFF_SECS` = 2s then 8s before the next call, at most 2 retries; if it still fails, the node stays pending as before. The waits run with no `LOCK` held, so they do not delay turns. A timeout is never retried: each one lasts up to `--timeout` seconds and holds `NAP`, so retries would delay later naps, and the next nap retries the node anyway. The `check_summary` retry loop is separate and has no waits. Chat turns use the same schedule.
- A turn on a live process does not wait for the nap. A launch (first turn, or a respawn after a reset or failure) waits for a running nap through `Store::load_after_nap`, then reads the committed tree and shows pending nodes as below.

### Nap consistency

- Snapshot: under a shared `LOCK` the nap reads log and tree once. `log.jsonl` is append-only, so the entries under any pending node never change after the snapshot.
- Curator calls, `check_summary` retries and outage backoff run with no `LOCK` held.
- Commit: for each summary (or raw fallback) the nap takes the exclusive `LOCK`, re-reads `tree.jsonl`, and asks `commit_decision`. `Write` appends one fsynced record, then updates `tree.idx`. `Taken` means another nap committed the node first: the nap drops its own text, warns `chat memory kept the first summary for #<id>`, and keeps the committed text. Either way the nap continues from the re-read tree.
- Order: `nap_step` returns `Done` for a node already in the tree, `Blocked` for a parent whose child has no committed summary, else `Ask` with the prompt. A parent prompt is always built from committed child text, so a parent never summarizes a dropped child.
- Racing naps: `NAP` makes naps run one at a time. If two naps still overlap (for example an older binary without `NAP`), first-writer-wins at commit plus first-record-wins in `parse_tree` keep one summary per node. Records are written whole under the exclusive `LOCK`, so naps never interleave lines.
- Failure: a curator error, a timeout, or a nap that is killed before its commit writes nothing for that node. The node stays in `pending` and the next nap retries it. Nodes committed before the failure stay.
- Tests: pure unit tests in `nap.rs` cover `nap_step`, `commit_decision`, a race of two naps on one node, and uncommitted work staying pending. The shell test `nap_curator_runs_without_the_store_lock` checks that `LOCK` is free during curator calls.

### Recent history

The newest live-tail messages show their full raw text, newlines kept, within a token budget.

- Budget: `--recent-history-tokens <TOKENS>`, else `[chat] recent_history_tokens`, else 8192 (`RECENT_HISTORY_TOKENS`). `0` turns it off: the tail is then settled lines only. There is no env var.
- Estimate: `ceil(bytes / 3)` of the message text (`estimate_tokens`). This is more conservative than the `chars / 4` used by the status line, so the verbatim run stays under the budget.
- Run: `verbatim_start` walks from the newest message back to the start of the tail and adds each estimate. It stops at the first message that does not fit, so the run is one contiguous suffix with no gaps.
- Oversized: a newest message above the budget gives an empty run. It and all older tail messages use the settled rule (summary, or the `[raw excerpt]` fallback while the summary is pending).
- `zoom` on a message still returns its full raw text.
- Rollover: only the tail is verbatim. Older messages are in the older view in compressed form. The memory is read when a process starts, so a long-lived process keeps its first view; messages after it arrive as turns in the process's own conversation.
- The turn and the status size (`measure_memory`) use the same budget.

### Pending summaries

While a nap runs, a turn can load a tree with pending nodes. `view` and `tail_lines` never drop them:

- A cover node with no summary is shown through its halves when the line budget allows, down to single messages; otherwise as a marker (see below). Halves with committed summaries show those summaries.
- A long message with no leaf summary shows `fallback_summary` of its text, marked `[raw excerpt] `. This excerpt exists only in the view; it is never written to `tree.jsonl`.
- The view stays within its line budget (200 lines), or the cover length if that is larger. To show a missing node through its halves, the view first merges the oldest sibling pair whose parent has a summary (one line freed), then splits the newest missing node (one line spent). A missing node that cannot be shown this way is one line `#<id> [not summarized] zoom <id> for its parts` (`UNAVAILABLE_MARK`). `zoom` on it lists its halves (summary or `not compressed yet`), down to full messages.
- Tradeoff: under a tight budget with nothing to merge, old ranges that the previous rule expanded in full now show as a marker, so the model sees less until it zooms. Only older ranges become markers; newer ranges stay expanded. The view is read at process start, so a new process uses the committed summaries.

## MCP tools

`[chat] mcp_servers` in the ralph config (default `["mcptools"]`) names servers to import. `select_servers` copies each entry verbatim from the top-level `mcpServers` of `~/.claude.json`. A name absent there, or equal to `ralph-chat`, prints one warning and chat starts without it. `ralph-chat` is inserted last, so an import cannot shadow it. The file is written once at chat start: config changes need a restart. Imported entries can carry secrets, which is why they go in a file and not in argv. Turns run with the chat's permission mode (default `auto`), which decides whether imported tools need approval.

Hidden `ralph chat-mcp --store <DIR> --socket <PATH>` speaks newline-delimited JSON-RPC 2.0 on stdio (server name `ralph-chat`). At chat start the shell writes `<store>/chat-<pid>/mcp.json` (mode `0600`) holding `ralph-chat` plus the servers named in `[chat] mcp_servers`, and `build_mcp_args` passes `--mcp-config <store>/chat-<pid>/mcp.json --allowedTools mcp__<server>__*,... --strict-mcp-config`, so only those servers load. The allow list names every server in `mcp.json`: `--setting-sources project,local` skips allow rules in `~/.claude/settings.json`, and without this list the auto-mode classifier blocks these MCP calls. `chat-mcp` takes no permission mode or worktree directory; the chat process owns both. Each `recall` call re-reads log and tree without locking, so it sees fresh state. `zoom` and `read` hold a shared `LOCK` as described in [Index](#index).

Worker tools run inside `ralph chat`, not in `chat-mcp`. At start the chat sweeps `<store>`, then creates the private directory `<store>/chat-<pid>/` (mode `0700`, created with `DirBuilder` so it fails if the path exists; a leftover directory that the sweep kept makes chat start fail with a clear error), binds `<store>/chat-<pid>/chat.sock` inside it (then mode `0600`, so the socket is never reachable with looser rights), writes `mcp.json` in the same directory, and writes the owner record `<store>/chat-<pid>.owner` (mode `0600`, JSON `pid` and `ps -o lstart=` start time). The sweep reads each `chat-<pid>` directory and each `.owner` record. The pure `chat_socket::socket_fate` deletes a directory and its record when the record is missing, unreadable or names another pid, or when the owner is dead or has a different start time; it keeps them only when the owner is alive with the same start time. An orphan `.owner` record, one with no `chat-<pid>` directory, goes through `chat_socket::orphan_sidecar_fate` with the same rule: it is deleted unless its owner is alive with the same start time. Quitting the chat (Ctrl-D, or SIGTERM/SIGHUP during a turn) ends the main loop, and `SocketGuard` drops and removes its own directory (with the socket) and record. A SIGTERM/SIGHUP or a lost terminal stdin at the prompt goes through the input watcher instead: `ExitCleanup::run` kills watches, shuts down headless hosts, removes the same directory and record, then exits with code 129. A SIGKILL leaves both for the next start's sweep. `mcp.json` passes `--socket <path>` to `chat-mcp`. `chat-mcp` keeps `zoom` and `recall` and forwards `spawn_worker`, `reply`, `close_worker`, `watch` and `suggest_reply` to the socket as one JSON line `{tool, args}` per connection; the chat answers with one line `{text, is_error}` after it checks the turn marker (`command_allowed`) and parses the arguments (`worker::parse_command`). If nothing listens, the tool returns an error that starts with `no running ralph chat` and names the socket path; there is no fallback. `ralph ask` loads no `chat-mcp`, so it cannot spawn workers. A Unix socket path may not exceed 103 bytes (macOS `sun_path` is 104 with the NUL byte); a longer `<store>/chat-<pid>/chat.sock` makes chat start fail with a message that asks for a shorter `--store`.

`chat-mcp` answers `zoom`, `recall`, `search`, `read`, `changes` and `help` itself. It forwards `watch`, `schedule`, `suggest_reply` (and `spawn_worker`, `reply`, `close_worker`, below) to the chat socket, so the running chat produces their results. `suggest_reply` is not offered to workers (it is in the chat-mcp tool list and not in worker-mcp). Claude subagents of the main thread inherit it. The last call in a turn wins.

### search

`search` (`chat_memory/search.rs`) ranks the raw messages for a query; `recall` stays the regex tool (every hit, newest first). The pure part tokenizes, parses the query, filters and scores; `search` drives it over an `Archive` in chunks of 256 entries, so only one chunk of `Entry` values is live. There is no term index: each call scans the whole log under the shared `LOCK`, so an entry is searchable as soon as its append commits.

- Tokens: lowercase runs of letters, digits and `_`. Identifiers stay whole: `-`, `.` and `::` between word characters join (`guz-709`, `foo::bar`, `a.b`, `main.rs`). A token is compared whole, never as a substring: `GUZ-709` does not match `GUZ-7090`. A joined token also keeps its parts (split on `-`, `.` and `::`: `rate-limited` has `rate` and `limited`; `chat_memory::search` has `chat_memory` and `search`). A single-part query term matches a whole token or a part: `rate` finds `rate-limited`, `guz` finds `GUZ-709`. A joined query term such as `GUZ-709` matches whole tokens only. A joined token counts at most once for a term, whether the term matches its whole form or any of its parts, however often a part repeats; the length for BM25 stays the number of whole tokens. A quoted single word such as `"rate"` is a phrase of one word: it matches whole tokens only, so it does not match `rate-limited`.
- Query: bare words are optional units; each `"quoted phrase"` is a unit whose whole tokens must appear consecutively and is required; parts do not join phrases, so `"rate limited"` does not match `rate-limited`. An unclosed quote is an error (`unclosed quote in query.`). A hit needs every phrase and at least one matching unit. A query with no token is an error.
- Rank: BM25 (`k1` 1.2, `b` 0.75, token counts as length) over the entries that pass `role`, `since` and `until`; document frequencies come from one scan of those entries. Ties go to the newer entry.
- Dates: `since` and `until` parse with `chrono`. `since` later than `until`, after the date expansion, is an error; the same date for both is valid. A date means that UTC day: `since` is its start, `until` includes the whole day. A timestamp bound is inclusive and may carry any offset. An entry whose `at` does not parse is excluded when a date bound is set.
- Cursor: `<offset>.<count>.<hash>` where `count` is the log entry count the scan ended with (a mid-scan index rebuild is counted, so the next page is not stale) and `hash` is FNV-1a over the normalized query, role, bounds and limit. Each page rescans and ranks again, then returns hits from `offset`. A changed query, filter or limit gives `cursor does not match this query`; a different entry count gives `stale cursor; the log changed`.
- Snippet: about 160 characters of whitespace-collapsed text, with the first match near the start, `…` at cut ends.
- Evidence recall: a labeled fixture in the unit tests (10 queries, recall@5 = 1.0) measures whether the right entry ranks in the top 5, not whether a model answers correctly.
- Bench: `cargo xtask bench-memory` has two search cases (one rare phrase, one word in every entry). Its `full` path rebuilds both indexes before the scan, its `indexed` path loads them.

### read

`read` (`chat_memory/range.rs`) pages through a flat range of the log. `zoom` navigates the tree one node at a time and `recall` searches by regex; `read` returns the originals in order, so the model can read a stretch it already located. The `id` is a range `a-b` (inclusive, any bounds, not only aligned blocks) or one index. `b` is clamped to the log end; `a` past the end, `a > b`, a budget outside 1 to 16384, a malformed cursor, or a cursor outside the range all return `isError: true`.

- Each record is a header `#<id> · <role> · <date> · <n> chars` and then its text verbatim (whitespace and newlines kept). Records are separated by a blank line.
- `mode: raw` returns the original text. `mode: summary` returns the leaf summary for a message longer than `SUMMARY_BYTES`, `[not summarized]` (`UNAVAILABLE_MARK`) when that leaf has no summary yet, and the raw text for short messages. Use the same mode on every page of one read, because the cursor offset counts characters of the text shown; the cursor records its mode and a read in the other mode is rejected.
- `budget` is a page size in tokens, measured with `estimate_tokens` (bytes / 3). A page holds whole records while they fit.
- A record that does not fit is split at a character boundary, never inside a UTF-8 character, and its header gains `chars a-b` (1-based, inclusive). A page always carries at least one character, so paging always advances.
- When more remains the page ends with `next cursor: <next>.<offset>@<end><m>`. Pass it back as `cursor` with the same `id` and `mode`. `<offset>` is the character offset inside record `<next>`; `<m>` is `r` (raw) or `s` (summary), the mode that issued the cursor. A cursor in the other mode, one with no marker (the older format) or one with an unknown marker returns `isError: true`. Otherwise the page ends with `(end of range)`.
- Snapshot: the first call fixes `end` as `min(b + 1, log length)` and the cursor carries it, so messages appended between pages never appear, and a full traversal has no gaps or duplicates.
- Loading (`Archive::read`): each call loads a window of entries from the cursor (or `a`) through `log.idx`, never the whole log; in `summary` mode it reads only the leaf summaries of long entries in the window, through `tree.idx`. The first window holds entries whose JSON lines add up to the page budget in bytes; when the page needs an entry past the window before the budget is spent (`Read::More`), the window doubles. The page is the same as one built from the whole log (tested).

Workers can be tmux-hosted or headless (Cursor and opencode). See [Headless workers](headless-workers.md) for `HarnessId`, old `cursor: true/false` record compatibility, the chat-owned `HeadlessHost` lifecycle and how to add another headless harness.

`spawn_worker` takes `id`, `task`, optional `ticket` (a tracker ticket key; letters, digits and dashes; default the worker id when it is `<KEY>-<digits>` for a key in `[tickets]`, see [Configuration](../configuration.md#tickets---ticket-keys)), optional `harness` (`claude` default, `opencode`, `cursor`, or `codex`, a headless `codex app-server`), optional `model` (a model name or alias for claude and cursor, `provider/model` for opencode). The claude model is the pure `worker::resolve_claude_model`, first hit wins: the `model` argument, `[claude] model`, then claude's own default (no `--model` flag); an invalid or unloadable config adds a warning and uses the default. The opencode model is the pure `worker::resolve_opencode_model`, first hit wins: the `model` argument, `[opencode] model`, then `openai/gpt-6.1-sol`; the chat process resolves it at spawn, and an `[opencode] model` that is not `provider/model` adds a warning to the result and uses the default; a config that fails to load also adds a warning and uses the default. The cursor model is the pure `worker::resolve_cursor_model`, first hit wins: the `model` argument, `[cursor] model`, then cursor's own default (no `--model` flag). An invalid or unloadable config adds a warning and uses the default. Cursor's ACP fixes one variant per model, so spawn has no reasoning-effort or fast argument. `worker::parse_command` refuses an unknown harness, a claude or cursor model that is empty or has whitespace, and an opencode model without a provider and name. Claude runs in tmux session `ralph-<project>-<id>` through a login `zsh -lic`; every harness works in `<dir>/<id>` on branch `worker/<id>`. The worktree directory comes from the pure `worker::resolve_worktree_dir`, first non-empty wins: `--worktree-dir`, `RALPH_WORKTREE_DIR`, `[chat] worktree_dir`, then `.worktrees`; a leading `~` expands to home, then the result joins the repo root (an absolute path stays as is). A config that fails to load skips `worktree_dir` and adds a warning to the result. Spawn and close both prune stale worktree entries, then take the path of `worker/<id>` from `git worktree list --porcelain` (`worker::worktree_for_branch`) and use `<dir>/<id>` only when the branch has no worktree, so a worker made under an earlier setting is still found. Spawn reuses that worktree and an existing `worker/<id>` branch. Otherwise it runs `wt switch [--create --base @] worker/<id> --no-cd` with `--config-set worktree-path=<dir>/<id>`, so the worktree lands where close expects it whatever the user's wt template is; if `wt` is not installed or fails, it falls back to `git worktree add [-b]`. The spawn result says which path ran (`WorktreeVia::note`). close_worker removes either kind with `git worktree remove` and `git branch -D`. Claude gets `--permission-mode <MODE>` (the chat's mode), `--mcp-config <store>/workers/<id>.json`, `--add-dir <store>/attachments` (spawn creates it; pasted `[Image #N: <path>]` paths in task or reply text are read from there), and the worker rules via `--append-system-prompt`. opencode runs headless on the chat's own server (see the opencode harness below), with no tmux session; ralph writes `<worktree>/opencode.json` with `model`, `permission.external_directory` allowing `<store>/attachments/**`, and a local `ralph-worker` MCP server, and adds `/opencode.json` next to the worktree directory (only when it is inside the repo) in the shared `.git/info/exclude`. Each worker signals ready by creating `<store>/ready/<id>`, which spawn deletes first: Claude through a `SessionStart` hook (matcher `startup`) in `<store>/workers/<id>.settings.json` passed with `--settings`; opencode, the chat, once the server accepts the first prompt. For Claude, spawn polls up to 20 s, reading the pane only to accept the folder-trust prompt; a timeout is not an error ("not confirmed yet" plus the tmux session), but a gone tmux session or a trust prompt still showing is. Before any git step, spawn runs a preflight (`workers/spawn.rs`), so a failed preflight leaves no worktree, branch or exclude line: claude needs `tmux` and `zsh` on PATH and `claude` in a `zsh -lic` shell (`command -v`); cursor needs `agent` on PATH; codex needs `codex` on PATH; opencode writes `<store>/opencode-preflight/<id>` (the time) and waits up to 30 s for the chat to start or reuse its server and write `<store>/opencode-healthy/<id>`, or to write `<store>/opencode-error/<id>`, so a missing binary, an unhealthy server or no running chat fails here. If start fails after the worktree step, spawn rolls back only what it created, decided by the pure `worker::rollback_plan`: it removes the worktree (`git worktree remove`, never `--force`, so a dirty worktree stays) only when this spawn created it and the harness is not still running (a live tmux session or an owner file), and deletes the branch (`git branch -D`) only when the worktree was removed, this spawn created the branch, and `git rev-list --count <tip at creation>..worker/<id>` is 0. The user sees the start error; rollback failures are appended to it (`worker::rollback_report`).

Cursor harness: `cursor` runs one `agent acp` child per worker (JSON-RPC over stdio through the `agent-client-protocol` crate, no tmux, cwd = the worktree). The child is always `agent acp`. A resolved model is applied after `session/new`, and again after `session/load` on resume, with `session/set_config_option` (`worker::select_cursor_model`). An exact advertised option value is sent as-is. A short name selects the advertised value for that name. Cursor's ACP fixes one variant per model name: `session/new` offers only `mode` and `model`, and a value that is not in that list is rejected. If a name is listed more than once, the cheapest listed value is sent (`fast=false`, then no `fast`, then `fast=true`, then the lowest effort). Any other string is sent unchanged, and the agent's rejection is the spawn error. Setting the option rewrites the user's Cursor model default. Before the set, ralph writes `cursor-model-default.json` in the ralph config directory (`worker::cursor_default_snapshot`). It then puts back `model`, `selectedModel`, `modelParameters`, `hasChangedDefaultModel`, `modelSelectionHistory` and `maxMode` in `~/.cursor/cli-config.json`, and `selectedModelVariantId` in `~/.cursor/acp-config.json` (`worker::restore_json_keys`), and deletes the snapshot. A crash between the set and that restore leaves the files on the worker model. The next chat start (`CursorHost::new`) sees the snapshot and repairs them (`worker::cursor_default_crash`). With no snapshot the files cannot be told from a change the user made. `agent --model` does not change the ACP session's current model. `chat-mcp` lives only for one turn, so the long-lived `ralph chat` owns the child. Spawn prepares the worktree, writes `<store>/cursor-spawn/<id>` (a JSON `SpawnRequest` with the time) and polls every 250 ms for `<store>/ready/<id>` or `<store>/cursor-error/<id>`, giving up after 30 s (it removes the request). The host drops a request older than 30 s. Right after starting the child, before `initialize`, it writes `<store>/cursor/<id>`: a JSON owner record with the chat pid and start time and the process group id and start time (`ps -o lstart=`, guarding pid reuse), not a bare child pid. It runs `initialize` (protocol must be 1, else error) and `session/new` with the `ralph-worker` stdio MCP server, removes the spawn request and writes ready; if the request is already gone (spawn timed out), it terminates the child. A failed or timed-out start kills the group and removes its owner file. Each `agent acp` start rewrites `~/.cursor/cli-config.json`, as reported in GUZ-570 testing. A model set also rewrites the model default in that file and `selectedModelVariantId` in `~/.cursor/acp-config.json`; ralph restores those keys after the set. The snapshot written before the set is removed when the restore succeeds. Accepted risk: a global Cursor MCP server named `ralph-worker` (`worker::SERVER_NAME`) replaces ralph's own. A different `agent --version` than the tested `2026.10.14` only warns; `authRequired` becomes "run `agent login`".

Cursor ownership and cleanup: the child runs in its own process group, so its MCP servers die with it: terminate sends SIGTERM to the group, waits 3 s, then SIGKILL. The `agent` ignores stdin EOF after `session/new`, so a killed chat leaves the child alive until a sweep: on chat start (every owner file), on close and on respawn of that id, the pure `worker::sweep_decision` returns `Reclaim` (owner chat dead: kill the group if its start time still matches, delete the files, go on at once), `Wait` (this chat owns it: use the close handoff below) or `Busy` (another live chat owns it: refuse). A close is not refused when the owner is the caller's own chat, found by `worker::caller_owns_worker` on the caller's ancestor pids from `ps -o ppid=`, since chat-mcp runs below claude below `ralph chat`. Quitting `ralph chat` terminates every owned child through its host (see [Headless workers](headless-workers.md)). The ACP MCP entry passes `--owner <store>/cursor/<id>` to `worker-mcp`, which refuses a report (tool error "worker closed", nothing posted) once the owner file is gone (`worker::accept_report`).

Cursor permissions: the session thread registers an `on_receive_request` handler for `session/request_permission`; it stores the `Responder` and the options in a per-worker queue and never answers by itself, except for the worker's own `ralph-worker-report: report` tool: `worker::auto_allow_option` picks the `allow_once` option and answers at once with its exact `optionId`, no queue and no `blocked/<id>` marker. With `[cursor] permissions = "yolo"` (read at worker start; default `ask`) `auto_allow_option` does the same for every request that has an `allow_once` option and never picks `allow_always`; a wrong value or unreadable config warns and uses `ask`. Every other tool waits for the person, and each such request (the second and later too) posts one inbox message with status `blocked` naming the tool, its summary and the valid `optionId`s (`worker::permission_alert_report`); the monitor's check adds no second message for Cursor workers. The front request is mirrored, within one 250 ms chat poll, in `<store>/blocked/<id>` as JSON `{tool, summary, options:[{optionId,name,kind}]}` (built by `worker::permission_content`; existing blocked readers only test that the file exists). The person answers through `reply`: for a cursor worker with both the owner file and `blocked/<id>`, `Workers::reply` writes `<store>/cursor-answer/<id>` and waits up to 30 s for the chat poll to consume it. The chat applies `worker::match_option` (exact, case-sensitive `optionId` after trimming surrounding whitespace; option names are not accepted): a match answers `Selected`, then shows the next queued request or removes the marker; no match leaves the request pending and returns an error through `cursor-error/<id>` listing the valid `optionId`s. `CursorHost::cancel_pending` answers every pending request `Cancelled` and clears the marker; close, shutdown and terminate call it before killing the group.

Codex permissions: `[codex] permissions` (`ask` default, `yolo`) reuses the Cursor queue and `blocked` marker; the person answers through `reply`, which writes `<store>/codex-answer/<id>`. Details in [headless-workers.md](headless-workers.md#codex-hosting).

Cursor prompts and interrupts: a `reply` with no waiting permission writes one entry per message under `<store>/cursor-prompt/<id>/` (named `worker::prompt_entry_name`, written hidden then renamed). The chat poll queues them in name order; `run_turns` starts a `session/prompt` only after the previous one ended, so a mid-turn reply waits for the next turn. `interrupt: true` skips the permission answer and writes under `<store>/cursor-interrupt/<id>/` instead. Opencode also supports interrupts through its own queue (see below); Codex uses the same queue under `codex-interrupt/` (see headless-workers.md); tmux workers return "interrupt needs a Cursor, Codex or opencode worker". Cursor's result is the real outcome, handed back through a result file: the entry name travels with `Inbound::Interrupt`, and after `PromptQueue::accept` `run_turns` writes `cancelled` (the steps include `CancelSession`, checked by `worker::cancels_turn`) or `sent` to `<store>/cursor-interrupt-result/<id>/<entry>` (written hidden then renamed). `Workers::reply` polls every 250 ms for up to 30 s, removes the result, and `worker::interrupt_reply` words it: cancelled, or sent with nothing cancelled; a timeout says the interrupt was queued but ralph chat did not confirm, outcome unknown. Chat start removes the whole `cursor-interrupt-result/` dir (a killed chat leaves results); close, sweep and spawn remove the id's dir. The chat poll sends the interrupt to `run_turns`, where `worker::PromptQueue` puts it at the front and returns `CancelPermissions` (all pending permissions answered `Cancelled`) and, when a turn is running, `CancelSession` (an ACP `session/cancel` notification). The pending prompt returns `cancelled`; `worker::turn_outcome` maps it (or `end_turn` after an interrupt) to `Cancelled`, which queues no `REPORT_REMINDER`, posts no `blocked` report and sets no `waiting`/`unreported` marker. The interrupt text runs next in the same session. Close and sweep remove `cursor-interrupt/<id>` with `cursor-prompt/<id>`.

Cursor traffic log: every `agent acp` worker appends to `<store>/acp-logs/<id>.log` the JSON-RPC bytes in both directions (lines `<epoch secs> in|out <chunk>`, `in` = ralph to agent) and the agent's stderr (`err`), through `LoggedRead`/`LoggedWrite` around the stdio handed to the connection (`acp_log.rs`). Chunks are raw reads and writes, not one frame per line. When a write would pass 1 MB (`ACP_LOG_CAP`, decided by `worker::rotates`) the file is renamed to `<id>.log.1`, replacing the old one, and a fresh file starts, so at most about 2 MB per worker. The log is appended across respawns and never deleted on close.

Cursor frames: the pure `worker::encode` turns a `WorkerCommand` into an `AcpCall` (`Prompt`, `Cancel`, `PermissionResponse`) that `acp_worker.rs` sends for the prompt, cancel and permission-answer sites; `worker::decode_update` maps the report tool call to `WorkerEvent::Reported`; the prompt-response stop reason stays decoded by `worker::turn_outcome`, because ACP stop reasons do not fit `TurnEnd` without losing `TurnOutcome::Stopped`.

Cursor reporting: after `session/new` the chat sends the task as `session/prompt` (`WORKER_PROMPT`, a blank line, then the task, as for opencode) without delaying ready. Each worker has one prompt queue; `worker::turn_outcome` maps each response, and a prompt that errors or ends with anything but `end_turn` posts a `blocked` report to the inbox. Close sets a closing flag first, so the `cancelled` stop reason posts no `blocked` report. The `session/update` handler sets a per-turn flag when a `tool_call_update` is the `ralph-worker-report: report` tool (`worker::is_report_tool_call`). A turn ending with `end_turn` and no report queues one `REPORT_REMINDER` prompt; if that turn also ends without a report, the worker gets `waiting/<id>` and `unreported/<id>`, as a claude worker does after its Stop hook gives up. The next prompt removes `waiting/<id>`. Worker checks use `Workers::nudge` to queue a `cursor-prompt/<id>/` entry; no pane or tmux attach hint is used.

Cursor resume: Cursor saves a session only once a prompt turn has sent its first `session/update`, so the chat does not write the record after `session/new`. `run_turns` holds it and writes `<store>/cursor-session/<id>` (JSON `SessionRecord`: sessionId, cwd, inbox, the canonical chat store path as owner, the resolved model when one was set) once, after the first turn that ends with a stop reason and saw at least one `session/update` while not loading (`worker::session_saved`). Quitting the chat while a turn runs sends `session/cancel`, waits for that turn to end, then applies the same rule; `CursorHost::shutdown` stops every worker first, then waits for all of them against one shared 500 ms deadline before it kills the groups, so an agent that never answers is bounded by it. A worker quit before its first turn produced an update has no record, so it is not resumed and is not resumable. Quitting the chat (and the chat-start sweep of a dead chat's owner file) keeps `ready/<id>`, so the leftover hint lists it at the next chat start; only close removes `ready/<id>`. Quitting the chat keeps a written record; close, a failed start and an unclaimed start remove it. A chat store holds exactly one chat, so the store path is the chat identity. On chat start, after the owner sweep, a background thread resumes each record (`CursorHost::resume_all`): `worker::resume_decision` skips, with a warning, a record with no owner, with another store, or when the agent does not advertise `loadSession`; a record whose owner file is still held by a live chat, an unreadable record, or a missing worktree is skipped the same way. An eligible record gets a new `agent acp`, `initialize`, `session/load` (sessionId, cwd, the same MCP server), then `session/set_config_option` when the record stored a model, and no task prompt. While `session/load` runs the `session/update` handler ignores updates, so replayed history never marks a turn reported. A failed load (including an active run) is warned, written to `cursor-error/<id>` and not retried until the next chat start; the record stays.

Opencode harness: `opencode` runs on one `opencode serve --hostname 127.0.0.1 --port <free>` child of `ralph chat`, started for preflight/spawn or supervision of persisted sessions, directly without a shell wrapper (ralph's own environment plus `OPENCODE_PASSWORD`; a missing binary fails at once with "opencode not found on PATH"). It runs in its own process group with basic auth (user `opencode`, a random password in `OPENCODE_PASSWORD`). The chat writes `<temp_dir>/ralph-opencode-<chat pid>.json` (`std::env::temp_dir()`, port, password, chat pid and `ps -o lstart=` start time, the server pid and its start time, mode 0600, written fresh with `create_new`) so the status line can ask `GET /api/session/active`; a read that parses a record whose pid or start time is not this chat's removes it (an unreadable or unparsable file is left alone), and chat start deletes records of dead or pid-reused chats (`worker::server_record_fate`) and first stops the old server process group (SIGTERM, 500 ms, SIGKILL) when the recorded server pid and start time still match (`worker::stale_server_group`; a record without server fields only loses its file). Spawn writes `<store>/opencode-spawn/<id>` (a JSON request with the time) and polls every 250 ms for `<store>/ready/<id>` or `<store>/opencode-error/<id>`, giving up after 30 s. The host's poll thread consumes requests in order: close, answer, prompt, interrupt, preflight, spawn. It drops a spawn request older than 30 s, waits up to 20 s for `/api/info` when starting the server, creates the session with `POST /api/session` (`id` = `ses_ralph<id>`, `location.directory` = the worktree, `model`, `permissions`), writes `<store>/opencode-session/<id>`, posts `WORKER_PROMPT` and the task to `/api/session/<sid>/prompt`, then writes the owner file `<store>/opencode-owner/<id>` and the ready marker.

Opencode turns: session create, prompt posts and permission replies retry up to `TRANSIENT_RETRIES` (2) times, 500 ms apart, on HTTP 404, 408, 429 or 5xx (`transient_request_error`); a turn that fails with a transient status resends its prompt the same way. One `GET /api/event` stream (SSE) feeds the pure `TurnState` for every session; a silent stream is dropped after 45 s and reconnected. After connection/reconnection, `reconcile_all` verifies persisted sessions and repairs state from `/api/session/active`, pending permissions and latest messages. The separate 3-second snapshot tracks process descendants for shutdown, not session reconciliation. `reply` writes prompts under `<store>/opencode-prompt/<id>/` and, with `interrupt: true`, under `<store>/opencode-interrupt/<id>/` (the chat calls `/api/session/<sid>/interrupt` first, synchronously, and writes `cancelled` or `sent` from its `{"interrupted":bool}` reply to `<store>/opencode-interrupt-result/<id>/<entry>`; `Workers::reply` awaits it like Cursor's, up to 30 s, and a failed call leaves the outcome unknown; chat start, spawn and close clear the dir); a reply to a worker with a waiting permission writes `<store>/opencode-answer/<id>` and the chat posts `/api/session/<sid>/permission/<rid>/reply`.

Opencode supervision: a server that dies mid-turn posts a `blocked` report; the supervision loop attempts a restart without waiting for a new request. Chat-owned host shutdown (see [Headless workers](headless-workers.md)) removes the server record, sends SIGTERM to the process group, waits up to 3 s, sends SIGKILL, then kills tracked descendants. Worker close does not stop this server.

Reporting: the worker's `ralph-worker` MCP tool `report` (`status` = `done`, `blocked` or `question`, any other value is a tool error; `text` = full summary) is the only way a worker reaches the chat. After it posts to `<store>/inbox/`, the tool touches the marker `<store>/reported/<id>`; spawn deletes the marker first. Harness hooks never send or build a report; they only stop a worker from going idle without one. Claude's settings file adds a `Stop` hook that runs the hidden `ralph worker-stop-hook --reported <store>/reported/<id> --unreported <store>/unreported/<id>`. It reads the hook input with serde, and the pure `worker::stop_decision` decides: while `background_tasks` is not empty it allows the stop; else if the marker exists it deletes it and allows; else if `stop_hook_active` is false it blocks with `worker::REPORT_REMINDER`; else it gives up and touches the unreported marker, so a worker that still will not report gets one push per stop and no loop; a report or the consume step removes the unreported marker. Malformed input, or input without `stop_hook_active`, lets the worker stop and prints a warning to stderr. Claude permission prompts stay open and wait for the person; the `PermissionRequest` hook only touches `<store>/blocked/<id>` and prints nothing, so it neither allows nor denies. A `Notification` hook with matcher `idle_prompt` deletes `blocked/<id>` and touches `<store>/waiting/<id>` only while `unreported/<id>` exists. A second `Stop` hook deletes `blocked/<id>`. A prompt cancelled with Esc or denied fires no `PostToolUse`, so these two hooks end a stale blocked state; an Esc cancel clears it at the next `idle_prompt` (about 60 s). `UserPromptSubmit` and `PostToolUse` hooks delete `blocked/<id>` and `waiting/<id>`, so new input or an answered prompt ends the wait. opencode workers get the same reminder and markers from the chat: the SSE turn state (`TurnState`) queues one `REPORT_REMINDER` prompt after a turn that ended without a report, and a second such turn touches `waiting/<id>` and `unreported/<id>`. Sessions are created with the permission rules `allow *` then `deny question` (the last match wins), so tools run without asking and questions are refused; a permission request that still arises is mirrored in `blocked/<id>` and answered with `reply_worker`.

Tmux ownership: `spawn_worker`, `reply` and `close_worker` look up the worker's session by name (`ralph-<project>-<id>`, or the older `ralph-<id>`) and compare its `@ralph_store` tag with this chat's store in the pure `worker::session_owner`. The shell canonicalizes both sides (symlinks resolved) and `worker::same_store` also normalizes lexically (trailing and doubled slashes, `.`, `..`). A session tagged with another store, or untagged, belongs to another chat: spawn, reply and close refuse it; `close_worker` with `force` skips the check. Headless ownership uses the store-local owner/session files described above, not tmux tags.

`close_worker` takes `id`, optional `abandon` and optional `force` (both default false). Like `spawn_worker`, it needs the newest log entry to be from the person. The shell collects the facts (owner, hosting kind, worktree dirty per `git status --porcelain`, `git rev-list --count <base>..worker/<id>`, opencode metadata from the chat's opencode owner or session file, or `<worktree>/opencode.json`), and the pure `worker::close_plan` decides. The base comes from the pure `worker::base_branch`, first non-empty wins: `[chat] worker_base` in the ralph config (read at each close), the branch behind `refs/remotes/origin/HEAD`, then `main`. Close never uses the branch checked out at spawn, so a stale or deleted spawn branch cannot block it. After a successful close it unsets any leftover `branch.worker/<id>.ralphBase` that an earlier version wrote; if that fails, the close still succeeds and its result ends with a warning that gives the `git config --unset` command. A missing config file is normal; a config that fails to read or parse skips `worker_base`, and the close result (success or refusal) ends with a warning naming the config path, the error and the base used instead. It refuses a foreign worker unless `force` is set; it refuses unmerged commits or a dirty worktree unless `abandon` is set. If no session, worktree or branch is left, it clears any remaining markers, otherwise refuses.

The first close step is dispatched by `HarnessId`, not by a Cursor flag or a generic "headless" test:

| Harness | Worker-specific close |
| --- | --- |
| `Claude` | `KillSession`: `tmux kill-session` for the owned session, if present |
| `Cursor` | `TerminateCursor`: hand off through `<store>/cursor-close/<id>` to terminate only that worker's ACP process group and remove its files |
| `Opencode` | `RemoveOpencodeSession`: hand off through `<store>/opencode-close/<id>` to interrupt an in-flight turn, delete only that worker's session (`DELETE /api/session/<sid>`, normally `ses_ralph<id>`; HTTP 404 means already gone), evict its worktree location with `DELETE /api/debug/location?location[directory]=<worktree>`, and remove its opencode files and owner |

The headless close handoffs wait up to 30 s for the owner file to vanish. The opencode handoff waits until both the owner file and the session record are gone, so session deletion finishes before worktree removal; on timeout or an error the close stops before removing the worktree. For a non-`Opencode` harness that still has opencode metadata, `close_plan` prepends `RemoveOpencodeSession` before the kind-specific step. An opencode close never kills a tmux session, calls `TerminateCursor`, or shuts down the shared `opencode serve`; other workers keep their sessions.

The common remaining steps, skipping absent resources, are `git worktree remove` (`--force` when dirty and abandoned), `git branch -D worker/<id>`, `git worktree prune`, then clearing the worker's markers (`worker::marker_paths`: `<store>/ready/<id>`, `reported/<id>`, `blocked/<id>`, `waiting/<id>`, `unreported/<id>`, `sent/<id>`, `activity/<id>`, `gone/<id>`), which spawn also clears first. A failed step stops the close and names the step; opencode location-eviction errors only warn. After successful worktree removal, home-directory cleanup runs only for the matching harness: Claude data for `Claude`, Cursor data for `Cursor`, neither for `Opencode` (so it never scans `~/.cursor`). Cleanup failures only add warnings; the exact paths and ownership checks are documented in [Worker leftovers](worker-leftovers.md).

At chat start, ids in `<store>/ready/` print one hint line (`chat_status::orphan_hint`) when they are not a discovered running worker (a tmux session, a Cursor worker this chat owns, or an opencode worker), not a Cursor worker whose owner-file chat is alive and whose `agent acp` process group is still the one recorded there (`worker::agent_held`; a dead chat's agent is reclaimed by the sweep, so it is listed), and not a Cursor worker that still has a `cursor-session/<id>` record. The hint still says "no tmux session" and suggests `close_worker`. Chat never deletes these markers by itself. Cursor workers keep `ready/<id>` across a chat quit or crash; close removes it.

## Skills

Turns run with `--setting-sources project,local`, so `~/.claude/skills` does not load. No skills are bundled. The user names skill directories (each holds a `SKILL.md`, for example `~/.claude/skills/show-me`) and chat exposes them through a plugin.

- Sources, highest first: `--skill <PATH>` (repeatable), `RALPH_CHAT_SKILLS` (`:`-separated, empty entries dropped), `[chat] skills = [...]` in the ralph config. The highest non-empty source replaces the lower ones; lists are not merged. With none set, no `--plugin-dir` is passed and nothing is written.
- A leading `~` or `~/` expands to the home directory. Duplicate paths keep the first. Relative paths are made absolute.
- At start, a path without a readable `SKILL.md` prints one warning and is skipped. Two skills with the same directory name: the first wins, the other warns and is skipped.
- Slash expansion: chat turns wrap the input, so Claude Code never expands a leading `/<name>`. Ralph does it for user turns only (worker messages are never expanded). If the message starts with `/<name>` followed by whitespace or end, and `<name>` is a configured skill, the prompt gets `Base directory for this skill: <dir>`, the `SKILL.md` body without its frontmatter, then the original message. The rest of the message, trimmed, replaces every `$ARGUMENTS` in the body; without that token and with non-empty arguments, an `ARGUMENTS: <args>` line is appended. The store keeps the original message; only the sent prompt is expanded. Unknown names, a bare `/`, and `/name` prefixes that are longer words pass through unchanged. A `disable-model-invocation` frontmatter flag only stops the model from invoking the skill itself; `/<name>` still runs it, and ralph does not warn about it.
- Config is loaded once at start; it supplies both `mcp_servers` and `skills`. On load error chat warns once and uses defaults.
- If at least one skill survives, chat builds a temporary plugin directory (removed when chat exits) with `.claude-plugin/plugin.json` (`{"name": "ralph"}`) and `skills/<name>` as symlinks to the skill directories. Each turn adds `--plugin-dir <dir>`. Skills appear as `ralph:<name>`.
- Skills are read at start: changes to the list need a restart.

## Images

- Ctrl-V (macOS only) runs `osascript` to write the clipboard as PNG to `<store>/attachments/.clipboard-<pid>.tmp`, then `attachment::parse_image` checks it. A valid image is renamed to `<sha256>.<ext>` (same image, same file; nothing is ever deleted) and `[Image #N: <absolute path>]` is inserted at the cursor. On send the image is drawn under the message (see [Rendering images](#rendering-images)). `N` is one above the largest `[Image #N:` already in the draft (`attachment::next_number`), else 1. No image on the clipboard prints `No image on the clipboard.`; a bad image prints `Image paste failed: <error>` and removes the temp file.
- Limits: 10 MiB per image (`MAX_IMAGE_BYTES`); PNG, JPEG, GIF or WebP by magic bytes (the clipboard script always asks for PNG). No paste on Linux or Windows; a path typed by hand works the same way.
- The placeholder is plain text: `log.jsonl`, history and memory hold only the text with the path, never the image bytes. Claude reads the image itself with its Read tool when it sees the path. Chat creates `<store>/attachments` at start and each turn passes `--add-dir <store>/attachments` (`build_attachments_args`), so a store outside the working directory still reads without a prompt.
- Workers: placeholders in `spawn_worker` task or `reply` text pass through unchanged. Claude workers get `--add-dir <store>/attachments`; opencode workers get `permission.external_directory` for `<store>/attachments/**` (see [MCP tools](#mcp-tools)).

### Rendering images

Local PNG, JPEG, GIF and WebP images in agent replies and in `!shell` cell output draw inline through the Kitty graphics protocol. Pure logic is in `ralph_core::kitty`; file reads and terminal detection are in `crates/ralph/src/render/image.rs`.

- What renders: a markdown `![alt](path)` in reply prose or in the message shown after a `!shell` cell, where `path` is absolute, `~/` or relative to the working directory. `http(s)`, `data:` and other URL schemes stay text. Markers inside fenced code blocks and inline code spans are ignored. Raw Kitty graphics sequences (`ESC _ G ... ESC \`) in cell output pass through to the terminal on display under Kitty directly; under tmux they are stripped.
- Detection, once at chat start: stdin and stdout must be terminals. Without `TMUX`, ralph sends a Kitty graphics query plus a device-attributes query with echo and line buffering off and waits up to 200 ms; images draw only if the terminal answers OK before the device-attributes reply. In tmux, ralph first runs `tmux display -p -t $TMUX_PANE '#{allow-passthrough}'` (null stdin, about 300 ms timeout). Only `on` or `all` continues: ralph sends the query wrapped in DCS passthrough (`ESC P tmux;` with each ESC doubled) followed by `ESC[5n`, and `ESC[0n` is the end marker. `off`, an unknown value, a failed probe or a missing `TMUX_PANE` means no query, no delay, text fallback. Limits: keys typed during the check are dropped, and a reply arriving after the timeout can leak into the prompt. With color off (`NO_COLOR` set or stdout not a terminal) no image is drawn and the query is skipped (no delay): reply markers print as plain markdown text. `ralph ask` and pipes never render images.
- tmux drawing: each image gets an id (1 to 255), is sent as `U=1` virtual chunks wrapped one by one, and is shown as rows of U+10EEEE placeholder cells colored with the id (256-colour foreground) and row/column diacritics. Image size is capped to 297 rows and 297 columns (diacritics table).
- PNG passes through (signature and IHDR checked); JPEG, GIF (first frame) and WebP are decoded (see Formats). At most 10 MB per file.
- Sizing: columns are the image width in cells (pixel width over the cell pixel width from `window_size()`), capped at the wrap width and at least 1; rows keep the aspect ratio. Rows are capped at the terminal height; a clamped image gets fewer columns to keep the aspect ratio (at least 1). When the terminal reports no pixel size, ralph assumes an 8x16 px cell (1:2). Both `c` and `r` are always sent.
- Formats: PNG is sent as is (`f=100`). JPEG, GIF and WebP are decoded to RGBA (RGB for opaque WebP); a long side over 2048 px is box-averaged down to 2048 (aspect kept, alpha-weighted); then the pixels are zlib-compressed and sent as `f=32` or `f=24` with `o=z` (`ralph_core::kitty_image::prepare`). Header pixel caps before decoding: 25,165,824 for JPEG and GIF, 6,291,456 for WebP; over the cap falls back to text. Known limits: EXIF orientation is ignored, GIF and WebP draw the first frame only (at frame size), decoder panics are not caught.
- Fallback: an unsupported, oversize, missing or unreadable file prints `[image: alt (path)]` and a line end. An image marker's own line end is dropped, so each image or fallback takes exactly its rows or one line. On an unsupported terminal (or in `ralph ask`) markers are not parsed: the `![alt](path)` text goes to the normal markdown renderer.
- Attachments: each `[Image #N: path]` in a sent message is drawn below the echoed message with the same placement and sizing rules (`render_attachments`, paths from `attachment::attachment_paths`). A path that cannot be drawn (missing, unsupported, over 10 MB) prints nothing extra. The sent text is unchanged.
- Model copy: `build_message` strips Kitty graphics sequences from cell output before trimming, so image bytes never reach Claude, `log.jsonl` or memory.
- Known limits: Ctrl-L or any clear-screen erases drawn images and they are not redrawn. Reedline issue #1237 misplaces the prompt after image output, so each image is sent with `C=1` (cursor does not move) and ralph prints exactly `r` newlines. A marker split across streamed chunks is not recognized. Raw Kitty sequences in cell output render in place inside the `result` block (one opening and one closing fence); ralph adds a line end after the final chunk (no `m=1`) when none follows and relies on the terminal's default cursor move, so a sequence using `C=1` from a cell may overlap later text.
- tmux limits: `allow-passthrough on` passes data only while the pane is visible; a hidden pane at chat start gives text fallback. Outer replies go to the active pane: a non-active ralph pane may get no reply, and another pane may receive reply bytes. Multiple attached clients are untested. Ids cycle 1 to 255, so the 256th image reuses id 1 and older placeholders show the newer image. An OK reply does not prove placeholder support: a terminal that answers OK but lacks placeholders shows blank cells. Kitty may evict old images at its storage quota, leaving blank placeholder cells.

## Storage and isolation

- Global store `~/.ralph/chat`: `log.jsonl`, `tree.jsonl`, `log.idx`, `tree.idx`, `LOCK`, `NAP`, `history.txt`, `editor.md`, `usage.jsonl`, `attachments/`, and an optional `config.toml` that overrides the global config per key for chats using this store (see [configuration](../configuration.md#configuration-precedence)). It is not project-scoped.
- `LOCK` is a file lock: exclusive for append and for each nap commit, shared for settled load and the nap snapshot. `NAP` is an exclusive file lock held for the whole nap; `napping()` probes it. Store paths that are symlinks or multiply-linked files are rejected.
- Isolation: `--setting-sources project,local` plus a `claudeMdExcludes` entry for `~/.claude/CLAUDE.md` when the home directory is known. Chat turns can change this with `[chat]` keys (`Isolation::for_chat`): `user_settings = true` uses `user,project,local`; `user_claude_md = true` drops the home entry; `project_claude_md = false` adds `CLAUDE.md`, `CLAUDE.local.md` and `.claude/CLAUDE.md` of the chat process directory (not ancestors). The key is left out when the list is empty. The curator keeps the default. Project and local settings stay active; this is context isolation, not a sandbox.
- User agents in `~/.claude/agents` do not load, so `build_agents_args` passes the bundled `SUBAGENTS` (`evidence-collector` haiku, `implementer` sonnet, `reviser` opus) as `--agents <json>`. These copies may drift from `~/.claude/agents`.
- Turns and claude workers run with the chat's resolved permission mode (default `auto`). The chat process adds `--permission-mode <MODE>` to each claude worker command, so chat and workers never differ. opencode workers ignore it.

## Usage

Every completed Claude call (each turn, including failed exits but not interrupted ones, and each nap attempt) appends one line to `usage.jsonl`: `{at, kind, trigger, input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens, cost_usd, duration_ms, context_tokens}`, where `context_tokens` is input + cache read + cache creation tokens of the last assistant message (absent when none carried usage), with `kind` `turn` or `nap`, and `trigger` (turn only) `user` or `worker`. `cost_usd` is the running total of the claude process, not a per-call cost. Turn lines also carry `process_turn` (the turn number on the claude process, 1 on a launch), `request_at` (RFC 3339 time of the last main-thread assistant event of the turn; subagent events are skipped) and `reset` (`tokens`, `turns` or `restart`, on the line of the turn that launched the process after a reset only; the first launch of a ralph run has none) and `run` (`<pid>-<start RFC 3339>` of the `ralph chat` run that wrote the line; the status bar sums only lines with its own `run`, so two chats on one store do not mix, and older lines without `run` are ignored). `process_turn` counts only turns where a claude process ran; a failed spawn leaves it unchanged. A policy reset gives `tokens` or `turns`; a crash, failed turn, cancel, stale relaunch or a process that died while idle gives `restart`. Nap lines carry none of the four. On the first turn of each process, turn lines also carry `view_bytes`, `view_lines`, `view_head_hash` (FNV-1a 64 of the first 1024 bytes of the rendered view) and `view_hash` (of the whole view), to trace prompt-cache misses. Calls without usage data append nothing. Appends do not take `LOCK`. Total turn cost, from the last line of each process (a process starts at `process_turn` 1):

```bash
jq -s '[.[] | select(.kind == "turn" and .process_turn != null)] | group_by(.run) | map(reduce .[] as $t ([]; if $t.process_turn == 1 or length == 0 then . + [$t.cost_usd // 0] else .[-1] = ($t.cost_usd // .[-1]) end) | add) | add' ~/.ralph/chat/usage.jsonl
```
