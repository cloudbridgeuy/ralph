# ralph chat Command

`ralph chat` is a single long-running chat with one persistent memory. Messages run on one persistent `claude -p` process that chat resets under a policy (see [Process reset](#process-reset)). The model sees a compressed view of the whole chat and can open details through a private MCP server. Bare `ralph` (no subcommand) runs `ralph chat`.

## CLI

```bash
ralph chat [--skill <PATH>]... [--permission-mode <MODE>] [--worktree-dir <DIR>] [--no-inbox-sound] [--no-inbox-notification] [--skip-summary]
ralph                      # same as ralph chat with defaults
ralph chat history <read|zoom|recall|search> <words>... [--cursor <C>] [--store <DIR>]
ralph chat --thread <NAME>  # create or open a thread; see Threads
ralph thread <ls|drop <NAME>|merge <NAME> [--view]|park <NAME>|revive <NAME>|pull <NAME>> [--store <DIR>]
```

- `ralph chat history` prints what the model's `read`, `zoom`, `recall` or `search` tool returns for the same input, then exits. It starts no chat, turn or model call, and works while a chat runs on the store. See [History commands](#history-commands).

- `--skill <PATH>` (repeatable) adds a skill directory. See Skills.
- `--permission-mode <MODE>` sets the claude permission mode for turns and claude-tmux workers. Precedence: flag, `RALPH_CHAT_PERMISSION_MODE`, `[chat] permission_mode` in the ralph config, then `auto`. Resolved once at chat start. `ralph ask` has its own setting.
- `--worktree-dir <DIR>` sets where spawned workers get their worktrees. Precedence: flag, `RALPH_WORKTREE_DIR`, `[chat] worktree_dir`, then `.worktrees`. A leading `~` expands to home; a relative path resolves against the repo root of each spawn, not the chat's cwd. The chat process resolves the rest on each spawn and close.
- `--wrap-width <N>` caps the wrap width of rendered replies, worker reports and the prompt area (status line, draft, footer). Precedence: flag, `RALPH_WRAP_WIDTH`, `[chat] wrap_width`; `0` or unset = terminal width. The smaller of the cap and the terminal width wins, read at each render. A value that is not a whole number stops chat start with an error. See [configuration](../configuration.md).
- `--no-inbox-sound` and `--no-inbox-notification` turn off the inbox alert parts (see Inbox alerts).
- `--skip-summary` skips the [startup recap](#startup-recap) for this run.
- `--store <DIR>` sets the store path. Precedence: `--store`, then `RALPH_CHAT_STORE`, then `~/.ralph/chat`; an empty `RALPH_CHAT_STORE` counts as unset, and a missing home directory is an error when neither is set. A relative path resolves against the cwd at startup. The directory is created at startup. Parallel chat instances need separate stores (the session name is only a label and does not separate them); otherwise they share the log, `history.txt`, `editor.md`, and `inbox/`.
- `--name <NAME>` sets the session name shown in the status bar and the terminal title. Precedence: flag, `[chat] name`, git root folder name, cwd folder name, then `ralph`. See [Session name](#session-name).
- Hidden subcommands: `ralph chat-mcp --store <DIR> --socket <PATH>` and `ralph chat-nap --store <DIR> [--timeout 600]` (`NAP_TIMEOUT_SECS`). Both are spawned by ralph itself.
- Input is a reedline editor on the main thread with prompt `>>> `. While the editor reads, `crate::warn::warn` from any thread sends each row of its box to reedline's external printer (`print_above_prompt`, 256 rows), so the box prints above the prompt and the prompt and hint line repaint below it; a full printer and every other moment write to stderr. Enter sends; Alt-Enter or Ctrl-J inserts a newline; Ctrl-G opens `[chat] editor` (an argv list such as `["nvim", "-c", "normal! Go", "-c", "startinsert"]`; the file path is appended as the last arg; an empty list warns and falls back), else `$VISUAL`, `$EDITOR`, or `vi` (one program, no splitting), on `<store>/editor.md`, prefilled with the last assistant reply, a `──── write below ────` line, and the draft; the text below the last separator line replaces the draft (never sent; an empty result keeps the old draft). Ctrl-V pastes a clipboard image as `[Image #N: path]` (see [Images](#images)). Esc Esc clears the whole draft (Ctrl-Z undoes it, Ctrl-O redoes). Tab completes the `/hold` argument (see [/hold](#hold)) and the `/view` path (see [/view](#view)); on any other line it opens an empty reedline menu that reads `NO RECORDS FOUND`. With `[chat] edit_mode = "vi"` the editor uses reedline's vi insert and normal keymaps: Esc leaves insert mode, so Esc Esc does not clear; Ctrl-U clears the whole draft in insert and normal mode instead. The insert keymap keeps Alt-Enter, Ctrl-J, Ctrl-V, Ctrl-G, Ctrl-O, Tab and Shift-Tab; normal mode keeps Ctrl-G. Visual mode is off: when a key (`v`) enters it, the edit-mode wrapper switches straight back to normal mode before reedline paints, so no selection starts; `fv`, `tv` and `rv` still work. The prompt indicator is `>>> ` in insert mode and `::: ` in normal mode. The pure `chat_edit_mode` core module resolves the key and the indicator. Up/Down and Ctrl-R use the history file `<store>/history.txt` (1000 entries). Ctrl-D or Ctrl-C at the prompt quits; an empty message does nothing unless reports are unread (see Worker inbox); `[chat] empty_submit` and `empty_prompt` change this (see [configuration](../configuration.md)). A turn has no time limit. While chat sits at the prompt or in `/hold` with a live claude process, ralph keeps the prompt cache warm (see [Keepalive](#keepalive)). Ctrl-C during a turn cancels that turn (nothing is stored) and returns to the prompt with the message restored as the draft; SIGTERM and SIGHUP end the chat. While a turn runs, chat keeps a `<store>/turn` marker (`user` or `worker`, removed when the turn ends); the chat socket server reads it so `spawn_worker`, `close_worker` and `watch` work only in a user-started turn (`reply` also in a worker turn).
- A dark-gray full-width rule (the shared termimad skin's `---`, default gray(6) `―`) prints before the turn and after the reply.

## Single instance

`chat::run` calls `Store::claim_chat` right after `Store::new`: an exclusive `try_lock` on `<store>/CHAT`, held for the life of the chat, with the pid written inside. A second chat on the same store exits with `store <path> is in use by pid <N>; use --store <DIR> or RALPH_CHAT_STORE for a second chat` (the pid part is left out when the file is unreadable). The pure `holder_pid` and `store_in_use_message` live in `chat_memory/claim.rs`. The claim is a `ChatClaim` (`crates/ralph_server/src/chat/claim.rs`) that unlocks on drop: a child spawned at the same moment shares the open file description until exec, so closing the fd alone can leave the flock held and a reclaim in the same process fails with its own pid (GUZ-1248). The OS releases the lock when the process dies, so a crash leaves no stale claim. flock is per inode, so `/tmp` and `/private/tmp` give the same lock. `CHAT` is a separate file from `LOCK` and `NAP`, so `chat-nap`, `chat-mcp`, worker writes and chats on other `--store` dirs are not blocked. Parallel chats need separate stores (GUZ-436).

## Threads

A thread is a named side chat forked from the main chat. `ralph chat --thread <NAME>` creates the thread on first use and opens it after that. A name is 1 to 32 lowercase letters, digits or dashes, not starting with a dash; `main` is reserved.

- Storage: a thread is a nested store `<store>/threads/<NAME>/` with its own log, tree, `CHAT` claim, inbox, socket and workers. `thread.json` holds `{base, created}`, plus `merged: {at, digest}` once merged and `parked: {at}` while parked (a file without them still parses): `base` is the main log length when the thread was made. `ensure` writes it once, under the thread's `CHAT` claim; later opens keep it.
- Switch (`Route::Switch`, `Command::Thread`, `Command::Main`): `crates/core/src/chat_switch.rs` holds the pure code for `/thread <name>` and `/main`. `parse_switch_args` and `parse_main_args` give a `SwitchTarget`. `switch_decision` refuses the current target and a merged or parked thread (`open_check`). `switch_blockers` refuses while workers or watches run. A switch typed during a turn queues and is checked when the turn ends. `chat/switch.rs` is the shell: `check` reads the target's `thread.json`, lists workers and watches, and probes the target's `CHAT` claim. `switch_argv` builds the `chat` argv for the new process; it drops `--name`, so the new chat titles itself by thread name. The loop leaves with `ChatExit::Switch`, and `chat::run` returns it. Only then does `execute_chat` in `main.rs` replace the process (`exec`) with `ralph chat` on the target, so every Drop has run: the `CHAT` claim, the model session, the headless shutdown and the editor. `Reedline::read_line` and `Drop` leave raw mode first (`vendor/reedline/src/engine.rs`). Before it leaves, the chat saves queued lines and the editor buffer to history (`unsent_texts`) and drops the model session; keepalive stays inert because `idle` is false. Failures: if another chat takes the target between the check and the exec, the new chat fails with its in-use message and exits; if the `exec` fails, ralph prints `could not start the new chat` and exits. Either way the user lands at the shell. A queued `/thread` or `/main` is its own batch (`next_batch`). When `check` refuses the switch or `save_unsent` fails, the arm puts the switch line, the queue entries after it (`carried`) and the text already in the editor back in the prompt (`refused_draft`, `restore_prompt`); with a signal pending after a failed save it exits instead; the `!` shell failure path uses the same helper. A multi-line entry with extra words after the switch argument (`/thread auth\nfix` or `/main\nfix`) gets the usage refusal (`Command::args` and the parse functions split on any whitespace) and returns to the prompt; `/thread\nauth` is a valid switch to `auth`. Saved schedules stay on disk and do not fire while away. See [Switching threads](threads.md#switching-threads).
- Config: a thread loads main's `config.toml`. `config_root` maps `<main>/threads/<NAME>` to `<main>` by the store path as written (`--store`, `RALPH_CHAT_STORE` or the default), never by the symlink-resolved path; `set_store_layer` and chat start (`store_config_path`) use it. A plain store that is a symlink to `<x>/threads/foo` loads its own `config.toml`, and a thread folder that is a symlink loads main's.
- View: the system prompt's older part is a header, a 100-line (`MAIN_PREFIX_LINES`) view of main's entries before `base`, a second header, then the thread's own older view. The middle and the verbatim tail are the thread's own. Every thread id carries its name: `#auth:4-7`. `thread_split` builds it; `turn.rs` calls `fork_view` at each process launch.
- Ids: in `zoom` and `read`, `auth:5` (or `#auth:5`) is thread `auth`, and an id without a prefix (or `main:5`) is main. From a thread, a main id at or after `base` fails with `#N is after this thread's fork point (#base); pull to see it.`. `recall` and `search` take an optional `thread` argument (`main` or a name); without it they search the caller's own messages. From a thread, main searches stop at `base` (`Archive::limit_to`). An unknown name gives `no thread <NAME>; `ralph thread ls` lists them.`. Output ids get the `<NAME>:` prefix at the start of each item, read block and hit line, so text inside messages is never changed.
- `ralph chat --thread <NAME> history zoom auth:0` reads a thread from the shell; main can read any thread by prefix. `history recall|search … --in <main|NAME>` sets the `thread` argument (`in_scope`); `zoom` and `read` refuse `--in` and take the thread in the id.
- `/threads` (`Route::ThreadOp`, `Command::Threads`) prints the same list in the chat, in main's chat and in a thread's chat, with no model call. `crates/core/src/chat_thread_cmd.rs` parses it to a `ThreadOp`; `chat/thread_cmd.rs` is the shell and calls `list` on `config_root` of the chat's store. A refusal, such as a usage error, puts the line back in the prompt like a refused switch. `parse_thread_op` returns `None` when the args do not have the command's shape (extra words after `/threads`, a word count other than one, a name that fails `ThreadName::parse`, an unknown flag); `route_input` then returns `Route::Send`, like `workers_route`, so `/merge requests are failing` and user skills named `/pull` reach the model. Only `/pull`, `/park` and `/merge` with no args give a usage error. The same fallback covers `/pull`, `/park` and `/merge`. After a thread op succeeds the chat refreshes the status (`monitor.refresh(true)`), so the inbox count shows a merge at once. It waits in the queue during a turn.
- `ralph thread ls` prints one line per thread: name, `forked at #<base>`, message count, creation time, `merged <at>` or `parked <at>`, then `<N> worker(s)` (running workers of the thread folder) and `<N> unread` (reports in the thread's inbox), each only when not 0 (`ls_counts`); `no threads in <store>` when there are none (`empty_list_message`; the in-chat `/thread ls` prints `no threads`). The unread count comes from `Inbox::unread_count`, which reads the ledger and the pending report files but never writes or deletes them, so `ls` is safe while the thread's chat is open. `ralph thread drop <NAME>` takes the thread's `CHAT` claim and deletes its folder; it refuses with `thread <NAME> is in use by pid <N>; close its chat first.` while a chat has it open, and with `thread <NAME> has running workers (<ids>); close them from thread <NAME>'s chat first.` while a worker spawned from the thread runs (`guard_check` on `running_workers` of the thread folder). There is no `--close-workers` flag: the worker close path can refuse a dirty tree or unmerged commits, so workers are closed from the thread's chat. The saved watch records (`threads/<NAME>/watches/`) and schedule tasks (`threads/<NAME>/schedule/`) go with the folder, and drop says how many: `dropped thread <NAME> and its 2 saved watches or schedules` (`drop_message`). A worker spawned from a thread belongs to the thread folder: its report lands in the thread's inbox and main's `/workers` does not list it.
- `ralph thread merge <NAME>` squashes a thread into main. It refuses like `drop` (unknown, open chat, running workers) and holds the thread's `CHAT` claim for the whole merge. It also refuses while the thread has saved watch or schedule records, with `thread <NAME> has 1 saved watch or schedule; stop it from thread <NAME>'s chat before merging.`: a merged thread never opens again, so its records could never restore or be stopped. These refusals come before the curator call, so they cost nothing. Each attempt is one curator call (`run_curator`, the nap's Haiku command, usage `kind` `merge`), up to 3 calls in total, and gets `merge_prompt`: the thread's 200-line view with `#<NAME>:` ids, and the rules. `check_digest` takes a reply that is not empty, at most 2048 bytes (`MAX_DIGEST_BYTES`), cites at least one `#<NAME>:a-b` id and no other thread; else `digest_with` asks again with the reason, at most 3 attempts (`MAX_MERGE_ATTEMPTS`). A refused or failed curator call changes nothing. On success, `thread.json` gets `merged`, then main's inbox gets a report with worker `thread:<NAME>` and status `merged`; main's next turn reads it as `[thread <NAME> · merged]` plus the digest, so main's cache is not rebuilt. The curator runs silent (`invoke_subprocess_silent`, the same `Display::Silent` pump as a ping), so a rejected attempt never reaches the terminal; the command prints only the final block. If the inbox post fails, the thread stays merged and the error names `thread.json`, which holds the digest.
- `ralph thread merge <NAME> --view` (alias `--rebase`) merges with no model call: the same refusals, claim and freeze as squash (`merge_with`), but the report is `view_block`: a header line (`Thread <NAME>, forked from main at #<base>, with its memory view posted to main:`) and the thread's view at a 100-line budget (`VIEW_BLOCK_LINES`) with `#<NAME>:` ids. It refuses a thread with no messages, and a block over 64 KB (`MAX_VIEW_BLOCK_BYTES`) with a hint to use squash. Measured on a real store, view lines average about 490 bytes and stay under about 570, so a 100-line block is at most about 57 KB (about 12-14k tokens). The report status is `view` (`VIEW_STATUS`), so main reads `[thread <NAME> · view]` plus the block; entries posted before the rename keep `rebased`, and no code matches `view` or `rebased`; `merged.digest` in `thread.json` holds the block. Main pays for the block once, on its next turn, then naps it like any worker entry.
- `/merge <NAME>` in main's chat squashes with `merge_thread` after `merge_precheck` (unknown, merged, workers, saved records, open chat: refused before any question) and a y/n (`merge_question`: one paid Haiku call, up to 3); the answer loop is the one `/schedule` uses (`ask_answer` in `chat/schedule.rs`, with `read_answer` and `parse_answer`). After `y` it runs in the foreground with the curator built as in `ralph thread merge` (`CallSite::Merge`, `NAP_TIMEOUT_SECS`); no background path. An explicit `n` or `no` cancels with `merge cancelled.` and the queue goes on. Ctrl-C or a closed input gives no answer (`ask_answer` returns `None`, `merge_answer` maps it to `Err`): the command and the rest of the queue return to the prompt and nothing is sent. A signal (SIGTERM or SIGHUP) while a refused thread command or `/thread` switch is handled instead saves the command, the queue and any typed text to chat history and exits. `/schedule` keeps `ask_yes_no`, where no answer means no.
- `/merge <NAME> --view` (or `--rebase`) in main's chat runs `view_thread` with no model call and no confirmation (`ThreadOp::Merge { view: true }`, `parse_merge`); the same claim and refusals apply, and the thread's own chat must be closed. It prints `posted thread <NAME>'s memory view to main's inbox.` (`view_posted_message`) and the report, and the chat does not exit. In a thread's chat it refuses with `/merge runs in main's chat. Run /main, then /merge <name>.`. `VIEW_FLAG` (`"--view"`) is the one constant for the flag text in the usage text, and a test checks that the `/merge <name> --view` help entry matches it; the parser also accepts the alias `--rebase`, and `--view --rebase` is refused as a repeat. The clap flag of `ralph thread merge` is separate and has `rebase` as a hidden alias.
- A merged thread is read-only, so its citations still resolve: `ralph chat --thread <NAME>`, `drop` and a second `merge` refuse with `thread <NAME> is merged into main and stays read-only; `ralph chat --thread <NAME> history` still reads it.` (`merged_check`); `history` and main's `#<NAME>:` ids still read it. `reply`, `close_worker` and `/nudge` refuse a `thread:` id with `<id> is a merged thread's digest, not a worker; there is nothing to reply to, nudge or close.` (`refuse_thread_report`).
- `ralph thread park <NAME>` writes `parked`. It refuses like `drop` (unknown, merged, open chat, running workers) and refuses a thread that is already parked. A parked thread does not open: `ralph chat --thread <NAME>` refuses with `thread <NAME> is parked; `ralph thread revive <NAME>` opens it again.` (`open_check`, which also gives the merged refusal). `/park <NAME>` in main's chat runs the same `park_thread` with no model call and prints the same text as the shell command (`parked_message`) (`ThreadOp::Park`); in a thread's chat it refuses with `/park runs in main's chat. Run /main, then /park <name>.`, and there is no `/revive`. Watches and schedules belong to the thread's own store and run only inside its chat process, so they pause while it is parked: closing the chat already killed its watches, persistent watch records stay in `threads/<NAME>/watches/`, and due tasks wait. `ralph thread revive <NAME>` only clears `parked` (`revive_check`: refuses a merged thread and `thread <NAME> is not parked.`); the next `ralph chat --thread <NAME>` runs `Watches::restore` and `restore_schedule` as every chat open does, so overdue tasks fire late and passed watch deadlines post their reports at once. `history` still reads a parked thread. Park keeps the saved records, so revive brings them back. `drop` and `merge` work on a parked thread; a merge clears `parked`, so a thread is never both.
- `ralph thread pull <NAME>` sets `base` to main's current log length and prints `pulled thread <NAME>: fork point #<old> -> #<new>, <N> new main message(s).`, or `thread <NAME> is already at main's end (#<N>).` without a write. It refuses an unknown or merged thread and an open thread chat (`is in use by pid <N>; close its chat first.`), so no live claude process holds the old view; it works on a parked thread. `/pull <NAME>` in main's chat runs the same `pull_thread` with no model call (`ThreadOp::Pull`, `chat/thread_cmd.rs`); it refuses in a thread's chat with `/pull runs in main's chat. Run /main, then /pull <name>.` (`op_refusal`), and a refusal puts the line back in the prompt. The chat does not exit. Every chat open reads `thread.json` again (`open_fork`) and the chat-mcp `Memory` reads it when the claude process starts, so the next `ralph chat --thread <NAME>` launches with the new main prefix and main ids up to the new `base`. That launch has a cold prompt cache, like every chat open, so a pull costs nothing extra. The thread's own log, tree and ids do not change.
- `/fork <NAME>` opens the thread in a new Rex block: it runs `rex split -b $REX_BLOCK --label "thread <NAME>" -c <cwd> -- <ralph> chat --thread <NAME> --store <main>`, with `env RALPH_CONFIG_DIR=<dir>` before `<ralph>` only when that variable is set. From a thread's chat it forks a sibling from main (`config_root`), not a nested thread. It refuses a bad name or a word count other than one (usage), and a merged, parked or open thread (the `ralph chat --thread` and `pull` messages); an unknown name is fine, the new chat creates it. Without `REX_BLOCK` it opens nothing and prints the shell-quoted command to run in another terminal. It is local, starts no turn and waits in the queue while a turn runs. The status bar of the new chat already shows the thread name. `parse_fork_args` and `fork_launch` are pure; `thread::fork` reads the environment and runs `rex`.

For a task-first walkthrough of these commands, see the [Threads Guide](threads.md).

## Turn loop

1. A launch (`Store::load_after_nap`) first waits for a running nap, then `Store::load_settled` takes a shared `LOCK`, then reads log and tree. It waits only while an append or a nap commit holds `LOCK` (one fsynced line each), not for curator calls. Nodes that are still pending show as described in [Pending summaries](#pending-summaries).
2. `split_view(entries, tree, VIEW_LINES, recent_history_tokens)` builds the memory view in three parts from two cuts of the verbatim start: the frozen cut snaps down to a multiple of `OLDER_VIEW_STEP` (256 entries), the tail cut to a multiple of `TAIL_STEP` (32 entries). The older part is the view (`VIEW_LINES`, 200 lines) of every entry before the frozen cut. It goes in the system prompt, so it stays byte-identical across respawns (and claude's prompt cache for it holds) until the verbatim start crosses a 256-entry boundary. A nap that failed partway can later summarize a node below the frozen cut, so the older view can change without the cut moving. The middle covers the frozen cut to the tail cut with one summary line per 32-entry block (at most 7 blocks). A block without a summary splits into halves down to leaf lines, so with summaries missing the middle can still reach 224 raw lines; a corrupt entry shows as a notice. The tail starts at the tail cut. Entries between the tail cut and the verbatim run show as summaries. The rest is the verbatim run: the newest entries within the recent-history budget (see [Recent history](#recent-history)). The three cover every entry once. The view is built only when the turn needs a new `claude` process (step 4); a turn on a live process does not use it.
3. For a worker turn, one `worker` entry per report is appended to the log. The user message waits for step 6.
4. One `claude` process serves the whole chat. The first turn (and any turn after the process died or a turn failed) runs `build_chat_command`: a fresh `claude --verbose --permission-mode <MODE>` (the chat's resolved mode) with isolation args, `--append-system-prompt-file /tmp/ralph-<uid>/<key>-<pid>/system-prompt.md` (the chat's private socket directory, described below) holding the system prompt and older view (`turn_system_prompt(custom, images, older)`: the built-in text, or with `[chat] prompt_file` the file text in place of the behaviour rules and with the tool contract and the images paragraph kept, then each `append_prompt_files` text, then the older view; just the prompt while the older part is empty; files are read once at chat start into `CustomPrompt`; each launch rewrites the file, mode `0600`, with control characters dropped, a test checks that the file holds the same bytes the old argument carried; that claude builds the same prompt, and so keeps the same prompt cache prefix, from a file as from an argument is not verified; the text never goes on the command line, where `ps` would show it to any local user), the MCP args, `--settings` with `autoCompactEnabled` false (merged with the CLAUDE.md exclude and `"totalTokensReminder":"off"`; nap's `--settings` carries `"totalTokensReminder":"off"` without `autoCompactEnabled`; `totalTokensReminder` is a setting internal to claude, undocumented and possibly renamed, so claude's varying `<total_tokens>` line stays out of the cached system prompt), `--input-format stream-json --output-format stream-json` and `-p`. Memory is injected at process start only: the first message is the middle lines, the tail lines, a blank line, `New message:`, then the message. Later turns send the message text only, as one stream-json `user` line (`ralph_core::stream::user_line`); the process keeps the conversation. The command starts with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, so claude starts no background tasks and the process stays alive after each `result`. The `Session` owns the piped stdin and the stdout/stderr reader threads for its whole life, and `Session::turn` can be called many times. A turn ends at the top-level `result` event (parsed with `ralph_core::stream::result_is_error`, not text-matched); if claude exits mid-turn ralph reads its remaining lines for up to 3 s (`EXIT_GRACE`) before it finishes; chat turns have no time limit (`timeout_secs` is not used). The process stays up and the next turn reuses it. The session is dead, and the next turn respawns it from the store, when the process exits, stdout closes before `result`, or a turn is killed. Before each turn chat polls the child with `waitid` and `WNOWAIT`, which does not reap it, so a process that exited while idle is dropped and respawned. Before it sends the message, `Session::drive` discards the stdout lines that the process wrote after the last `result`. If one of them is a `result`, the turn fails with `LeftoverResult` and chat respawns the process, as for a process that exited while idle. A line that arrives after this check still goes into the turn: stream-json lines carry no turn id. A turn that exits non-zero, has no reply, or errors drops the session too, as does a reset (see [Process reset](#process-reset)). On cancel or SIGINT the session writes one `control_request` `interrupt` line (`interrupt_line`) and keeps reading until `result`. With no `result` within 3s it kills the process group and the session is dead. Dropping the `Session` closes stdin, waits, and kills after 3s. On every chat exit, a lost terminal included (`watch_input` drops the session before `exit`), ralph kills the claude process group before it reaps claude and never signals the group after that (`group_signal_safe`); nap and inbox-alert helpers start through `spawn_detached`, which reaps them on a thread. There is no `--resume` and no `--agent`. Worker triggers use the same path.
5. Output goes through the spinner subprocess runner and `StreamProcessor`, as in `ralph ask`. Boxed warnings (TTY, no `NO_COLOR`) start with CR and clear-to-end-of-line so they never begin on a spinner line. A reply fence tagged `bash`, `sh`, `zsh` or `shell` shows each line laid out like a Bash tool call (`core::shell_format::format_fence`, every `;` kept visible, a split pipeline ends its line with ` |`, so a paste stays valid shell) and highlighted as `sh`, with color off too; a fence with a `\` continuation, a heredoc or a quote that spans lines, or a line that does not parse, shows unchanged. Only the display changes: the log, memory and Claude keep the raw text.
6. On exit code 0 with response text, the user message (if any) and then the reply are appended verbatim and a detached `ralph chat-nap` is spawned (stdio null; spawn failure only warns). Otherwise a warning `chat turn failed (exit N)` prints and the loop continues. Only the subprocess call is wrapped in `retry_on_outage`: a non-zero exit whose stderr or response text matches an outage marker, waits 2s then 8s and respawns the process from the store with the first-message form and runs the turn again (at most 2 retries), warning `chat turn hit an outage (<kind>); retrying in Ns (k/2)`. The wait polls the cancel flag every 100ms, so Ctrl-C ends the turn as a cancel; SIGTERM and SIGHUP end it too. Cancel and interrupt are never retried. If the first stdin write to a reused process fails (it died after the check), the turn starts a fresh process from the store once and sends the first-message form; the dead process never got the message, so it is sent once, and this is not an outage retry. After the retries run out, or for any non-outage failure, the warnings and draft restore below apply unchanged. Only the final attempt writes a usage record, and only the first turn of each process carries the view and prompt-size fields.
7. A turn that is cancelled (Ctrl-C), fails, or hits a subprocess error stores nothing for a user message, including any partial reply, and returns to the prompt with the message preloaded as the draft (`draft_after`). A cancelled turn also drops the claude process, so the next turn respawns it from the store. Worker report entries from step 3 stay in the log. SIGTERM and SIGHUP end the chat.

The system prompt tells the model that the message starts with the compressed chat, that `#<id>` lines are summaries, to use `zoom`, `recall` and `search` before guessing or asking (`read` pages a range of ids), that `[worker ...]` messages come from workers, not the person, to call `workers` for worker status and never inspect system processes (`ps`, `pgrep`, `tmux ls`) or mention other chats' processes, that a next step of waiting becomes `/hold <id>` for one pending worker, a bare `/hold` when several are pending and any report matters, or `/hold <a> <b>` naming only the relevant ones when some are irrelevant (a watch plus `/hold watch:wN` for outside events, the `schedule` tool for a set time) unless a decision waits on the person (merge, push, Done, cleanup, a worker's question), which is then the suggested reply, and never "check back in N minutes", and never to claim manual saving. On a worker message the model may `reply` only with an answer already settled in the chat (a decision the person made, approved scope, a step in an agreed plan); merges, pushes, PRs, Linear status changes, new scope and anything public go to the person, and every worker reply is listed in its next message to the person. `spawn_worker` and `close_worker` are only for what the person asked in their latest message, `abandon` only when the person said to drop the work, and `force` only when the person said to close a worker of another chat. The chat MCP server enforces this with the pure `worker::command_allowed`: in a turn the person started every worker command is allowed, in a worker-triggered turn only `reply` is, in a `/send-it` run turn only what the approved plan allows (see [/send-it](#send-it)), and anything else is refused. Messages that start with `[worker watch:<name> · watch]` are watch reports from the `watch` tool, not from an agent or the person; before calling `watch` the model shows the exact command and waits for approval. Its delegation rules keep turns short: the model reads inline only to scope (at most 3 tool calls per question), sends multi-file reads, broad searches and test runs to `evidence-collector`, all code edits to `implementer`, and fixing work that fell short to `reviser`, and every dispatch prompt states goal, question, known facts, owned files, output cap, stop condition and tool budget, "Report not-found, do not widen scope.", and "You are a subagent. Don't run mem." After 2 failed repair rounds it diagnoses; after a 3rd it waits for the person. The images paragraph says how to show an image: with `Inline` the model writes `![alt](/absolute/path)` for a local file (http(s) and data: URLs stay text); with `Text` it gives the path or describes the image; in both it opens images in another app only when the person asks. `images` is a `ReplyImages` chosen once at chat start from `render::image::detect` (`Inline` when it finds image support, else `Text`), so the prompt stays the same across turns. It also must lead with the answer and end with one next step, call `help` first when the person asks how ralph chat itself works, show a 3-5 line plan when a request is ambiguous, treat a worker "done" as unverified until it checks the diff, tests, git and Linear, cite the `#<id>` behind facts from older chat, and say it has no erase tool when asked to forget.

## Queued messages

Ctrl-Q during a turn, or typing text, pauses the display of the turn output and opens a queue editor. Typed text seeds the editor, so no typing is lost. The turn keeps running and the output is held.

- Enter with text adds the text as a queue entry, except a read-only command (`/help`, `/config`, `/workers`, `/workers costs`, `/inbox list`, `/inbox peek N`, `/watch list`, a bare `/watch`, `/schedule` and `/schedule list`, and the usage or unclosed-quote replies of `/inbox`, `/watch`, `/schedule` and `/diff`): it runs at once, prints before the held output returns, and is not queued. The turn is not cancelled. Other commands (`/inbox`, `/inbox drop N`, `/hold`, `/nudge`, `@<id> <text>`, `/watch start`, `/watch stop`, `/schedule cancel`, `/diff` with a target) stay queued. Empty Enter or Ctrl-D adds nothing.
- Ctrl-Q in the editor backs out: a non-blank draft is added as the last entry, and the queue is held. The turn is not cancelled. At turn end ralph sends nothing and puts the entries, joined with a blank line, in the next prompt. Ctrl-Q during the same turn opens the editor again; the queue stays held.
- Each of these closes the editor, prints the held output, and resumes live output.
- Ctrl-C in the editor (a host command, `queue_ctrl_c`) clears a non-empty draft and the turn keeps running; on an empty draft it cancels the turn and holds the queue.
- Ctrl-G in the editor opens the same external editor as at the prompt, on `<store>/editor.md`, prefilled with the queue draft only (no reply, no separator); the whole file replaces the draft (an empty result keeps it). The editor child runs on the key thread, so nothing else reads stdin meanwhile; the turn keeps running and its output stays held. A failure prints `Editor failed: <error>`. Ctrl-V is off here.
- While the editor is open, a queue block follows the session name in the status bar: `turn running · QUEUED N`, or `turn done · QUEUED N` once the turn ended (no `· QUEUED N` part at 0 entries). Compact forms: `running · QN` / `done · QN`, then `▶ QN` / `✓ QN`. A held queue (after a back-out or an editor Ctrl-C) says `HELD` instead: `turn running · HELD N`, `running · HN`, `▶ HN`, and the `done` / `✓` forms likewise. When the bar is too narrow, the block is dropped after mail and before the session name. The mode block never drops. The turn's end repaints the editor through its reedline repaint signal, so the block flips without a key press. The mode block keeps `NAP`, `INBOX`, `WORK` or `IDLE`.
- Nothing sends while the editor is open. A turn that ends meanwhile waits for the editor to close.
- After a normal reply, ralph joins the entries with a blank line, in typed order, and sends them as one message as if typed at the prompt. Slash commands and `!` cells behave as at the prompt.
- A `!` or `!!` entry (see [Executable cells](#executable-cells)) or a `/thread`, `/main`, `/threads`, `/pull`, `/park` or `/merge` entry (`is_cell_command` in `crates/core/src/chat_thread_cmd.rs`; for `/threads`, `/pull`, `/park` and `/merge` only a line that `parse_thread_op` accepts, with a usage reply for a missing name, so `/merge requests failing on CI` is plain text and joins) is never joined: the entries before it go as one message, then it runs alone, then the entries after it, in typed order (`next_batch` in `crates/ralph/src/chat/queue.rs`). The rest waits while each part runs; a cancelled or failed part puts itself and the rest in the next prompt, joined with a blank line.
- Only the merged text goes to `history.txt`.
- After a cancel, a failed turn, an editor Ctrl-C, or a back-out, ralph sends nothing and puts the entries, joined with a blank line, in the next prompt. A restored cancelled message comes first, then a blank line, then the entries. On exit (SIGTERM or SIGHUP) the entries and any typed text are saved to the chat history, and one line `N queued message(s) not sent; saved to history.` goes to stderr. A `/thread` or `/main` switch prints the same line after it saves unsent text. If a save fails, the line says `not all saved to history` instead. A switch whose save fails without a signal prints no such line: the text returns to the prompt.
- Text typed during a turn opens the queue editor seeded with it (`chat_typed::typed`): all printable text of the read, before and after a Ctrl-Q, with Tab and inner line breaks kept. Control bytes, arrows and other escape sequences, Alt keys, bracketed-paste markers (the paste content stays) and invalid UTF-8 are dropped; a read with no text and no Ctrl-Q is ignored. A read that ends inside a UTF-8 character or an escape sequence waits up to two 10 ms polls for the rest. Ctrl-C and Ctrl-Z still signal (the terminal keeps ISIG). Bytes left in stdin when the turn ends are read, not flushed; their text is never sent but joins the next prompt draft, after the draft and the queue entries. If the input closes, ralph stops reading keys during the turn. Ctrl-Q at the idle prompt does nothing.

## Startup recap

Before the first prompt, after the leftover-workers hint, chat prints a short recap of where the log ended. It makes no model call and costs nothing. The pure `chat_recap::recap` builds it from the log and live facts; the log has no session marker, so "previous session" is the end of the log.

```text
last session · 2h ago
  you: <first non-empty line of the last user message>
  next: <Next step line of the last assistant reply>
  live: 2 workers · 3 unpushed
```

- `next` is the last line of the last assistant reply that starts with `Next step:` or `Next:` (any case; leading `*`, `_`, `-`, `>`, `#` are ignored). The suggested reply itself is not used: it lives only in memory and is not saved.
- `live` comes only from live reads at start, never from summaries: the running workers of this store, and `git rev-list --count @{u}..HEAD` in the cwd. The git read is limited to 2 seconds with the bounded command helper; a timeout, no upstream or no repo counts as 0. A zero count is left out, and so is the whole line when both are 0.
- Each line is cut with `…` to the wrap width (`--wrap-width`, `RALPH_WRAP_WIDTH` or `[chat] wrap_width`, capped by the terminal width). Corrupt log lines are skipped. The text has no color.
- Nothing prints when the log is empty, has no assistant reply, `[chat] resume_summary = false`, or `--skip-summary` is given.

## Suggested reply

The chat-mcp tool `suggest_reply` takes one required `text`. The socket server parses it with the pure `chat_suggestion::parse_suggestion` (trimmed; empty, a line break, or more than 200 characters is a tool error that says what to fix, and the text is never cut) and stores it in an in-memory slot owned by the running chat; a later call replaces the earlier one. The tool description says a reply of exactly `/hold [<target> ...]` naming listed targets can start that hold at once. It has no risk marker and no turn check. The slot is cleared right before each turn starts and taken right after it ends, so a call outside a turn is dropped and a suggestion shows only in the first prompt after the turn that set it.

At turn end the pure `chat_suggestion::turn_end` returns a `Next`: `Hold`, `Prefill` or `Nothing`. A prefill goes to the editor through the same insert path as a restored draft, with the cursor at the end. Held or queued text always wins: a kept message, a held draft or queue entries replace the suggestion, and queued text that ralph sends by itself drops it. The suggestion fills the prompt only after a normal reply, and not when a schedule approval question was shown after that turn. Enter sends it, it is editable, and Ctrl-U clears it (Esc Esc too in emacs mode). Clearing it and pressing Enter follows the normal empty-submit rule. The suggestion is drawn in the `[theme.input] suggestion` color until the first edit, in emacs and vi modes alike; after that the buffer stays in the normal color even if you retype the same words. Held or queued text keeps the normal color. With `NO_COLOR` or no TTY the suggestion is not colored. A suggestion sent unchanged stays in the suggestion color in scrollback, which marks it as accepted. The system prompt and tool description tell the model to call it first, before any reply text, with the exact quoted words of its Next step line, and never to mention it; the tool result repeats that the reply comes next. ralph never parses reply text.

A suggestion that is exactly `/hold`, `/hold <target>` or `/hold <t1> <t2> ...` enters that hold at once, with no pre-fill, when `[chat] auto_hold` is on (the default), the turn replied normally and no draft or queue text is held. The text must be canonical: `HoldFilter::parse` reads what follows `/hold` and the suggestion is accepted only when `HoldFilter::render` gives back the same text (one ASCII space between tokens, no tabs, no double spaces, no leading or trailing whitespace, no duplicate target, case as listed). Every target must be a worker in the status list (any state: running, busy, permission, idle or done; a closed worker is no longer listed), an active watch as `watch:<name>`, or a schedule as `schedule:<id>`, from `chat_hold::hold_targets`. A bare `/hold` needs at least one hold target and holds for anyone. Any other text, any unknown target, or `auto_hold = false` pre-fills the text as before. ralph prints the dim line `auto-hold: <label> · Ctrl-Q to type` (`<label>` is `anyone`, the target, or the targets joined by `, `) and runs the same hold as a typed `/hold`; Ctrl-Q returns to an empty prompt, and a pending report that does not match stays unread.

The first line you submit after a suggestion is pre-filled appends one record to `suggestions.jsonl`: `{ts, run, turn, outcome, suggestion, sent}`. `run` is the chat run id, as in `usage.jsonl`. `sent` is the trimmed submitted line, a model prompt, a local command or an empty submit alike, and `turn` is the `process_turn` of the turn that produced the suggestion, as in `usage.jsonl`. The pure `chat_suggestion::outcome` gives `accepted` when `sent` equals the suggestion, `extended` when `sent` starts with the suggestion and is longer, and `discarded` otherwise, including an empty `sent`. An auto-hold writes its own record at once, with outcome `held` and `sent` equal to the suggestion. Exit without a submit (Ctrl-C, Ctrl-D) logs nothing, and neither does a suggestion that was never shown. A write failure only warns.

## Worker inbox

Worker reports never interrupt the draft. A watcher thread polls every 500 ms and repaints the prompt in place (reedline `RepaintSignal`), keeping the buffer and cursor.

- Each arriving inbox file moves into the queue `<store>/inbox.json` (oldest first, positions from 1 that shift up when a report leaves); unread is the queue length. A report leaves the queue only when sent to main or dropped, and is deleted from the file. An old file with `next_id`, `id` and `read` fields still loads; its read entries are dropped. Tmux workers have sessions named `ralph-<project>-<id>` (`<project>` = the git top-level folder name, letters, digits and dashes only, else `repo`), so the same id in two projects does not collide. Names are cosmetic: at spawn ralph tags each session with the tmux user options `@ralph_store` = the canonical store path and `@ralph_id` = the bare id, and the status line reads the id from `@ralph_id`. Only sessions tagged with this chat's store and an id are listed (sessions without both, including ones started before `@ralph_id`, are ignored; missing tmux or no server means no tmux workers). Headless Cursor and opencode workers are listed from their owner files instead (see [Headless workers](headless-workers.md)). A worker with a `blocked/<id>` marker (a pending permission request) shows `permission` whatever its reports say, and counts as working. A claude-tmux worker's state is the status of its latest report, else `running`. A `reply`, a nudge or a spawn writes the marker `<store>/sent/<id>`; while it exists a `done`, `blocked` or `question` status is ignored (a `check` status is not), so the worker shows as working until its next report, which removes the marker (`chat_status::superseded`). For opencode workers ralph asks the chat's own opencode server for `GET /api/session/active` (one call for all workers, every 5 s and after each turn or inbox read, only while an opencode worker runs): `busy` while `ses_ralph<id>` is in it, else the latest report status, else `idle`; if the call fails they fall back to the claude rule.
- External report: a program outside ralph can post to the inbox (see `ralph inbox post`). The record is a normal `Report` with `worker` = `external:<source>`, status `report` and the posted text. `inbox_post::external_report` (core) builds it: the source follows the thread name rule (1 to 32 lowercase letters, digits or dashes, not starting with a dash), the text is at most 65536 bytes of non-empty UTF-8, `\r\n` becomes `\n`, and one leading byte order mark (U+FEFF) is stripped. Text with a refused character is refused with `The report contains the refused character U+XXXX.`, naming the first one. The refused set is the C0 controls except newline and tab, so a lone `\r` or an ESC. It is also DEL, the C1 controls, and U+2028 and U+2029, which `str::lines` does not split on. It is also the format characters from `chat_name::is_format_char`, including U+00AD, bidi controls such as U+202E and U+2066 to U+2069, U+200B, and the tag characters U+E0020 to U+E007F, so subdivision flag emoji are refused. A U+FEFF anywhere else is refused. U+200C and U+200D, the joiners, are allowed. Nothing is truncated: a report over the size cap is refused. `inbox_post::check_store` accepts only an existing directory that holds `log.jsonl` or `LOCK`, so a post never creates a store.
- Worker status: the worker-mcp tool `set_status` takes one required `text` (at most 120 characters; controls stripped, newlines become spaces, empty or longer is a tool error) and atomically appends to `<store>/status/<id>` (an entry is an RFC 3339 time line and a text line; the file keeps the last 5 entries, oldest first, through the pure `worker::append_status`; an old single-entry file still decodes). It is not a report: it writes no inbox entry or marker and costs no turn. `/workers` shows the newest entry with its age, and `/workers <id>` lists all kept entries; `close_worker` removes the file, spawn clears a leftover one for a reused id, and `set_status` is refused with `Could not set status: worker closed.` once the worker is closed. The worker prompt tells workers to set it when they start and when their activity changes.
- Spawn record: every spawn, whatever the harness, writes `<store>/spawn/<id>` atomically (JSON `SpawnRecord`: optional `ticket`, optional `tracker` of `linear` or `jira`, optional `base_sha`, optional `harness` (the harness id the spawn launched; a record from an older release lacks it, the decoder accepts the legacy `HarnessId` aliases (`true` reads as Cursor, `false` and `"tmux"` as Claude), and any other unknown value reads as missing without losing the other fields), and `at` in epoch seconds; every field has a serde default, so a file with missing or extra fields still decodes). The pure `worker::resolve_ticket` picks the ticket: an explicit `ticket` wins and gets the tracker of the `[tickets]` key it matches as `<KEY>-<digits>` (else none, the key is kept); without one, the id must be exactly `<KEY>-<digits>` for a configured key (case-sensitive), else the worker has no ticket. Close removes the file with the status file (`close_clear_paths`), and spawn clears a leftover one before it writes the new one. `/workers <id>` reads it.
- Worker check: when `[chat] worker_check_secs` is above 0 (default 60), the watcher thread runs `Monitor::check` every that many seconds. For each running worker it reads the `ready`, `blocked`, `waiting`, `unreported` and `sent` markers (a `sent` marker means the last report is old, so the worker is never counted as reported), and the last real report (`done`, `blocked` or `question`) seen in the inbox or logged as a worker entry in the chat log at start (so a restart keeps it). Only `ClaudeTmux` workers get a pane capture, skipped when blocked, waiting, or ready and reported; headless workers have no pane. The pure `worker_check::plan` classifies the observations. Markers, all in `<store>/<dir>/<id>`: `blocked` = a permission request is pending, `waiting` = the worker stopped without a report after one reminder, `unreported` = the reminder failed (the hooks and host turn logic that write and clear them are in [MCP tools](#mcp-tools)). A waiting worker gets one nudge per wait, `worker_check::NUDGE_TEXT` ("You stopped without calling report. Call the report tool now: done, blocked or question.") through `Workers::nudge`: typed into tmux or queued to the headless host. Only a report that lands after the nudge re-arms it. Each state change that needs the person posts one inbox message with status `check`, which raises the usual alert; `check` posts never count as reports. Both headless kinds report waiting without an attach hint. A Cursor permission wait posts no check message: the worker host posts its own alert for every pending request (see Cursor permissions); an opencode permission wait posts a check message with instructions to ask the person and relay the answer with `reply`.
- Daily drift check: the status watcher thread also runs `DailyTick` (`version_drift.rs`). At chat start it reads `last_check` from `drift.json` and `[workers] verify_on_drift` once, then keeps `last_check` in memory. When the check is due (`last_check` missing or 24 h old, so a start after a long pause checks at once) it starts a detached `ralph worker drift-check --inbox <store>/inbox`, so the tick never waits on a probe. Nothing runs while chat is not running. See [Version drift](headless-workers.md#version-drift).
- Heartbeat: a Cursor, opencode or Codex worker's host writes `activity/<id>` (`<epoch secs> running|background|idle|failed`, rewritten only when the second or the state changes; a turn that ends on an error writes `failed` instead of `idle` (`worker::turn_end_activity`: claude `result` with `is_error`, a Codex turn with status `failed`, an opencode failure including a transient one that is about to be resent, a Cursor prompt that errors; an interrupted or normal end writes `idle`); `running` and `background` are busy, `idle` and `failed` are not) on every ACP request, notification, turn start and turn end (opencode: every SSE event of the worker's session, running from prompt or turn start to turn end; Codex: every app-server stdout line, with `gone/<id>` on stdout EOF or a `try_wait` exit, written once), and `gone/<id>` when the `agent acp` child exits or its connection ends without a close or chat exit (reason text; the host's 250 ms poll `try_wait`s each live child, which also reaps it, and writes `agent acp exited (<status>)` once per exit) or when the shared `opencode serve` dies without a chat exit (first line `scope server pid <n>`, then the reason). Spawn, resume and close clear both. A server-scope `gone` stays across the server restart; the monitor deletes it after it posts the Dead message, so the next server death alerts again; with `worker_check_secs = 0` no Dead message posts and the marker stays until spawn, resume or close. On each worker check the monitor feeds the markers to the pure `HeadlessState` reducer and `liveness`: a Running worker (not blocked) with no activity for `[chat] worker_quiet_secs` (default 300; measured: silences outside tool calls reached 132 s and a tool call is silent for its whole run, see [Quiet periods](headless-workers.md#quiet-periods-2026-10-22)) is Quiet and posts one `check` message `quiet <n> s; may be stuck on a prompt`; a `gone` marker makes it Dead and posts one message naming the reason. Each fires once per episode; new activity re-arms Quiet. Idle, blocked and starting workers are never Quiet. Runs on the worker check tick, so `worker_check_secs = 0` turns it off. One server death posts a single message naming the server, the reason and every affected worker (the message's worker field is the sorted comma-joined ids). Claude workers: the check remembers which Claude sessions were alive; one that vanishes while its `ready/<id>` marker remains gets `gone/<id>` (`tmux session ended`) and one Dead message. Close clears `ready/<id>` before killing the session (and restores it if the session survives), so a clean close posts nothing. A death while chat is not running posts nothing; the startup leftover hint (`orphan_hint`) lists it.
- Tmux-only check states: trust = the folder-trust dialog shows; unknown = the worker is ready, no report came, the harness is not busy, and no `unreported` marker is set. Busy means `activity/<id>` says `running` or `background` (written by the Claude hooks, see Reporting), or the pane footer shows a busy marker (`esc to interrupt`, or `← N agent(s)` with N of 1 or more). A busy marker expires when the pane is read and its footer shows no busy marker: `running` after 600 s and `background` after 3600 s (`worker_check::RUNNING_STALE_SECS`, `BACKGROUND_STALE_SECS`, `busy_mark_stale`; the age is `now` minus the mark time). The worker is then unknown and posts the unknown item once. This covers an Esc interrupt in tmux (no hook runs, so `running` stays) and a background task that never ends. A live turn always shows `esc to interrupt` and `PostToolUse` refreshes the mark, so 600 s tolerates a footer misread; a long background gate run is common, so `background` waits an hour. Without a pane read the marker stays authoritative. Pane changes no longer count: a worker that ended its turn while a background task runs has `background` and a static pane, so it stays working. The `unreported` marker means `waiting` is due at the next `idle_prompt`, so the worker counts as working until then (that marker means `waiting` is due at the next `idle_prompt`, so the worker counts as working until then). A check never types into a permission prompt or the trust dialog. Tmux check messages describe waiting, a permission prompt, the trust dialog or an unknown wait and end with `tmux attach -t <session>`. Unknown posts at most once per wait: flips to working (a spinner or status-line redraw) do not post it again; a report, waiting, blocked or trust state re-arms it.
- Inbox alerts: on each poll the watcher compares pending reports with the last poll (reports pending at chat start never alert). For new reports it asks tmux for focus and the pure `inbox_alert::inbox_alert` decides. Inside tmux, `tmux display -p -t $TMUX_PANE '#{pane_active} #{window_active} #{session_id}'` plus `tmux list-clients -t <session> -F '#{client_flags}'` give `Visible` when the pane and its window are active and a client has the `focused` flag, else `Hidden`. Outside tmux, no attached client, or a failed query give `Unknown`, which alerts unless `[chat] inbox_alert_unknown_focus = "silent"`. `Visible` never alerts, and nothing alerts when both `inbox_alert_sound` and `inbox_alert_notification` are off. When the chat sends terminal status (see [Terminal status](#terminal-status)) and the report it sends at that moment is `blocked` `kind=question`, Rex owns the alert and ralph plays no sound and sends no notification; during a turn, a cell or `/hold` the report is `working`, so ralph still alerts (the pure `inbox_alert::inbox_alert` gets the terminal state from `report_for` with the new unread count). An alert plays a sound (`afplay /System/Library/Sounds/Glass.aiff` on macOS, else a terminal bell) and, with `inbox_alert_notification`, a notification `<id> <status>, ...` (`osascript display notification` on macOS, else OSC 9, wrapped for tmux passthrough). Limits: a tmux client that never got a focus-out (background pty, terminal without focus reporting) counts as focused and suppresses the alert; focus follows the terminal app, not window visibility (minimised, other Space, second monitor). Only inbox reports alert.
- Status line: a lualine-style bar painted above the input. `status_segments::segments` builds segments from `Status`, `layout` picks which fit, and `chat_statusbar` paints them. Left: mode block (bright, bold; one of `HOLD`, `NAP`, `INBOX`, `WORK`, `IDLE`, see below), the session name (see [Session name](#session-name)), the queue block (only in the queue editor; forms in [Queued messages](#queued-messages)), the hold block (only during `/hold`: `from <source>`, `from anyone` or `from a, b` for several targets, then `<source>`, `anyone` or `from N` with N the target count; same drop priority as the queue block), `📬 N unread` (soft; absent at 0 unread). Right, soft to bright: `workers`, `watch`, the schedule cell (armed and running scheduled tasks: `sched <id> <HH:MM>` for one, `+<N>d` after a later day, `N scheduled`, `SN`; absent with none; same colors as `watch`), the process cell (`ralph_core::chat_process`), `$cost` (bright, bold). The process cell has four forms, long to short: `T12/30 · ctx 62% · cache 41m! · shift ~9 msg`, `T12/30 · 62% · 41m!`, `12/30 62% 41m!`, `41m!`. `T` is the turn count on the live claude process over `reset_turns`, 0 with no live process. `ctx` is the last turn's `context_tokens` over `reset_tokens` (`–` with no live process or no `context_tokens`). `cache` is an estimate of the minutes left of the prompt cache, counted from the later of `request_at` (the last streamed main-thread reply line of the last turn) and the last keepalive ping, with an assumed one-hour TTL (rounded up; `cold` with no live process, no `request_at` or 0 s left). `!` follows the minutes when the cache creation of the last turn is at least half of its input total, the sum of `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` (`restart_write`). `shift ~N msg` is the entries left until the older view moves to the next 256-entry cut (`entries_to_shift`); only the longest form shows it. On the first turn after a reset the two long forms start with `↻ tokens · `, `↻ turns · ` or `↻ restart · `. `$` is the session total (it leaves out cancelled turns, which write no usage line, and counts pings): the sum, over the claude processes that ran since this `ralph chat` started, of the last `cost_usd` of each process (see [Usage](#usage)). Pings count: a ping line joins the totals of its process, so the last `cost_usd` of each process still wins. The delta is the last turn's cost minus the last earlier row of the same process that has a cost, so it leaves out earlier pings. Nap cost is not included. It shows as `$4.12 (+0.31)`, then `$4.12`; the delta is the last turn's cost. It is absent when no turn has a cost. The cell is recomputed every 500 ms and the status repaints once per minute; usage and shift refresh every 5 s and after each turn or inbox read. The usage refresh does not reread `usage.jsonl`: the monitor holds a `UsageTail` (file id, byte offset, own-run rows) that starts at the file end when chat starts, reads only the bytes appended since, and keeps only whole lines (a torn last line waits for the next read). A changed file id or a shorter file resets the tail and rereads from 0. Limit: ralph sees an idle process death only at the next turn, so until then the cell still counts the process as live. The filler runs the full width in the base background. When the bar is too wide, `layout` compacts the least important segment first, and drops segments only after every form is compact. Drop order, first to last: schedule, watches, workers, cost, process (it shrinks to the cache-only form first), mail, queue, name; the mode block stays. Colors come only from the `[theme.status]` table (`mode_*` (including `mode_hold_fg` and `mode_hold_bg`), `store_fg` (the name text), `workers_fg`, `watches_fg` and `base_bg`, resolved by `status_theme.rs`; keys and defaults in [configuration](../configuration.md#status-line-colors-themestatus)). Segments are plain colored blocks; `[chat] status_powerline = true` adds powerline glyphs between them. With no color (`NO_COLOR` or no TTY) the bar is plain text with `│` between segments and no padding. Not shown: git branch and elapsed time, because the status data has none of them.
- Status modes: `status_mode::mode` picks the mode block, first match wins: `NAP` (a nap holds the `NAP` lock), `INBOX` (unread above 0), `WORK` (a worker is `running`, `busy` or `permission`, or any watch exists), else `IDLE`. Each mode has its own `mode_<name>_fg` / `mode_<name>_bg` keys. The queue, mail, process and cost blocks take the active mode's colors, so the coloured ends of the bar match the mode block; blocks of the same color run together with no separator in block mode. There is no turn mode; during a turn the bar renders only in the queue editor, where the queue block shows the turn state. `Store::napping` try-locks the store `NAP` file in shared mode and releases it at once, so the probe never blocks. Only the one chat on the store (see [Single instance](#single-instance)) starts naps, so `NAP` always means this chat's nap.
- Footer: `footer` in `chat_status.rs` builds a hint line, painted under the input with one empty line after it, so the prompt is never the last terminal line. Stock reedline 0.52.1 erases everything below the cursor on repaint, so `vendor/reedline` carries upstream nushell/reedline plus the footer commit (`Prompt::render_prompt_footer`) and `Reedline::with_wrap_width`. The painter soft-wraps the prompt area at the capped width, or at the terminal width without a cap: draft rows break between words (UAX #14, as in replies; a word longer than a row breaks inside it) and each wrapped row starts with the `::: ` continuation prefix. The breaks and prefixes are display-only; the submitted text is what was typed. Mouse-click mapping still assumes character wrap; chat does not enable it through `[patch.crates-io]`. Bracketed paste is on, so a multi-line paste stays in the draft.

### Keepalive

Claude's prompt cache lives one hour. While chat waits at the prompt or in `/hold` with a live claude process, the keepalive thread (`chat/keepalive.rs`) wakes every 30 s and asks the pure `keepalive_action`. It returns `Ping` when no turn runs, the session is alive, the last reply or ping is at least 55 min old (`KEEPALIVE_PING_SECS`), and the last real turn ended less than `[chat] keepalive_hours` ago (default 4; `0` turns it off). A ping sends the user message `PING. Reply with only PONG.` through `Session::ping`, which shares `Session::drive` with `Session::turn` but runs the pump in `Display::Silent`: no spinner, no stdout or stderr, no gate; the pump still parses the stream, so the result carries the reply and costs. A ping writes nothing to the memory log or `process_turns`, but it does enter the claude conversation and costs a cache read. A ping that exits and carries usage appends a `kind` `ping` line to `usage.jsonl` (see [Usage](#usage)), written while the session lock is still held. A ping that times out writes no row, so its cost is not in `$`. The thread holds the session lock for one ping, at most 60 s (`PING_TIMEOUT`); a real turn that starts meanwhile prints its rule, shows the `Waiting for response...` spinner while it waits, and then runs. A ping ignores Ctrl-C and SIGINT (only `PING_TIMEOUT` ends it); a Ctrl-C pressed during that wait cancels the turn once the lock frees, before anything is sent. A ping that times out or breaks the pipe kills the process group and marks the session dead, so the next turn respawns it from the store with a `restart` reset (`ping_follow_up` returns `Kill`). A ping that exits non-zero leaves the session alive and the cache clock alone (`Keep`); the next ping waits `KEEPALIVE_RETRY_SECS` (5 min) after it. After `KEEPALIVE_MAX_KEEPS` (3) `Keep` results in a row, pings stop until the next real turn; a `Warm` result also resets the count. After every ping the thread checks that the process is still alive; a dead process gives `Kill` (`ping_follow_up` takes the `alive` flag), so `live` goes false and no cache clock is stamped. On a lost terminal, `watch_input` waits up to `PING_TIMEOUT` for the session lock (a ping may hold it), then drops the session and exits, also when the wait ends. The clocks are wall time (UTC), so a sleeping laptop counts as idle time. Limit: after the hours run out, or after a reset drops the session, no ping is sent until the next real turn; a new real turn starts the hour count again.

### External reports

`ralph inbox post --store <DIR> --from <SOURCE> <FILE|->` (see the [CLI reference](../cli-reference.md#ralph-inbox)) writes one inbox file for an outside program. The shell is `crates/ralph/src/inbox_post.rs`: it joins `--store` to the current directory, checks the store with the pure `inbox_post::check_store` (an existing directory with `log.jsonl` or `LOCK`, else it refuses and writes nothing), reads at most 65537 bytes of the file or stdin, builds the record with `inbox_post::external_report` (it refuses non-UTF-8, oversized, empty and control-character text, after it turns `\r\n` into `\n`), and writes it with `Inbox::post` using sequence 0 and the current UTC time as `at`. The file name keeps the nanosecond digits of the RFC 3339 time, so a collision needs two posts from the same source in the same nanosecond; the second rename then overwrites the first report, and ralph accepts that.

A chat that is open picks the file up on the next 500 ms poll like any report: it counts as unread, shows under `/inbox` labelled as worker `external:<source>` (the person's view uses the record's worker field), and raises the usual alert. It never starts a turn by itself. `/hold external:<source>` matches it, so a hold on that source wakes the chat. A chat that is closed finds the file at its next start and counts it as unread. The model sees the `[external <source> · report]` header and the text as untrusted data (see [Worker inbox](#worker-inbox)).

### /inbox commands

N is a position in the unread queue: oldest first, from 1, positive integer. Positions shift up after a send or a drop. An unknown N prints `No report N. /inbox list shows the queue.` and changes nothing.

| Command | Effect | Starts a turn |
| --- | --- | --- |
| `/inbox`, or Enter on an empty prompt with reports unread | Sends every queued report to main and deletes it from the queue: one `worker` log entry per report, then one turn with all reports in one message. With nothing unread, `/inbox` prints `No unread reports.` and Enter does nothing. `[chat] empty_submit = "inbox-first"` sends `empty_prompt` instead of doing nothing; `"phrase"` always sends it, so only `/inbox` opens the inbox | yes |
| `/inbox next` | Same as `/inbox` for the oldest report only (position 1). With nothing unread, prints `No unread reports.` | yes |
| `/inbox N` | Same as `/inbox` for the report at position N only. Unknown N prints the not-found message | yes, when the report exists |
| `/inbox list` | Prints one row per queued report, `#<position>  <worker>  <status>  <age>`, columns padded, oldest first (`No reports.` when empty); age is `<n>s` under a minute, `<n>m` under an hour, `<n>h` under a day, else `<n>d`, `0s` for a future time and `?` for an unparsable one (pure `inbox::list`) | no |
| `/inbox peek N` | Prints report N in full with the same header box and markdown as `/inbox`; removes nothing | no |
| `/inbox drop N` | Removes report N from the queue and prints `Dropped report N.`. Before the queue changes, appends one JSON line `{timestamp, worker, status, text}` to `<store>/inbox-drops.jsonl` (append-only, never rewritten); an unknown N logs nothing. The unread count refreshes after a drop | no |
| any other `/inbox` argument | Prints the usage string (below) | no |

Usage string: `Usage: /inbox [next | N | list | peek N | drop N]`. `/inboxfoo` is a normal message. Local commands never start a turn or call the model. Each report that `/inbox`, `next`, `N` or `peek` prints goes under a header box from the pure `frame::worker_header` (`● worker <id> · <status>`, border and status colors from the agent palette: blue border, green for done, red for blocked or failed, yellow for waiting or check by default; sized by display width and cut to the terminal width), then its text as markdown through the chat renderer with the agent `MarkdownTheme` from `[theme.agent]` (see [configuration](../configuration.md); code blocks default to the assistant theme); plain text (header `[worker <id> · <status>]`) when stdout is not a TTY or `NO_COLOR` is set. The model still gets the plain `[worker <id> · <status>]` message.

### /hold

`/hold [<target> ...]` waits for an inbox report and runs it as a normal inbox turn. ralph answers it itself; it starts no model turn. It is not a read-only command, so during a turn it is queued like `/inbox`.

- The filter is the exact sender of a report (`report.worker`, not the inbox file name): a worker id, `watch:<name>` for a watch report, or `schedule:<id>` for a scheduled task report. `schedule:<id>` also matches the reports of the scheduled worker `sched-<id>`; `/workers schedule:<id>` shows that worker. A bare `/hold` matches any report and the bar reads `from anyone`. A watch needs its `watch:` prefix: `/hold ci` waits for a worker named `ci` and does not match `watch:ci`; there is no automatic mapping. Typed with two or more arguments, the line is a hold only when every argument is a listed target, repeats included (`/hold hi hi` is a message when `hi` is not listed) (`chat_hold::hold_targets`); otherwise it is a normal message, so `/hold on, check the CI first` and `/holdfoo` stay messages. The hold then matches a report from any argument; the bar reads `from a, b` and shrinks to `from N`. Repeated arguments collapse (`/hold a a` is `/hold a`). A single unknown id arms the hold anyway; the bar shows the id. A model suggestion `/hold`, `/hold <target>` or `/hold <t1> <t2>` with listed targets runs it without a keypress (see Suggested reply and `chat.auto_hold`).
- One shot. While held there is no prompt. The first matching unread report starts a turn that sends only that report (the same as `/inbox N` for its position); then the hold is off. Nothing re-arms it. Reports that do not match stay unread in the queue.
- Tab after `/hold ` (with or without a partial word, for each argument in turn) opens a reedline columnar menu (`completion_menu`) of this chat's worker ids, `watch:<name>` for active watches and `schedule:<id>` for armed and running schedules, sorted, deduped (a running schedule is also a `schedule:<id>` watch) and filtered by the word before the cursor, without the targets already typed on the line. Tab moves on, Shift-Tab moves back, Enter takes the pick. The candidates come from the monitor's in-memory `Status` (refreshed every 500 ms), so a keypress reads no file and runs no tmux; a worker that started less than 500 ms ago can be missing. Only the main editor completes; the queue editor does not. Pure logic: `ralph_core::chat_hold::hold_completions`; the reedline `Completer` is `HoldCompleter` in `crates/ralph/src/chat/editor.rs`.
- A matching report that is already unread when `/hold` runs starts its turn at once.
- The keepalive thread keeps pinging while the hold waits: the chat loop sets a separate `idle` flag for the prompt and for the hold, and the keepalive reads that flag instead of `at_prompt`. The flag goes false before the inbox turn starts.
- Exit keys: Ctrl-Q or Ctrl-D leave the hold and return to the prompt. Ctrl-C also leaves it (the SIGINT sets the interrupt flag, which hold clears) and does not quit the chat. A hangup (stdin closed, SIGTERM, SIGHUP) quits the chat. Hold puts the terminal in the partial mode used by the queue editor (no echo, no line buffering, Ctrl-Q arrives as a key) when stdin is a terminal.
- The status bar shows the `HOLD` mode, above `NAP` in the mode order, and the filter. It is redrawn in place (carriage return, clear line, bar, no newline) each time the status changes (for example a new unread report); one newline is printed when the hold ends, on every exit path. Hold clears a stale interrupt flag on entry. If the inbox ledger cannot be read, hold prints one warning and leaves. A nap or the store lock does not stop the hold; the turn that follows waits as any inbox turn does.
- Progress lines: with `[chat] hold_progress` on (the default), one dim line per held running worker sits above the bar and is redrawn in place, at most 3, then `+N more`; they are cleared when the hold ends. A line reads `<id> · held <elapsed> · <busy|idle|failed> · rebase <n>/<m> · <k> commits · <last pane line>`, for example `GUZ-1162 · held 14m · busy · rebase 9/15 · 3 commits · cargo test`. `held <elapsed>` counts from the hold start (`45s`, `14m`, `1h05m`). At a narrow width segments drop right to left (hint, commits, rebase, activity, elapsed); the id stays, and the hint is cut to the room left with `…`. A background thread gathers the facts at hold start and then every 30 seconds, loads the config once when it starts, and sends each result over a channel; the hold loop only takes the newest result that already arrived, so it never waits. Every git and tmux command runs with a 3 second limit (`chat/bounded.rs` kills it; the pure verdict is `bounded_command::poll_verdict`, which also kills the command when the exit check itself errors, so no orphan stays), and a command that times out drops its segment like any failed source. The thread stops when the hold ends. The gathered facts are: the activity marker, the rebase step from `<git-path rebase-merge>/msgnum` and `end` in the worker worktree, commits since the base (`chat.worker_base` or the default branch) and, for tmux workers only, the last non-blank pane line. A source that fails drops its segment. The hint is display only; no decision reads it. With `NO_COLOR` set or no terminal, the line is plain text. Limits: the worker listing (`running_workers`, one tmux call) has no time limit, so a hung tmux stops new facts but not the hold; the lines can wrap if the terminal shrinks after a draw. Pure logic in `ralph_core::chat_hold_progress` (`line`, `lines`, `rebase_progress`, `last_hint`, `held_ids`, `redraw`); the shell is `crates/ralph/src/chat/hold_progress.rs`.
- Pure logic in `ralph_core::chat_hold` (`HoldFilter`, `first_match`, `hold_key`, `redraw`, `hold_completions`); the polling loop is `crates/ralph/src/chat/hold.rs` and the dispatch is in the chat main loop.

### /nudge

`/nudge <id> [text]` sends worker `<id>` a request for one line of progress. ralph answers it itself; it starts no model turn, so `usage.jsonl` gets no main row. It is not a read-only command, so during a turn it is queued like `/hold`; a bare `/nudge` is queued too, because it can send.

- The default text is `PROGRESS_REQUEST`: "Nudge: reply with one line of progress (current step, blocker), then keep going on the same plan." Text after the id replaces it, inner spaces kept. `/nudgefoo` is a normal message.
- A bare `/nudge` reads this chat's worker ids, the same list as the status bar and Tab: with one worker it sends that worker `PROGRESS_REQUEST`; with none it prints `/nudge: no workers running`; with two or more it prints `Usage: /nudge <id> [text]; running: <ids>`, ids sorted. With a first word, that word is always the id; there is no auto-select (`/nudge hi there` sends `there` to worker `hi`).
- The send is the `reply` tool path, `Workers::reply(id, text, false, None)`: the same delivery, `sent/<id>` go-ahead mark and pickup wait as a model `reply`, so ralph prints the same line, for example `Sent to worker GUZ-1; busy.` or `Sent to worker GUZ-1; no reaction after 5s.` The wait is at most the reply confirm timeout (5 s).
- Refusal: when `blocked/<id>` exists, for a named or an auto-selected worker (the worker waits on a permission request; the claude `PermissionRequest` hook and the headless harnesses write it), ralph sends nothing and prints `/nudge: worker <id> waits on a permission request; answer it by request id.` Text typed into a claude-tmux pane could answer the prompt; permission answers stay on request ids.
- An unknown or closed id, or a failed send, prints `/nudge: <error>`.
- Records: `/nudge` writes no record of its own and never writes the auto-continue record (`auto-continued/<id>`, `auto-continue.jsonl`). Its `sent/<id>` mark is a go-ahead like any reply, so it resets a stall record and the next failed turn gets its one auto-continue again (see [Auto-continue](#auto-continue)).
- Tab after `/nudge ` completes this chat's worker ids only (no watches or schedules), for the id word only; the menu, filtering and source are the same as `/hold`. Pure logic: `ralph_core::chat_nudge` (`parse_nudge_args`, `resolve_nudge`, `nudge_completions`, `blocked_refusal`, `failure_line`); the shell is `crates/ralph/src/chat/nudge.rs`, dispatched from `run_local`.

### @<id> <text>

A typed line that starts with `@<id>` followed by whitespace or the end of the line sends `<text>` to worker `<id>` as written. It starts no model turn, so it costs $0 and `usage.jsonl` gets no main row. It is not a read-only command, so during a turn it is queued like `/nudge`.

- Only a leading `@` counts. The id is the characters up to the first whitespace; the text is everything after it, newlines kept (a multiline paste works), trimmed at both edges. `@` in the middle of a line, an email address, a bare `@` and `@ text` are normal messages.
- `@@text` is a normal message with exactly one leading `@` removed: `@@GUZ-1 hi` sends `@GUZ-1 hi` to the model.
- The send is `Workers::reply(id, text, false, None)`, the path `/nudge` uses, so ralph prints the same line, for example `Sent to worker GUZ-1; busy.` There is no interrupt form and no permission answer. A worker of a scheduled task is refused with the same line the `reply` tool gives.
- Refusals print `@<id>: <reason>` and record nothing: empty text; a merged thread's digest id (`thread:<name>`); an id that is not one of this chat's workers (the line lists the running ids and names `@@`); a worker with `blocked/<id>` (it waits on a permission request; answer by request id). A failed send prints `@<id>: <error>`.
- Memory: a sent line appends one `user` entry, `@<id> <text>`, a newline, then `Result: <reply line>`. It sets no pending-turn marker and writes no usage row or ledger entry. The model finds it with `search` and `read` like any user entry; it is never a `worker` entry, so the worker-check ignores it.
- During a `/send-it` run the line is queued, and the run loop takes the queued line as a takeover, as for any typed line (see [/send-it](#send-it)).
- Tab after a leading `@` completes this chat's worker ids. Pure logic: `ralph_core::chat_direct` (`parse_direct`, `resolve_direct`, `direct_completions`, `memory_line`, `failure_line`); the shell is `crates/ralph/src/chat/direct.rs`, dispatched from `run_local`. `/help` does not list it yet.

### /send-it

`/send-it <instructions>` runs an approved plan unattended: ralph restates free-form instructions as numbered steps, each with an exit criterion, plus the actions the run may take, explicit grants and caps; the person approves once and the run needs no input. `/send-itx` is a normal message. For a task-first how-to, see the [send-it guide](send-it.md).

- `/send-it <instructions>` sends one user turn that asks the model to call the chat-mcp tool `propose_run` once and not start the work. The tool parses the plan (a step with no criterion is refused) and stores it as `<store>/send-it/run.toml`, with no approval. After the turn, ralph prints the plan and `Plan <hash>: not approved. ...`, or `No new run plan was stored. ...` when the turn stored none. One active run: while an approved plan exists, both `/send-it <instructions>` and the tool refuse with `Plan <hash> is approved and active. Stop it with /send-it off first.`; an unapproved plan is replaced. Bare `/send-it` prints the usage and default caps.
- `/send-it status` prints the stored plan, its hash and its approval. `/send-it edit` opens `run.toml` in the chat editor (`[chat] editor`, `$VISUAL`, `$EDITOR`), then rewrites it without the approval and prints it again; a file that no longer parses prints its error and `Fix it with /send-it edit.` `/send-it off` deletes the file. None of these starts a turn.
- `/send-it go` approves only the plan whose hash the last `/send-it` output showed (proposal, status or edit), and only when typed at the prompt; a line queued during a turn is refused. It writes `approved = "<hash>"` into `run.toml`, prints `Plan <hash> approved. Running it.` and starts the run (see Run below). A started run uses up the shown hash, so running the plan again needs `/send-it status` first. The hash is 12 hex characters of sha256 over the canonical plan, so layout does not change it and any content change does; an approval counts only while it equals the current hash, so an edit made outside ralph also clears it.
- Templates (opt-in, never the default path): `/send-it save <name> [<ticket>]` writes the stored plan, approved or not, to `<store>/send-it/templates/<name>.toml` in the `run.toml` format without `approved`. `<name>` and `<ticket>` take letters, digits and dashes (`worker::is_ticket_key`). Each whole-token `<ticket>` (not inside `GUZ-123` or `GUZ-12-old`) becomes `{ticket}`; with no ticket, or a ticket not in the plan, the plan is saved as is and the notice says so. Saving over a name prints `Template <name> replaced.` `/send-it templates` lists the `.toml` names in order. `/send-it <ticket> <name>`, exactly two words whose second is a saved name, fills `{ticket}`, stores the result as `run.toml` with no approval and prints it like `/send-it status`, so `/send-it go` approves it again; it starts no turn and is refused while an approved run is active. Any other text is free-form instructions. Templates live in the chat's own store, so threads do not share them.
- Run: progress lives only in the chat process; quitting the chat ends the run, and the next `/send-it go` starts at the stopped step kept in `run.toml` (see Stop notices), or at step 1. Quitting mid-run leaves the plan approved, so new plans are refused until `/send-it off` clears it. The first turn sends a brief (`send-it run <hash> is approved. ...`, the plan, the allowed actions) and step 1; each later step sends its `[send-it i/N]` line. Run turns use `Trigger::SendIt`, so their usage rows say `send_it`. Before each step turn ralph prints `Running: step i/N, T of M turns, $X of $Y.`, and after a met step `send-it: step i/N met (<criterion>)`. T counts step and judge turns, and a report turn that settles nothing; the turn that reads the held report and settles its step is not counted, so each watch, check or worker step adds at most one free turn. Every turn adds its cost to $X, so the cost cap still covers report turns. After every turn of the run (step, judge, or the worker turn that reads a held report) the hook in `chat/mod.rs` calls `SendIt::tick`, which reloads `run.toml`, then `dispatch`: a worker step holds on that worker (`/hold <worker>` semantics); a check or watch step starts watch `watch:send-it-<n>` and holds on it, and `Watches::start` hands back the slot where the watch leaves its `WatchOutcome` before it posts the report; a judge step sends `judge_prompt`, and the model answers it with the chat-mcp tool `step_result` (see Driver). A stop prints the notice, sends the inbox alert (`blocked_alert`) and the Blocked terminal frame; a finished run prints `send-it done: ...`. Leaving a run's hold (Ctrl-Q or Ctrl-D) stops it as `you took over`; text typed or queued during a run turn stops it the same way and then runs as usual, except a queued `/send-it off`, which stops it as `Off` and then deletes the plan. While a run continues, ralph shows no suggestion and does not auto-hold. Allowed actions: while a plan is approved, the chat socket passes its `allowed` list to `command_allowed` (`None` when no plan is approved). A run turn checks every tool against it; a worker turn checks `reply` against it, and keeps the person-only refusal for other tools, which does not stop the run. Outside a run a worker turn can always reply. `spawn_worker` needs `spawn` with the same harness, `reply` needs `reply`, `close_worker` needs `close` and is refused with `abandon` or `force`, `watch` needs `watch`, and `schedule` is always refused. `merge`, `push`, `pr`, `linear_write` and `paid_run` open no tool; the prompt alone holds them. A refused tool gets "The approved run does not allow `<tool>`. The run stops; ralph tells the person." (`Refused.stops_run`), and the next tick stops the run as `Refused`, before every turn stop except `Off` and `PlanChanged`.
- Plan: the pure `chat_send_it::parse_run(args, defaults)` turns the tool JSON `{goal, steps: [{do, criterion}], allowed, grants, caps}` into a `RunPlan`. A `criterion` is `worker_done {worker}`, `watch_passes {command}`, `check_passes {command}` or `judge {question}`; an `allowed` action is `spawn {harness}`, `reply`, `close`, `watch`, `merge`, `push`, `pr`, `linear_write` or `paid_run {max_usd}`; a grant is `turn_cap {turns}` or `cost_cap {usd}`. A step with no criterion is refused by number (`Step 2 has no exit criterion. ...`), as are an empty goal or step, no steps, an unknown kind and a cap of 0 or less. Missing caps take the `[chat]` send-it limits and 2 judge rounds.
- Restatement: `render_run` prints `Goal:`, the numbered steps each with an `exit:` line, `Allowed:` (or `none`), `Caps:`, and the grants in their own `You pre-approve:` block (`- nothing` when there are none).
- Driver: the pure `advance(plan, progress, event)` returns the next `Progress` and `Next`. `Start` sends step 1 as `[send-it 1/N] <do> · exit: <criterion>`. `TurnEnded(run)` stops at the turn or cost cap (a grant replaces the cap), else waits on the criterion: `Hold(worker)`, `Watch(command)`, `Check(command)` or `Judge`. `question` and `blocked` reports never reach `advance` (`tick` decides them); a report from the step's worker with status `done`, a watch outcome `Exited(0)`, or a `step_result` with `met: true` moves to the next step or `Done`; another status stops with `Unmet`, any other watch outcome (non-zero exit, signal, stop, timeout, wait failure) with `CheckFailed`; a judge turn with `met: false` or with no `step_result` call is a failed round: it sends the step again as `<step line>\njudge: not met: <evidence>` (no call gives `the judge turn made no step_result call`) until the judge rounds run out (`JudgeRounds`). An event that does not fit the step's criterion waits. A check or watch step runs as a plain watch with id `watch:send-it-<n>` (`check_spec`), and the driver takes its structured `WatchOutcome`, never the report text. A judge step sends `judge_prompt`, which asks the model, in the same chat turn on the chat model, to call `step_result {met, evidence}` once. `parse_step_result` needs a boolean `met` and one line of `evidence` of at most 300 characters; a bad call returns the error to the model in the same turn. The chat socket takes `step_result` only in a `Trigger::SendIt` turn and keeps the last call in `SendIt`'s slot; each `SendIt::tick` takes the slot, so a result never carries into a later turn.
- Tick: `start_run(file)` starts only an approved plan, as a `Driving` state (plan hash, `Progress`, `Run`, `Awaiting` a turn, a verdict or a report from a source). `tick(driving, ended)` runs after every run turn: it adds the cost and counts the turn (not for an `Awaiting::Report` turn whose events settle the step: met, unmet, failed check or done), then stops first on a missing file or a queued `/send-it off` entry (`Off`), a plan whose hash differs or lost its approval (`PlanChanged`), a tool the plan refused (`Refused`), a turn with no reply, text the person typed or queued during the turn (`TookOver`), a schedule approval asked (`NeedsYou`), or a flagged report (`WorkerFlagged`): any unread one, or a drained one unless the plan allows `reply` and `Ended::answered` holds its worker. The chat socket records the worker of each successful `reply` with `SendIt::answer`; `SendIt::tick` takes that list and `/send-it go` clears it. Next it folds the awaited events (drained reports from the source that are not flagged, the watch outcome, the `step_result`) through `advance`; `Done` or a stop wins, else the caps stop before the next send. A met step returns `send-it: step i/N met (<criterion>)`; a judged step adds `: <evidence>`. `running_line` shows the step, turns and cost against the caps.
- Stop notices: `send-it stopped at step N/M: <why>. The plan is kept. Fix the cause, show it with /send-it status, then type /send-it go to resume from step N. /send-it off deletes it.` for the turn cap, the cost cap, a missed criterion, a failed check, a flagged worker, the last judge round (`... after the last judge round: <evidence>`), a changed plan, a turn without a reply, a schedule approval, a refused tool ("the plan does not allow `<tool>`", for example `spawn_worker codex`), or the person taking over. When the run's own approval was not in `run.toml` (for example a changed plan), nothing is kept and the notice is `send-it stopped: <why>. To run it again, show the plan with /send-it status, then type /send-it go.` A finished run prints `send-it done: N/N steps in T turns, $X.` and that restart hint. After a stop or a finished run the plan stays in `run.toml` without its approval (`stop_file`, only when the approval is the run's own hash), so `/send-it save` and new plans work; a failed write prints its error after the notice. A stop also writes `[stopped] step = N, hash = <plan hash>` outside the plan hash; a finished run, a new proposal and a filled template clear it. `/send-it status` then says `stopped at step N/M`, and `/send-it go` (same hash rule) resumes at step N with fresh caps; a different hash or a step out of range starts at step 1. On resume (`start_run` with `Seen`, built by `worker_states` from the logged `[worker ID · status]` headers (`logged_states`), the monitor's seen map, unread inbox reports and `running_workers`) the pure `probe` tests step N first: `worker_done` with last status `done` is met and the next step is sent; a known or running worker holds on it without a resend; an unknown worker gets the step. A check or watch step starts its watch with `Progress.probing`, and a non-zero exit sends the step instead of `CheckFailed`; a judge step sends `judge_prompt`, and a not-met verdict sends the step without a judge round. A met probe prints the met line. A fresh start never probes. Only `/send-it off` deletes `run.toml`. `Off` prints `send-it off: the run stopped and its plan is deleted.` `blocked_alert` and `blocked_report` build the inbox alert and the Blocked terminal status frame for a stop.
- Config (`[chat]`): `send_it_max_turns` (15) and `send_it_max_usd` (5.0) are the default caps. Out-of-range values are reset to the default with a warning; see [configuration](../configuration.md).
- Code: pure logic in `ralph_core::chat_send_it` (`parse_send_it_args`, `template::{template_name, template_text, fill_template, match_template, save_notice, render_templates}`, `read_run`/`write_run`, `plan_hash`, `approve`, `release`, `propose_refusal`, `propose_prompt`, `propose_run_tool`, `step_result_tool`, `parse_step_result`); `/send-it` routes to `Route::SendIt(SendItCommand)`; the shell `chat/send_it.rs` owns `run.toml` and `templates/`, serves `propose_run` and `step_result` through the chat socket, and ticks and dispatches the run (`Active`, `Driven`).

## Session name

The session name is a label for the chat. It shows in the status bar, and in the terminal title (see [Terminal title](#terminal-title)). The pure `chat_name::resolve_name` takes the first source that is not empty after sanitising:

1. `--name <NAME>`
2. `[chat] name` in the ralph config
3. The folder name of the git root, found by walking up from the cwd to the first directory that holds `.git` (a directory or a file, so worktrees count). The walk stops before the home directory, so a `.git` in `~` itself or above it does not count when the cwd is under home; outside home the walk goes to the filesystem root. ralph does not run git.
4. The folder name of the cwd. ralph uses the resolved directory path (`std::env::current_dir`), so a symlinked directory names the chat after its target
5. `ralph`

`chat_name::sanitise_name` trims the text, removes control characters and Unicode format characters (general category Cf), keeps at most 32 characters (counted as characters, not bytes), and trims again. A source that is empty after that falls through to the next one. `crates/ralph_server/src/chat/name.rs` finds the git root and builds the sources.

The name is a label only. Two chats that share a store still share the memory, the inbox and the workers; use `--store` to separate them. The name does not change the store path or any worker name.

Status bar: the name segment sits right after the mode block on the left, with the colors the store path used (`store_fg` on `base_bg`). It has one form and no short variant. It has priority 1, so it drops last, just before the mode block, which never drops (full drop order in the Status line bullet under [Worker inbox](#worker-inbox)). The store path is no longer in the bar: `/help` and the `help` topic `config` print `Store: <dir>` instead.

## Terminal status

The chat reports its state to the terminal with OSC 7501 (Program Status Protocol rev 0.4), so Rex can show it. Each report is `ESC ] 7501 ; state=<state>[:kind=question]:app=ralph[:msg=<base64>] BEL`. `msg` is the standard base64 of UTF-8 text with control characters removed and at most 2048 bytes (cut at a character boundary). The pure builder is `program_status::encode`; a sequence over 4096 bytes is dropped.

The pure `program_status::report_for(phase, status)` picks the report. The first rule that matches wins.

| Rule | Report |
| --- | --- |
| `/hold` is active | `working`, msg `holding <filter>` (`anyone` for a bare `/hold`, `a, b` for several targets) |
| A chat turn is running | `working` |
| A cell (`!` or `!!` shorthand or `!<runtime>` fence) is running | `working` |
| Unread worker reports at the prompt | `blocked`, `kind=question`, msg `1 worker report` or `N worker reports` |
| The last turn replied and nothing was submitted since | `done` |
| Anything else, including nap and background workers with no turn | `idle` |

"Working" means only that a chat turn or a cell is running. A worker report that arrives mid-turn or mid-cell does not change it. The phase (`Turn`, `Cell`, `Replied`, `Prompt`) lives on the monitor: the chat loop sets it when a line is submitted, to `Cell` before the message's cells run (a message with no cells passes through at once), to `Turn` around each turn, and `/hold` publishes its filter there. A cancelled (Ctrl-C) or unstartable cell sends no message, so the phase goes to `Prompt` and the report to `idle`; a cell that exits non-zero still sends the message, so `working` stays on into the turn. A cell shorter than one watcher tick may never show `working`.

Reports are sent from one place, the status watcher tick (every 500 ms, so a state change shows within about half a second plus the tick work). The shell in `chat/term_status.rs` writes one `write_all` plus flush to stdout and only when the bytes differ from the last report. Write errors are ignored. Inside tmux (`TMUX_PANE` set) the sequence is wrapped in a DCS passthrough, which needs `allow-passthrough on`.

On exit the chat sends `state=clear` with no id: on quit, Ctrl-D, an error or a panic (a drop guard in `chat::run`), and when the terminal is lost (before `process::exit`). After the clear the watcher writes nothing more. A hard kill (SIGKILL) cannot clear the record.

Reports are sent only to Rex: the pure `program_status::status_enabled` is true when `[chat] terminal_status` is on, stdout is a terminal, and `REX_SESSION` is set and not empty (it survives a tmux started inside Rex, where `TERM_PROGRAM` is `tmux`). The chat computes it once at start; the same value tells the inbox alert that Rex owns it. A tmux server started from Rex keeps `REX_SESSION`, so a client attached to it later from another terminal still gets reports and loses ralph's own alert at the prompt. `NO_COLOR` does not affect reports.

## Terminal title

At start the chat sets the terminal window title to `ralph · <name>` (see [Session name](#session-name)). It first pushes the old title with `ESC [ 22 ; 0 t`, then sets the new one with `ESC ] 2 ; ralph · <name> BEL`. On exit it pops the old title with `ESC [ 23 ; 0 t`. The pure builders are `term_title::title_start` and `term_title::title_end`; the name is stripped of control characters again before it goes into the sequence. There is no tmux passthrough wrap.

The restore is part of `TermStatus::clear`, so it runs once: from the drop guard in `chat::run` on quit, Ctrl-D, an error or a panic, and from the watcher thread when the terminal is lost (before `process::exit`).

The title is off when stdout is not a terminal or `[chat] terminal_title = false`. `NO_COLOR` does not affect it. Inside tmux the title reaches the outer terminal only with `set-titles on`. A hard kill (SIGKILL) and a panic in the watcher thread do not restore the old title.

## Watches

A watch is a shell command (`sh -c`) that runs as a child process of `ralph chat`, in its own process group, with stdin closed. Ralph keeps only a bounded tail of its stdout and stderr.

- When the watch exits, ralph posts exactly one `watch` report to the worker inbox. The text holds the exit code (or killed or timed-out note), the output tail, and the follow-up instruction.
- The report goes through the inbox, so it never interrupts the chat channel.
- Stopping a watch posts one "stopped" report. Closing the chat kills every watch and its child processes and posts nothing.
- The runner lives in `crates/ralph_server/src/watches.rs`; the pure report and tail logic lives in `crates/core/src/watch.rs`.
- Persistent watches are saved as one JSON file each in `<store>/watches/` (spec, `started_at`, timeout deadline, wake deadline), written atomically before the command starts.
- On every `ralph chat` start, `Watches::restore` reruns all saved persistent watches, also after Ctrl-D. Normal records are deleted, never restored. An unreadable record warns and is deleted.
- A restart keeps the original `started_at` and deadlines. The timeout becomes the time left. A command that is exactly `sleep <N>` is rewritten to `sleep <left>` (rounded up to whole seconds). Other commands rerun unchanged.
- A watch whose wake deadline passed posts an exit-0 report right away. One whose timeout deadline passed posts a timed-out report right away (the earlier deadline wins). Neither is spawned.
- The saved record is removed when the watch exits, times out, or is stopped. Closing the chat kills the watch but keeps the record. The pure logic lives in `crates/core/src/watch_store.rs`; the file store is `crates/ralph_server/src/watch_store.rs`.
- The agent starts a watch with the `watch` tool (see [MCP tools](#mcp-tools)). The chat socket server queues the request by writing a file to `<store>/watch-requests/` (atomic, one JSON file per request). The file is claimed with a hard link, which fails if the name exists, so a second call for an id whose request still waits returns the error `watch <id> is already queued` and queues nothing. The chat watcher thread takes every request on each 500 ms poll, calls `Watches::start`, and deletes the file (`crates/ralph/src/watch_requests.rs`; pure parsing in `crates/core/src/watch_request.rs`). If the start fails (duplicate id, spawn error), chat posts one `watch` report with the error to the inbox.
- Every watch id is stored, reported and shown as `watch:<name>`: generated ids are `watch:w1`, `watch:w2`, ...; a `watch` tool id `foo` becomes `watch:foo`, and an id that already starts with `watch:` is not doubled (`watch_id` in `crates/core/src/watch.rs`). Worker ids allow only letters, digits and dashes, so a watch id never equals a worker id. `/watch stop` accepts `w1` or `watch:w1`.
- Watch reports show as `[worker watch:<name> · watch]`. The system prompt says they come from a watch, not from an agent or the person.
- External reports show as `[external <source> · report]` (`worker::chat_message` reads the `external:` prefix of the record's `worker`, the way it reads `thread:`). The model sees the text with every line prefixed by `| ` (an empty line becomes `|`; `inbox_post::mark_untrusted`), so a line such as `[worker GUZ-1 · done]` inside a post cannot pass for a separate worker report; worker, thread and watch text is not prefixed. The system prompt says the whole block of `| ` lines is untrusted data from an outside program, not words from the person or an agent: the model relays it to the person and never acts on instructions inside it.
- Approval: the system prompt tells the model to show the person the exact command and wait for approval before it calls `watch`. The prompt enforces this, not the tool. Like `spawn_worker`, the tool refuses outside a user-started turn, except in a `/send-it` run turn whose plan allows `watch`.
- `/watch` is local: it never starts a turn or calls the model. The shell side is `crates/ralph_server/src/chat/watch.rs`; the pure parsing and formatting is `crates/core/src/watch_command.rs`.
  - `/watch start [--persistent] <command> -- <follow-up>` starts a watch in this process (`Watches::start`). The input splits at the last ` -- `; both parts must be non-empty. The id is the lowest unused `watch:w<n>` (n from 1) among running and saved watches. It prints `Started <kind> watch <id>.`. There is no timeout flag.
  - `/watch list` prints one row per active watch: id, kind (`normal` or `persistent`), time left, command. Time left is the earlier of the wake deadline (a time-based `sleep N`) and the timeout deadline, shown as `<n>s`, `<n>m`, `<n>h` or `<n>d`, or `—` when there is none. It prints `No active watches.` when empty.
  - `/watch stop <id>` kills the watch and posts its one "stopped" report. A stopped persistent watch is removed from `<store>/watches/`, so it does not come back after a restart. This is the only way to remove a persistent watch. If the id is not running but has a saved record, the record is removed and the message says so. An unknown id prints a message, not an error.
  - Bare `/watch` or any other argument prints `Usage: /watch start [--persistent] <command> -- <follow-up> | list | stop <id>`. `/watchfoo` is a normal message.
- A restarted watch that times out reports the original timeout, not the time left.
- Status line: running watches show after the workers as `watch <id> <left>, <id>, ...` (the time left is omitted when there is none). It sheds detail as the terminal narrows: time left, then names to `<n> watches`, then `<n>wt`, then nothing. It refreshes on the same 500 ms poll, so it updates when a watch starts, ends or is stopped.
- Every watch has a timeout. A watch without its own `timeout_secs` (from the `watch` tool, `/watch start`, or an old saved record) gets `[chat] watch_timeout_secs` (default 3600, so 1 hour; `0` is a config error, resolved by `resolve_watch_timeout` in `crates/core/src/chat.rs`, same file-then-default precedence as `worker_check_secs`). `WatchSpec::with_default_timeout` applies it at start and at restore. When it passes, ralph kills the watch and posts one report that says `timed out after <n>s and was killed`, where `<n>` is the original limit.

## Scheduled tasks

The model schedules a shell command or a worker with the `schedule` tool (see [MCP tools](#mcp-tools)). A command runs as a watch when it is due; a worker runs a brief in its own worktree. Pure logic: `crates/core/src/schedule.rs`, `schedule_request.rs`, `schedule_command.rs` and `schedule_worker.rs`. Shell: `crates/ralph/src/schedule_store.rs`, `crates/ralph/src/chat/schedule.rs` and `crates/ralph/src/chat/schedule_worker.rs`.

- Tool fields: `id`, exactly one of `command` or `brief`, optional `follow_up`, `at` (a future RFC 3339 time, or local `HH:MM` for its next occurrence in the local time zone, daylight saving included) or `after` (`90s`, `10m`, `2h`, `1h30m`; give exactly one of `at` and `after`), optional `timeout_secs` (a command: else `[chat] watch_timeout_secs`; a worker: else 2 h, at most 8 h, larger is rejected). A worker takes no `follow_up`. An error: a duplicate `id`, an `id` with a space, slash or control character, an RFC 3339 `at` that is not in the future, an `HH:MM` that a daylight saving change skips.
- The tool writes the task as `proposed` to `<store>/schedule/<id>.json`. Nothing runs until you approve it.
- Approval is a y/n question at the prompt. It shows the id, the command, the time and the timeout; a worker shows `Scheduled worker <id>:`, the full brief indented, `Base: origin/main at fire time. Never pushes.`, then the time and timeout. Control characters in the command or brief show as `\x1b`, `\r`, `\n` and so on. `y` or `yes` arms the task; if the file cannot be saved it prints `Could not arm <id>: <error>` and the task stays proposed. `n`, `no` or Ctrl-C cancels it and removes the file. Any other answer asks again. The question comes before held text. After a question (any answer) the `suggest_reply` pre-fill is dropped, since nothing is left to approve; the `schedule` tool result also tells the model not to suggest a reply to approve it.
- Tasks run only while `ralph chat` is on. Each 500 ms tick starts every armed task that is due as a watch named `schedule:<id>` and marks it `running`. The watch is not persistent. Its report reaches the inbox tagged `schedule:<id>`; the task file goes when that watch ends.
- Worker kind. Each tick, `plan_worker_tick` decides from the records, the inbox reports and the live worker ids; no model turn runs. A due worker is started on a short-lived thread (`Workers::spawn` can block 20 s) as worker `sched-<id>` (`:` is not valid in a branch name) with the claude harness forced: the other harnesses have neither the scheduled prompt nor the guard. Branch `worker/sched-<id>`. Before the worktree is made, `git fetch origin` runs and the worktree is cut from `origin/main`, not HEAD. The fetch never prompts: `GIT_TERMINAL_PROMPT=0`, and `GIT_SSH_COMMAND` is `<base> -o BatchMode=yes` (pure `fetch_ssh_command`), where the base is the `GIT_SSH_COMMAND` of the chat process, else the repository `core.sshCommand`, else `ssh`, so the repository key stays. It runs in its own process group and the whole group is killed after 60 s; a timeout is a spawn failure. The stderr read waits at most 2 s after git exits, so the setup lock is held about 62 s at most. Fetch and guard setup run under one process-wide lock. The worker runs with `--permission-mode auto` whatever mode the chat uses: auto never stops to ask, a refused action is denied and the worker goes on, and the classifier still guards risky actions; `--disallowedTools` still applies. The ids `sched-*` are reserved: `spawn_worker` refuses them, `reply` refuses a `sched-<id>` worker while its schedule record exists, and a worker-kind schedule id must be letters, digits and dashes. A late worker gets `Ran late: due HH:MM, started HH:MM.` before its brief.
- Prompt rule. The scheduled worker prompt (`SCHEDULED_WORKER_PROMPT`, chosen by `SpawnArgs.scheduled`, not by brief text) says: act, never ask; never push, merge, open a PR or change Linear; commit only on your own branch; send one report (`done`, or `blocked` with the reason) whose text ends with an `assumptions:` line (`assumptions: none` when the task was clear), then stop and never wait for an answer.
- Cap and lateness. At most 2 worker records run at once. A due worker over the cap stays `armed` and starts on a later tick; it is late when it starts more than one tick (500 ms) after its time. The running record stores a `deadline` (start plus timeout).
- Timeout. At the deadline only the harness stops (`Workers::stop_harness`). The worktree and branch stay. A `schedule:<id>` report says it timed out and whether the harness was stopped or could not be stopped (with the error), and the record is removed.
- Slow start. While the spawn thread runs, the task counts as alive (an in-flight set), so a spawn slower than the 60 s grace is not reported as vanished. The thread checks that the record is still running before it spawns and after it returns. If the record is gone (cancel, timeout), a harness that started is stopped, and a failed spawn posts no report.
- Reports. A scheduled worker report reaches the inbox as the worker (`sched-<id>`) and is not consumed or hidden: the tick reads the inbox without draining it, and keeps a copy of reports the person already drained. `done` closes the worker (`Workers::close` without abandon or force); if close refuses (commits or changes), only the harness stops and the branch stays. `blocked` and `question` remove the record and leave the worker open for you; it leaves the cap. A spawn failure posts a `schedule:<id>` report and removes the record. A running worker whose harness is gone for more than 60 s with no report gets a `schedule:<id>` report and its record is removed.
- Restart. A worker record that was running and whose worker is still alive stays `running` (no second run). If its harness is gone it goes back to `armed`, late, with no deadline, and fires again in the same worktree.
- No-push guard (scheduled worktrees only, `worker/guard.rs` plan, `workers/guard.rs` shell). Five layers: (1) claude runs with `--disallowedTools` `Bash(git push:*)`, `Bash(gh pr:*)`, `Bash(gh api:*)`; (2) the worktree gets `core.hooksPath` set in its own config (`git config --worktree`) to `<git-common-dir>/ralph-schedule-hooks`, one directory per repository; (3) that directory holds a `pre-push` that refuses, plus a forwarder for each executable hook of the repository, so the repository hooks such as `pre-commit` still run; forwarders without a matching real hook are removed, and hooks are written through unique temp files that are removed when the write fails (a sweep also removes temp files older than 60 s, `abandoned_temp_hooks`); (4) every remote of the common config gets `remote.<name>.pushurl` = `ralph-refused://<name>` in the worktree config, and every shared `remote.*.pushurl` value P gets `url.ralph-refused://.insteadOf` = P (a per-worktree pushurl only adds a value, so without the rewrite git would still push to P), so `git push --no-verify` fails; (5) `url.ralph-refused://.pushInsteadOf` has one value per prefix in the worktree config: `/`, `./`, `../`, `file://`, `ssh://`, `git@`, `git://`, `http://` and `https://`. A push to an explicit URL of those forms, with or without `--no-verify`, goes to `ralph-refused://` and fails. If a remote's fetch url starts with a shared push url P, the insteadOf rewrite would break fetching, so the task is not started: a `schedule:<id>` report names the remote and the reason and the record is removed. The plan first runs `git config --worktree --unset-all` on each of the two url keys (the shell accepts exit 5, key absent), then `--add` for each value. This removes stale values from an earlier run, so the steps are idempotent with no duplicates. The only change to the main `.git/config` is `extensions.worktreeConfig = true`.
- Known gaps. A scp-like `host:path` without a user and a bare relative path without `./` are not rewritten, so a push to them is not refused by layer 5. Linear writes through the user's MCP tools are blocked only by the prompt rule, not by a flag. A worker can unset its own worktree config, which removes layers 2 to 5. A `done` report that arrives while the chat is down, followed by a machine reboot (the harness is gone), makes the task run again: the record still says running, so it goes back to `armed`.
- A task missed while the chat was off fires at once, marked late; its follow-up says when it was due. A task that was running when the chat died or closed goes back to `armed` and fires late on restart; once shutdown starts, the tick no longer removes running tasks whose watch was stopped.
- `/schedule` (or `/schedule list`) lists every task: id, state (`cmd` or `worker`, then `proposed`, `armed`, `running`), local time (with the date when it is not today), time left, a `late` marker, the command or the first line of a worker brief (a running worker shows `sched-<id>: ` before it; control characters escaped as in the approval question). `/schedule cancel <id>` (or `schedule:<id>`) removes the file and stops the watch of a running command (cancelling a running worker task stops `sched-<id>` with `Workers::stop_harness`, which keeps its worktree and the branch `worker/sched-<id>`, and removes the record); an unknown id prints a not-found line. `/schedule` never creates a task. `/schedule list` and the usage reply run mid-turn; `cancel` is queued.
- Status cell: armed and running tasks (command and worker). One task shows `sched <id> <HH:MM>` (with `+<N>d` after the time when it is due N local days later, e.g. `09:00+1d`), several show `<N> scheduled`, the narrowest form is `S<N>`.
- Scheduling does not take the memory `LOCK`. A second chat on one `--store` is refused (see [Single instance](#single-instance)).

## /help

`/help` is local: it never starts a turn or calls the model. Only the bare command (after trimming) counts: `/help x`, `/help me fix the build` and `/helpfoo` are normal messages. It prints `Store: <dir>`, a blank line, then the pure `chat_help::help_text(width)` (through `help_with_store`), word-wrapped to the prompt width (the terminal width, capped by `--wrap-width`); a section whose text column would be under 30 columns puts each text under its label:

- Commands: one row per form of `/help`, `/inbox`, `/watch`, `/schedule`, `/diff`, `/workers`, `/hold`, `/nudge`, `/send-it`, `/fork`, `/thread`, `/threads`, `/pull`, `/park`, `/merge`, `/main`, `/config`, `/view`, `/read`, `/zoom`, `/recall` and `/search`, from `Command::ALL`. `route_input` matches the same table, so a command cannot route without a help row.
- Cells: the `!` and `!!` shorthands and `!<runtime>` fences.
- Keys: at the prompt, in vi mode, during a turn, and in the queue editor (`PROMPT_KEYS`, `VI_KEYS`, `TURN_KEYS`, `QUEUE_KEYS`).
- Status bar: one row per segment `Kind`, the five modes (`HOLD`, `NAP`, `INBOX`, `WORK`, `IDLE`; first match wins), each part of the process cell (`T12/30`, `ctx 62%`, `cache 41m`, `!`, `shift ~9 msg`) and the `↻ tokens`, `↻ turns` and `↻ restart` marks.

The chat-mcp tool `help` gives the model the same text: no `topic` returns `help_text` unwrapped, `topic` (`diff` or `/diff`) returns that command's rows from `Command::ALL`, and an unknown topic is a tool error that lists the topics (`chat_help::help_topic`, answered by `chat-mcp` itself). Topic `config` returns `Store: <dir>`, the resolved `config.toml` path, the store file path (`<store>/config.toml`, which overrides the global file per key), the location, environment override and precedence text, and the section names; `config <section>` (`chat` or `[chat]`) returns that section of `docs/configuration.md`, embedded with `include_str!` and split by `chat_help::config_sections`. `handle_request` answers it as `Outcome::ConfigHelp`, and `chat/mcp.rs` fills in `config::config_path()` and the store directory. Topic `images` returns how a reply shows an image (`IMAGES_HELP`). A command topic whose name matches a config section ends with `Settings: help topic "config <name>"`. `SYSTEM_PROMPT` tells the model to call it for questions about settings and for requests to change how ralph behaves or looks, to propose a code change only when no setting covers the request, to edit the global `config.toml` by default and the store file only for a store-specific setting, to copy the edited file to `config.toml.bak` first, and, after editing, to run `ralph config check --store <store>` and copy `config.toml.bak` back over the edited file if it fails (`config::check` reports unknown keys via `serde_ignored`, theme and chat-setting warnings, and the hard chat-startup errors).

Staleness tests: `chat_help` tests fail when a `Command` does not route or has no row, when `status_segments::segments` builds a segment kind with no legend, or when `status_mode::mode` returns a mode with no legend. `every_chat_binding_has_a_help_entry` in `crates/ralph/src/chat/tests.rs` builds the real emacs, vi and queue keymaps, keeps the bindings that differ from reedline's defaults, and fails when one has no key table entry. Keys handled outside reedline (Esc Esc, Ctrl-C, Ctrl-D, Ctrl-Q during a turn) are listed in the tables by hand. Another test fails when `Command::ALL`, `MODES` or `RESETS` misses a variant, and the thread legend is checked against `thread_variants` of a real cell.

## /config

`/config` is local: it never starts a turn or calls the model, and it runs mid-turn. Only the bare command counts: `/config x` and `/configfoo` are normal messages. It prints `config::config_view` of the `ConfigSnapshot` that `run` builds once at start, so it shows what this chat resolved, not a fresh read:

- Warnings from chat start first, in the order they printed: the store fallback (`ignoring store config ...`), the security-key notices, `Failed to load config` when chat fell back to defaults, the theme, `[changes]` and `edit_mode` warnings, the prompt-file warnings (`Skipping prompt file ...`), and the editor, `worker_quiet_secs`, reset-limit and `empty_prompt` warnings. Skill warnings are not repeated; a skill dir that does not exist shows as `(missing)` in Sources.
- `config files changed on disk since start; restart the chat to apply` when loading both files now gives a different merged config than at start (`effective_now`). It compares only `config.toml` values, not the contents of prompt or skill files.
- Sources, as absolute paths: config dir, global `config.toml` (after `RALPH_CONFIG_DIR`, made absolute against the cwd), store `config.toml` (the path chat loaded, derived from the store as written, not symlink-resolved) and the store (canonical, so `/tmp` shows as `/private/tmp` on macOS), `usage.jsonl`, the claude config dir (`[claude] config_dir` or `~/.claude`), `prompt_file`, each `append_prompt_files` entry and each resolved skill dir (`--skill`, `RALPH_CHAT_SKILLS` or `[chat] skills`, before the `SKILL.md` check), resolved as the chat resolved them. Each `/config` checks these files again: a config file, `usage.jsonl`, prompt file or skill dir that does not exist now ends in `(missing)`.
- Environment: each set, non-empty variable from a fixed list: the `RALPH_*` variables of `config show` plus `RALPH_CONFIG_DIR`, `RALPH_CHAT_STORE`, `NO_COLOR`, `VISUAL` and `EDITOR`, with the key it overrides. None of them holds a secret, so values print as they are.
- Flags: the `ralph chat` flags given at start (`--store`, `--recent-history-tokens`, `--wrap-width`, `--skill`, `--permission-mode`, `--worktree-dir`, `--no-inbox-sound`, `--no-inbox-notification`, `--skip-summary`), with the key each overrides.
- Merged config: the `config show` rows (`leaf_sources` over the start layers; after a store fallback no row is tagged `store`; after a failed load the chat runs on defaults and no row is tagged `global` or `store`). A store value that hides a global one lists both (`chat.wrap_width = 100  [store; global = 80]`). A key that a flag or variable overrides shows that value, tagged `flag NAME` or `env NAME`, then every layer it hides with its file value (`chat.wrap_width = 90  [flag --wrap-width; store = 100, global = 80]`). A flag beats a variable. `RALPH_THEME` also overrides `theme.assistant.code`. An overridden key with no file value gets its own row.

The chat sets the store config layer to the canonical store path, so its store warnings name that path too.

## /view

`/view <file.md>` is local: it never starts a turn or calls the model, writes no `usage.jsonl` row, and waits in the queue while a turn runs (`runs_mid_turn` is false). The rest of the line is the path (spaces allowed), absolute, `~/` or relative to the working directory. Bare `/view` prints `Usage: /view <file.md>`; `/viewer` is a normal message.

- Tab after `/view ` completes the path in the same menu as `/hold`: the typed text up to the last `/` is the directory (`~/` expands; empty is the working directory), the rest is a prefix. The menu lists matching subdirectories (with a trailing `/`) and `.md`/`.markdown` files, sorted; dot entries show only for a `.` prefix. Pure logic: `ralph_core::chat_view::{view_path_query, view_path_completion}`; the shell reads the directory in `view_completions` in `crates/ralph/src/chat/editor.rs`.
- Refusals (`ralph_core::chat_view::view_refusal`), checked in this order: `/view: no such file: <path>`, `/view: <path> is a directory`, `/view shows .md and .markdown files: <path>` (extension case-insensitive), `/view: <path> is N bytes; the limit is 2097152`. A file that is not UTF-8 prints `/view cannot read <path>: <error>`.
- Rendering: `chat/view.rs` reads the file and prints it through `render_markdown_with` with the inbox display (agent `MarkdownTheme` and highlighter), so it looks like a worker report without the header. Code and diff fences go through `render_text_block` with the same `RenderContext`, so they highlight exactly as in replies.
- Images: `rebase_images` rewrites each relative `![alt](path)` to the file's directory (absolute, `~/` and URL targets stay as written; markers in code spans and fenced blocks are untouched), then the normal image path draws it; see [Rendering images](#rendering-images).
- Mermaid pictures: where the terminal shows images, each mermaid block draws as a PNG with no fence. One `ralph __mermaid --picture` child per block reads a JSON `PictureRequest` (source, resolved `[mermaid.style]`, room) on stdin, lays it out with bezel-mermaid (`max_width` = columns × cell width × font size / cell height), rasterizes the SVG with resvg and writes the PNG to stdout; the parent kills it after `picture_timeout_ms` or above `max_rss_mb`. The picture never grows past text at cell height and shrinks to fit the columns and rows (`ralph_core::mermaid_fit::picture_fit`). The cell size comes from the image probe, else 8×16.
- Fallback: a render error, a kill, or text below `min_text_ratio` of the cell height draws the block as a text diagram through the `[mermaid]` child, as in replies; so does a terminal with no images. Model replies always use text diagrams.
- Style: `[mermaid.style]` in [configuration](../configuration.md#mermaidstyle---diagram-pictures); the default `ui` palette maps `[theme.ui]` to RGB (`terminal_rgb`: a fixed soft table for the 16 ANSI names, the xterm cube and grey ramp for 16–255) on a fixed dark ground. Accent is `spinner`, critical is `ask_error`; node fills (`surface` 14%, `surface_alt` 24%) and borders (55%) are the accent mixed into the ground; the 8 series colors are the distinct UI colors plus blue, then each mixed halfway to the text color. The picture cannot follow the terminal's own ANSI palette, as no OSC query is made.

## /diff

`/diff` is local: it never starts a turn or calls the model. `/difffoo` is a normal message.

| Input | Shows |
| --- | --- |
| `/diff` | the last finished chat turn (same as `/diff last 1`) |
| `/diff last N` | net changes over the last N finished chat turns (N >= 1) |
| `/diff ago N` | the single chat turn N back (N >= 1) |
| `/diff worker <id>` | that worker's changes since it spawned |
| `/diff worker <id> last N` or `ago N` | that worker's last N turns, or the turn N back |
| `/diff now` | the working tree against the index, as plain `git diff` |

The ranges use the same snapshots and rules as the `changes` tool (`last` and `ago`, rebase-aware). If snapshots are off, there is none yet, or N is larger than the finished turns, `/diff` prints one plain line and runs nothing. After an upstream change it may print the upstream note first. An empty snapshot range prints `no changes` (same wording as the `changes` tool) and runs no pager. There are no absolute turn numbers.

The words after the range keywords are git diff args: `/diff -U1 -- a` is the last chat turn with `-U1 -- a`, and `/diff worker w1 last 2 --stat` is a worker range with `--stat`. `/diff now [git diff args]` is the working-tree diff: `git diff` in the chat's working directory. Words are split on whitespace, with quotes and backslash escapes (a trailing backslash is kept; no `$` expansion or globs), and are passed after `[changes] diff_args`. In a range, the two snapshot revs come right after `diff`, before `diff_args`. An unclosed quote prints `/diff: unclosed quote` and runs nothing. A bad count, a missing worker id, or `last`, `ago` or `now` as the worker id prints a usage line and runs nothing.

```toml
[changes]
pager = "git" # git | delta | hunk
diff_args = [] # default git diff args; typed /diff args follow
```

- `pager = "git"` (default): `git diff <revs> <diff_args> <typed>`. The user's `core.pager` in git config is left untouched.
- `pager = "delta"`: `git -c core.pager=delta diff ...` for this call only.
- `pager = "hunk"`: `git -c core.pager=hunk pager diff ...`, with `core.pager=hunk pager` as one argument.
- Any other pager string warns once at chat start (`[changes] pager = "..." is unknown; using git`) and uses `git`. Loading the config still succeeds.
- ralph does not write `core.pager`. Snapshot ranges set `GIT_DIR` and the alternate object dir for the spawned git only; `/diff now` sets no environment variables.

The spawn runs only after reedline `read_line` has turned raw mode off, so a full-screen pager returns to a normal prompt. `git diff` exiting 1 (there are changes) is not a chat error. A failure to start git warns and returns to the prompt.

## /workers

`/workers` is local: it never starts a turn or calls the model. Only the bare command and `/workers <id>` (one token) count; `/workers a b` and `/workersfoo` are normal messages. Only live workers appear (`running_workers`); a Codex worker has only what its shared record gives. The shell is `crates/ralph/src/chat/workers.rs`; the pure parsing and layout is `crates/core/src/workers_view.rs`, with the detail view in `crates/core/src/workers_view/detail.rs`. The ticket and PR lookups run in background threads; `/workers` never waits for them (see [Remote lookups](#remote-lookups)).

| Column | Source |
| --- | --- |
| ID, HARNESS | the running worker record |
| STATE | the status bar state (`Monitor::status`) |
| REPORT | `<text> · <age> ago` of the worker's status when it has set one (`set_status`, see [Worker inbox](#worker-inbox)) and its time is later than the latest report's (both parsed as RFC 3339; equal or unparsable report times keep the report; no report at all shows the status), else `<status> <age> ago` of the latest real report (`done`, `blocked`, `question`): worker entries in the chat log (read only) and unread inbox reports, newest first |
| HEAD | `git log -1 --format=%h %s` in the worker worktree (`git worktree list --porcelain`, branch `worker/<id>`) |
| +/- | `+A -D Nf` over tracked changes of the worktree against `git merge-base HEAD <base>`, plus ` ?N` for untracked files, each file counted (`git status --porcelain -uall`; omitted at 0). Every git call runs with `--no-optional-locks`, so `/workers` never takes the worktree `index.lock`; binary files count as files with 0 lines; one failed git call makes the whole cell `?` |
| BEHIND | `git rev-list --count HEAD..origin/<base>` |
| TICKET | the remote state of the spawn record's ticket (see [Remote lookups](#remote-lookups)); prefixed with the key when the key is not the worker id |
| PR | the newest PR of branch `worker/<id>`: `#12 draft`, `#12 open`, `#12 approved`, `#12 changes`, `#12 merged`, `#12 closed` |

BEHIND counts against the local remote-tracking ref `origin/<base>` (base = `[chat] worker_base`, else `origin/HEAD`, else `main`), so it is stale until a fetch; no network is used, and a missing ref shows `?`. +/- uses the merge-base with `<base>`. In the table a `-` cell is wrapped in a code span (backslash escapes are not honored) so termimad does not draw a list bullet. A missing value shows `-`, a failed lookup `?`, a lookup not done yet `…`.

With color on, table cells are colored from the `[theme]` palette: STATE (`done` green, `blocked` red, `question` and `permission` yellow, `running` and `busy` link color), `+N` green, `-N` red and BEHIND above 0 yellow. The core view marks these cells with the zero-width characters U+206A to U+206E (`TONE_*` in `workers_view.rs`, stripped from cell text), and `chat/workers.rs` turns them into colors after the table renders. With color off the table has no markers.

With no live worker it prints `No live workers.`. By default, the list is a markdown table through the chat renderer when it fits the prompt width (columns plus `cols + 1` border cells, as termimad draws them without padding); the HEAD subject is cut with `…` down to 20 characters first. Else each worker is a block, every line cut to the width. Set `[workers] view = "list"` to always use these blocks; `view = "table"` keeps the default table with a block fallback and does not change `/workers <id>`:

```
● GUZ-844 · claude · busy
  report  done 12m ago
  head    2f7f8c0 fix(chat): exact /help, width-wrapped…
  diff    +120 -40 in 3 files ?2 · 2 behind origin/main
  ticket  In Progress
  pr      #12 open
```

`/workers <id>` prints that block plus the branch, worktree path, base ref, tmux session (claude only), the set markers among `blocked`, `waiting`, `unreported`, `sent` and `gone`, and the heartbeat from `activity/<id>` (`running|idle <age>`), the `ticket` line from the spawn record (`GUZ-918 (linear) · In Progress`, or just the key when the tracker is unknown; `-` without a ticket), the `pr` line as `#12 open · <url>` (a URL that does not fit goes uncut on the next line), then one `status: <text> (<age> ago)` line for each kept status, newest first, then the last 5 reports newest first as `<status> <age>  <first line>`. The detail view always shows the status lines above the reports; the table and the REPORT cell use only the newest status. In the table the status text is cut with the HEAD subject to share the width budget, so one long status does not force the list. An id that is not live prints `No live worker <id>. /workers lists them.`

### /workers costs

`/workers costs` prints all-time token totals from the global usage record (`<config_dir>/usage.jsonl`), so closed workers count. `costs` is a reserved word, not a worker id. Spawn refuses it. Rows group by harness and model: `main` is the chat thread (`turn` and keepalive `ping` rows), `nap` the memory summaries and thread merge digests (`merge` rows), `ask` the `ralph ask` calls, `subagent` the claude usage outside the main loop of any of those calls, and worker rows use their `harness`. A row with no `model` goes under `unknown`. RUNS counts chat processes (`run`), nap, ask or subagent rows, or worker sessions (`worker_id` plus `session_id`, so a reused id counts again). The main HARNESS USD sums the last running `cost_usd` of each claude process per run (`session_cost`); that total already includes the process's subagents, so `subagent` rows carry no `cost_usd` and their HARNESS USD is `n/a`. A process's cost goes to the last model known for that process. Its tokens move with its cost to that model. A run that spans two models counts once in each model's RUNS, so the RUNS column does not sum. A run with a process that has no `cost_usd` shows `+`. For every row, main included, USD is list price times tokens: each token kind (input, cache read, cache write per tier, output) times its price from the `ralph wire` price table and `[wire.prices]` overrides, at read time. A recorded `cost_usd` does not replace it. USD from token prices starts with `~`, because it is an estimate: it ignores provider discounts and surcharges. HARNESS USD sums the `cost_usd` that the harness reported for the same rows, as a cross-check (`n/a` when no row has one, `+` when some rows have none). `reasoning_tokens` are a part of `output_tokens` and are not priced a second time. The table adds OpenAI Standard-tier rows for codex workers (`gpt-6-astra`, `gpt-6.1-sol`, `gpt-6.1-terra`, `gpt-6-luna`; input, cached input, output and 30m writes; from https://developers.openai.com/api/docs/pricing, checked 2026-10-28) in `crates/core/src/wire/provider/openai/price.rs`. Batch, Fast and Ultrafast tiers are not priced. The cost views leave codex dollars out: codex rows count tokens only, and a group with only codex rows reads `excluded` instead of dollars (GUZ-1550). Cache write tokens with no tier (codex writes have no TTL, claude rows written before the 5m/1h split was parsed, or `cache_creation_input_tokens` above the 5m plus 1h split) are billed at an assumed tier when the resolved price has it. Rows with harness `claude` assume 1h: ralph sets the 1h cache (GUZ-413), and transcripts showed 100% 1h writes on 1,550,879 nap tokens and on main session 40e879e6 (84,277 tokens). Other rows assume 30m, because codex sends no cache TTL. Without a price for the assumed tier (for example a `[wire.prices]` override with no `cache_write_30m`; the Anthropic ratios used here have no 30m multiplier) they are left out; the rest of the row is still priced and its USD ends in `+`. A recorded tier is always priced as recorded. A partial `[wire.prices]` override for a gpt model fills its missing prices from Anthropic ratios (cached input 0.1x, output 5x of input), so set `input`, `cache_read` and `output`. Those dollars ignore the fast-mode (2x) and US-geo (1.1x) factors, so they can read low. A turn's calls split into worker rows by prompt tier, so the long tier (for example haiku-5-5 above 100k) applies only to calls above the line. Rows written before this change have no tier flag. They still price from the row's sum. A price change reprices old rows. USD shows `n/a` when no price is recorded and ends in `+` when part of it is unknown. 5M and 1H show `–` when no row in the group records that tier, and a count ending in `+` when only some rows do: the rows with no recorded tier are unknown, not zero, so the count is a lower bound (a recorded `0` stays `0`). The total row follows the same rule. REASONING follows the same rule as 5M and 1H: `–` when no row in the group records it, and a count ending in `+` when only some rows do. The pure model is `crates/core/src/worker_costs.rs`; the shell is `costs` in `crates/ralph/src/chat/workers.rs`.

`/workers costs [harness|model|role|ticket] [today|7d|all]` picks a view and a window. `model` is the harness and model table above, and it is the default view; `all` is the default window; a bare `/workers costs` is unchanged. A window alone (`/workers costs 7d`) keeps the default view. The view comes first, in lower case. Any other word, a repeated kind of word or more than two words sends the whole line to the model as a message, like any unknown `/workers` text. The parser is `parse_costs_args` in `crates/core/src/worker_costs/args.rs`, routed by `workers_route` in `crates/core/src/chat_status.rs`. The shell (`costs` in `crates/ralph/src/chat/workers.rs`) reads `usage.jsonl` and the `analytics/workers.jsonl` of this chat's store, with the local clock time (`chrono::Local::now()`) taken there. Spawns of another store are not in that file, so their worker rows read `unknown` in the `ticket` view.

Other views group the same rows by another key, with the columns INPUT, OUTPUT, CACHE READ, CACHE WRITE, 5M, 1H, REASONING and USD (no RUNS, and no HARNESS USD). `harness` merges the models of each harness. `role` groups by the row role: `main`, `nap`, `merge` (thread merge digests, apart from `nap`), `ask`, `subagent` and `worker`. `ticket` groups worker rows by the ticket of the worker that wrote them. The ticket comes from `<store>/analytics/workers.jsonl` (see [headless-workers.md](headless-workers.md)): a usage row joins a `spawn` event when the `worker_id` matches and the row `at` lies from the spawn time to 1 s after the matching `close` time. A worker with no `close` event has no upper bound, a reused id joins the window that holds the row time, and a row that matches no window never falls back to the worker id alone. Rows with no ticket (main, nap, ask, subagent, a worker row with no matching window, a spawn with no ticket) share one `unknown` row, which sorts last. A cursor worker writes no usage rows, so each cursor spawn with no joined usage row adds an unknown entry: a row whose tokens and USD all read `unknown` (never `0`), or, when it joins a row that has usage, a `+` after each count and the USD. In the `harness` and `role` views this entry goes to the `cursor` harness and to `worker`. The `harness and model` view takes no workers file and shows no such entry. The pure model is `crates/core/src/worker_costs/views.rs`, the ticket join is `crates/core/src/worker_costs/tickets.rs`.

A window limits every view to rows whose `at` is at or after its start (`window_start` in `crates/core/src/worker_costs/window.rs`): `today` starts at local midnight (`today_start` is one pure function of the local clock time: it builds midnight of the local date and takes the earliest matching instant, so a day with a DST change starts at the right hour, also late in the evening; a midnight that does not exist starts at the first valid local time after the gap, found in 15-minute steps up to 4 hours), `7d` starts 7*24 h before now, and `all` has no start. A row whose `at` is missing or not valid RFC 3339 is skipped in every view and window (`ralph usage` prints the count). A cursor spawn counts in a window when its spawn time is inside it. The ticket join still reads every spawn, so a row inside the window joins a worker that spawned before it. In the `harness and model` view, HARNESS USD of `main` is the last running `cost_usd` of each claude process among the rows in the window, minus the last running `cost_usd` of that process before the window start, so it counts only spend inside the window. A process with no row before the window loses nothing, and a process with no row in the window is left out. In the `harness`, `role` and `ticket` views the USD column shows its source. A row with `cost_source` `harness` (and a `cost_usd`, for any kind except the main `turn` and `ping` rows, whose `cost_usd` is a running total that cannot be summed per row) counts at its reported cost. A group that has only such rows shows `1.23 reported`. Any other row is priced from its tokens at list price, and a group with such a row starts with `~`, also when other rows of the group are reported. `n/a` is no price, and a `+` after the number is a part with no known cost (a cursor spawn with no usage row, or a model with no price).

### Remote lookups

The pure model is `crates/core/src/workers_view/remote.rs`; the shell is `crates/ralph_server/src/chat/workers_remote.rs`. A worker has a ticket lookup only when its spawn record has a tracker (`-` otherwise, no lookup): Linear runs `mcptools linear issue get <KEY> --history-limit 0 --json` and reads `state`; Jira runs `mcptools atlassian jira get <KEY> --json` and reads `status`. The PR lookup runs `gh pr list --head worker/<id> --state all --json number,state,isDraft,url,reviewDecision` in the chat's working directory and takes the newest item; an empty list is `-`. `[workers] pr_provider = "none"` skips it. Settings are in [Configuration](../configuration.md#workers---workers-remote-lookups).

`/workers` renders from a cache held by the chat and never waits. A key that is missing or older than `cache_secs` shows `…`, and `/workers` starts one detached thread for it unless one runs already. The thread runs the command in its own process group with `lookup_timeout_ms` as a hard bound (output is read through a channel with the remaining time) and kills the whole group at the deadline, then stores the result; if the thread dies first, a guard stores `?`. `[workers]` comes from the config `/workers` reloads on each call (defaults when it fails to load). A timeout, non-zero exit or output that does not parse stores `?`, cached like a result. The next `/workers` shows the result. A result for a worker that has closed is only cached. The threads are never joined, so they do not hold the chat open.

## History commands

`/read <id> [raw|summary] [--cursor <c>]`, `/zoom <id>`, `/recall <regex>` and `/search <words> [--cursor <c>]` print the chat memory with the same text as the model's `read`, `zoom`, `recall` and `search` tools (see [MCP tools](#mcp-tools)). ralph answers them itself: no turn, no model call. They run during a turn too. `ralph chat history <tool> <words>... [--cursor <c>]` does the same outside chat; it resolves the store as `ralph chat` does (`--store`, `RALPH_CHAT_STORE`, `~/.ralph/chat`), prints the text and exits non-zero on a tool error.

- One implementation: the pure `chat_memory::history_tool(name, words, cursor, tag)` builds the tool arguments and calls `parse_tool_call`, the parser of the model's calls, which returns a `MemoryCall` (scope and `Tool`). `thread::Memory::call` routes it to main or a thread (see [Threads](#threads)) and `Store::call` runs it, for the slash commands, the CLI and `chat-mcp`.
- Words: `/read` takes an id and an optional mode; `/zoom` takes an id; the rest of a `/recall` line is the pattern, inner spaces kept; the rest of a `/search` line is the query. A last `--cursor <c>` pair on `/read` or `/search` is the cursor from a page's `next cursor:` line. `/search` has no role, date or limit filters; the defaults apply (20 hits a page). The CLI joins its words with one space.
- Errors: bad words print the tool error (for example `Missing or empty string argument 'id'.` for a bare `/zoom`). `route_input` returns `Route::History(Err(..))` for them, so they are never sent to the model as a message. `/readme` and other longer words stay messages.
- Locks: they take only the shared `LOCK` that the model's tools take (see [Index](#index)), never `CHAT` or `NAP`, so they work while a chat or a nap runs; a nap commit or an append makes them wait briefly. A missing store reads as empty and creates nothing. Like the model's tools, a read can save an index file it extended.
- Tab does not complete them or their arguments.

## Process reset

The persistent `claude` process is dropped, and the next turn respawns it from the store through `Turn::launch`, when `reset_reason` (`crates/core/src/chat.rs`) returns a reason (`turns` or `tokens`) rather than none after a turn:

- Turns on this process reach `[chat] reset_turns` (default 30).
- The last assistant message's `context_tokens` reach `[chat] reset_tokens` (default 140000). No usage means no token trigger.
- The `result` event has `terminal_reason` `blocking_limit` (claude's context is full). Only the structured field counts, never the text `Prompt is too long`. The turn counts as failed: warning, `Unanswered`, no reply stored, session dropped. The usage record is still written.

Compaction stays off. A respawn waits for a running nap (`load_after_nap`: shared `NAP` try-lock, spinner while it blocks) and then loads under the shared `LOCK`; no lock is held while claude runs. A nap that is spawned but has not yet taken `NAP` when the respawn loads is not waited for: the respawn reads the committed tree and shows the nodes as pending.

## Turn snapshots

Unless `[changes] enabled = false`, every turn (user and worker-report turns) snapshots the working tree of the repo the chat started in, before and after the model call. A chat outside a git repo does nothing and prints no warning; this is decided once at start. A snapshot failure warns and never stops the turn.

- Storage: one bare git dir per repo at `<store>/snapshots/<repo-dir-name>.git`, with its own objects and no link to the repo. The repo's own refs and objects are untouched.
- Refs: `refs/ralph/chat/turn-<n>/start` and `.../end`. `<n>` continues from the highest existing number, also across restarts.
- Content: `git read-tree -m -i HEAD` into a private index at `<side>/index/chat`, then `git add -A -- . <excludes>` (see Excludes), so tracked files stay even when ignored and `.gitignore` and `info/exclude` apply to untracked files, then `write-tree` and `commit-tree`. When the branch has no commit yet, `git read-tree --empty` resets that private index instead, so entries indexed by an earlier snapshot do not survive an exclude. `read-tree` runs without the side object dir; stat-clean entries reuse blobs an earlier snapshot wrote there and `add -A` rehashes the rest. Snapshot commits have no parents. Cost: with no commit yet, `read-tree --empty` drops the stat cache every turn, so `add -A` rehashes the whole worktree each turn.
- Excludes: `snapshot_excludes` (pure, `crates/core/src/snapshot.rs`) turns canonical repo, store and side dir paths into git pathspecs of the form `:(exclude,literal,top)<repo-relative path>`. The side dir is always excluded when it is inside the repo. The whole store folder is excluded when it is inside the repo and is not the repo root. A thread store (`<main>/threads/<name>`) is replaced by its main store (`config_root`) first, by its written path only, before any symlink resolves (the same rule as `open_fork`), so a symlinked thread folder cannot hide the main store and a plain folder symlinked to a thread folder is not a thread store, and so a thread chat, or a worker started from one, excludes the main store and every snapshot repo in it, not only its own thread folder. A thread store also excludes the snapshot repo folder of its main store (`snapshot_excludes` takes it as `main_side`), so when the main store is the repo root a thread turn skips `<repo>/snapshots/<slug>.git` as well as its own side dir; a folder already under the store exclude is not listed twice. A path outside the repo gets no pathspec, and the repo root never gets one. `IndexStep::AddAll.args` appends them after `add -A -- .`. Before each `add`, `write_tree` pipes the exclude paths to one `git check-ignore -z --stdin` (`check_ignore_payload`, pure, `crates/core/src/snapshot/ignore.rs`) and drops every exclude git reports as ignored (`without_ignored`, pure), because `git add` exits 1 when an exclude pathspec names an ignored path (for example a store under a gitignored `.claude`); an ignored path stays out of the snapshot through `.gitignore`. When `check-ignore` reports nothing or fails, the list is kept as is. The shell joins the store to the working directory and maps a thread store to its main store by the written path, then canonicalizes the repo, main store and side dir (a relative path joins the process working directory, `normalize_lexically` in core drops `.` and `..` parts, symlinks resolve, and a path that does not exist yet resolves through its nearest existing ancestor), and `Snapshotter::open` and `open_worktree` compute the list once. When the store is the repo root, the warning `snapshot-store-is-repo-root` shows once (`repo_root_store_message`, pure) and only its snapshots folder is skipped; for a thread store the warning says "snapshots folders" because both the side dir and the main store's snapshot repo folder are skipped. A store or side dir inside the repo whose path is not valid UTF-8 cannot become a pathspec; `not_excludable_message` (pure) detects it and the warning `snapshot-store-not-excludable` shows once; it names the path that failed, the store or the snapshot repo folder. Big untracked files elsewhere in the repo are not excluded; keep them out with `.gitignore`. Worker snapshots and report diffstats use the same exclude list (`open_worktree` computes it for the worktree), so a store inside the worktree is not snapshotted into itself. A relative store path resolves against the working directory (`exclude_base`, pure); when the working directory is unavailable the exclude is skipped and the warning `snapshot-store-relative-no-cwd` shows once. Snapshot repos made before the exclude may hold captured store files in up to 20 kept turns; they age out with pruning and `gc --auto`. To reclaim the space now, delete `<store>/snapshots/<slug>.git`. That repo is shared by the chat and by every worker that uses the store, so it drops up to 20 turns of the chat and up to 20 turns of each worker. Worker refs are pruned to the last 20 at each worker turn and are deleted only by `close_worker` (and a failed spawn); a worker that is never closed keeps its refs until you delete the repo.
- Index lock: each tree write holds a flock on `<index>.ralph-lock` (`snapshot_lock_path`), so one index has one writer across chat, worker hooks and the worker MCP server. While it is held, a git `<index>.lock` (`index_lock_path`) is stale because no live ralph snapshot holds it, which includes a git that outlived its ralph parent, so ralph deletes it before `read-tree`. The wait is bounded (`SNAPSHOT_LOCK_WAIT`, 5 s, polled every `SNAPSHOT_LOCK_POLL`); past it the snapshot is skipped with a warning that names the lock, so a hung git cannot stall a Stop hook.
- Message: the ref name, then trailers `Ralph-Head: <sha>` (HEAD at snapshot time) and `Ralph-Base: <sha>` (merge-base of HEAD and the default branch, left out when it cannot be resolved; same default-branch rule as the worker base). Older snapshots have no trailers. Built by `snapshot_message`, read by `parse_snapshot_base`.
- Pruning: after each turn the last 20 turns stay; older start and end refs are deleted, then `git gc --auto --prune=1.hour.ago` reclaims objects.
- Code: pure logic in `crates/core/src/snapshot.rs`; git calls in `crates/ralph_server/src/snapshot.rs`; the turn hook in `crates/ralph_server/src/chat/snapshots.rs`.

### Worker snapshots and report diffstats

Claude, Cursor and opencode workers snapshot their worktree into the same side dir, keyed by the main repo name (from `git rev-parse --git-common-dir`). Snapshots come from ralph's own side dir, not from opencode's `/api/session/<sid>/diff`.

- Refs: `refs/ralph/workers/<id>/turn-<k>`, private index at `<side>/index/workers/<id>`. Turn 0 is taken at spawn; turn `k` at the end of each turn (Claude Stop hook, Cursor `run_turns`, opencode `Effect::Snapshot`, which the pure `TurnState` emits first on every `TurnEnded` from SSE or `reconcile`, resends included, but not while the chat is closing; the chat's SSE thread runs the git calls). The `/opencode.json` line that spawn adds to the repo's `info/exclude` keeps ralph's opencode config out of the snapshots unless the repo tracks that file. The last 20 stay. `close_worker` deletes the refs, then the index under that lock. It keeps the `.ralph-lock` file, so a waiting writer and a new one share one lock; unlinking it would let two writers lock different files.
- Report: the worker MCP server (`worker-mcp --worktree`) appends two `git diff --stat` blocks to the report text, rendered by `render_changes`: since spawn (merge-base of `HEAD` and the worker base branch against a fresh tree of the worktree, so untracked files count) and since the last turn snapshot (labelled turn `latest + 1`). A block that cannot be computed is left out. Output is uncapped. The since-spawn block is already rebase-safe, because it diffs from the current merge-base. The since-last-turn block is rebase-aware (see "Reading changes").
- `[changes] enabled = false` also turns off worker snapshots and report diffstats: the spawn decides once (`snapshots_enabled`), takes no turn 0, and passes no `--worktree` to the worker hooks and MCP server (opencode: `opencode.json`'s `worker-mcp` command, built by `worker_mcp_args`; the spawn handoff carries `snapshots`, and resumed opencode sessions read the config at chat start). `close_worker` still clears leftover refs and index from workers spawned while it was on.
- Code: pure helpers in `crates/core/src/snapshot.rs` and `crates/core/src/changes.rs`; git calls in `crates/ralph_server/src/worker_changes.rs`.

### Reading changes

The `changes` tool of `chat-mcp` lets the main thread read a diff without leaving chat. It runs `git diff` in the side dir (`--no-pager --no-color`), so the output is plain text.

- Scope: turns are counted back from the newest finished turn, so the model never needs absolute turn numbers. `last=N` and `ago=N` (1 or more, not both) are resolved by the pure `resolve_range` over the listed refs. With no `worker`, the chat repo (`chat-mcp` runs in the chat's directory); finished turns are those with an end snapshot, so the running turn never counts. `last=N` (default 1) gives the start snapshot of the Nth newest finished turn to the end snapshot of the newest; `ago=N` gives one finished turn (`ago=1` is the newest, `ago=2` the one before). With `worker`, that worker's worktree, where each step between two consecutive turn snapshots is a finished turn: no `last` or `ago` gives `turn-0` to the highest turn (since spawn); `last=N` spans the last N steps; `ago=N` is the single step N back. An N larger than the finished turns is not clamped: it is an error such as `last=5 is more than the 3 finished turns of the chat; use last 3 or less`. The removed `turn` and `since` arguments are rejected with an error that names `last` and `ago`. Other errors: `no finished chat turn snapshots yet`, `no snapshots for worker X`, `no snapshots`.
- Rebase handling: after a rebase onto a newer default branch, a plain diff would count commits pulled in from the default branch. `diff_base` compares the `Ralph-Base` of the two snapshots (the fresh `current_base` for the since-last-turn report block). Same base, or both unresolved: `Direct`, diff as is. The newer snapshot has `Ralph-Base` equal to its `Ralph-Head` (the checkout sits on the default branch, such as a chat on main): `Direct`, so a moved base is its own commits. Both bases known and different: `Rebase`, and the older snapshot is moved onto the new base with `git merge-tree --write-tree --merge-base=<old> <new> <snapshot>`, then that tree is diffed. Missing trailers or one unresolved base: `Unknown`, diff as is. Any `merge-tree` failure (git older than 2.40, a conflict, unparsable output) falls back to the unmoved diff. Every fallback and `Unknown` appends the line `note: could not separate upstream commits from these snapshots; counts may include commits pulled in by a rebase`. The rebase step never fails the call. `merge-tree` runs with `GIT_DIR` set to the side dir and the repo object dir as an alternate, so its objects land in the side dir and never in the user's repo.
- Format: `stat` is `--stat`, `files` is `--name-status`, `patch` is `--patch`. `paths` limit the diff. The first output line says what the range is, such as `changed in chat turn 3`. No changes gives `no changes`.
- Cap: output keeps whole lines from the start while the body fits in `max_bytes` (default 32768), never splits a UTF-8 character, and ends with `… <B> bytes omitted (<F> files not shown); narrow with paths or format=stat`. Body and footer together stay within `max_bytes`, except when `max_bytes` is smaller than the footer: then only the footer shows. The label line is not counted. Worker report diffstats stay uncapped.
- `[changes] enabled = false` makes the tool return an error that says snapshots are off. A chat outside a git repo, or with no snapshots yet, returns `no snapshots`.
- Limit: changes after the latest snapshot are not shown; a running turn has no end snapshot until it finishes.
- Code: pure parsing and range resolution in `crates/core/src/changes.rs`, the cap in `crates/core/src/changes/cap.rs`; rebase handling in `crates/core/src/changes/rebase.rs`; the tool call in `crates/ralph_server/src/chat/changes.rs`; `render_diff` and the git helpers in `crates/ralph_server/src/snapshot.rs`.

## Executable cells

A fenced block in a message you type whose info string is `!<runtime>` (for example ```` ```!zsh ````) is a cell. Worker reports and agent replies never run cells; a `!` fence inside another fence is not a cell. Parsing and message building are pure in `ralph_core::chat_cell`, the live-output gate and sanitiser in `ralph_core::chat_cell_stream`; PATH lookup, spawn and streaming are in `crates/ralph/src/chat/cell.rs`.

Shorthand: a message whose first character is `!` is the same as one `!shell` cell holding everything after the `!` (all lines; trailing newlines dropped; a longer fence when the body has backtick fences). The pure `bang` and `shell_cell` in `ralph_core::chat_cell` rewrite it before parsing. The prompt trims the line first, so ` !ls` runs like `!ls`; `hi !ls` is plain text, and so is `!` alone or `!` followed only by whitespace. A failed or cancelled cell restores the draft as typed (`!ls`).

Local shorthand: a message that starts with `!!` (after the same trim) runs everything after the `!!` as one `!shell` cell (`Route::Shell`, `cell::run_local`), with the same live output, sanitiser and shell state as `!`, so `!!cd /tmp` moves later `!` and `!!` cells. Nothing goes to Claude: no turn, no `log.jsonl` or memory entry, no `usage.jsonl` line, no nap. The terminal shows the live output, then the message rendered and an `exit N` line on a non-zero exit, and the prompt returns empty. `!!` alone or followed only by whitespace is plain text and is sent; `!!!x` runs `!x`. Ctrl-C or a missing runtime restores `!!<command>` as the draft. The line goes to `history.txt` as typed. During a turn a `!!` line is queued and runs after the turn (see [Queued messages](#queued-messages)). It is not read-only, so it never runs mid-turn.

- On Enter, cells run in order, one process each, in the chat's working directory. The runtime is found by exact name on `PATH`; the code goes to its stdin. No sandbox. Stdout and stderr are two pipes, each read by its own thread. The terminal shows one dim line `▸ cell N · runtime`, then the output live as it arrives, both streams on stdout in arrival order, plus a newline if the output did not end with one.
- Live output never reaches the terminal raw: each stream goes through its own `Sanitizer` (`ralph_core::chat_cell_stream`), which keeps printable text, `\n`, `\t` and plain SGR colour (`ESC [ digits ; : m`, only with color on) and drops every other escape sequence (CSI cursor moves and private modes, OSC titles, clipboard and hyperlinks, DCS, SOS, PM, APC including kitty graphics, two-character escapes, a bare `ESC`) and every other C0/C1 control. `\r` becomes a newline and `\r\n` one newline, so a progress bar prints one line per update. Invalid UTF-8 becomes `U+FFFD`. State carries across reads, so a sequence or a UTF-8 char split between two chunks is handled the same as a whole one. At stream end it emits an SGR reset if it passed any colour. The captured text sent to Claude is the raw output, not the sanitised one.
- Claude gets the message with the `!` removed, then per cell: `[cell N · runtime · exit C]`, the code, a ```` ```stdout ```` fence and a ```` ```stderr ```` fence. An empty stream has no fence; with both empty the line is `(no output)`. A non-zero exit still sends. The store keeps this enriched message.
- After all cells ran, the terminal shows the message (the `!` removed) rendered as markdown (images: see [Rendering images](#rendering-images)). The output is not repeated (it was shown live); a cell with a non-zero exit is followed by an `exit N` line (`core::chat_cell::display_results`). The display never reaches Claude, `log.jsonl` or memory.
- Caps shape only what Claude receives and apply to stdout and stderr each: `[chat] cell_output_limit` (200 lines, first half and last half kept) and `cell_output_bytes` (65536, head and tail kept), each with a marker in place of the cut: `… N lines trimmed …` and `… N bytes trimmed …`. For an odd limit the head keeps `limit / 2` and the tail keeps the larger rest. `0` disables a cap. See [configuration](../configuration.md).
- A missing runtime prints ``runtime `X` not found``, runs nothing, sends nothing, and puts the text back in the prompt. Ctrl-C kills the running cell and its process group, ends the turn without sending, and restores the draft.
- `!shell` runs `$SHELL -i` (`/bin/sh` when unset) and keeps state between `!shell` cells, in one message and in later messages, until ralph exits. One process per cell, no long-running shell. The stdin is a generated prologue plus the cell code. The prologue empties the prompt variables and prompt hooks, turns off verbose and xtrace, unsets `HISTFILE` (a leading space keeps the first line out of history) so no state or code reaches the history file, dumps a START snapshot to fd 3 (a pipe ralph reads into memory, never disk), restores the saved state, installs an exit hook that dumps an END snapshot to fd 3, then re-enables verbose and xtrace if they were on. The snapshot has the exported env, `$PWD`, functions and aliases. `diff(END, START)` is the saved state: new, changed and removed exports, functions and aliases, plus the end directory. START is taken before the restore, so the diff holds everything done since ralph started, and inherited env and `.zshrc` definitions are never copied. The prologue ends with a marker byte on stdout and then on stderr; output before it on each stream (rc noise, the first prompt) is dropped from the live view and from Claude's message. Restore text and the prologue never appear in the live output or in Claude's message.
- `!shell` state works for zsh and bash only (bash is best effort; macOS bash 3.2 untested). Any other shell runs without state and warns once. A snapshot that cannot be read (for example the cell closed fd 3) or a failed spawn warns and resets the state to clean; the message still sends. A cancelled cell (Ctrl-C) keeps the state from before that cell. Not carried: shell options, background jobs, open connections, `precmd`/`preexec` hooks (cleared inside `!shell` cells), anything outside the snapshot.
- The prompt shows the raw buffer, so the `!` stays visible while you type.

## Memory

- Log: `log.jsonl`, append-only, one `{role, at, text}` per line (`role` is `user`, `assistant` or `worker`, `at` is RFC 3339). Each append is fsynced under `LOCK`, then `log.idx` is brought up to date under the same lock (see [Index](#index)). A complete line that does not parse is kept as a placeholder entry at its position, shown as `[corrupt entry]` (role `worker`, empty `at`). The placeholder carries an explicit `corrupt` flag that only the parser sets: the flag is never written to `log.jsonl` (`#[serde(skip)]`), so a real entry with that text stays a normal entry. `parse_log` (`Store::load`: turn view, status bar, nap, check, editor) and the archive (`read`, `zoom`, `recall`, `search`) both give the placeholder the id of its line and show every later entry with the same ids. The placeholder can never be written back: the log writer takes a separate `NewEntry` type, so a loaded `Entry` (including a `[corrupt entry]` placeholder) cannot be written back, and the compiler enforces it. The turn view shows no placeholder as a message. `view` and `tail_lines` replace it with a notice line, `[#12: unreadable log line, skipped]`, and merge consecutive placeholders into one line, `[#12-14: unreadable log lines, skipped]` (`merge_notices`, pure, in `notice.rs`); ids of the other entries do not change, and a run that crosses the older view, the middle and the tail gives each of them its own notice. The status bar counts the same lines and shows no entry text. `read`, `zoom`, `recall` and `search` keep the `[corrupt entry]` line per id, so a caller can still address each id. `recall` and `search` never match the placeholder. `pending` never offers a leaf or block whose range holds a placeholder, so the nap never summarizes it; `view` splits a skipped range into its children, and the middle splits a 32-entry block into halves down to the damaged leaf. A trailing line without newline is ignored. `Store::append` truncates a torn last line (a crash mid-append) under the exclusive `LOCK` before it writes, so a new entry never glues onto it (`log_tail`, pure; the file reads and `set_len` are in `trim_torn_tail`), and warns with the byte offset.
- Tree: `tree.jsonl`, one `{lo, hi, text}` record per line, indexed by `tree.idx` (see [Index](#index)). Nodes are aligned power-of-two blocks `[lo, hi)` over log indexes, ids print as `5` or `4-7`. First record wins for a duplicate node; invalid records warn and are skipped. Summaries are at most `SUMMARY_BYTES` = 512 bytes, one line.
- Leaves are single messages. Outside the verbatim run (see [Recent history](#recent-history)), messages of 512 bytes or fewer stay in the view with whitespace collapsed and need no node. Longer ones get a leaf summary node. Parent nodes merge two children and exist only for complete blocks. A node is written once and never rebuilt.
- `cover(t, budget)` picks the nodes for the view: all leaves if the log fits the budget, otherwise a cover of the whole log, oldest first, tuned to use the budget. A cover node with no summary yet is shown through its halves or a marker (see [Pending summaries](#pending-summaries)).
- View line formats: message `#<i> <role> <at> <text>`; summary `#<id> <summary>`.
- `zoom` leaf lines already carry the full timestamp (`entry_line`), while range lines are summaries with no single time, so no zoom change was made for timestamps.
- This is a port of the OptMem cover, pending and tree_put design. There is no runtime dependency on `~/.optmem`.

### Index

`log.idx` and `tree.idx` let `read` and `zoom` load only the entries and summaries they show. `log.jsonl` and `tree.jsonl` stay the record; each index is a cache that is always safe to delete.

- Format (`chat_memory/index.rs`, one generic `Index<S: Slot>`): a 52-byte header (magic `RLPHLOGX` or `RLPHTREX`, version 3, `covered`, `tail`, `hash`, `skipped` line count, slot count, all little-endian), then fixed-size slots. `log.idx` has one `u64` start offset per entry; `tree.idx` has one `{lo, hi, start, end}` slot of four `u64` per valid record, in file order. `covered` ends on the newline of the last scanned line, `tail` is that line's start, and `hash` is the FNV-1a hash of the bytes `[tail, covered)`.
- Same visible content as the parsers: only complete, non-blank lines are scanned. In `log.idx` every complete line is a slot, a corrupt one too, so later entries stay visible; the line is not parsed when the index is built. Entry ids are line ordinals, so `#<id>` does not change. In `tree.idx` an invalid record is skipped (`parse_tree`), and `TreeIndex::find` returns the first slot of each node, so the first record wins.
- Freshness (`Index::freshness`, pure): a file shorter than `covered` or a tail whose hash differs means `Rebuild`; a file that ends at `covered` is `Fresh`; a longer file is `Extend`, which scans only the bytes past `covered`. A file with a bad magic, version, length, slot or offset order decodes as missing, which also means a full rebuild.
- Writes: `Store::append` updates `log.idx` under the exclusive `LOCK` after the log fsync; the nap commit updates `tree.idx` under the same lock after the record is written. `refresh` and `write_plan` decide: nothing, an in-place extend (new slots at the end, then the header at 0; a crash in between leaves a length the header does not match, so the next load rebuilds), or a full file written to a temp file and renamed over the index. The temp file is named `.<index>.<6 letters or digits>.tmp` (`index_temp_prefix`, `is_index_temp`). `check_path` rejects a symlinked or hard-linked index. A failed index write only warns: the line is already committed.
- Readers (`read`, `zoom`, `recall`, `search`, `Store::with_archive`) hold a shared `LOCK` for the whole call. They open the log and the tree and fix their lengths, read both indexes and extend or rebuild them in memory, answer, then save each index they had to extend or rebuild (`save_stale`). That save writes the whole file to a temp file and renames it, never in place: no writer runs under the shared lock, readers that hold it see the same lengths and so write the same bytes, and a concurrent reader sees the old file or the new one. No write plan is built on this path. An index for a missing file is not saved, and a store directory that does not exist reads as empty without creating anything (no directory, no `LOCK`). Summaries come from `IndexedTree`, one read per wanted node.
- Temp-file sweep: a save killed between the temp write and the rename leaves its temp file. `Store::append` removes every file whose name `is_index_temp` matches (`sweep_index_temps`) after its own index update, under the exclusive `LOCK`: no save runs then, so every match is orphaned and no age check is needed. Symlinks and other names stay. A failed sweep only warns.
- Self-healing (`Archive::retry`): a decode only checks the header, lengths and offset order, so a damaged slot can still decode. Each load checks what it reads: the log lines in a window must start at the stored offsets (the read starts one byte early to catch an offset inside a line) (a line that does not parse is not a failed check: it becomes the placeholder); a tree slot must end before `covered`, parse as a record, and name the node it is filed under. A failed check is `InvalidData`: the call rebuilds both indexes from their files, runs once more, and the reader saves the rebuilt indexes.
- Warnings (`Archive::warnings`): each call that loads a corrupt log line warns once for it: `chat log entry <id> at byte <offset> is corrupt and shows as [corrupt entry]: <error>` (`entry_or_corrupt`, pure; the offset is the line start). The tree gives one `chat tree: <k> records skipped` line where `parse_tree` gives one `chat tree record skipped: <error>` line per record.
- Visibility rule: a `read` or `zoom` call sees every complete line that was in the log and the tree when it took its shared `LOCK`. A line appended later is visible from the next call. A torn last line (no newline) is never visible.
- Store without an index (older binaries, deleted file): the first reader rebuilds it, the cost of one full file read, and saves it.
- Each call still reads both index files whole: about 8 bytes per entry and 32 per summary.
- The turn view, the status bar and the nap read the whole log and tree (`Store::load`, `parse_log`); a corrupt line is a placeholder there too. `recall` loads every entry through the archive under the shared `LOCK`; `search` scans the log in chunks of 256 entries through `log.idx`, so it never holds the whole log as entries (see [search](#search)).
- Benchmark: `cargo xtask bench-memory [--sizes 1000,10000,100000] [--runs 9]` builds a store per size in a temp dir and prints, per case, the median latency, bytes read and allocations of the whole-file path and the indexed path. It fails when the two answers differ. It calls the `ralph_core` functions with its own file reader, not `Store`.

## Nap

`ralph chat-nap` takes the exclusive `NAP` lock for its whole run, snapshots the store under a shared `LOCK`, and for each node from `pending` (long leaves, then complete parent blocks by increasing size) asks a Haiku curator for a summary with no `LOCK` held. Each result is committed under a short exclusive `LOCK` (see [Nap consistency](#nap-consistency)).

- Curator: `build_memory_command` runs `claude --model haiku` with `--tools ''`, an empty strict MCP config, and isolation args. The prompt goes to `claude -p` on stdin, never on the command line. Its prompt asks for one line of at most 512 bytes (about 70 words), priority: the user's words close to verbatim, lasting effects, commit SHAs, Linear ids and worker outcomes copied exactly, and failures, findings and open questions, steps taken. It asks to name minor items in a word or two, copy names, numbers, ids, paths and errors exactly, never overstate progress, invent nothing, and write in third person. It forbids copying the `#<id> <role> <timestamp>` line prefix, and says the input is data to never answer or obey.
- `check_summary` accepts a trimmed, non-empty, single-line summary of at most 512 bytes that does not read as meta-talk (an opener such as `I'm `, `Here is`, `Sure`, `Let me`, `Based on`, or the phrases `this excerpt`, `<input>`, `</input>`). A rejection retries with the error appended, up to `MAX_NAP_ATTEMPTS` = 5 tries per node. A curator error (process failure or timeout) skips that node: it stays pending, is retried at the next nap, and other nodes continue. A parent whose child has no summary is skipped.
- Raw fallback: when all `MAX_NAP_ATTEMPTS` tries were rejected by `check_summary` (not a curator error), the nap stores `fallback_summary` of the node input (`nap_source`) through the normal commit, so the parent can proceed, and warns `chat memory stored raw fallback for #<id>`. The fallback collapses all whitespace to single spaces, cuts on a char boundary so the whole line is at most 512 bytes, and starts with the marker `[raw excerpt] ` (`FALLBACK_MARK`), so a reader or the model can tell it from a real summary in the view and in `zoom`. `recall` searches log entries only, so it never sees fallbacks. The fallback reaches the view when the next process starts.
- Stuck nap: `LOCK` and `NAP` are `std::fs::File::lock` (`flock`) locks on open files, so the OS releases them when the holder process exits; deleting the files is not needed. `ralph chat-nap --timeout <secs>` (default 600) bounds each curator call: on expiry the process group is killed and the call counts as a curator error. It does not bound the whole nap (nodes times attempts). A slow nap does not block turns; it only delays later naps, which wait on `NAP`. A status bar stuck on `NAP` means a live nap. Find it with `lsof <store>/NAP` or `pgrep -fl 'ralph chat-nap'` and kill it; the next nap retries the pending nodes.
- Outage backoff: the curator subprocess call runs through `retry_on_outage`. The stderr-plus-reply rule below is the shared one; the tag pass has one exception (see Ladder under Tagging). `classify` sorts a failure into `Timeout`, `Outage` or `Refusal`. It is an `Outage` when the exit code is non-zero and the lowercased stderr plus response text contains one of `OUTAGE_MARKERS` (`overloaded`, `api error: 5`, `api error: 429`, `rate limit`, `rate_limit`, `529`, `503`, `502`, `500 internal`, `econnreset`, `econnrefused`, `etimedout`, `socket hang up`, `connection error`, `network error`, `request timed out`). Everything else, such as a refusal, bad output or an unknown error, is a `Refusal` and is never retried. An outage waits `OUTAGE_BACKOFF_SECS` = 2s then 8s before the next call, at most 2 retries; if it still fails, the node stays pending as before. The waits run with no `LOCK` held, so they do not delay turns. A timeout is never retried: each one lasts up to `--timeout` seconds and holds `NAP`, so retries would delay later naps, and the next nap retries the node anyway. The `check_summary` retry loop is separate and has no waits. Chat turns use the same schedule.
- A turn on a live process does not wait for the nap. A launch (first turn, or a respawn after a reset or failure) waits for a running nap through `Store::load_after_nap`, then reads the committed tree and shows pending nodes as below.

### Nap consistency

- Snapshot: under a shared `LOCK` the nap reads log and tree once. `log.jsonl` is append-only, so the entries under any pending node never change after the snapshot.
- Curator calls, `check_summary` retries and outage backoff run with no `LOCK` held.
- Commit: for each summary (or raw fallback) the nap takes the exclusive `LOCK`, re-reads `tree.jsonl`, and asks `commit_decision`. `Write` appends one fsynced record, then updates `tree.idx`. `Taken` means another nap committed the node first: the nap drops its own text, warns `chat memory kept the first summary for #<id>`, and keeps the committed text. Either way the nap continues from the re-read tree.
- Order: `nap_step` returns `Done` for a node already in the tree, `Blocked` for a parent whose child has no committed summary, else `Ask` with the prompt. A parent prompt is always built from committed child text, so a parent never summarizes a dropped child.
- Racing naps: `NAP` makes naps run one at a time. If two naps still overlap (for example an older binary without `NAP`), first-writer-wins at commit plus first-record-wins in `parse_tree` keep one summary per node. Records are written whole under the exclusive `LOCK`, so naps never interleave lines.
- Failure: a curator error, a timeout, or a nap that is killed before its commit writes nothing for that node. The node stays in `pending` and the next nap retries it. Nodes committed before the failure stay.
- Tests: pure unit tests in `nap.rs` cover `nap_step`, `commit_decision`, a race of two naps on one node, and uncommitted work staying pending. The shell test `nap_curator_runs_without_the_store_lock` checks that `LOCK` is free during curator calls.

### Recent history

The newest live-tail messages show their full raw text, newlines kept, within a token budget.

- Budget: `--recent-history-tokens <TOKENS>`, else `[chat] recent_history_tokens`, else 8192 (`RECENT_HISTORY_TOKENS`). `0` turns it off: the tail is then settled lines only. There is no env var.
- Estimate: `ceil(bytes / 3)` of the message text (`estimate_tokens`). This is more conservative than the `chars / 4` used by the status line, so the verbatim run stays under the budget.
- Run: `verbatim_start` walks from the newest message back to the start of the tail and adds each estimate. It stops at the first message that does not fit, so the run is one contiguous suffix with no gaps.
- Oversized: a newest message above the budget gives an empty run. It and all older tail messages use the settled rule (summary, or the `[raw excerpt]` fallback while the summary is pending).
- `zoom` on a message still returns its full raw text.
- Rollover: only the tail is verbatim. Older messages are in the older view in compressed form. The memory is read when a process starts, so a long-lived process keeps its first view; messages after it arrive as turns in the process's own conversation.
- The turn and the status size (`measure_memory`) use the same budget.

### Pending summaries

While a nap runs, a turn can load a tree with pending nodes. `view` and `tail_lines` never drop them:

- A cover node with no summary is shown through its halves when the line budget allows, down to single messages; otherwise as a marker (see below). Halves with committed summaries show those summaries.
- A long message with no leaf summary shows `fallback_summary` of its text, marked `[raw excerpt] `. This excerpt exists only in the view; it is never written to `tree.jsonl`.
- The view stays within its line budget (200 lines), or the cover length if that is larger. To show a missing node through its halves, the view first merges the oldest sibling pair whose parent has a summary (one line freed), then splits the newest missing node (one line spent). A missing node that cannot be shown this way is one line `#<id> [not summarized] zoom <id> for its parts` (`UNAVAILABLE_MARK`). `zoom` on it lists its halves (summary or `not compressed yet`), down to full messages.
- Tradeoff: under a tight budget with nothing to merge, old ranges that the previous rule expanded in full now show as a marker, so the model sees less until it zooms. Only older ranges become markers; newer ranges stay expanded. The view is read at process start, so a new process uses the committed summaries.

## Tagging

After each reply, chat starts a background pass that labels new messages `rule`, `decision` or `approval` with Haiku (`claude-haiku-5-5`). It writes `<store>/tags.jsonl`. `log.jsonl` is never changed. Search can filter on the labels (see [search](#search)). Nothing else reads them yet: `read` and `zoom` look the same as before. Turn it off with `[chat] tag_entries = false` (see [configuration](../configuration.md)).

- Spawn: `spawn_tag` runs right after `spawn_nap`, as the hidden `ralph chat-tag --store <DIR> --run`. It is detached; the turn does not wait for it. The command checks `tag_entries` itself, so a disabled chat spawns a process that only moves the start row and exits. If the global or the store `config.toml` fails to load, tagging is off for that turn: the process exits with no model call and no row (`chat_memory::tag_plan`).
- Entry id: the 0-based line index in `log.jsonl`, the same id `read` and `search` print.
- Start point: the first row of `tags.jsonl` is `{"v":1,"start":<entry count>,"at":...}`, written by the first pass. Only entries with an id of at least `start` are tagged. The last start row wins. With `tag_entries = false`, each `chat-tag` run appends a new start row at the current entry count (none if the last one already is), so turning tagging on later never tags the gap. There is no backfill. One pass tags at most 100 entries (`MAX_PER_PASS`); the next reply's pass takes the rest.
- Rows: a tagged row is `{"v":1,"n":<id>,"rule":b,"decision":b,"approval":b,"model":...,"prompt":"v2","at":...}`. The last row for an id wins. `decision` is for user messages only: the code forces it false for an assistant or worker entry, whatever the model says (`chat_memory::restrict_decision`). The search `tag` filter applies the same rule on read (`passes` in `search/request.rs`, which has the entry role), so a stored `decision:true` on a non-user entry never matches; `tags.jsonl` is read alone, not the log. A model reply row with no `decision` key is malformed and goes to the ladder. A stored row with no `decision` key (a v1 row, or a row from before `decision` returned) decodes with `decision` false. A pass tags only entries that have no row; it never reads the prompt version, so a new prompt version does not re-tag old entries. A `failed:true` row counts one failed pass. A `skipped:true` row ends retries for that id. Torn or unknown lines are ignored.
- Pass: the pure `chat_memory::tag` module lists the entries with no tag and no skip, builds batches (`### ENTRY <n> (<role>)`, plus up to three earlier entries as context), and parses the reply. The shell runs `claude --model claude-haiku-5-5 --system-prompt <prompt> --tools ''` with the batch on stdin. The prompt is `chat_memory/tag_prompt.txt` (version `v2`).
- Ladder: batches hold 20 entries; a batch that fails retries with 5, then 1. A call that never finishes (timeout, or an outage that outlasts the backoff) and a stop by SIGTERM end the pass and write no rows, so the entries stay untagged and the next pass retries them (`chat_memory::tag_reply`). The final check of a failed call reads stderr and the reply lines that start with `API Error`, because `claude -p` prints an API error as its reply with an empty stderr (`tag_failure_kind`); it never reads an exit-0 reply, and entry numbers such as 503 in a reply never count. Any other non-zero exit gives no reply text and goes to the ladder. Error text never says whether an entry or the account is at fault, so a health guard decides (`chat_memory::after_call`, `isolated`, `take_confirmed`). 4 non-zero exits in a row end the pass with no further rows, even after good calls; a good call only resets the count. An entry that fails alone after a non-zero exit gets a `failed` row only if a LATER call of the same pass exits 0; if the pass ends first, it gets no row and the next pass retries it. An entry left out of an exit-0 reply is confirmed at once. An entry that failed alone is left out of the context lines of later batches in the pass, so its text cannot fail their calls. An entry with a stored `skipped` row, or a `failed` row and no tag, is left out of the context of later passes too (`context_exclusions`); a later tag clears a `failed` row. The remaining stall: if two adjacent entries are bad and sit at the front of a round's first 5-chunk, the calls go 20-batch, 5-chunk, entry 0 alone, entry 1 alone, which is 4 non-zero exits in a row. This holds at any queue length. The pass stops, costs those 4 calls, writes no rows, and repeats on every pass until the entries are removed or changed. A call that exits 0 with an empty reply, or text that is not a tag list, counts as a reply with no tags, so the ladder and the 2-failure skip handle it. After 2 failed passes an entry gets a `skipped` row and is not retried.
- Locks: `TAG` is an exclusive file lock held for the pass; a second pass that finds it held exits as busy. The first pass reads the log once more after it releases `TAG` and, if entries landed meanwhile, takes `TAG` again for them, so they are tagged in the same run. The pass takes the shared `LOCK` only to read the log. It never takes `CHAT` or `NAP`, so it runs while a turn or a nap runs.
- Cost: each Claude call that returns usage writes a usage row with `kind` `tag` and `role` `tag`. Cost views count `tag` rows as `nap`.

## MCP tools

`[chat] mcp_servers` in the ralph config (default `["mcptools"]`) names servers to import. `select_servers` copies each entry verbatim from the top-level `mcpServers` of `~/.claude.json`. A name absent there, or equal to `ralph-chat`, prints one warning and chat starts without it. `ralph-chat` is inserted last, so an import cannot shadow it. claude and claude-tmux workers import the same list into their own `<store>/workers/<id>.json` ([details](headless-workers.md)). The file is written once at chat start: config changes need a restart. Imported entries can carry secrets, which is why they go in a file and not in argv. Turns run with the chat's permission mode (default `auto`), which decides whether imported tools need approval.

Hidden `ralph chat-mcp --store <DIR> --socket <PATH>` speaks newline-delimited JSON-RPC 2.0 on stdio (server name `ralph-chat`). At chat start the shell writes `mcp.json` (mode `0600`) in the chat's private socket directory `/tmp/ralph-<uid>/<key>-<pid>/` holding `ralph-chat` plus the servers named in `[chat] mcp_servers`, and `build_mcp_args` passes `--mcp-config /tmp/ralph-<uid>/<key>-<pid>/mcp.json --allowedTools mcp__<server>__*,... --strict-mcp-config`, so only those servers load. The allow list names every server in `mcp.json`: `--setting-sources project,local` skips allow rules in `~/.claude/settings.json`, and without this list the auto-mode classifier blocks these MCP calls. `chat-mcp` takes no permission mode or worktree directory; the chat process owns both. `zoom`, `recall`, `read` and `search` each go through `Store::with_archive`: on an existing store each call holds a shared `LOCK` for the whole call and reads the log and tree fresh, so it sees every line committed before it took the lock (see [Index](#index)); on a missing store it takes no lock, reads as empty and creates nothing.

Worker tools run inside `ralph chat`, not in `chat-mcp`. At start the chat creates the runtime root `/tmp/ralph-<uid>` (mode `0700`, `wire::store::ensure_store_root`: chat start fails if the root is a symlink, not a directory, owned by another user or not mode `0700`, and the message names the fix). The path is hardcoded and reads no environment variable. `<key>` is the first 12 hex characters of the SHA-256 of the canonical store path (`chat_socket::StoreKey`), so each store and thread has its own key. The chat sweeps, then creates the private directory `/tmp/ralph-<uid>/<key>-<pid>/` (mode `0700`, created with `DirBuilder` so it fails if the path exists; a leftover directory that the sweep kept makes chat start fail with a clear error), binds `chat.sock` inside it (then mode `0600`, so the socket is never reachable with looser rights), writes `mcp.json` in the same directory (and `system-prompt.md` at each launch), and writes the owner record `<store>/chat-<pid>.owner` (mode `0600`, JSON `pid` and `ps -o lstart=` start time). The sweep reads each `<key>-<pid>` directory of this store's key in the runtime root (directories of other stores are left alone) and each `.owner` record in `<store>`. The pure `chat_socket::socket_fate` deletes a directory and its record when the record is missing, unreadable or names another pid, or when the owner is dead or has a different start time; it keeps them only when the owner is alive with the same start time. An orphan `.owner` record, one with no `<key>-<pid>` directory, goes through `chat_socket::orphan_sidecar_fate` with the same rule: it is deleted unless its owner is alive with the same start time. Quitting the chat (Ctrl-D, or SIGTERM/SIGHUP during a turn) ends the main loop, and `SocketGuard` drops and removes its own directory (with the socket) and record. A SIGTERM/SIGHUP or a lost terminal stdin at the prompt goes through the input watcher instead: `ExitCleanup::run` kills watches, shuts down headless hosts, removes the same directory and record, then exits with code 129. A SIGKILL leaves both for the next start's sweep in the same store; a runtime directory whose store is gone stays until `/tmp` is cleared. `mcp.json` passes `--socket <path>` to `chat-mcp`. `chat-mcp` keeps `zoom` and `recall` and forwards `spawn_worker`, `reply`, `close_worker`, `watch` and `suggest_reply` to the socket as one JSON line `{tool, args}` per connection; the chat answers with one line `{text, is_error}` after it checks the turn marker (`command_allowed`) and parses the arguments (`worker::parse_command`). If nothing listens, the tool returns an error that starts with `no running ralph chat` and names the socket path; there is no fallback. `ralph ask` loads no `chat-mcp`, so it cannot spawn workers. A Unix socket path may not exceed 103 bytes (macOS `sun_path` is 104 with the NUL byte). The socket path does not depend on the store depth and is at most 55 bytes; a longer path makes chat start fail with a message that names the runtime root. A chat started by an older ralph keeps its `<store>/chat-<pid>/` directory, and its `mcp.json` still passes that path to `chat-mcp`; the new sweep does not remove those directories.

`chat-mcp` answers `zoom`, `recall`, `search`, `read`, `changes` and `help` itself. It forwards `workers`, `watch`, `schedule`, `suggest_reply`, `propose_run`, `step_result` (and `spawn_worker`, `reply`, `close_worker`, below) to the chat socket, so the running chat produces their results. `suggest_reply` is not offered to workers (it is in the chat-mcp tool list and not in worker-mcp). Claude subagents of the main thread inherit it. The last call in a turn wins.

### search

`search` (`chat_memory/search.rs`) ranks the raw messages for a query; `recall` stays the regex tool (every hit, newest first). The pure part tokenizes, parses the query, filters and scores; `search` drives it over an `Archive` in chunks of 256 entries, so only one chunk of `Entry` values is live. There is no term index: each call scans the whole log under the shared `LOCK`, so an entry is searchable as soon as its append commits.

- Tokens: lowercase runs of letters, digits and `_`. Identifiers stay whole: `-`, `.` and `::` between word characters join (`guz-709`, `foo::bar`, `a.b`, `main.rs`). A token is compared whole, never as a substring: `GUZ-709` does not match `GUZ-7090`. A joined token also keeps its parts (split on `-`, `.` and `::`: `rate-limited` has `rate` and `limited`; `chat_memory::search` has `chat_memory` and `search`). A single-part query term matches a whole token or a part: `rate` finds `rate-limited`, `guz` finds `GUZ-709`. A joined query term such as `GUZ-709` matches whole tokens only. A joined token counts at most once for a term, whether the term matches its whole form or any of its parts, however often a part repeats; the length for BM25 stays the number of whole tokens. A quoted single word such as `"rate"` is a phrase of one word: it matches whole tokens only, so it does not match `rate-limited`.
- Query: bare words are optional units; each `"quoted phrase"` is a unit whose whole tokens must appear consecutively and is required; parts do not join phrases, so `"rate limited"` does not match `rate-limited`. An unclosed quote is an error (`unclosed quote in query.`). A hit needs every phrase and at least one matching unit. A query with no token is an error.
- Rank: BM25 (`k1` 1.2, `b` 0.75, token counts as length) over the entries that pass `role`, `tag`, `since` and `until`; document frequencies come from one scan of those entries. Ties go to the newer entry.
- Dates: `since` and `until` parse with `chrono`. `since` later than `until`, after the date expansion, is an error; the same date for both is valid. A date means that UTC day: `since` is its start, `until` includes the whole day. A timestamp bound is inclusive and may carry any offset. An entry whose `at` does not parse is excluded when a date bound is set.
- Cursor: `<offset>.<count>.<hash>` where `count` is the log entry count the scan ended with (a mid-scan index rebuild is counted, so the next page is not stale) and `hash` is FNV-1a over the normalized query, role, tag, bounds and limit. Each page rescans and ranks again, then returns hits from `offset`. A changed query, filter or limit gives `cursor does not match this query`; a different entry count gives `stale cursor; the log changed`.
- Tag: `tag` (`rule`, `decision` or `approval`) keeps only entries whose latest `tags.jsonl` row has that label. The shell reads the file (`chat::tag_store::with_tags`) and gives the pure scan the matching ids; a tagged request without ids matches nothing. The tag is part of the cursor hash. Only entries written after tagging began carry tags; the CLI is `ralph chat history search <words> --tag <label>`.
- Snippet: about 160 characters of whitespace-collapsed text, with the first match near the start, `…` at cut ends.
- Evidence recall: a labeled fixture in the unit tests (10 queries, recall@5 = 1.0) measures whether the right entry ranks in the top 5, not whether a model answers correctly.
- Bench: `cargo xtask bench-memory` has two search cases (one rare phrase, one word in every entry). Its `full` path rebuilds both indexes before the scan, its `indexed` path loads them.

### read

`read` (`chat_memory/range.rs`) pages through a flat range of the log. `zoom` navigates the tree one node at a time and `recall` searches by regex; `read` returns the originals in order, so the model can read a stretch it already located. The `id` is a range `a-b` (inclusive, any bounds, not only aligned blocks) or one index. `b` is clamped to the log end; `a` past the end, `a > b`, a budget outside 1 to 16384, a malformed cursor, or a cursor outside the range all return `isError: true`.

- Each record is a header `#<id> · <role> · <date> · <n> chars` and then its text verbatim (whitespace and newlines kept). Records are separated by a blank line.
- `mode: raw` returns the original text. `mode: summary` returns the leaf summary for a message longer than `SUMMARY_BYTES`, `[not summarized]` (`UNAVAILABLE_MARK`) when that leaf has no summary yet, and the raw text for short messages. Use the same mode on every page of one read, because the cursor offset counts characters of the text shown; the cursor records its mode and a read in the other mode is rejected.
- `budget` is a page size in tokens, measured with `estimate_tokens` (bytes / 3). A page holds whole records while they fit.
- A record that does not fit is split at a character boundary, never inside a UTF-8 character, and its header gains `chars a-b` (1-based, inclusive). A page always carries at least one character, so paging always advances.
- When more remains the page ends with `next cursor: <next>.<offset>@<end><m>`. Pass it back as `cursor` with the same `id` and `mode`. `<offset>` is the character offset inside record `<next>`; `<m>` is `r` (raw) or `s` (summary), the mode that issued the cursor. A cursor in the other mode, one with no marker (the older format) or one with an unknown marker returns `isError: true`. Otherwise the page ends with `(end of range)`.
- Snapshot: the first call fixes `end` as `min(b + 1, log length)` and the cursor carries it, so messages appended between pages never appear, and a full traversal has no gaps or duplicates.
- Loading (`Archive::read`): each call loads a window of entries from the cursor (or `a`) through `log.idx`, never the whole log; in `summary` mode it reads only the leaf summaries of long entries in the window, through `tree.idx`. The first window holds entries whose JSON lines add up to the page budget in bytes; when the page needs an entry past the window before the budget is spent (`Read::More`), the window doubles. The page is the same as one built from the whole log (tested).

Cursor harness: a new `cursor` worker runs `agent -p` once per turn (print mode, no tmux, cwd = the worktree; see [Cursor print mode](headless-workers.md#cursor-print-mode)). `[cursor] permissions = "ask"` asks the person per shell command through the hook bridge; MCP calls are not gated. An auth error still reads "not logged in; run `agent login`". A resolved model is applied after `session/load` with `session/set_config_option` (`worker::select_cursor_model`). An exact advertised option value is sent as-is. A short name selects the advertised value for that name. If a name is listed more than once, the cheapest listed value is sent (`fast=false`, then no `fast`, then `fast=true`, then the lowest effort). With no snapshot the files cannot be told from a change the user made. `agent --model` does not change the ACP session's current model. `chat-mcp` lives only for one turn, so the long-lived `ralph chat` owns the child. Spawn prepares the worktree, writes `<store>/cursor-spawn/<id>` (a JSON `SpawnRequest` with the time) and polls every 250 ms for `<store>/ready/<id>` or `<store>/cursor-error/<id>`, giving up after 30 s (it removes the request). The host drops a request older than 30 s. On an ACP resume, right after starting the child and before `initialize`, the host writes `<store>/cursor/<id>`: a JSON owner record with the chat pid and start time and the process group id and start time (`ps -o lstart=`, guarding pid reuse), not a bare child pid. Cursor ownership and cleanup: the child runs in its own process group, so its MCP servers die with it: terminate sends SIGTERM to the group, waits 3 s, then SIGKILL. The `agent acp` child ignores stdin EOF, so a killed chat leaves the child alive until a sweep: on chat start (every owner file), on close and on respawn of that id, the pure `worker::sweep_decision` returns `Reclaim` (owner chat dead: kill the group if it is still ours, delete the files, go on at once). The group is ours when the leader pid runs with the recorded start time; a leader pid with another start time is reused and never signalled. When the leader pid is gone, the pure `worker::cursor_group_reclaimable` reads `ps -axo pid=,ppid=,pgid=,command=` rows: the group must have members, and each member whose parent is outside the group must run a command under `cursor-agent/versions/` (its descendants may run anything, such as `tsserver`). `worker::group_live` combines the two, `Wait` (this chat owns it: use the close handoff below) or `Busy` (another live chat owns it: refuse). A close is not refused when the owner is the caller's own chat, found by `worker::caller_owns_worker` on the caller's ancestor pids from `ps -o ppid=`, since chat-mcp runs below claude below `ralph chat`. Quitting `ralph chat` terminates every owned child through its host (see [Headless workers](headless-workers.md)). Cursor permissions: a print worker in `ask` mode enqueues each hook-bridge shell ask on the same per-worker queue and `blocked/<id>` marker, answered with `allow_once` or `deny` (see [headless-workers.md](headless-workers.md#cursor-print-mode)). Codex permissions: `[codex] permissions` (`ask` default, `yolo`) reuses the Cursor queue and `blocked` marker; the person answers through `reply` with `request`, which writes `<store>/codex-answer/<id>`. Details in [headless-workers.md](headless-workers.md#codex-hosting).

Cursor prompts and interrupts: a `reply` with no waiting permission writes one entry per message under `<store>/cursor-prompt/<id>/` (named `worker::prompt_entry_name`, written hidden then renamed). Chat start removes the whole `cursor-interrupt-result/` dir (a killed chat leaves results); close, sweep and spawn remove the id's dir. The chat poll sends the interrupt to `run_turns`, where `worker::PromptQueue` puts it at the front and returns `CancelPermissions` (all pending permissions answered `Cancelled`) and, when a turn is running, `CancelSession` (an ACP `session/cancel` notification). The pending prompt returns `cancelled`; `worker::turn_outcome` maps it (or `end_turn` after an interrupt) to `Cancelled`, which queues no `REPORT_REMINDER`, posts no `blocked` report and sets no `waiting`/`unreported` marker. The interrupt text runs next in the same session. Close and sweep remove `cursor-interrupt/<id>` with `cursor-prompt/<id>`.

Reply confirmation (GUZ-1120): a plain `reply` (no `request`, no `interrupt`, not a permission answer) writes the `sent` marker, then polls every 250 ms (`HANDOFF_POLL`) for up to 5 s (`REPLY_CONFIRM`) and returns one line: `Sent to worker <id>; busy.` (a turn is running), `; reported.` (the `sent` marker is gone), `; taken, not started after <n>s.` (headless only: the prompt entry file was consumed but no turn is running) `; no reaction after <n>s.`, or `Not delivered to worker <id>: it is not running.` (Codex, claude, opencode and Cursor: the host found no live worker for the entry and left a `.<entry>.lost` marker; the probe removes it). Busy and reported stop the poll at once. tmux workers are busy when the pane footer shows `esc to interrupt` or `← N agent` (`worker_check::pane_busy`; a pane change alone is not a signal, because the paste changes the pane); headless workers are busy when `<store>/activity/<id>` says `running`. The pure `worker::uptake` picks the result (lost, then reported, then busy, then taken, then silent) and `worker::delivery_line` words it. Permission answers and interrupts keep their own results. `Workers::nudge` (the monitor thread) does not wait and keeps `Nudged worker <id>.` for headless workers.

Cursor traffic log: every `agent acp` worker appends to `<store>/acp-logs/<id>.log` the JSON-RPC bytes in both directions (lines `<epoch secs> in|out <chunk>`, `in` = ralph to agent) and the agent's stderr (`err`), through `LoggedRead`/`LoggedWrite` around the stdio handed to the connection (`acp_log.rs`). Chunks are raw reads and writes, not one frame per line. When a write would pass 1 MB (`ACP_LOG_CAP`, decided by `worker::rotates`) the file is renamed to `<id>.log.1`, replacing the old one, and a fresh file starts, so at most about 2 MB per worker. The log is appended across respawns and never deleted on close.

Cursor frames: the pure `worker::encode` turns a `WorkerCommand` into an `AcpCall` (`Prompt`, `Cancel`, `PermissionResponse`) that `acp_worker.rs` sends for the prompt, cancel and permission-answer sites; `worker::decode_update` maps the report tool call to `WorkerEvent::Reported`; the prompt-response stop reason stays decoded by `worker::turn_outcome`, because ACP stop reasons do not fit `TurnEnd` without losing `TurnOutcome::Stopped`.

Cursor reporting: a print worker sends the task as its first turn (`WORKER_PROMPT`, a blank line, then the task, as for opencode) without delaying ready. Every harness gets its report rule from `WORKER_PROMPT`: the report text ends with an `assumptions:` line that names each decision the worker made where the task was ambiguous, or `assumptions: none` (GUZ-1215). Each worker has one prompt queue; `worker::turn_outcome` maps each response, and a prompt that errors or ends with anything but `end_turn` or `cancelled` posts a `blocked` report to the inbox. Close sets a closing flag first, so the `cancelled` stop reason posts no `blocked` report. The `session/update` handler sets a per-turn flag when a `tool_call_update` is the `ralph-worker-report: report` tool (`worker::is_report_tool_call`). A turn ending with `end_turn` and no report queues one `REPORT_REMINDER` prompt, and so does a `cancelled` turn that no ralph interrupt asked for (GUZ-953); if that turn also ends without a report, the worker gets `waiting/<id>` and `unreported/<id>`, as a claude-tmux worker does after its Stop hook gives up. The next prompt removes `waiting/<id>`. Worker checks use `Workers::nudge` to queue a `cursor-prompt/<id>/` entry; no pane or tmux attach hint is used.

Cursor resume: a print worker writes `<store>/cursor-session/<id>` (JSON `SessionRecord`: chat id, cwd, inbox, the canonical chat store path as owner, the model, `permissions` the mode) at start and updates the chat id after each turn; a record with `permissions` resumes in print mode with that mode. Only old records with no `permissions`, written by the removed ACP fresh start, resume on `agent acp`. Quitting the chat while an ACP turn runs sends `session/cancel` and waits for that turn to end; `CursorHost::shutdown` stops every worker first, then waits for all of them against one shared 500 ms deadline before it kills the groups, so an agent that never answers is bounded by it. Quitting the chat (and the chat-start sweep of a dead chat's owner file) keeps `ready/<id>`, so the leftover hint lists it at the next chat start; only close removes `ready/<id>`. Quitting the chat keeps a written record; close, a failed start and an unclaimed start remove it. A chat store holds exactly one chat, so the store path is the chat identity. On chat start, after the owner sweep, a background thread resumes each record (`CursorHost::resume_all`): `worker::resume_decision` skips, with a warning, a record with no owner, with another store, or (ACP) when the agent does not advertise `loadSession`; a record whose owner file is still held by a live chat, an unreadable record, or a missing worktree is skipped the same way. An eligible ACP record gets a new `agent acp`, `initialize`, `session/load` (sessionId, cwd, the same MCP server), then `session/set_config_option` when the record stored a model, and no task prompt. While `session/load` runs the `session/update` handler ignores updates, so replayed history never marks a turn reported. A failed load (including an active run) is warned, written to `cursor-error/<id>` and not retried until the next chat start; the record stays.

Opencode harness: `opencode` runs on one `opencode serve --hostname 127.0.0.1 --port <free>` child of `ralph chat`, started for preflight/spawn or supervision of persisted sessions, directly without a shell wrapper (ralph's own environment plus `OPENCODE_PASSWORD`; a missing binary fails at once with "opencode not found on PATH"). It runs in its own process group with basic auth (user `opencode`, a random password in `OPENCODE_PASSWORD`). The chat writes `<temp_dir>/ralph-opencode-<chat pid>.json` (`std::env::temp_dir()`, port, password, chat pid and `ps -o lstart=` start time, the server pid and its start time, mode 0600, written fresh with `create_new`) so the status line can ask `GET /api/session/active`; a read that parses a record whose pid or start time is not this chat's removes it (an unreadable or unparsable file is left alone), and chat start deletes records of dead or pid-reused chats (`worker::server_record_fate`) and first stops the old server process group (SIGTERM, 500 ms, SIGKILL) when the recorded server pid and start time still match (`worker::stale_server_group`; a record without server fields only loses its file). Spawn writes `<store>/opencode-spawn/<id>` (a JSON request with the time) and polls every 250 ms for `<store>/ready/<id>` or `<store>/opencode-error/<id>`, giving up after 30 s. The host's poll thread consumes requests in order: close, answer, prompt, interrupt, preflight, spawn. It drops a spawn request older than 30 s, waits up to 20 s for `/api/info` when starting the server, creates the session with `POST /api/session` (`id` = `ses_ralph<id>`, `location.directory` = the worktree, `model`, `permissions`), writes `<store>/opencode-session/<id>`, posts `WORKER_PROMPT` and the task to `/api/session/<sid>/prompt`, then writes the owner file `<store>/opencode-owner/<id>` and the ready marker.

Opencode turns: session create, prompt posts and permission replies retry up to `TRANSIENT_RETRIES` (2) times, 500 ms apart, on HTTP 404, 408, 429 or 5xx (`transient_request_error`); a turn that fails with a transient status resends its prompt the same way. One `GET /api/event` stream (SSE) feeds the pure `TurnState` for every session; a silent stream is dropped after 45 s and reconnected. After connection/reconnection, `reconcile_all` verifies persisted sessions and repairs state from `/api/session/active`, pending permissions and latest messages. The separate 3-second snapshot tracks process descendants for shutdown, not session reconciliation. `reply` writes prompts under `<store>/opencode-prompt/<id>/` and, with `interrupt: true`, under `<store>/opencode-interrupt/<id>/` (the chat calls `/api/session/<sid>/interrupt` first, synchronously, and writes `cancelled` or `sent` from its `{"interrupted":bool}` reply to `<store>/opencode-interrupt-result/<id>/<entry>`; `Workers::reply` awaits it like Cursor's, up to 30 s, and a failed call leaves the outcome unknown; chat start, spawn and close clear the dir); a reply to a worker with a waiting permission writes `<store>/opencode-answer/<id>` and the chat posts `/api/session/<sid>/permission/<rid>/reply`.

Opencode supervision: a server that dies mid-turn posts a `blocked` report; the supervision loop attempts a restart without waiting for a new request. Chat-owned host shutdown (see [Headless workers](headless-workers.md)) removes the server record, sends SIGTERM to the process group, waits up to 3 s, sends SIGKILL, then kills tracked descendants. Worker close does not stop this server.

Reporting: the worker's `ralph-worker` MCP tool `report` (`status` = `done`, `blocked` or `question`, any other value is a tool error; `text` = full summary) is the only way a worker reaches the chat. After it posts to `<store>/inbox/`, the tool touches the marker `<store>/reported/<id>`; spawn deletes the marker first. Harness hooks never send or build a report; they only stop a worker from going idle without one. Claude's settings file adds a `Stop` hook that runs the hidden `ralph worker-stop-hook --reported <store>/reported/<id> --unreported <store>/unreported/<id>`. It reads the hook input with serde, and the pure `worker::stop_decision` decides: while `background_tasks` is not empty it allows the stop; else if the marker exists it deletes it and allows; else if `stop_hook_active` is false it blocks with `worker::REPORT_REMINDER`; else it gives up and touches the unreported marker, so a worker that still will not report gets one push per stop and no loop; a report or the consume step removes the unreported marker. Malformed input, or input without `stop_hook_active`, lets the worker stop and prints a warning to stderr. Claude permission prompts stay open and wait for the person; the `PermissionRequest` hook only touches `<store>/blocked/<id>` and prints nothing, so it neither allows nor denies. A `Notification` hook with matcher `idle_prompt` deletes `blocked/<id>` and touches `<store>/waiting/<id>` only while `unreported/<id>` exists. A second `Stop` hook deletes `blocked/<id>`. A prompt cancelled with Esc or denied fires no `PostToolUse`, so these two hooks end a stale blocked state; an Esc cancel clears it at the next `idle_prompt` (about 60 s). `UserPromptSubmit` and `PostToolUse` hooks delete `blocked/<id>` and `waiting/<id>`, so new input or an answered prompt ends the wait. The same two hooks write `activity/<id>` as `running`, which also clears `background` and `failed`. The Stop hook gets `--activity <store>/activity/<id>` and writes `background` when `stop_decision` is `AllowBackground` (`worker::stop_activity_state`), else `idle`. A `StopFailure` hook (claude fires it instead of Stop when an API error ended the turn; its output is ignored) writes `failed`. opencode workers get the same reminder and markers from the chat: the SSE turn state (`TurnState`) queues one `REPORT_REMINDER` prompt after a turn that ended without a report, and a second such turn touches `waiting/<id>` and `unreported/<id>`. Sessions are created with the permission rules `allow *` then `deny question` (the last match wins), so tools run without asking and questions are refused; a permission request that still arises is mirrored in `blocked/<id>` and answered with the `reply` tool's `request` argument (the request id) and an `optionId`.

Tmux ownership: `spawn_worker`, `reply` and `close_worker` look up the worker's session by name (`ralph-<project>-<id>`, or the older `ralph-<id>`) and compare its `@ralph_store` tag with this chat's store in the pure `worker::session_owner`. The shell canonicalizes both sides (symlinks resolved) and `worker::same_store` also normalizes lexically (trailing and doubled slashes, `.`, `..`). A session tagged with another store, or untagged, belongs to another chat: spawn, reply and close refuse it; `close_worker` with `force` skips the check. Headless ownership uses the store-local owner/session files described above, not tmux tags.

`close_worker` takes `id`, optional `abandon` and optional `force` (both default false). Like `spawn_worker`, it needs the newest log entry to be from the person. The shell collects the facts (owner, hosting kind, worktree dirty per `git status --porcelain`, `git rev-list --count <base>..worker/<id>`, opencode metadata from the chat's opencode owner or session file, or `<worktree>/opencode.json`), and the pure `worker::close_plan` decides. The base comes from the pure `worker::base_branch`, first non-empty wins: `[chat] worker_base` in the ralph config (read at each close), the branch behind `refs/remotes/origin/HEAD`, then `main`. Close never uses the branch checked out at spawn, so a stale or deleted spawn branch cannot block it. After a successful close it unsets any leftover `branch.worker/<id>.ralphBase` that an earlier version wrote; if that fails, the close still succeeds and its result ends with a warning that gives the `git config --unset` command. A missing config file is normal; a config that fails to read or parse skips `worker_base`, and the close result (success or refusal) ends with a warning naming the config path, the error and the base used instead. It refuses a foreign worker unless `force` is set; it refuses unmerged commits or a dirty worktree unless `abandon` is set. If no session, worktree or branch is left, it clears any remaining markers, otherwise refuses.

The first close step is dispatched by `HarnessId`, not by a Cursor flag or a generic "headless" test:

| Harness | Worker-specific close |
| --- | --- |
| `ClaudeTmux` | `KillSession`: `tmux kill-session` for the owned session, if present |
| `Cursor` | `TerminateCursor`: hand off through `<store>/cursor-close/<id>` to terminate only that worker's ACP process group and remove its files |
| `Opencode` | `RemoveOpencodeSession`: hand off through `<store>/opencode-close/<id>` to interrupt an in-flight turn, delete only that worker's session (`DELETE /api/session/<sid>`, normally `ses_ralph<id>`; HTTP 404 means already gone), evict its worktree location with `DELETE /api/debug/location?location[directory]=<worktree>`, and remove its opencode files and owner |

The headless close handoffs wait up to 30 s for the owner file to vanish. The opencode handoff waits until both the owner file and the session record are gone, so session deletion finishes before worktree removal; on timeout or an error the close stops before removing the worktree. For a non-`Opencode` harness that still has opencode metadata, `close_plan` prepends `RemoveOpencodeSession` before the kind-specific step. An opencode close never kills a tmux session, calls `TerminateCursor`, or shuts down the shared `opencode serve`; other workers keep their sessions.

The common remaining steps, skipping absent resources, are `git worktree remove` (`--force` when dirty and abandoned), `git branch -D worker/<id>`, `git worktree prune`, then clearing the worker's markers (`worker::marker_paths`: `<store>/ready/<id>`, `reported/<id>`, `blocked/<id>`, `waiting/<id>`, `unreported/<id>`, `sent/<id>`, `activity/<id>`, `gone/<id>`), which spawn also clears first. A failed step stops the close and names the step; opencode location-eviction errors only warn. After successful worktree removal, home-directory cleanup runs only for the matching harness: Claude data for `Claude` and `ClaudeTmux`, Cursor data for `Cursor`, neither for `Opencode` (so it never scans `~/.cursor`). Cleanup failures only add warnings; the exact paths and ownership checks are documented in [Worker leftovers](worker-leftovers.md).

At chat start, ids in `<store>/ready/` print one hint line (`chat_status::orphan_hint`) when they are not a discovered running worker (a tmux session, a Cursor worker this chat owns, or an opencode worker), not a Cursor worker whose owner-file chat is alive and whose `agent acp` process group is still the one recorded there (`worker::agent_held`; a dead chat's agent is reclaimed by the sweep, so it is listed), and not a worker that still has a `cursor-session/<id>`, `codex-session/<id>` or `claude-session/<id>` record to resume (`cursor_owner::resumable_ids`). The hint still says "no tmux session" and suggests `close_worker`. Chat never deletes these markers by itself. Cursor workers keep `ready/<id>` across a chat quit or crash; close removes it.

## Skills

Turns run with `--setting-sources project,local`, so `~/.claude/skills` does not load. No skills are bundled. The user names skill directories (each holds a `SKILL.md`, for example `~/.claude/skills/show-me`) and chat exposes them through a plugin.

- Sources, highest first: `--skill <PATH>` (repeatable), `RALPH_CHAT_SKILLS` (`:`-separated, empty entries dropped), `[chat] skills = [...]` in the ralph config. The highest non-empty source replaces the lower ones; lists are not merged. With none set, no `--plugin-dir` is passed and nothing is written.
- A leading `~` or `~/` expands to the home directory. Duplicate paths keep the first. Relative paths are made absolute.
- At start, a path without a readable `SKILL.md` prints one warning and is skipped. Two skills with the same directory name: the first wins, the other warns and is skipped.
- Slash expansion: chat turns wrap the input, so Claude Code never expands a leading `/<name>`. Ralph does it for user turns only (worker messages are never expanded). If the message starts with `/<name>` followed by whitespace or end, and `<name>` is a configured skill, the prompt gets `Base directory for this skill: <dir>`, the `SKILL.md` body without its frontmatter, then the original message. The rest of the message, trimmed, replaces every `$ARGUMENTS` in the body; without that token and with non-empty arguments, an `ARGUMENTS: <args>` line is appended. The store keeps the original message; only the sent prompt is expanded. Unknown names, a bare `/`, and `/name` prefixes that are longer words pass through unchanged. A `disable-model-invocation` frontmatter flag only stops the model from invoking the skill itself; `/<name>` still runs it, and ralph does not warn about it.
- Config is loaded once at start; it supplies both `mcp_servers` and `skills`. On load error chat warns once and uses defaults.
- If at least one skill survives, chat builds a temporary plugin directory (removed when chat exits) with `.claude-plugin/plugin.json` (`{"name": "ralph"}`) and `skills/<name>` as symlinks to the skill directories. Each turn adds `--plugin-dir <dir>`. Skills appear as `ralph:<name>`.
- Skills are read at start: changes to the list need a restart.

## Images

- Ctrl-V (macOS only) runs `osascript` to write the clipboard as PNG to `<store>/attachments/.clipboard-<pid>.tmp`, then `attachment::parse_image` checks it. A valid image is renamed to `<sha256>.<ext>` (same image, same file; nothing is ever deleted) and `[Image #N: <absolute path>]` is inserted at the cursor. On send the image is drawn under the message (see [Rendering images](#rendering-images)). `N` is one above the largest `[Image #N:` already in the draft (`attachment::next_number`), else 1. No image on the clipboard prints `No image on the clipboard.`; a bad image prints `Image paste failed: <error>` and removes the temp file.
- Limits: 10 MiB per image (`MAX_IMAGE_BYTES`); PNG, JPEG, GIF or WebP by magic bytes (the clipboard script always asks for PNG). No paste on Linux or Windows; a path typed by hand works the same way.
- The placeholder is plain text: `log.jsonl`, history and memory hold only the text with the path, never the image bytes. Claude reads the image itself with its Read tool when it sees the path. Chat creates `<store>/attachments` at start and each turn passes `--add-dir <store>/attachments` (`build_attachments_args`), so a store outside the working directory still reads without a prompt.
- Workers: placeholders in `spawn_worker` task or `reply` text pass through unchanged. Claude workers get `--add-dir <store>/attachments`; opencode workers get `permission.external_directory` for `<store>/attachments/**` (see [MCP tools](#mcp-tools)).

### Rendering images

Local PNG, JPEG, GIF and WebP images in agent replies and in `!shell` cell output draw inline through the Kitty graphics protocol. Pure logic is in `ralph_core::kitty`; file reads and terminal detection are in `crates/ralph/src/render/image.rs`.

- What renders: a markdown `![alt](path)` in reply prose or in the message shown after a `!shell` cell, where `path` is absolute, `~/` or relative to the working directory. `http(s)`, `data:` and other URL schemes stay text. Markers inside fenced code blocks and inline code spans are ignored. Raw Kitty graphics sequences (`ESC _ G ... ESC \`) in cell output pass through to the terminal on display under Kitty directly; under tmux they are stripped.
- Detection, once at chat start: stdin and stdout must be terminals. Without `TMUX`, ralph sends a Kitty graphics query plus a device-attributes query with echo and line buffering off and waits up to 200 ms; images draw only if the terminal answers OK before the device-attributes reply. In tmux, ralph first runs `tmux display -p -t $TMUX_PANE '#{allow-passthrough}'` (null stdin, about 300 ms timeout). Only `on` or `all` continues: ralph sends the query wrapped in DCS passthrough (`ESC P tmux;` with each ESC doubled) followed by `ESC[5n`, and `ESC[0n` is the end marker. `off`, an unknown value, a failed probe or a missing `TMUX_PANE` means no query, no delay, text fallback. Limits: keys typed during the check are dropped, and a reply arriving after the timeout can leak into the prompt. With color off (`NO_COLOR` set or stdout not a terminal) no image is drawn and the query is skipped (no delay): reply markers print as plain markdown text. `ralph ask` and pipes never render images.
- tmux drawing: each image gets an id (1 to 255), is sent as `U=1` virtual chunks wrapped one by one, and is shown as rows of U+10EEEE placeholder cells colored with the id (256-colour foreground) and row/column diacritics. Image size is capped to 297 rows and 297 columns (diacritics table).
- PNG passes through (signature and IHDR checked); JPEG, GIF and WebP are decoded (see Formats). At most 10 MB per file.
- Sizing: columns are the image width in cells (pixel width over the cell pixel width from `window_size()`), capped at the wrap width and at least 1; rows keep the aspect ratio. Rows are capped at the terminal height; a clamped image gets fewer columns to keep the aspect ratio (at least 1). When the terminal reports no pixel size, ralph assumes an 8x16 px cell (1:2). Both `c` and `r` are always sent.
- Formats: PNG is sent as is (`f=100`). JPEG, GIF and WebP are decoded to RGBA (RGB for opaque WebP); a long side over 2048 px is box-averaged down to 2048 (aspect kept, alpha-weighted); then the pixels are zlib-compressed and sent as `f=32` or `f=24` with `o=z`. GIF animations use native Kitty frames, composed as full canvases with disposal and delays (minimum 10 ms). Over 128 frames or 16,777,216 total unscaled canvas pixels, or for a single frame, GIF uses the existing first-frame path. Header pixel caps before decoding: 25,165,824 for JPEG and GIF, 6,291,456 for WebP; over the cap falls back to text. Known limits: EXIF orientation is ignored, WebP draws the first frame only, GIF fallback uses the frame size, and decoder panics are not caught.
- Fallback: an unsupported, oversize, missing or unreadable file prints `[image: alt (path)]` and a line end. An image marker's own line end is dropped, so each image takes its rows plus the path line and each fallback takes one line. On an unsupported terminal (or in `ralph ask`) markers are not parsed: the `![alt](path)` text goes to the normal markdown renderer.
- Path line: after each drawn image (direct or tmux, reply or attachment) `draw_image` prints one dim line (`ralph_core::file_link::path_line`) with the image's absolute path: `~/` and relative paths expanded and symlinks resolved (`canonicalize`, else `std::path::absolute`). The visible text is the plain path through the shared `schedule::escape_controls`: control characters show as `\n`, `\r`, `\t` or `\xHH`, and bidi and format characters (U+200B to U+200F, U+202A to U+202E, U+2066 to U+2069, U+FEFF) show as `\u{XXXX}`, so a file name cannot inject terminal sequences or reorder the text. A non-UTF-8 file name shows replacement characters, while the link keeps the real bytes. A path that is not absolute prints dim with no link. An OSC 8 hyperlink wraps it (`ESC ]8;;file:///<path> ESC \`, empty host, ST terminators, bytes other than `A-Z a-z 0-9 - . _ ~ /` percent-encoded), so a terminal with OSC 8 support opens the file in its default app and other terminals show plain text. The link bytes are not part of any width or wrap calculation: image output goes around the prose wrapper. In tmux the link is sent raw (no DCS passthrough); tmux forwards it only when the outer terminal has the `hyperlinks` feature (for example `set -as terminal-features ',*:hyperlinks'`), else the plain path shows. Over ssh or Rex the path names a file on the remote machine, so a local click can open nothing or a different file. The fallback `[image: alt (path)]` gets no path line and no link.
- Attachments: each `[Image #N: path]` in a sent message is drawn below the echoed message with the same placement and sizing rules (`render_attachments`, paths from `attachment::attachment_paths`). A path that cannot be drawn (missing, unsupported, over 10 MB) prints nothing extra. The sent text is unchanged.
- Model copy: `build_message` strips Kitty graphics sequences from cell output before trimming, so image bytes never reach Claude, `log.jsonl` or memory.
- Known limits: Ctrl-L or any clear-screen erases drawn images and they are not redrawn. Reedline issue #1237 misplaces the prompt after image output, so each image is sent with `C=1` (cursor does not move) and ralph prints exactly `r` newlines. A marker split across streamed chunks, a marker inside inline code or a fenced block, and a marker in a tmux pane hidden after chat start draw nothing and print no `[image: alt (path)]` fallback, even though the system prompt tells the model not to add caveats; this is accepted. Raw Kitty sequences in cell output render in place inside the `result` block (one opening and one closing fence); ralph adds a line end after the final chunk (no `m=1`) when none follows and relies on the terminal's default cursor move, so a sequence using `C=1` from a cell may overlap later text.
- tmux limits: `allow-passthrough on` passes data only while the pane is visible; a hidden pane at chat start gives text fallback. Outer replies go to the active pane: a non-active ralph pane may get no reply, and another pane may receive reply bytes. Multiple attached clients are untested. Shared image IDs cycle 1 to 255 and are deleted on reuse, so older placements can disappear when the 256th image reuses id 1. An OK reply does not prove placeholder support: a terminal that answers OK but lacks placeholders shows blank cells. Kitty may evict old images at its storage quota, leaving blank placeholder cells.

## Storage and isolation

- Global store `~/.ralph/chat`: `log.jsonl`, `tree.jsonl`, `log.idx`, `tree.idx`, `LOCK`, `NAP`, `TAG`, `tags.jsonl`, `history.txt`, `editor.md`, `suggestions.jsonl`, `analytics/timing.jsonl` ([timing log](#timing-log)), `attachments/`, and an optional `config.toml` that overrides the global config per key for chats using this store (see [configuration](../configuration.md#configuration-precedence)). A store `config.toml` that fails to load falls back to the global config with a warning, and setting a security-relevant key warns once; details are in [configuration](../configuration.md). It is not project-scoped.
- `LOCK` is a file lock: exclusive for append and for each nap commit, shared for settled load and the nap snapshot. `NAP` is an exclusive file lock held for the whole nap; `napping()` probes it. Store paths that are symlinks or multiply-linked files are rejected.
- Isolation: `--setting-sources project,local` plus a `claudeMdExcludes` entry for `~/.claude/CLAUDE.md` when the home directory is known. Chat turns can change this with `[chat]` keys (`Isolation::for_chat`): `user_settings = true` uses `user,project,local`; `user_claude_md = true` drops the home entry; `project_claude_md = false` adds `CLAUDE.md`, `CLAUDE.local.md` and `.claude/CLAUDE.md` of the chat process directory (not ancestors). The key is left out when the list is empty. The curator keeps the default. Project and local settings stay active; this is context isolation, not a sandbox. With `[claude] config_dir` set, the `CLAUDE.md` entry uses that folder and the command gets a `CLAUDE_CONFIG_DIR='<dir>'` prefix (turns, nap and `ralph ask`).
- User agents in `~/.claude/agents` do not load, so `build_agents_args` passes the bundled `SUBAGENTS` (`evidence-collector` haiku, `implementer` sonnet, `reviser` opus) as `--agents <json>`. These copies may drift from `~/.claude/agents`.
- Turns and claude-tmux workers run with the chat's resolved permission mode (default `auto`). The chat process adds `--permission-mode <MODE>` to each claude-tmux worker command, so chat and workers never differ. opencode workers ignore it.

## Usage

Every Claude call that returns usage (each turn, including failed, cancelled, interrupted and timed-out ones whose `result` line arrived, each keepalive ping that exits, and the final attempt of each nap or `ralph thread merge` curator call (one per memory node during a nap), including a timed-out or interrupted one whose `result` line arrived; `retry_on_outage` drops the earlier outage attempts) appends one line to the global `<config dir>/usage.jsonl` (the platform config dir plus `ralph`, or `$RALPH_CONFIG_DIR`), shared by all stores; older per-store `usage.jsonl` files are no longer read or written. Each line is one `write_all` on an `O_APPEND` file: `{at, kind, trigger, input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens, cost_usd, duration_ms, context_tokens, harness, model, session_id, cost_source, reasoning_tokens, cache_write_5m, cache_write_1h}`, where the last three come from the `result` line's `usage.output_tokens_details.thinking_tokens` and `usage.cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` (absent when claude omits them; a tier is never guessed), and `harness` is `claude`, `model` and `session_id` come from the stream init event (claude 2.1.318 emits it with the first turn of each process, not at launch: in a measured probe no init line came before the first user line; ralph carries them to later turns of the same process; absent when no init was seen), `cost_source` is `harness` when `cost_usd` is set, and `context_tokens` is input + cache read + cache creation tokens of the last assistant message (absent when none carried usage), with `kind` `turn`, `ping`, `nap`, `merge` (one `ralph thread merge` curator call; same fields as nap, without `run`), `ask` or `subagent`, and `trigger` (turn only) `user` or `worker`. `cost_usd` is the running total of the claude process, not a per-call cost. Turn lines also carry `process_turn` (the turn number on the claude process, 1 on a launch), `request_at` (RFC 3339 time of the last main-thread assistant event of the turn; subagent events are skipped) and `reset` (`tokens`, `turns` or `restart`, on the line of the turn that launched the process after a reset only; the first launch of a ralph run has none) and `run` (`<pid>-<start RFC 3339>` of the `ralph chat` run that wrote the line; the status bar sums only lines with its own `run`, so two chats on one store do not mix, and older lines without `run` are ignored; it reads only lines appended after the chat started, see the `UsageTail` note under the status line). `process_turn` counts only turns where a claude process ran; a failed spawn leaves it unchanged. A policy reset gives `tokens` or `turns`; a crash, failed turn, cancel, stale relaunch or a process that died while idle gives `restart`. Ping lines carry `run`, `request_at`, and the same `harness`, `model`, `session_id` and `cost_source` as turn lines (model and session id are the ones the turn shell carries for the live process), but no `process_turn`, `reset` or view fields, so they join the process of the turn before them. The shell updates this identity after every turn, including a failed, cancelled or interrupted one (`turn_metadata` takes the partial metadata of a timeout or interrupt, and none otherwise), so a launch that fails clears the old process's `session_id` and `model` before the next ping. The keepalive thread writes the ping line to the global record before it releases the session lock, so no turn line lands ahead of it; a failed write shows one warning on stderr. Every row also carries `store`, the canonical path of the chat store that wrote it (symlinks and `..` resolved, the same string in every row kind: turn, nap, ping and worker; older rows may hold the path as given, and rows from before `store` existed lack it). Nap lines carry `run` (the chat run that spawned the nap, passed as `chat-nap --run`) and `store`, and none of `process_turn`, `request_at`, `reset` or the view fields. On the first turn of each process, turn lines also carry `view_bytes`, `view_lines`, `view_head_hash` (FNV-1a 64 of the first 1024 bytes of the rendered view) and `view_hash` (of the whole view), to trace prompt-cache misses. Every turn, ping, nap, merge and ask call also appends one `subagent` line per model for the claude usage that is not the main loop of that call: Task subagents, compaction and other internal calls (`subagent_records`). The source is the `result` line's `modelUsage`, a running total per claude process for every model it called. `Session` holds the previous value per process, and turns and pings both advance it (`model_usage_since`), so each call sees only its own delta; one-shot processes start from zero. For the main model, the call's own top-level `usage` (the main loop) is taken off the delta, so no token is priced twice; a model with nothing left writes no line. A subagent line has `kind` and `role` `subagent`, `harness` `claude`, the model from the `modelUsage` key, the call's `session_id`, `run` and `store` (none on ask lines), the 5m and 1h write tiers and `reasoning_tokens` from `thinkingTokens`, and no `cost_usd`. The main model is matched to its key by exact name; if claude ever names it differently, its main loop would be counted twice. The undocumented `model_usage_since_last_result` is not read. Calls without usage data append nothing. The turn shell writes the line before it handles the cancel or exit, from the result or the partial result of a timeout or interrupt. Exits that still lose a line: a cancel or Ctrl-C where no `result` line arrives within the 3 s interrupt grace (ralph kills the process), a process killed by a signal, a spawn failure, a stale or leftover-result session (no usage), a `ralph chat` that is itself killed (tmux close, crash), and a nap or curator call that fails with no `result` line. Appends do not take `LOCK`. Total cost (turns and pings), from the last line of each process (a process starts at `process_turn` 1):

Every row has a `role` key: `main` for a turn or a ping, `nap`, `tag` (a tag pass call), `merge`, `worker`, or `ask` (one row for each `ralph ask` call that reports usage, with no `store` and no `run`). The `role` follows from `kind` and cannot differ from it. Every row is built as a `LedgerRow` (`ralph_core::chat_memory`) whose fields are private, and is written only through `ledger::record` (`crates/ralph_server/src/ledger.rs`).

```bash
jq -s '[.[] | select((.kind == "turn" and .process_turn != null) or .kind == "ping")] | group_by(.run) | map(reduce .[] as $t ([]; if $t.process_turn == 1 or length == 0 then . + [$t.cost_usd // 0] else .[-1] = ($t.cost_usd // .[-1]) end) | add) | add' <config dir>/usage.jsonl
```

### Timing log

`<store>/analytics/timing.jsonl` holds one JSON line per timing event, next to `analytics/workers.jsonl`. `usage.jsonl` and `workers.jsonl` are unchanged. Every row has `v` (1), `at` (RFC 3339), `store` (the canonical store path, as in usage rows), `event`, and `run` (the same `<pid>-<start RFC 3339>` id the usage rows carry; absent when the writer has none). A reader must ignore fields it does not know. Optional fields are left out when empty.

- `turn`: one row per chat turn, written when the turn ends. `turn_ms` (start to end), `memory_wait_ms` (time blocked in `load_after_nap`, so it includes the wait for a running nap or a reset or launch on process start; summed over relaunches in the turn), `outage_wait_ms` and `outage_retries` (the sleeps of `retry_on_outage`, counted in its `wait` closure), `model_ms` (the `duration_ms` of the turn's usage row; absent when the turn wrote none), `ok` (true only for a turn that got a reply; failed, cancelled and exited turns write `ok:false`).
- `nap`: one row per nap, written when it ends. `total_ms`, `pending_at_start` (nodes waiting when the nap took its snapshot), `calls` (curator calls), `lock_held_ms` (time holding the `NAP` lock) and `nap_lock_wait_ms` (time waiting to get it).
- `nap_call`: one row per curator call of a nap, including calls that wrote no usage row. `node` (the node id, `lo` or `lo-hi`), `attempt` (1-based, up to `MAX_NAP_ATTEMPTS`), `duration_ms`, `outcome` (`ok`, `rejected` when `check_summary` refused the reply, `failed`, or `timeout`) and `exit` (the process exit code when known).

Writes are best effort: an I/O error shows one warning and never fails a turn or a nap. Rows are one `write_all` on an `O_APPEND` file opened with `O_NOFOLLOW`, with no `LOCK`. `ralph thread merge` and keepalive pings write no timing rows. Limit: an `outage_retry` outcome is not written; a call's retries inside one curator run show only in the usage rows and the final outcome.

### Claude worker usage

A claude-tmux worker's Stop hook (`ralph worker-stop-hook`, given `--worker`, `--usage` and `--usage-seen`) also appends rows to the chat's `usage.jsonl`, so the tokens outlive `close_worker`. It reads `session_id` and `transcript_path` from the hook input, then the main transcript and `<transcript without .jsonl>/subagents/agent-*.jsonl`. The pure `ralph_core::worker::transcript_usage` keeps the last line of each `message.id` (earlier lines carry partial output counts), skips messages with a null `stop_reason` (a later Stop picks them up) and ids already listed in `<store>/workers/<id>.usage-seen`, and sums the rest per model and prompt tier with the wire Anthropic mapping (`map_usage`). A message with model `<synthetic>` or with all token counts zero gives no row, but its id is still marked seen. Each model and tier becomes one line with `kind` `worker`, `worker_id`, `turn_id` (the worker snapshot turn of that Stop; absent without snapshots), `harness` `claude`, `model`, `session_id`, the four token counts, `reasoning_tokens` (thinking tokens, raw), `cache_write_5m`, `cache_write_1h` and `long_prompt` (true when the calls in the row are above the model's long prompt tier); `cost_usd` and `duration_ms` are null. Worker lines carry `store` (the hook's `--store`, when given) and no `run`, so the status bar skips them. The hook command also carries an optional `--config-store <path>` (needs `--store`): the chat's store path as written, not symlink-resolved. The hook uses it only for the store config layer (`set_store_layer`) and falls back to `--store` when it is absent, so hooks in older settings files still work. `--store` stays the canonical path for the usage key, worker ownership and snapshots. A failure only warns and never changes the Stop decision. `close_worker` removes the `.usage-seen` file. `--usage` is the chat's `usage.jsonl`, resolved at spawn so rows do not depend on the tmux server environment (such as `RALPH_CONFIG_DIR`). The spawn makes the path absolute against the chat's working directory. A settings file without it falls back to `usage_path()`. Duplicate rows are possible in three cases: a lost `.usage-seen` file recounts every message, an append that fails partway repeats rows on the next Stop, and a seen-file write that fails after the appends does the same. Limit: a turn cut off by `close_worker` before its Stop is not recorded. A claude worker writes the same rows from its session transcript with `harness` `claude`, at each turn end, at claude exit and at close (see headless-workers.md).

A yolo cursor worker appends one row per `agent -p` result with `harness` `cursor` and `cost_usd` null (see [headless-workers.md](headless-workers.md#cursor-print-mode)).

A codex worker appends the same kind of rows with `harness` `codex` and `session_id` the codex thread id (`crates/ralph_server/src/codex_usage.rs`). There is no seen-file. The pure `ralph_core::worker::TurnUsage` counts each `thread/tokenUsage/updated` event as its thread `total` minus the last `total` seen on that thread (per field, saturating at 0), and sums those per model and prompt tier; codex re-sends an unchanged `last` on rate-limit updates, a full context window and resume replay, so summing `last` would count calls twice. With no earlier `total` (the first event after the thread starts or resumes) it counts `last`; an event without both breakdowns is ignored. A usage event counts when its `turnId` is the bound turn or the turn this worker process bound just before it (`Turns::owns_event`). A turn stays bound after it ends until the next turn starts, and the previous id stays accepted for one more turn, so usage that arrives after `turn/completed` (also when a queued prompt or the report reminder starts at once) goes into the next flush. Every other event (no bound turn yet, an older or unknown `turnId`, no `turnId`, the resume replay, whose turn was not bound in this process) moves the `total` baseline but adds nothing. A `model/rerouted` counts only for the bound turn, or with no `turnId` while a turn is bound; it switches the model for later calls of that turn, and each turn start resets the model to the thread model. `input_tokens` is `inputTokens` minus `cachedInputTokens` and `cacheWriteInputTokens` (saturating at 0; codex counts both inside input), `cache_read_input_tokens` is `cachedInputTokens`, `cache_creation_input_tokens` is `cacheWriteInputTokens` (older codex versions may omit it, and then it reads as 0), `output_tokens` is `outputTokens` and `reasoning_tokens` is `reasoningOutputTokens`. Rows are written once, on `turn/completed` of any status, or when the worker closes or its app-server exits while the turn is still open; the accumulator is emptied when its rows are taken, so none is written twice, and a model whose counts are all zero gives no row. `turn_id` is the worker snapshot turn (absent without snapshots, closing or exit). `cost_usd` is null. `/workers costs` and `ralph usage` keep codex dollars out of their totals and show `excluded` (GUZ-1550; see [/workers costs](#workers-costs)). Without a model the row model is `unknown`.

### ralph usage

`ralph usage` reads `<config_dir>/usage.jsonl` and prints cost reports. It never writes the ledger, calls no model and costs $0. The core is `crates/core/src/worker_costs/usage_report/` (pure: parse, filter, group, text, SVG charts); the shell is `crates/ralph/src/usage_cmd.rs`. It shares its grouping with the `/workers costs` views.

- Views: `ralph usage` or `ralph usage daily` (one row per local day, each as `2026-11-05 Thu`, a trend line, a total row), `ralph usage by <kind|store|harness|model|ticket|run>`, and `ralph usage cache` (hit rate per model).
- Money has two series. Reported dollars come from the harness (`cost_usd`). `est.` dollars are priced from tokens with the `ralph wire` table and `[wire.prices]` overrides. A group can show both: `$X + $Y est.`.
- A total is a lower bound when some rows have no price. Text reads `+ no price`; a daily chart bar reads `$X*` with the legend `* = some rows have no price`; a bar chart value reads `+ no price` too. A group where nothing has a price reads `name: no price`, never `$0`.
- Other states read `name: state`: `excluded` (codex, GUZ-1550: tokens count, dollars do not), `no data` (a cursor worker has no usage rows) and `no price`. A row with no model groups under `(model missing)`. A ticket of `unknown` is spend with no worker window: chat turns, naps and asks.
- Tickets come from the workers log. With no `--store`, the shell reads the workers log of every `store` found in the ledger rows (a missing log is skipped). `--store DIR` reads only that store's rows and log. Two stores that reuse a worker id at overlapping times can join to the wrong ticket.
- Token columns: `in` counts only uncached input; cache reads and writes are separate (see `usage cache`). `out` is output tokens.
- Filters (global, before or after the view): `--since` and `--until` (a local day or an RFC 3339 time; `--since` inclusive, `--until` exclusive), `--store`, `--harness`, `--model`, `--ticket`, `--kind`. Days are local days.
- A line that is not JSON, or has a missing or unreadable `at`, is skipped and counted: `malformed lines skipped: N`.
- Output: `--text` forces text. `--png <PATH>` renders the chart (daily bars with the weekday over the date on the x axis, or horizontal bars for `by`) with the bundled resvg and prints `Wrote <PATH>`. With neither flag, a terminal that can draw images (the same detection as chat images) shows the chart inline; anything else gets text. The two flags conflict. `usage cache --png` is an error (`the cache view has no chart`, exit 1, no file); `usage cache` on a terminal prints text.
- The legend `? = day with rows but no price` under the trend line appears only when the trend shows a `?`.
- Not covered: the legacy per-store ledger. Keepalive `ping` rows are counted under `main`; whether pings pay off is GUZ-1549.

## Auto-continue

A turn that ends on an API error leaves the worker idle with `activity/<id>` set to `failed`: the claude `StopFailure` hook writes it, and the headless harnesses write it when a turn ends in error (see Heartbeat above). With `[chat] auto_continue` on (the default), the worker check tick runs the pure `worker_stall::stall_action` over each running worker:

- busy (`running` or `background`) or no activity marker: nothing.
- a report since the last go-ahead: nothing, and the record `<store>/auto-continued/<id>` is deleted. A report counts when `sent/<id>` is absent (the `report` tool deletes it) or when the newest report of the worker (any of done, blocked or question, read from the inbox the monitor already tracks) is not older than the `sent/<id>` modification time (`worker_stall::reported_since_go_ahead`). The second rule covers the headless harnesses (codex, claude headless): a failed turn there posts a `blocked` failure report through the inbox and never deletes `sent/<id>`, so the person already has a report and decides; ralph does not send a second message. Auto-continue therefore acts on harnesses whose failed turn leaves no report, in practice Claude tmux through `StopFailure`.
- idle with `failed`, no record, and the failed mark not older than the `sent/<id>` modification time (the latest go-ahead; no `sent/<id>` allows it): `Continue`. A failure from before the latest go-ahead gets no continue. The shell checks again that the decision still holds, sends `CONTINUE_TEXT` ("Your last turn ended on an API error. Continue: start with git status, then follow the same rules as the last go-ahead.") through `Workers::nudge`. The shell writes the record `{at, reason, alerted}` first and the write result gates the send (`worker_stall::gate_send`): when the write fails the shell sends nothing and warns once per worker per failure streak (the streak ends at the next good write), so an unwritable `auto-continued/` cannot cause a send on every check. When the write works it sends; after a sent nudge it appends `{at, worker, harness, reason}` to `<store>/auto-continue.jsonl`, and after a failed send it removes the record (`worker_stall::after_send`). The record comes first so a crash or a fast failure between the send and the write cannot send a second continue.
- a record exists, not alerted, and the activity mark is newer than the record (the worker acted since the continue) and is idle or failed again: `Alert`. The same `Alert` fires when no newer mark appears within a grace of two check intervals (`worker_stall::grace_secs`) after the record, so a continue that was sent but never picked up (for example a rate-limit menu that swallows the keys) is reported once. A mark in the same second as the record counts as not newer; the grace covers it. The shell posts one `check` item, `Worker <id> is still idle with no report after one auto-continue.` plus `To look: tmux attach -t <session>` for tmux workers only, and sets `alerted`.
- an alerted record: nothing until a report deletes it or the worker closes (close deletes it).

Both files live in the store, so the state survives a chat restart. One continue per go-ahead: a new report resets it, and so does a go-ahead newer than the record (`sent/<id>` modification time strictly greater than the record's `at`): the action is `ResetRecord`, the shell deletes the record, and a later failure gets its one continue again. Ralph's own continue must not count: it writes the record, then `Workers::nudge` writes `sent/<id>` (later or in the same second), so after a sent nudge the shell rewrites the record with the current time (`ContinueStep::StampRecord`, before the log line), which is never earlier than that `sent/<id>`. The `You stopped without calling report` nudge for a worker that stopped without reporting is separate and unchanged. With `auto_continue` on, the pane check never posts the `can't tell what worker is waiting on` item for a tmux worker idle with `failed`: the continue and then the stall alert own that case. With `auto_continue` off the `can't tell` item posts as before.
