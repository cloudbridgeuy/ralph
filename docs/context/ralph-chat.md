# ralph chat Command

`ralph chat` is a single long-running chat with one persistent memory. Every message is a fresh, isolated `claude -p` turn. The model sees a compressed view of the whole chat and can open details through a private MCP server. Bare `ralph` (no subcommand) runs `ralph chat`.

## CLI

```bash
ralph chat [--timeout 600] [--skill <PATH>]... [--permission-mode <MODE>] [--worktree-dir <DIR>] [--no-inbox-sound] [--no-inbox-notification]
ralph                      # same as ralph chat with defaults
```

- `--timeout <secs>` per turn, default 600 (`CHAT_TIMEOUT_SECS`).
- `--skill <PATH>` (repeatable) adds a skill directory. See Skills.
- `--permission-mode <MODE>` sets the claude permission mode for turns and claude workers. Precedence: flag, `RALPH_CHAT_PERMISSION_MODE`, `[chat] permission_mode` in the ralph config, then `auto`. Resolved once at chat start. `ralph ask` has its own setting.
- `--worktree-dir <DIR>` sets where spawned workers get their worktrees. Precedence: flag, `RALPH_WORKTREE_DIR`, `[chat] worktree_dir`, then `.worktrees`. A leading `~` expands to home; a relative path resolves against the repo root of each spawn, not the chat's cwd. The chat process resolves the rest on each spawn and close.
- `--wrap-width <N>` caps the wrap width of rendered replies, worker reports and the prompt area (status line, draft, footer). Precedence: flag, `RALPH_WRAP_WIDTH`, `[chat] wrap_width`; `0` or unset = terminal width. The smaller of the cap and the terminal width wins, read at each render. A value that is not a whole number stops chat start with an error. See [configuration](../configuration.md).
- `--no-inbox-sound` and `--no-inbox-notification` turn off the inbox alert parts (see Inbox alerts).
- `--store <DIR>` sets the store path. Precedence: `--store`, then `RALPH_CHAT_STORE`, then `~/.ralph/chat`; an empty `RALPH_CHAT_STORE` counts as unset, and a missing home directory is an error when neither is set. A relative path resolves against the cwd at startup. The directory is created at startup. Parallel chat instances need separate stores; otherwise they share the log, `history.txt`, `editor.md`, `mcp.json`, and `inbox/`.
- Hidden subcommands: `ralph chat-mcp --store <DIR> --socket <PATH>` and `ralph chat-nap --store <DIR> [--timeout 600]`. Both are spawned by ralph itself.
- Input is a reedline editor on the main thread with prompt `>>> `. Enter sends; Alt-Enter or Ctrl-J inserts a newline; Ctrl-G opens `[chat] editor` (an argv list such as `["nvim", "-c", "normal! Go", "-c", "startinsert"]`; the file path is appended as the last arg; an empty list warns and falls back), else `$VISUAL`, `$EDITOR`, or `vi` (one program, no splitting), on `<store>/editor.md`, prefilled with the last assistant reply, a `──── write below ────` line, and the draft; the text below the last separator line replaces the draft (never sent; an empty result keeps the old draft). Ctrl-V pastes a clipboard image as `[Image #N: path]` (see [Images](#images)). Esc Esc clears the whole draft (Ctrl-Z undoes it, Ctrl-O redoes). With `[chat] edit_mode = "vi"` the editor uses reedline's vi insert and normal keymaps: Esc leaves insert mode, so Esc Esc does not clear; Ctrl-U clears the whole draft in insert and normal mode instead. The insert keymap keeps Alt-Enter, Ctrl-J, Ctrl-V, Ctrl-G and Ctrl-O; normal mode keeps Ctrl-G. Visual mode is off: when a key (`v`) enters it, the edit-mode wrapper switches straight back to normal mode before reedline paints, so no selection starts; `fv`, `tv` and `rv` still work. The prompt indicator is `>>> ` in insert mode and `::: ` in normal mode. The pure `chat_edit_mode` core module resolves the key and the indicator. Up/Down and Ctrl-R use the history file `<store>/history.txt` (1000 entries). Ctrl-D or Ctrl-C at the prompt quits; an empty message does nothing unless reports are unread (see Worker inbox). Ctrl-C during a turn cancels that turn (nothing is stored) and returns to the prompt with the message restored as the draft; SIGTERM and SIGHUP end the chat. While a turn runs, chat keeps a `<store>/turn` marker (`user` or `worker`, removed when the turn ends); the chat socket server reads it so `spawn_worker`, `close_worker` and `watch` work only in a user-started turn (`reply` also in a worker turn).
- A dark-gray full-width rule (the shared termimad skin's `---`, default gray(6) `―`) prints before the turn and after the reply.

## Turn loop

1. `Store::load_settled` takes the `LOCK` (blocking until any running nap finishes), then reads log and tree.
2. `frozen_block(entries, tree, VIEW_LINES, FROZEN_WINDOW, pinned)` and `tail_lines` build the memory view in two parts. `VIEW_LINES` is 200 lines total; `FROZEN_WINDOW` is 32 entries by default. The frozen part is the view of the first `entries / window * window` entries with budget `200 - window`; the chat process pins it and rebuilds only when the entry count crosses a multiple of the window, even if nap summaries land mid-window, so it stays byte-identical for the whole window (default 32 entries) and the prompt cache hits it. The tail is one line per entry after that point. The window comes from `--frozen-window <N>`, else `[chat] frozen_window` in the ralph config, else 32; valid values are 1 to 199, anything else fails chat start with an error.
3. For a worker turn, one `worker` entry per report is appended to the log. The user message waits for step 6.
4. `build_chat_command` runs a fresh `claude --verbose --permission-mode <MODE>` (the chat's resolved mode) with isolation args, `--append-system-prompt <SYSTEM_PROMPT + frozen block>` (`turn_system_prompt`; just `SYSTEM_PROMPT` while the frozen part is empty), the MCP args, `--output-format stream-json`, and `-p <prompt>`. There is no `--resume` and no `--agent`. The prompt is the tail lines, a blank line, `New message:`, then the message. Only tail lines precede the message; no task text follows it.
5. Output goes through the spinner subprocess runner and `StreamProcessor`, as in `ralph ask`.
6. On exit code 0 with response text, the user message (if any) and then the reply are appended verbatim and a detached `ralph chat-nap` is spawned (stdio null; spawn failure only warns). Otherwise a warning `chat turn failed (exit N)` prints and the loop continues.
7. A turn that is cancelled (Ctrl-C), times out, fails, or hits a subprocess error stores nothing for a user message, including any partial reply, and returns to the prompt with the message preloaded as the draft (`draft_after`). Worker report entries from step 3 stay in the log. SIGTERM and SIGHUP end the chat.

### /private

`/private <message>` sends one turn that is never stored. The prompt and the reply render like a normal turn (spinner, markdown, footer). `/private` with no text, or only whitespace, prints `Usage: /private <message>` and sends nothing; `/privatefoo` is a normal message. The pure `route_input` returns `Route::Private` or `Route::PrivateUsage`.

- The turn gets the same memory view as a normal turn (same frozen block, so the prompt cache still hits), but the message and the reply are never appended to `log.jsonl`: `trigger_entries` and `reply_entries` return nothing for `Trigger::Private`. No nap starts, so nothing reaches `zoom`, `recall` or the view of later turns. There is no `--resume`, so the next turn carries no trace of it.
- The pending-turn marker is `private`. `command_allowed` refuses every worker and watch tool in that turn; `zoom` and `recall` stay read-only. A private turn cannot write memory or direct workers.
- Cancel, timeout and error behave as in a normal turn: nothing is stored and the draft returns as `/private <message>`.
- The line never goes to `history.txt` (the input history), and up-arrow does not recall it in the same session. The pure `chat_status::keep_in_history` refuses `/private` lines (same parse as `route_input`, so `/privatex` is kept); the `ChatHistory` wrapper in `chat/editor.rs` drops them before `FileBackedHistory` sees them.
- `usage.jsonl` gets the cost and token numbers with `"trigger":"private"`, and no text.

`SYSTEM_PROMPT` tells the model that the message starts with the compressed chat, that `#<id>` lines are summaries, to use `zoom` and `recall` before guessing or asking, that `[worker ...]` messages come from workers, not the person, and never to claim manual saving. On a worker message the model may `reply` only with an answer already settled in the chat (a decision the person made, approved scope, a step in an agreed plan); merges, pushes, PRs, Linear status changes, new scope and anything public go to the person, and every worker reply is listed in its next message to the person. `spawn_worker` and `close_worker` are only for what the person asked in their latest message, `abandon` only when the person said to drop the work, and `force` only when the person said to close a worker of another chat. The chat MCP server enforces this with the pure `worker::command_allowed`: `spawn_worker` and `close_worker` need the newest log entry to be from the person, `reply` accepts a person or worker entry, and anything else is refused. Its delegation rules keep turns short: the model reads inline only to scope (at most 3 tool calls per question), sends multi-file reads, broad searches and test runs to `evidence-collector`, all code edits to `implementer`, and fixes to `reviser`, and every dispatch prompt states goal, question, known facts, owned files, output cap, stop condition and tool budget, "Report not-found, do not widen scope.", and "You are a subagent. Don't run mem." After 2 failed repair rounds it diagnoses; after a 3rd it waits for the person. It also must lead with the answer and end with one next step, show a 3-5 line plan when a request is ambiguous, treat a worker "done" as unverified until it checks the diff, tests, git and Linear, cite the `#<id>` behind facts from older chat, and say it has no erase tool when asked to forget.

## Worker inbox

Worker reports never interrupt the draft. A watcher thread polls every 500 ms and repaints the prompt in place (reedline `RepaintSignal`), keeping the buffer and cursor.

- Status line: the first prompt line above `>>> `, `📬 <unread> unread · workers <id> <state>, ... · watch <id> <left>, ... · mem <msgs> msgs ~<k> tok · cache <read> read <write> write <share>% tok $<cost>`; the cache part comes from the last turn in `usage.jsonl` and is hidden before any turn. The percentage is the cache-read token share: `read * 100 / (input + read + write)`, rounded down, or 0 when the total is zero. It is not a cost share; `usage.jsonl` has no per-bucket prices. `$<cost>` is the separate total turn cost, omitted when unavailable. It sheds detail as the terminal narrows (states, then names to a count, then labels), uses `c<share>% tok` for compact cache display, and never exceeds the width. The `📬` part is hidden when nothing is unread; the narrowest form is `📬 <unread>` or, with nothing unread, `<msgs>m ~<k>`. Dim when stdout is a tty and `NO_COLOR` is unset.
- Each arriving inbox file moves into the queue `<store>/inbox.json` (oldest first, positions from 1 that shift up when a report leaves); unread is the queue length. A report leaves the queue only when sent to main or dropped, and is deleted from the file. An old file with `next_id`, `id` and `read` fields still loads; its read entries are dropped. Tmux workers have sessions named `ralph-<project>-<id>` (`<project>` = the git top-level folder name, letters, digits and dashes only, else `repo`), so the same id in two projects does not collide. Names are cosmetic: at spawn ralph tags each session with the tmux user options `@ralph_store` = the canonical store path and `@ralph_id` = the bare id, and the status line reads the id from `@ralph_id`. Only sessions tagged with this chat's store and an id are listed (sessions without both, including ones started before `@ralph_id`, are ignored; missing tmux or no server means no tmux workers). Headless Cursor and opencode workers are listed from their owner files instead (see [Headless workers](headless-workers.md)). A claude worker's state is the status of its latest report, else `running`. A `reply`, a nudge or a spawn writes the marker `<store>/sent/<id>`; while it exists a `done`, `blocked` or `question` status is ignored (a `check` status is not), so the worker shows as working until its next report, which removes the marker (`chat_status::superseded`). For opencode workers ralph asks the chat's own opencode server for `GET /api/session/active` (one call for all workers, every 5 s and after each turn or inbox read, only while an opencode worker runs): `busy` while `ses_ralph<id>` is in it, else the latest report status, else `idle`; if the call fails they fall back to the claude rule. Memory is the log entry count and the view size at about 4 chars per token, refreshed every 5 s and after each turn or inbox read.
- Worker check: when `[chat] worker_check_secs` is above 0 (default 60), the watcher thread runs `Monitor::check` every that many seconds. For each running worker it reads the `ready`, `blocked`, `waiting`, `unreported` and `sent` markers (a `sent` marker means the last report is old, so the worker is never counted as reported), and the last real report (`done`, `blocked` or `question`) seen in the inbox or logged as a worker entry in the chat log at start (so a restart keeps it). Only `Tmux` workers get a pane capture, skipped when blocked, waiting, or ready and reported; headless workers have no pane. The pure `worker_check::plan` classifies the observations. Markers, all in `<store>/<dir>/<id>`: `blocked` = a permission request is pending, `waiting` = the worker stopped without a report after one reminder, `unreported` = the reminder failed (the hooks and host turn logic that write and clear them are in [MCP tools](#mcp-tools)). A waiting worker gets one nudge per wait, `worker_check::NUDGE_TEXT` ("You stopped without calling report. Call the report tool now: done, blocked or question.") through `Workers::nudge`: typed into tmux or queued to the headless host. Only a report that lands after the nudge re-arms it. Each state change that needs the person posts one inbox message with status `check`, which raises the usual alert; `check` posts never count as reports. Both headless kinds report waiting without an attach hint, or a permission wait with instructions to ask the person and relay the answer with `reply`.
- Tmux-only check states: trust = the folder-trust dialog shows; unknown = the pane has not changed since the last check, no report came, no Claude busy marker shows in the pane footer (`esc to interrupt`, or `← N agent(s)` with N of 1 or more), and no `unreported` marker is set (that marker means `waiting` is due at the next `idle_prompt`, so the worker counts as working until then). ralph never types into a permission prompt or the trust dialog. Tmux check messages describe waiting, a permission prompt, the trust dialog or an unknown wait and end with `tmux attach -t <session>`. Unknown posts at most once per wait: flips to working (a spinner or status-line redraw) do not post it again; a report, waiting, blocked or trust state re-arms it.
- Inbox alerts: on each poll the watcher compares pending reports with the last poll (reports pending at chat start never alert). For new reports it asks tmux for focus and the pure `inbox_alert::inbox_alert` decides. Inside tmux, `tmux display -p -t $TMUX_PANE '#{pane_active} #{window_active} #{session_id}'` plus `tmux list-clients -t <session> -F '#{client_flags}'` give `Visible` when the pane and its window are active and a client has the `focused` flag, else `Hidden`. Outside tmux, no attached client, or a failed query give `Unknown`, which alerts unless `[chat] inbox_alert_unknown_focus = "silent"`. `Visible` never alerts. An alert plays a sound (`afplay /System/Library/Sounds/Glass.aiff` on macOS, else a terminal bell) and, with `inbox_alert_notification`, a notification `<id> <status>, ...` (`osascript display notification` on macOS, else OSC 9, wrapped for tmux passthrough). Limits: a tmux client that never got a focus-out (background pty, terminal without focus reporting) counts as focused and suppresses the alert; focus follows the terminal app, not window visibility (minimised, other Space, second monitor). Only inbox reports alert.
- Status line: a lualine-style bar painted above the input. `status_segments::segments` builds segments from `Status`, `layout` picks which fit, and `chat_statusbar` paints them. Left: mode block (bright, bold; one of `NAP`, `INBOX`, `WORK`, `IDLE`, see below), `📬 N unread` (soft; absent at 0 unread), the store path (last two parts). Right, soft to bright: `workers`, `watch`, `mem N msgs ~Xk tok`, `cache R read W write P% tok` (soft), `$cost` (bright). The filler runs the full width in the base background. Each segment has long-to-compact forms (`📬 2 unread` to `📬 2`, `mem 132 msgs ~4.1k tok` to `132m ~4.1k`, workers with state, names, `2 workers`, `2w`; watches `2wt`; cache `c96% tok`). When the bar is too wide, `layout` compacts the least important segment first, and drops segments only after every form is compact. Drop order, first to last: store, watches, workers, cache, cost, memory, mail; the mode block stays. Colors come only from the `[theme.status]` table (`mode_*`, `store_fg`, `workers_fg`, `watches_fg`, `memory_fg` and `base_bg`, resolved by `status_theme.rs`; keys and defaults in [configuration](../configuration.md#status-line-colors-themestatus)). Segments are plain colored blocks; `[chat] status_powerline = true` adds powerline glyphs between them. With no color (`NO_COLOR` or no TTY) the bar is plain text with `│` between segments and no padding. Not shown: git branch and elapsed time, because the status data has none of them.
- Status modes: `status_mode::mode` picks the mode block, first match wins: `NAP` (a nap holds the store lock), `INBOX` (unread above 0), `WORK` (a worker is `running` or `busy`, or any watch exists), else `IDLE`. Each mode has its own `mode_<name>_fg` / `mode_<name>_bg` keys. The mail, cache and cost blocks take the active mode's colors, so the coloured ends of the bar match the mode block; blocks of the same color run together with no separator in block mode. There is no turn mode because the bar only renders at the prompt. `Store::napping` probes the store `LOCK` file without blocking and releases it at once, using a shared lock so the probe never makes a turn's settled load wait. Limit: another `ralph chat` on the same store that is mid-turn also holds the lock, so the bar shows `NAP` there too.
- Footer: `footer` in `chat_status.rs` builds a hint line, painted under the input with one empty line after it, so the prompt is never the last terminal line. Stock reedline 0.52.1 erases everything below the cursor on repaint, so `vendor/reedline` carries upstream nushell/reedline `main` (e9fcfdb) plus the footer commit (`Prompt::render_prompt_footer`) and `Reedline::with_wrap_width`. The painter soft-wraps the prompt area at the capped width, or at the terminal width without a cap: draft rows break between words (UAX #14, as in replies; a word longer than a row breaks inside it) and each wrapped row starts with the `::: ` continuation prefix. The breaks and prefixes are display-only; the submitted text is what was typed. Mouse-click mapping still assumes character wrap; chat does not enable it through `[patch.crates-io]`. Bracketed paste is on, so a multi-line paste stays in the draft.

### /inbox commands

N is a position in the unread queue: oldest first, from 1, positive integer. Positions shift up after a send or a drop. An unknown N prints `No report N. /inbox list shows the queue.` and changes nothing.

| Command | Effect | Starts a turn |
| --- | --- | --- |
| `/inbox`, or Enter on an empty prompt with reports unread | Sends every queued report to main and deletes it from the queue: one `worker` log entry per report, then one turn with all reports in one message. With nothing unread, `/inbox` prints `No unread reports.` and Enter does nothing | yes |
| `/inbox next` | Same as `/inbox` for the oldest report only (position 1). With nothing unread, prints `No unread reports.` | yes |
| `/inbox N` | Same as `/inbox` for the report at position N only. Unknown N prints the not-found message | yes, when the report exists |
| `/inbox list` | Prints one row per queued report, `#<position>  <worker>  <status>  <age>`, columns padded, oldest first (`No reports.` when empty); age is `<n>s` under a minute, `<n>m` under an hour, `<n>h` under a day, else `<n>d`, `0s` for a future time and `?` for an unparsable one (pure `inbox::list`) | no |
| `/inbox peek N` | Prints report N in full with the same header box and markdown as `/inbox`; removes nothing | no |
| `/inbox drop N` | Removes report N from the queue and prints `Dropped report N.`. Before the queue changes, appends one JSON line `{timestamp, worker, status, text}` to `<store>/inbox-drops.jsonl` (append-only, never rewritten); an unknown N logs nothing. The unread count refreshes after a drop | no |
| any other `/inbox` argument | Prints the usage string (below) | no |

Usage string: `Usage: /inbox [next | N | list | peek N | drop N]`. `/inboxfoo` is a normal message. Local commands never start a turn or call the model. Each report that `/inbox`, `next`, `N` or `peek` prints goes under a header box from the pure `frame::worker_header` (`● worker <id> · <status>`, border and status colors from the agent palette: blue border, green for done, red for blocked or failed, yellow for waiting or check by default; sized by display width and cut to the terminal width), then its text as markdown through the chat renderer with the agent `MarkdownTheme` from `[theme.agent]` (see [configuration](../configuration.md); code blocks default to the assistant theme); plain text (header `[worker <id> · <status>]`) when stdout is not a TTY or `NO_COLOR` is set. The model still gets the plain `[worker <id> · <status>]` message.

## Watches

A watch is a shell command (`sh -c`) that runs as a child process of `ralph chat`, in its own process group, with stdin closed. Ralph keeps only a bounded tail of its stdout and stderr.

- When the watch exits, ralph posts exactly one `watch` report to the worker inbox. The text holds the exit code (or killed or timed-out note), the output tail, and the follow-up instruction.
- The report goes through the inbox, so it never interrupts the chat channel.
- Stopping a watch posts one "stopped" report. Closing the chat kills every watch and its child processes and posts nothing.
- The runner lives in `crates/ralph/src/watches.rs`; the pure report and tail logic lives in `crates/core/src/watch.rs`.
- Persistent watches are saved as one JSON file each in `<store>/watches/` (spec, `started_at`, timeout deadline, wake deadline), written atomically before the command starts.
- On every `ralph chat` start, `Watches::restore` reruns all saved persistent watches, also after Ctrl-D or `/quit`. Normal records are deleted, never restored. An unreadable record warns and is deleted.
- A restart keeps the original `started_at` and deadlines. The timeout becomes the time left. A command that is exactly `sleep <N>` is rewritten to `sleep <left>` (rounded up to whole seconds). Other commands rerun unchanged.
- A watch whose wake deadline passed posts an exit-0 report right away. One whose timeout deadline passed posts a timed-out report right away (the earlier deadline wins). Neither is spawned.
- The saved record is removed when the watch exits, times out, or is stopped. Closing the chat kills the watch but keeps the record. The pure logic lives in `crates/core/src/watch_store.rs`; the file store is `crates/ralph/src/watch_store.rs`.
- The agent starts a watch with the `watch` tool (see [MCP tools](#mcp-tools)). The chat socket server queues the request by writing a file to `<store>/watch-requests/` (atomic, one JSON file per request). The file is claimed with a hard link, which fails if the name exists, so a second call for an id whose request still waits returns the error `watch <id> is already queued` and queues nothing. The chat watcher thread takes every request on each 500 ms poll, calls `Watches::start`, and deletes the file (`crates/ralph/src/watch_requests.rs`; pure parsing in `crates/core/src/watch_request.rs`). If the start fails (duplicate id, spawn error), chat posts one `watch` report with the error to the inbox.
- Every watch id is stored, reported and shown as `watch:<name>`: generated ids are `watch:w1`, `watch:w2`, ...; a `watch` tool id `foo` becomes `watch:foo`, and an id that already starts with `watch:` is not doubled (`watch_id` in `crates/core/src/watch.rs`). Worker ids allow only letters, digits and dashes, so a watch id never equals a worker id. `/watch stop` accepts `w1` or `watch:w1`.
- Watch reports show as `[worker watch:<name> · watch]`. The system prompt says they come from a watch, not from an agent or the person.
- Approval: the system prompt tells the model to show the person the exact command and wait for approval before it calls `watch`. The prompt enforces this, not the tool. The tool only refuses outside a user-started turn, like `spawn_worker`.
- `/watch` is local: it never starts a turn or calls the model. The shell side is `crates/ralph/src/chat/watch.rs`; the pure parsing and formatting is `crates/core/src/watch_command.rs`.
  - `/watch start [--persistent] <command> -- <follow-up>` starts a watch in this process (`Watches::start`). The input splits at the last ` -- `; both parts must be non-empty. The id is the lowest unused `watch:w<n>` (n from 1) among running and saved watches. It prints `Started <kind> watch <id>.`. There is no timeout flag.
  - `/watch list` prints one row per active watch: id, kind (`normal` or `persistent`), time left, command. Time left is the earlier of the wake deadline (a time-based `sleep N`) and the timeout deadline, shown as `<n>s`, `<n>m`, `<n>h` or `<n>d`, or `—` when there is none. It prints `No active watches.` when empty.
  - `/watch stop <id>` kills the watch and posts its one "stopped" report. A stopped persistent watch is removed from `<store>/watches/`, so it does not come back after a restart. This is the only way to remove a persistent watch. If the id is not running but has a saved record, the record is removed and the message says so. An unknown id prints a message, not an error.
  - Bare `/watch` or any other argument prints `Usage: /watch start [--persistent] <command> -- <follow-up> | list | stop <id>`. `/watchfoo` is a normal message.
- A restarted watch that times out reports the original timeout, not the time left.
- Status line: running watches show after the workers as `watch <id> <left>, <id>, ...` (the time left is omitted when there is none). It sheds detail as the terminal narrows: time left, then names to `<n> watches`, then `<n>wt`, then nothing. It refreshes on the same 500 ms poll, so it updates when a watch starts, ends or is stopped.
- Every watch has a timeout. A watch without its own `timeout_secs` (from the `watch` tool, `/watch start`, or an old saved record) gets `[chat] watch_timeout_secs` (default 3600, so 1 hour; `0` is a config error, resolved by `resolve_watch_timeout` in `crates/core/src/chat.rs`, same file-then-default precedence as `worker_check_secs`). `WatchSpec::with_default_timeout` applies it at start and at restore. When it passes, ralph kills the watch and posts one report that says `timed out after <n>s and was killed`, where `<n>` is the original limit.

## /diff

`/diff` is local: it never starts a turn or calls the model. `/difffoo` is a normal message. `turn` and `worker` are ordinary git arguments here, not turn or worker ranges.

Typed `/diff [git diff args]` runs `git diff` in the chat's working directory and waits. Words after `/diff` are split on whitespace, with quotes and backslash escapes (a trailing backslash is kept; no `$` expansion or globs), and are passed after `[changes] diff_args`. An unclosed quote prints `/diff: unclosed quote` and runs nothing.

```toml
[changes]
pager = "git" # git | delta | hunk
diff_args = [] # default git diff args; typed /diff args follow
```

- `pager = "git"` (default): `git diff <diff_args> <typed>`. The user's `core.pager` in git config is left untouched.
- `pager = "delta"`: `git -c core.pager=delta diff ...` for this call only.
- `pager = "hunk"`: `git -c core.pager=hunk pager diff ...`, with `core.pager=hunk pager` as one argument.
- Any other pager string warns once at chat start (`[changes] pager = "..." is unknown; using git`) and uses `git`. Loading the config still succeeds.
- ralph sets no environment variables and does not write `core.pager`.

The spawn runs only after reedline `read_line` has turned raw mode off, so a full-screen pager returns to a normal prompt. `git diff` exiting 1 (there are changes) is not a chat error. A failure to start git warns and returns to the prompt.

## Executable cells

A fenced block in a message you type whose info string is `!<runtime>` (for example ```` ```!zsh ````) is a cell. Worker reports and agent replies never run cells; a `!` fence inside another fence is not a cell. Parsing and message building are pure in `ralph_core::chat_cell`; PATH lookup, spawn and streaming are in `crates/ralph/src/chat/cell.rs`.

Shorthand: a message whose first character is `!` is the same as one `!shell` cell holding everything after the `!` (all lines; trailing newlines dropped; a longer fence when the body has backtick fences). `expand_bang_shell` in `crates/ralph/src/chat/cell.rs` rewrites it before parsing. Only the very first character counts: ` !ls` or `hi !ls` is plain text, and so is `!` alone or `!` followed only by whitespace. A failed or cancelled cell restores the draft as typed (`!ls`).

- On Enter, cells run in order, one process each, in the chat's working directory. The runtime is found by exact name on `PATH`; the code goes to its stdin. No sandbox. Stdout and stderr share one pipe. While a cell runs the terminal shows one dim line `▸ cell N · runtime`; the output is not echoed live.
- Claude gets the message with the `!` removed, then per cell: `[cell N · runtime · exit C]`, the code, and the output. A non-zero exit still sends. The store keeps this enriched message.
- After all cells ran, the terminal shows the message (the `!` removed) rendered as markdown. Each cell is followed by its full, untrimmed output in a ```` ```result ```` fence (longer fence if the output has backticks; none when the output is empty) and, for a non-zero exit, an `exit N` line (`core::chat_cell::display_results`). The display never reaches Claude, `log.jsonl` or memory.
- Caps shape only what Claude receives: `[chat] cell_output_limit` (200 lines, first half and last half kept) and `cell_output_bytes` (65536, head and tail kept), each with a `... trimmed ...` marker. `0` disables a cap. See [configuration](../configuration.md).
- A missing runtime prints ``runtime `X` not found``, runs nothing, sends nothing, and puts the text back in the prompt. Ctrl-C kills the running cell and its process group, ends the turn without sending, and restores the draft.
- `!shell` runs `$SHELL -i` (`/bin/sh` when unset) and keeps state between `!shell` cells, in one message and in later messages, until ralph exits. One process per cell, no long-running shell. The stdin is a generated prologue plus the cell code. The prologue empties the prompt variables and prompt hooks, turns off verbose and xtrace, unsets `HISTFILE` (a leading space keeps the first line out of history) so no state or code reaches the history file, dumps a START snapshot to fd 3 (a pipe ralph reads into memory, never disk), restores the saved state, installs an exit hook that dumps an END snapshot to fd 3, then re-enables verbose and xtrace if they were on. The snapshot has the exported env, `$PWD`, functions and aliases. `diff(END, START)` is the saved state: new, changed and removed exports, functions and aliases, plus the end directory. START is taken before the restore, so the diff holds everything done since ralph started, and inherited env and `.zshrc` definitions are never copied. Output before the prologue's end marker (rc noise, the first prompt) is dropped from the result. Restore text and the prologue never appear in the output, in Claude's message or in the result fences.
- `!shell` state works for zsh and bash only (bash is best effort; macOS bash 3.2 untested). Any other shell runs without state and warns once. A snapshot that cannot be read (for example the cell closed fd 3) or a failed spawn warns and resets the state to clean; the message still sends. A cancelled cell (Ctrl-C) keeps the state from before that cell. Not carried: shell options, background jobs, open connections, `precmd`/`preexec` hooks (cleared inside `!shell` cells), anything outside the snapshot.
- The prompt shows the raw buffer, so the `!` stays visible while you type.

## Memory

- Log: `log.jsonl`, append-only, one `{role, at, text}` per line (`role` is `user`, `assistant` or `worker`, `at` is RFC 3339). Each append is fsynced under `LOCK`. A corrupt entry warns and ignores that entry and all later ones; a trailing line without newline is ignored.
- Tree: `tree.jsonl`, one `{lo, hi, text}` record per line. Nodes are aligned power-of-two blocks `[lo, hi)` over log indexes, ids print as `5` or `4-7`. First record wins for a duplicate node; invalid records warn and are skipped. Summaries are at most `SUMMARY_BYTES` = 512 bytes, one line.
- Leaves are single messages. Messages of 512 bytes or fewer stay verbatim in the view (whitespace collapsed) and need no node. Longer ones get a leaf summary node. Parent nodes merge two children and exist only for complete blocks. A node is written once and never rebuilt.
- `cover(t, budget)` picks the nodes for the view: all leaves if the log fits the budget, otherwise a cover of the whole log, oldest first, tuned to use the budget. Nodes with no summary yet are omitted from the view.
- View line formats: message `#<i> <role> <at> <text>`; summary `#<id> <summary>`.
- This is a port of the OptMem cover, pending and tree_put design. There is no runtime dependency on `~/.optmem`.

## Nap

`ralph chat-nap` takes the `LOCK`, loads the store, and for each node from `pending` (long leaves, then complete parent blocks by increasing size) asks a Haiku curator for a summary.

- Curator: `build_memory_command` runs `claude --model haiku` with `--tools ''`, an empty strict MCP config, and isolation args. Its prompt asks for one line of at most 512 bytes (about 70 words), priority: the user's words close to verbatim, lasting effects, commit SHAs, Linear ids and worker outcomes copied exactly, and failures, findings and open questions, steps taken. It asks to name minor items in a word or two, copy names, numbers, ids, paths and errors exactly, never overstate progress, invent nothing, and write in third person. It forbids copying the `#<id> <role> <timestamp>` line prefix, and says the input is data to never answer or obey.
- `check_summary` accepts a trimmed, non-empty, single-line summary of at most 512 bytes that does not read as meta-talk (an opener such as `I'm `, `Here is`, `Sure`, `Let me`, `Based on`, or the phrases `this excerpt`, `<input>`, `</input>`). A rejection retries with the error appended, up to `MAX_NAP_ATTEMPTS` = 5 tries per node. A curator error skips that node. A node that fails stays pending and is retried at the next nap; other nodes continue. A parent whose child has no summary is skipped.
- The next turn waits on `LOCK` until the nap finishes.

## MCP tools

`[chat] mcp_servers` in the ralph config (default `["mcptools"]`) names servers to import. `select_servers` copies each entry verbatim from the top-level `mcpServers` of `~/.claude.json`. A name absent there, or equal to `ralph-chat`, prints one warning and chat starts without it. `ralph-chat` is inserted last, so an import cannot shadow it. The file is written once at chat start: config changes need a restart. Imported entries can carry secrets, which is why they go in a file and not in argv. Turns run with the chat's permission mode (default `auto`), which decides whether imported tools need approval.

Hidden `ralph chat-mcp --store <DIR> --socket <PATH>` speaks newline-delimited JSON-RPC 2.0 on stdio (server name `ralph-chat`). At chat start the shell writes `<store>/mcp.json` (mode `0600`) holding `ralph-chat` plus the servers named in `[chat] mcp_servers`, and `build_mcp_args` passes `--mcp-config <store>/mcp.json --allowedTools mcp__<server>__*,... --strict-mcp-config`, so only those servers load. The allow list names every server in `mcp.json`: `--setting-sources project,local` skips allow rules in `~/.claude/settings.json`, and without this list the auto-mode classifier blocks these MCP calls. `chat-mcp` takes no permission mode or worktree directory; the chat process owns both. Each `zoom` and `recall` call re-reads log and tree without locking, so it sees fresh state.

Worker tools run inside `ralph chat`, not in `chat-mcp`. At start the chat sweeps `<store>`, then creates the private directory `<store>/chat-<pid>/` (mode `0700`, created with `DirBuilder` so it fails if the path exists; a leftover directory that the sweep kept makes chat start fail with a clear error), binds `<store>/chat-<pid>/chat.sock` inside it (then mode `0600`, so the socket is never reachable with looser rights) and writes the owner record `<store>/chat-<pid>.owner` (mode `0600`, JSON `pid` and `ps -o lstart=` start time). The sweep reads each `chat-<pid>` directory and each `.owner` record. The pure `chat_socket::socket_fate` deletes a directory and its record when the record is missing, unreadable or names another pid, or when the owner is dead or has a different start time; it keeps them only when the owner is alive with the same start time. An orphan `.owner` record, one with no `chat-<pid>` directory, goes through `chat_socket::orphan_sidecar_fate` with the same rule: it is deleted unless its owner is alive with the same start time. Quitting the chat (Ctrl-D, `/quit`, or SIGTERM/SIGHUP during a turn) ends the main loop, and `SocketGuard` drops and removes its own directory (with the socket) and record. A SIGTERM/SIGHUP or a lost terminal stdin at the prompt goes through the input watcher instead: `ExitCleanup::run` kills watches, shuts down headless hosts, removes the same directory and record, then exits with code 129. A SIGKILL leaves both for the next start's sweep. `mcp.json` passes `--socket <path>` to `chat-mcp`. `chat-mcp` keeps `zoom` and `recall` and forwards `spawn_worker`, `reply`, `close_worker` and `watch` to the socket as one JSON line `{tool, args}` per connection; the chat answers with one line `{text, is_error}` after it checks the turn marker (`command_allowed`) and parses the arguments (`worker::parse_command`). If nothing listens, the tool returns an error that starts with `no running ralph chat` and names the socket path; there is no fallback. `ralph ask` loads no `chat-mcp`, so it cannot spawn workers. A Unix socket path may not exceed 103 bytes (macOS `sun_path` is 104 with the NUL byte); a longer `<store>/chat-<pid>/chat.sock` makes chat start fail with a message that asks for a shorter `--store`.

`chat-mcp` answers `zoom` and `recall` itself. It forwards `watch` (and `spawn_worker`, `reply`, `close_worker`, below) to the chat socket, so the running chat produces their results.

| Tool | Args | Result |
| --- | --- | --- |
| `zoom` | `id` (string, such as `16-31` or `5`) | A block id returns its two halves (summary lines, or `#<id> not compressed yet`; halves past the log end are dropped). A single index returns the raw message. |
| `recall` | `pattern` (string) | Case-insensitive regex over raw messages. Returns an index, newest hit first, one `#<id> · <role> · <date> · <preview>` line per hit (preview: ~80 chars around the first match, `…` at cut ends), at most 50 lines then `N more, narrow the pattern`, and a closing `(zoom <id> for the full text)`. No hits gives `no hits for <pattern>`. No byte cap. |
| `watch` | `id` (string, no spaces or slashes; stored as `watch:<id>`), `command` (string), `follow_up` (string), optional `persistent` (boolean, default false), optional `timeout_secs` (positive integer, default `[chat] watch_timeout_secs`, 1 hour) | Queues the watch and returns at once. The report arrives in the inbox when the command ends. Needs a user-started turn. The model must get the person's approval of the exact command first. |

Invalid ids, ids beyond the log, bad regexes, and store read errors return a tool result with `isError: true`.

Workers can be tmux-hosted or headless (Cursor and opencode). See [Headless workers](headless-workers.md) for `WorkerKind`, old `cursor: true/false` record compatibility, the chat-owned `HeadlessHost` lifecycle and how to add another headless harness.

`spawn_worker` takes `id`, `task`, optional `harness` (`claude` default, `opencode`, or `cursor`) and optional `model` (`provider/model`, opencode only, default `openai/gpt-6.1-sol`). `worker::parse_command` refuses an unknown harness, a `model` for claude, and a model without a provider and name. Claude runs in tmux session `ralph-<project>-<id>` through a login `zsh -lic`; every harness works in `<dir>/<id>` on branch `worker/<id>`. The worktree directory comes from the pure `worker::resolve_worktree_dir`, first non-empty wins: `--worktree-dir`, `RALPH_WORKTREE_DIR`, `[chat] worktree_dir`, then `.worktrees`; a leading `~` expands to home, then the result joins the repo root (an absolute path stays as is). A config that fails to load skips `worktree_dir` and adds a warning to the result. Spawn and close both prune stale worktree entries, then take the path of `worker/<id>` from `git worktree list --porcelain` (`worker::worktree_for_branch`) and use `<dir>/<id>` only when the branch has no worktree, so a worker made under an earlier setting is still found. Spawn reuses that worktree and an existing `worker/<id>` branch. Otherwise it runs `wt switch [--create --base @] worker/<id> --no-cd` with `--config-set worktree-path=<dir>/<id>`, so the worktree lands where close expects it whatever the user's wt template is; if `wt` is not installed or fails, it falls back to `git worktree add [-b]`. The spawn result says which path ran (`WorktreeVia::note`). close_worker removes either kind with `git worktree remove` and `git branch -D`. Claude gets `--permission-mode <MODE>` (the chat's mode), `--mcp-config <store>/workers/<id>.json`, `--add-dir <store>/attachments` (spawn creates it; pasted `[Image #N: <path>]` paths in task or reply text are read from there), and the worker rules via `--append-system-prompt`. opencode runs headless on the chat's own server (see the opencode harness below), with no tmux session; ralph writes `<worktree>/opencode.json` with `model`, `permission.external_directory` allowing `<store>/attachments/**`, and a local `ralph-worker` MCP server, and adds `/opencode.json` next to the worktree directory (only when it is inside the repo) in the shared `.git/info/exclude`. Each worker signals ready by creating `<store>/ready/<id>`, which spawn deletes first: Claude through a `SessionStart` hook (matcher `startup`) in `<store>/workers/<id>.settings.json` passed with `--settings`; opencode, the chat, once the server accepts the first prompt. For Claude, spawn polls up to 20 s, reading the pane only to accept the folder-trust prompt; a timeout is not an error ("not confirmed yet" plus the tmux session), but a gone tmux session or a trust prompt still showing is. Before any git step, spawn runs a preflight (`workers/spawn.rs`), so a failed preflight leaves no worktree, branch or exclude line: claude needs `tmux` and `zsh` on PATH and `claude` in a `zsh -lic` shell (`command -v`); cursor needs `agent` on PATH; opencode writes `<store>/opencode-preflight/<id>` (the time) and waits up to 30 s for the chat to start or reuse its server and write `<store>/opencode-healthy/<id>`, or to write `<store>/opencode-error/<id>`, so a missing binary, an unhealthy server or no running chat fails here. If start fails after the worktree step, spawn rolls back only what it created, decided by the pure `worker::rollback_plan`: it removes the worktree (`git worktree remove`, never `--force`, so a dirty worktree stays) only when this spawn created it and the harness is not still running (a live tmux session or an owner file), and deletes the branch (`git branch -D`) only when the worktree was removed, this spawn created the branch, and `git rev-list --count <tip at creation>..worker/<id>` is 0. The user sees the start error; rollback failures are appended to it (`worker::rollback_report`).

Cursor harness: `cursor` runs one `agent acp` child per worker (JSON-RPC over stdio through the `agent-client-protocol` crate, no tmux, no model option, cwd = the worktree). `chat-mcp` lives only for one turn, so the long-lived `ralph chat` owns the child. Spawn prepares the worktree, writes `<store>/cursor-spawn/<id>` (a JSON `SpawnRequest` with the time) and polls every 250 ms for `<store>/ready/<id>` or `<store>/cursor-error/<id>`, giving up after 30 s (it removes the request). The host drops a request older than 30 s. Right after starting the child, before `initialize`, it writes `<store>/cursor/<id>`: a JSON owner record with the chat pid and start time and the process group id and start time (`ps -o lstart=`, guarding pid reuse), not a bare child pid. It runs `initialize` (protocol must be 1, else error) and `session/new` with the `ralph-worker` stdio MCP server, removes the spawn request and writes ready; if the request is already gone (spawn timed out), it terminates the child. A failed or timed-out start kills the group and removes its owner file. Each `agent acp` start rewrites `~/.cursor/cli-config.json`, as reported in GUZ-570 testing; ralph keeps no backup. Accepted risk: a global Cursor MCP server named `ralph-worker` (`worker::SERVER_NAME`) replaces ralph's own. A different `agent --version` than the tested `2026.10.14` only warns; `authRequired` becomes "run `agent login`".

Cursor ownership and cleanup: the child runs in its own process group, so its MCP servers die with it: terminate sends SIGTERM to the group, waits 3 s, then SIGKILL. The `agent` ignores stdin EOF after `session/new`, so a killed chat leaves the child alive until a sweep: on chat start (every owner file), on close and on respawn of that id, the pure `worker::sweep_decision` returns `Reclaim` (owner chat dead: kill the group if its start time still matches, delete the files, go on at once), `Wait` (this chat owns it: use the close handoff below) or `Busy` (another live chat owns it: refuse). A close is not refused when the owner is the caller's own chat, found by `worker::caller_owns_worker` on the caller's ancestor pids from `ps -o ppid=`, since chat-mcp runs below claude below `ralph chat`. Quitting `ralph chat` terminates every owned child through its host (see [Headless workers](headless-workers.md)). The ACP MCP entry passes `--owner <store>/cursor/<id>` to `worker-mcp`, which refuses a report (tool error "worker closed", nothing posted) once the owner file is gone (`worker::accept_report`).

Cursor permissions: the session thread registers an `on_receive_request` handler for `session/request_permission`; it stores the `Responder` and the options in a per-worker queue and never answers by itself, except for the worker's own `ralph-worker-report: report` tool: `worker::auto_allow_option` picks the `allow_once` option and answers at once with its exact `optionId`, no queue and no `blocked/<id>` marker. With `[cursor] permissions = "yolo"` (read at worker start; default `ask`) `auto_allow_option` does the same for every request that has an `allow_once` option and never picks `allow_always`; a wrong value or unreadable config warns and uses `ask`. Every other tool waits for the person. The front request is mirrored in `<store>/blocked/<id>` as JSON `{tool, summary, options:[{optionId,name,kind}]}` (built by `worker::permission_content`; existing blocked readers only test that the file exists). The person answers through `reply`: for a cursor worker with both the owner file and `blocked/<id>`, `Workers::reply` writes `<store>/cursor-answer/<id>` and waits up to 30 s for the chat poll to consume it. The chat applies `worker::match_option` (exact, case-sensitive `optionId` after trimming surrounding whitespace; option names are not accepted): a match answers `Selected`, then shows the next queued request or removes the marker; no match leaves the request pending and returns an error through `cursor-error/<id>` listing the valid `optionId`s. `CursorHost::cancel_pending` answers every pending request `Cancelled` and clears the marker; close, shutdown and terminate call it before killing the group.

Cursor prompts and interrupts: a `reply` with no waiting permission writes one entry per message under `<store>/cursor-prompt/<id>/` (named `worker::prompt_entry_name`, written hidden then renamed). The chat poll queues them in name order; `run_turns` starts a `session/prompt` only after the previous one ended, so a mid-turn reply waits for the next turn. `interrupt: true` skips the permission answer and writes under `<store>/cursor-interrupt/<id>/` instead. Opencode also supports interrupts through its own queue (see below); tmux workers return "interrupt needs a Cursor or opencode worker". Cursor's result is the real outcome, handed back through a result file: the entry name travels with `Inbound::Interrupt`, and after `PromptQueue::accept` `run_turns` writes `cancelled` (the steps include `CancelSession`, checked by `worker::cancels_turn`) or `sent` to `<store>/cursor-interrupt-result/<id>/<entry>` (written hidden then renamed). `Workers::reply` polls every 250 ms for up to 30 s, removes the result, and `worker::interrupt_reply` words it: cancelled, or sent with nothing cancelled; a timeout says the interrupt was queued but ralph chat did not confirm, outcome unknown. Chat start removes the whole `cursor-interrupt-result/` dir (a killed chat leaves results); close, sweep and spawn remove the id's dir. The chat poll sends the interrupt to `run_turns`, where `worker::PromptQueue` puts it at the front and returns `CancelPermissions` (all pending permissions answered `Cancelled`) and, when a turn is running, `CancelSession` (an ACP `session/cancel` notification). The pending prompt returns `cancelled`; `worker::turn_outcome` maps it (or `end_turn` after an interrupt) to `Cancelled`, which queues no `REPORT_REMINDER`, posts no `blocked` report and sets no `waiting`/`unreported` marker. The interrupt text runs next in the same session. Close and sweep remove `cursor-interrupt/<id>` with `cursor-prompt/<id>`.

Cursor reporting: after `session/new` the chat sends the task as `session/prompt` (`WORKER_PROMPT`, a blank line, then the task, as for opencode) without delaying ready. Each worker has one prompt queue; `worker::turn_outcome` maps each response, and a prompt that errors or ends with anything but `end_turn` posts a `blocked` report to the inbox. Close sets a closing flag first, so the `cancelled` stop reason posts no `blocked` report. The `session/update` handler sets a per-turn flag when a `tool_call_update` is the `ralph-worker-report: report` tool (`worker::is_report_tool_call`). A turn ending with `end_turn` and no report queues one `REPORT_REMINDER` prompt; if that turn also ends without a report, the worker gets `waiting/<id>` and `unreported/<id>`, as a claude worker does after its Stop hook gives up. The next prompt removes `waiting/<id>`. Worker checks use `Workers::nudge` to queue a `cursor-prompt/<id>/` entry; no pane or tmux attach hint is used.

Cursor resume: after `session/new` the chat writes `<store>/cursor-session/<id>` (JSON `SessionRecord`: sessionId, cwd, inbox, and the canonical chat store path as owner). Quitting the chat keeps it; close, a failed start and an unclaimed start remove it. A chat store holds exactly one chat, so the store path is the chat identity. On chat start, after the owner sweep, a background thread resumes each record (`CursorHost::resume_all`): `worker::resume_decision` skips, with a warning, a record with no owner, with another store, or when the agent does not advertise `loadSession`; a record whose owner file is still held by a live chat, an unreadable record, or a missing worktree is skipped the same way. An eligible record gets a new `agent acp`, `initialize`, `session/load` (sessionId, cwd, the same MCP server) and no task prompt. While `session/load` runs the `session/update` handler ignores updates, so replayed history never marks a turn reported. A failed load (including an active run) is warned, written to `cursor-error/<id>` and not retried until the next chat start; the record stays.

Opencode harness: `opencode` runs on one `opencode serve --hostname 127.0.0.1 --port <free>` child of `ralph chat`, started for preflight/spawn or supervision of persisted sessions, directly without a shell wrapper (ralph's own environment plus `OPENCODE_PASSWORD`; a missing binary fails at once with "opencode not found on PATH"). It runs in its own process group with basic auth (user `opencode`, a random password in `OPENCODE_PASSWORD`). The chat writes `<temp_dir>/ralph-opencode-<chat pid>.json` (`std::env::temp_dir()`, port, password, chat pid and `ps -o lstart=` start time, mode 0600, written fresh with `create_new`) so the status line can ask `GET /api/session/active`; a read that parses a record whose pid or start time is not this chat's removes it (an unreadable or unparsable file is left alone), and chat start deletes records of dead or pid-reused chats (`worker::server_record_fate`). Spawn writes `<store>/opencode-spawn/<id>` (a JSON request with the time) and polls every 250 ms for `<store>/ready/<id>` or `<store>/opencode-error/<id>`, giving up after 30 s. The host's poll thread consumes requests in order: close, answer, prompt, interrupt, preflight, spawn. It drops a spawn request older than 30 s, waits up to 20 s for `/api/info` when starting the server, creates the session with `POST /api/session` (`id` = `ses_ralph<id>`, `location.directory` = the worktree, `model`, `permissions`), writes `<store>/opencode-session/<id>`, posts `WORKER_PROMPT` and the task to `/api/session/<sid>/prompt`, then writes the owner file `<store>/opencode-owner/<id>` and the ready marker.

Opencode turns: session create, prompt posts and permission replies retry up to `TRANSIENT_RETRIES` (2) times, 500 ms apart, on HTTP 404, 408, 429 or 5xx (`transient_request_error`); a turn that fails with a transient status resends its prompt the same way. One `GET /api/event` stream (SSE) feeds the pure `TurnState` for every session; a silent stream is dropped after 45 s and reconnected. After connection/reconnection, `reconcile_all` verifies persisted sessions and repairs state from `/api/session/active`, pending permissions and latest messages. The separate 3-second snapshot tracks process descendants for shutdown, not session reconciliation. `reply` writes prompts under `<store>/opencode-prompt/<id>/` and, with `interrupt: true`, under `<store>/opencode-interrupt/<id>/` (the chat calls `/api/session/<sid>/interrupt` first); a reply to a worker with a waiting permission writes `<store>/opencode-answer/<id>` and the chat posts `/api/session/<sid>/permission/<rid>/reply`.

Opencode supervision: a server that dies mid-turn posts a `blocked` report; the supervision loop attempts a restart without waiting for a new request. Chat-owned host shutdown (see [Headless workers](headless-workers.md)) removes the server record, sends SIGTERM to the process group, waits up to 3 s, sends SIGKILL, then kills tracked descendants. Worker close does not stop this server.

Reporting: the worker's `ralph-worker` MCP tool `report` (`status` = `done`, `blocked` or `question`, any other value is a tool error; `text` = full summary) is the only way a worker reaches the chat. After it posts to `<store>/inbox/`, the tool touches the marker `<store>/reported/<id>`; spawn deletes the marker first. Harness hooks never send or build a report; they only stop a worker from going idle without one. Claude's settings file adds a `Stop` hook that runs the hidden `ralph worker-stop-hook --reported <store>/reported/<id> --unreported <store>/unreported/<id>`. It reads the hook input with serde, and the pure `worker::stop_decision` decides: while `background_tasks` is not empty it allows the stop; else if the marker exists it deletes it and allows; else if `stop_hook_active` is false it blocks with `worker::REPORT_REMINDER`; else it gives up and touches the unreported marker, so a worker that still will not report gets one push per stop and no loop; a report or the consume step removes the unreported marker. Malformed input, or input without `stop_hook_active`, lets the worker stop and prints a warning to stderr. Claude permission prompts stay open and wait for the person; the `PermissionRequest` hook only touches `<store>/blocked/<id>` and prints nothing, so it neither allows nor denies. A `Notification` hook with matcher `idle_prompt` deletes `blocked/<id>` and touches `<store>/waiting/<id>` only while `unreported/<id>` exists. A second `Stop` hook deletes `blocked/<id>`. A prompt cancelled with Esc or denied fires no `PostToolUse`, so these two hooks end a stale blocked state; an Esc cancel clears it at the next `idle_prompt` (about 60 s). `UserPromptSubmit` and `PostToolUse` hooks delete `blocked/<id>` and `waiting/<id>`, so new input or an answered prompt ends the wait. opencode workers get the same reminder and markers from the chat: the SSE turn state (`TurnState`) queues one `REPORT_REMINDER` prompt after a turn that ended without a report, and a second such turn touches `waiting/<id>` and `unreported/<id>`. Sessions are created with the permission rules `allow *` then `deny question` (the last match wins), so tools run without asking and questions are refused; a permission request that still arises is mirrored in `blocked/<id>` and answered with `reply_worker`.

Tmux ownership: `spawn_worker`, `reply` and `close_worker` look up the worker's session by name (`ralph-<project>-<id>`, or the older `ralph-<id>`) and compare its `@ralph_store` tag with this chat's store in the pure `worker::session_owner`. The shell canonicalizes both sides (symlinks resolved) and `worker::same_store` also normalizes lexically (trailing and doubled slashes, `.`, `..`). A session tagged with another store, or untagged, belongs to another chat: spawn, reply and close refuse it; `close_worker` with `force` skips the check. Headless ownership uses the store-local owner/session files described above, not tmux tags.

`close_worker` takes `id`, optional `abandon` and optional `force` (both default false). Like `spawn_worker`, it needs the newest log entry to be from the person. The shell collects the facts (owner, hosting kind, worktree dirty per `git status --porcelain`, `git rev-list --count <base>..worker/<id>`, opencode metadata from the chat's opencode owner or session file, or `<worktree>/opencode.json`), and the pure `worker::close_plan` decides. The base comes from the pure `worker::base_branch`, first non-empty wins: `[chat] worker_base` in the ralph config (read at each close), the branch behind `refs/remotes/origin/HEAD`, then `main`. Close never uses the branch checked out at spawn, so a stale or deleted spawn branch cannot block it. After a successful close it unsets any leftover `branch.worker/<id>.ralphBase` that an earlier version wrote; if that fails, the close still succeeds and its result ends with a warning that gives the `git config --unset` command. A missing config file is normal; a config that fails to read or parse skips `worker_base`, and the close result (success or refusal) ends with a warning naming the config path, the error and the base used instead. It refuses a foreign worker unless `force` is set; it refuses unmerged commits or a dirty worktree unless `abandon` is set. If no session, worktree or branch is left, it clears any remaining markers, otherwise refuses.

The first close step is dispatched by `WorkerKind`, not by a Cursor flag or a generic "headless" test:

| Kind | Worker-specific close |
| --- | --- |
| `Tmux` | `KillSession`: `tmux kill-session` for the owned session, if present |
| `Cursor` | `TerminateCursor`: hand off through `<store>/cursor-close/<id>` to terminate only that worker's ACP process group and remove its files |
| `Opencode` | `RemoveOpencodeSession`: hand off through `<store>/opencode-close/<id>` to interrupt an in-flight turn, delete only that worker's session (`DELETE /api/session/<sid>`, normally `ses_ralph<id>`; HTTP 404 means already gone), evict its worktree location with `DELETE /api/debug/location?location[directory]=<worktree>`, and remove its opencode files and owner |

The headless close handoffs wait up to 30 s for the owner file to vanish. The opencode handoff waits until both the owner file and the session record are gone, so session deletion finishes before worktree removal; on timeout or an error the close stops before removing the worktree. For a non-`Opencode` kind that still has opencode metadata, `close_plan` prepends `RemoveOpencodeSession` before the kind-specific step. An opencode close never kills a tmux session, calls `TerminateCursor`, or shuts down the shared `opencode serve`; other workers keep their sessions.

The common remaining steps, skipping absent resources, are `git worktree remove` (`--force` when dirty and abandoned), `git branch -D worker/<id>`, `git worktree prune`, then clearing the worker's markers (`worker::marker_paths`: `<store>/ready/<id>`, `reported/<id>`, `blocked/<id>`, `waiting/<id>`, `unreported/<id>`, `sent/<id>`), which spawn also clears first. A failed step stops the close and names the step; opencode location-eviction errors only warn. After successful worktree removal, home-directory cleanup runs only for the matching kind: Claude data for `Tmux`, Cursor data for `Cursor`, neither for `Opencode` (so it never scans `~/.cursor`). Cleanup failures only add warnings; the exact paths and ownership checks are documented in [Worker leftovers](worker-leftovers.md).

At chat start, ids in `<store>/ready/` absent from this store's discovered running workers (tmux, Cursor and opencode) print one hint line (`chat_status::orphan_hint`) that suggests `close_worker`. The hint still says "no tmux session", but the test is absence from all discovered kinds. Chat never deletes these markers by itself.

## Skills

Turns run with `--setting-sources project,local`, so `~/.claude/skills` does not load. No skills are bundled. The user names skill directories (each holds a `SKILL.md`, for example `~/.claude/skills/show-me`) and chat exposes them through a plugin.

- Sources, highest first: `--skill <PATH>` (repeatable), `RALPH_CHAT_SKILLS` (`:`-separated, empty entries dropped), `[chat] skills = [...]` in the ralph config. The highest non-empty source replaces the lower ones; lists are not merged. With none set, no `--plugin-dir` is passed and nothing is written.
- A leading `~` or `~/` expands to the home directory. Duplicate paths keep the first. Relative paths are made absolute.
- At start, a path without a readable `SKILL.md` prints one warning and is skipped. Two skills with the same directory name: the first wins, the other warns and is skipped.
- Slash expansion: chat turns wrap the input, so Claude Code never expands a leading `/<name>`. Ralph does it for user turns only (worker messages are never expanded). If the message starts with `/<name>` followed by whitespace or end, and `<name>` is a configured skill, the prompt gets `Base directory for this skill: <dir>`, the `SKILL.md` body without its frontmatter, then the original message. The rest of the message, trimmed, replaces every `$ARGUMENTS` in the body; without that token and with non-empty arguments, an `ARGUMENTS: <args>` line is appended. The store keeps the original message; only the sent prompt is expanded. Unknown names, a bare `/`, and `/name` prefixes that are longer words pass through unchanged. A `disable-model-invocation` frontmatter flag only stops the model from invoking the skill itself; `/<name>` still runs it, and ralph does not warn about it.
- Config is loaded once at start; it supplies both `mcp_servers` and `skills`. On load error chat warns once and uses defaults.
- If at least one skill survives, chat builds a temporary plugin directory (removed when chat exits) with `.claude-plugin/plugin.json` (`{"name": "ralph"}`) and `skills/<name>` as symlinks to the skill directories. Each turn adds `--plugin-dir <dir>`. Skills appear as `ralph:<name>`.
- Skills are read at start: changes to the list need a restart.

## Images

- Ctrl-V (macOS only) runs `osascript` to write the clipboard as PNG to `<store>/attachments/.clipboard-<pid>.tmp`, then `attachment::parse_image` checks it. A valid image is renamed to `<sha256>.<ext>` (same image, same file; nothing is ever deleted) and `[Image #N: <absolute path>]` is inserted at the cursor. `N` is one above the largest `[Image #N:` already in the draft (`attachment::next_number`), else 1. No image on the clipboard prints `No image on the clipboard.`; a bad image prints `Image paste failed: <error>` and removes the temp file.
- Limits: 10 MiB per image (`MAX_IMAGE_BYTES`); PNG, JPEG, GIF or WebP by magic bytes (the clipboard script always asks for PNG). No paste on Linux or Windows; a path typed by hand works the same way.
- The placeholder is plain text: `log.jsonl`, history and memory hold only the text with the path, never the image bytes. Claude reads the image itself with its Read tool when it sees the path. Chat creates `<store>/attachments` at start and each turn passes `--add-dir <store>/attachments` (`build_attachments_args`), so a store outside the working directory still reads without a prompt.
- Workers: placeholders in `spawn_worker` task or `reply` text pass through unchanged. Claude workers get `--add-dir <store>/attachments`; opencode workers get `permission.external_directory` for `<store>/attachments/**` (see [MCP tools](#mcp-tools)).

## Storage and isolation

- Global store `~/.ralph/chat`: `log.jsonl`, `tree.jsonl`, `LOCK`, `history.txt`, `editor.md`, `mcp.json`, `usage.jsonl`, `attachments/`. It is not project-scoped.
- `LOCK` is an exclusive file lock held for append, settled load, and the whole nap. Store paths that are symlinks or multiply-linked files are rejected.
- Isolation: `--setting-sources project,local` plus a `claudeMdExcludes` entry for `~/.claude/CLAUDE.md` when the home directory is known. Project and local settings stay active; this is context isolation, not a sandbox.
- User agents in `~/.claude/agents` do not load, so `build_agents_args` passes the bundled `SUBAGENTS` (`evidence-collector` haiku, `implementer` sonnet, `reviser` opus) as `--agents <json>`. These copies may drift from `~/.claude/agents`.
- Turns and claude workers run with the chat's resolved permission mode (default `auto`). The chat process adds `--permission-mode <MODE>` to each claude worker command, so chat and workers never differ. opencode workers ignore it.

## Usage

Every completed Claude call (each turn, including failed exits but not interrupted ones, and each nap attempt) appends one line to `usage.jsonl`: `{at, kind, trigger, input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens, cost_usd, duration_ms}`, with `kind` `turn` or `nap`, and `trigger` (turn only) `user`, `worker` or `private`. Turn lines also carry `view_bytes`, `view_lines`, `view_head_hash` (FNV-1a 64 of the first 1024 bytes of the rendered view) and `view_hash` (of the whole view), to trace prompt-cache misses. Calls without usage data append nothing. Appends do not take `LOCK`. Total cost per kind:

```bash
jq -s 'group_by(.kind) | map({kind: .[0].kind, usd: (map(.cost_usd // 0) | add)})' ~/.ralph/chat/usage.jsonl
```
