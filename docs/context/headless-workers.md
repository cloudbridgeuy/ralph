# Headless workers

Worker hosting and chat-owned lifetimes are separate from the selected agent. For spawn, reply, reporting and close behavior, see [ralph chat](ralph-chat.md#mcp-tools); for home-directory cleanup, see [Worker leftovers](worker-leftovers.md).

## HarnessId and compatibility

`HarnessId` (`crates/core/src/worker/kind.rs`) selects the agent and describes how its worker is hosted:

| Harness | Name | Hosting |
| --- | --- | --- |
| `Claude` | `claude` (default) | One tmux session per worker |
| `Cursor` | `cursor` | `[cursor] permissions = "ask"`: one `agent acp` child per worker. `"yolo"`: one `agent -p` child per turn. Both owned by `CursorHost` |
| `Opencode` | `opencode` | One session per worker on the chat's shared `opencode serve`, owned by `OpencodeHost` |
| `Codex` | `codex` | One `codex app-server --listen stdio://` child per worker, owned by `CodexHost` (`crates/ralph/src/codex_worker.rs`) |
| `ClaudeHeadless` | `claude-headless` | One `claude -p` stream-json child per worker, owned by `ClaudeHeadlessHost` (`crates/ralph/src/claude_headless_worker.rs`) |

`HarnessId` replaces the old Cursor boolean in `RunningWorker`, `WorkerObservation` and `CloseState`, and spawn commands carry it. The separate `opencode` boolean remains as agent/session metadata, not the hosting discriminator. For example, `close_plan` can remove an old opencode session before closing a claude worker when that metadata is present.

`RunningWorker.kind` serializes as `"kind": "claude"`, `"cursor"`, `"opencode"`, `"codex"` or `"claude-headless"`. Its serde `alias = "cursor"` and `HarnessId`'s custom deserializer let old records with `"cursor": true` load as `Cursor`, `"cursor": false` as `Claude`, and the old `"tmux"` kind string as `Claude`. If neither field is present, the kind defaults to `Claude`; the `opencode` boolean does not infer a kind. Saving emits `kind`, not the old `cursor` key. Unknown kind strings are rejected. These are serialization compatibility rules, not a migration of the harness-specific owner/session files.

The shell discovers running kinds from tagged tmux sessions, this chat's Cursor owner files, Codex owner files and opencode owner files (`workers::running_workers`). Close separately derives the kind from a Cursor owner file first, then a Codex owner or session file, then an opencode owner or session file, otherwise `Claude`. This live kind drives the close steps and the cleanup. Only the `turns` field of the close row also uses the `harness` of the spawn record (see the `close` row notes); a worktree's `opencode.json` supplies cleanup metadata but does not by itself select `Opencode`. A tmux `Claude` worker also passes `--mcp-config <store>/workers/<id>.json` (mode `0600`, the same merged file as `claude-headless`: the `[chat] mcp_servers` entries copied from `~/.claude.json` plus `ralph-worker` last), then `--strict-mcp-config`, then `--allowedTools` with the `ralph-worker` tools and `mcp__<name>__*` per copied server, always followed by another flag and never by the task pointer. A ralph config that fails to load does not stop the import: the tmux spawn falls back to the default list (`["mcptools"]`) and no `config_dir`, as chat and the headless host do. A missing name warns through the start warning and the spawn goes on; so does a reserved name (`ralph-worker` or `ralph-chat`), with `worker: MCP server "<name>" is reserved by ralph; continuing without it`, and it is never imported or allowed as `mcp__<name>__*` (`worker::import_servers`); close and a failed spawn delete the file. It reads its task from `<store>/workers/<id>.task/task.md`, named by the last argv item, so the task text stays out of `ps` (see [spawn_worker](ralph-chat.md#mcp-tools)); close deletes that directory. The monitor captures panes only for `Claude`; checks for the headless harnesses use markers and omit tmux attach hints (`chat/monitor.rs`, `core/src/worker_check.rs`).

## One host per harness, owned by the chat

`HeadlessHost: Send + Sync` (`crates/ralph/src/workers/headless.rs`) is the shared lifecycle interface, not a per-worker interface:

| Method | Contract | Current implementations |
| --- | --- | --- |
| `resume(&self)` | Resume persisted workers or supervise shared resources on a dedicated thread | `CursorHost` calls `resume_all` to load eligible ACP session records; `CodexHost` and `ClaudeHeadlessHost` resume their session records through the shared `codex_worker::resume::Resumed`; `OpencodeHost` runs its server/event supervision loop (its constructor loads session records) |
| `poll(&self) -> bool` | Process queued worker requests; return false after host shutdown to end the poller | Each host consumes its own handoff directories; opencode also handles preflight requests |
| `shutdown(&self)` | Stop this host's resources at chat exit, never on an individual close or report | Cursor terminates its owned worker groups, including starts in progress, and skips a worker whose `agent acp` already exited and was reaped (its group was killed then); opencode stops the shared server process group and sweeps tracked descendants |

`chat::monitor::watch_headless` constructs `HeadlessShutdown` with an `Arc<dyn HeadlessHost>` for each of `CursorHost`, `OpencodeHost`, `CodexHost` and `ClaudeHeadlessHost`. Each host gets a separate resume thread and a separate poll thread, sleeping `HANDOFF_POLL` (250 ms) between polls. Blocking ACP or HTTP handoffs therefore do not hold up the other host or the status/check loop.

Cursor's `AcpWorker` and opencode's per-session `OpencodeSession` implement the core `HeadlessWorker` port (`capabilities`, `send`, `poll`). `send` runs `decide` first, then maps `Prompt`, `AnswerPermission` and `Close`; `Spawn`, `Resume` and `Interrupt` return an error because the host handles them (interrupt keeps the inherent `AcpWorker::interrupt`, which needs the result entry id). Turn start, turn end, permission changes and close push `WorkerEvent`s to a per-worker sink. Each 250 ms `CursorHost::poll` drains every worker, runs `reduce` and applies the effects: `blocked` and `waiting` markers are set and cleared there, and close clears `ready`, `blocked` and `waiting`. `unreported` and its `waiting` write stay direct; the `ready` write at spawn stays direct; `ReplyText` effects are ignored. `OpencodeSession` is a short-lived view built per request by `OpencodeHost::worker` (the API handle, the front pending permission and the session's shared event sink). Its `send` maps `Prompt`, `Interrupt` (full: a synchronous `POST /api/session/{id}/interrupt`, whose `{"interrupted":bool}` body becomes `WorkerEvent::Interrupted`; a failed call warns and yields outcome `None`), `AnswerPermission` and `Close` (`DELETE /api/session/{id}`, then `Closed`); `Spawn` and `Resume` return the host-handles-it error. `OpencodeHost::run` turns each `Effect` into events (`Ready`, `TurnStarted`, `PermissionAsked`, `PermissionSettled`) and `apply_events` polls them, runs `reduce` and applies the marker effects at once; `reported` clear, `unreported` and its `waiting` write, and the ready write at spawn stay direct. The interrupt outcome reaches chat through `<store>/opencode-interrupt-result/<id>/<entry>` (`cancelled` or `sent`), awaited by `Workers::reply` like Cursor's; a failed interrupt writes nothing, so chat reports the outcome unknown after 30 s. ACP `decode_update` emits `WorkerEvent::Activity { at }` for every `session/update` frame (plus `Reported` for the report tool call), and the notification handler writes it to the activity marker through `Heartbeat::touch_at`. opencode's `session_activity` does the same for every session-tagged SSE event; `OpencodeWorker::route` writes it through `touch_at` (turn start and end still call `set_running`).

The chat keeps the `HeadlessShutdown` guard alive across its input loop. Dropping it, including on an early error return, shuts down hosts in reverse construction order. `ExitCleanup` holds clones of the same hosts: on input loss it kills watches, calls each host's shutdown, then the input watcher exits the process. Shutdown must tolerate repeat calls. It is per host and chat-owned, not per worker: `close_worker` uses worker-specific close handoffs and never calls `HeadlessHost::shutdown`. Closing even the last opencode worker leaves the server available for the next spawn; a report does not stop either host.

## Adding the next headless harness

The shared trait unifies lifecycle orchestration only; it is not a plugin registry or a generic spawn/reply protocol. A future headless Claude or Codex adapter needs the following wiring, following the existing Cursor and opencode implementations:

1. Add the harness choice, argument validation and MCP schema in `crates/core/src/worker.rs`, and its preflight/spawn handoff in `crates/ralph/src/workers/spawn.rs`. `claude` is the tmux harness and the default; `claude-headless` is the opt-in stream-json harness served by `ClaudeHeadlessHost`. `codex` is served by `CodexHost`; `spawn_headless` in `workers/spawn.rs` is shared by cursor and codex.
2. Add a `HarnessId` variant if it uses a new hosting mechanism. Update both `HarnessId`'s serialized variants and its compatible deserializer; preserve the old boolean mapping and default. Extend running-worker discovery, ownership, reply/nudge/permission routing and close-kind detection in `workers.rs`, plus pane/check handling in `chat/monitor.rs` and `core/src/worker_check.rs`. These paths still have explicit harness/kind branches.
3. Implement `HeadlessHost` for the adapter and register one host in `HeadlessShutdown::new`. Keep resume/supervision and request polling independent, honor the closed state and make shutdown safe to repeat. No new harness-specific lifecycle loop or exit guard belongs in chat orchestration.
4. Keep worker close separate from host shutdown. Extend the pure `close_plan`/`CloseStep` dispatch in `core/src/worker/ownership.rs` and the shell's step executor only as needed. Shared resources must survive another worker's close. Keep home-directory cleanup explicitly scoped by kind, rather than treating every non-tmux worker as Cursor.
5. Reuse the worktree, marker and `ralph-worker` report contracts. Add pure/unit coverage for serialization compatibility, close isolation, discovery/check behavior and lifecycle dispatch, following the existing tests; update the harness details and cleanup docs alongside the adapter.

## Codex hosting

`CodexHost` (`crates/ralph/src/codex_worker.rs`) mirrors `CursorHost`. Spawn writes `<store>/codex-spawn/<id>`; the host starts `codex app-server --listen stdio://` in the worktree and writes the owner file `<store>/codex/<id>` at once. Pure protocol lives in `crates/core/src/worker/codex/` (`rpc.rs`: framing and request ids; `protocol.rs`: params, version, login and model checks, MCP startup verdict).

Start order, all inside a 20 s deadline: `initialize` (`experimentalApi`), `initialized`, version check, `account/read`, `model/list` (always, paged; checks model and effort), `thread/start` or `thread/resume`, wait for `mcpServer/startupStatus/updated` of `ralph-worker` to reach `ready`, `turn/start` with the task as the first turn, then `ready/<id>`. The session record is written after the first turn ends ok, not before it. Version rule: older than 0.162 fails; 0.162 up to the probed 0.164.x passes; a newer minor passes with a warning through `crate::warn::warn` unless `ralph worker verify codex` recorded that version (probed 0.164.0; 0.162.1 earlier).

`thread/start` sets `approvalPolicy: "on-request"`, `approvalsReviewer: "user"`, `sandbox: "workspace-write"` and a runtime `config.mcp_servers.ralph-worker` entry (`required: true`, `default_tools_approval_mode: "approve"`, so the `report` tool needs no elicitation). Server requests that are not approvals (and approvals of a stale `turnId`) are answered with JSON-RPC error -32601, so they fail closed. Approvals follow the permission flow below.

`resume` is Partial: needs saved history, worktree and codex login; `close` is Full: an in-memory trust override stops Codex writing a global trust entry (GUZ-847, see Codex resume and close). `heartbeat` is Partial: app-server frames count as activity, not progress; silent long tools can yield false Quiet; 300 s default (GUZ-648). Every app-server stdout line (handshake, deferred, hook and unmapped frames included) calls `Heartbeat::touch`. A notification that ralph does not map is logged once per method per worker to `acp-logs` with tag `unmapped`, never to the chat. `TurnStarted` and `TurnEnded` set the running flag. Child exit shows as stdout EOF in the pump thread or as `try_wait` in `CodexWorker::poll`; a shared flag lets the first one write `gone/<id>` and push `ProcessGone` once, and never after a close; `poll` always `try_wait`s a live child, so an EOF-first exit is still reaped. Live check (codex-cli 0.164.0, `worker_quiet_secs = 10`, `worker_check_secs = 2`): during `sleep 75` frames came at gaps of 31, 17 and 20 s, giving 3 Quiet episodes, 3 `quiet` alerts and 3 recoveries; an idle worker posted no Quiet; an unmapped `skills/changed` frame touched activity while idle; `kill -9` of an idle app-server posted one Dead message within 1 s, none in the next 25 s, and the child was reaped. `perm-ask` is Partial: protocol-raised requests only. `perm-yolo` is Partial: single-request accepts only (GUZ-647). `interrupt` is Partial: outcome unknown after 30 s.

Codex permissions (GUZ-647): `[codex] permissions` (`"ask"` default, `"yolo"`) is read when a worker starts; a wrong value warns and uses `ask`. Pure classification is in `crates/core/src/worker/codex/approvals.rs`; permission answers match by request id, never by queue position (see [Permission request ids](#permission-request-ids)); the queue, `blocked` marker and one `blocked` inbox report are the same host code Cursor uses (`crates/ralph/src/permission_queue.rs`, `PermissionOption`/`BlockedContent`/`PermissionMode` in `core/src/worker/permissions.rs`). Handled requests: `item/commandExecution/requestApproval` (options are the request's `availableDecisions` strings, or accept/decline/cancel when absent), `item/fileChange/requestApproval` (accept/decline/cancel), `mcpServer/elicitation/request` (accept/decline/cancel when `_meta.codex_approval_kind` is `mcp_tool_call`, else decline/cancel) and `item/permissions/requestApproval` (only `decline`, which grants nothing). `acceptForSession`, `*Amendment` decisions and persist options are never published or picked. Replies are `{decision}` for commands and file changes, `{action}` for elicitations (no `persist`, no `content`) and `{permissions: {}, scope: "turn"}` for a grant. `yolo` answers `accept` at once for commands, file changes and tool-call elicitations when `accept` is offered; everything else waits for the person. The person answers through `reply` with `request` (the JSON-RPC id as a string) and an exact `optionId` (`<store>/codex-answer/<id>`); only the request with that id gets the answer. `serverRequest/resolved` drops the request and clears the marker when none remain; an interrupt drops all pending requests without answering, because Codex settles them itself. A later answer for a settled request is refused through `codex-error/<id>`. `item/permissions/requestApproval` never fired in the probes, so that path is untested live.

Codex interrupts use the Cursor transport: `reply` writes `<store>/codex-interrupt/<id>/<entry>` and polls `<store>/codex-interrupt-result/<id>/<entry>` (250 ms, 30 s). `Turns` reads the turn id from the `turn/start` reply (`result.turn.id`; `turn/started` is the fallback). A running turn gets `turn/interrupt {threadId, turnId}`, sent without waiting for its reply. The result file says `cancelled` only after `turn/completed` of that turn with `status: interrupted`; the interrupt prompt starts right after, before queued replies. A turn that ends `interrupted` with no `turn/interrupt` sent by ralph is treated as an unreported end and gets the reminder (GUZ-953). An idle worker, or a `-32600` reply, writes `sent` (nothing cancelled) at once. A missing reply writes nothing, so chat reports the outcome unknown. Frames that arrive while a request waits for its reply are kept and handled in order afterwards, and events whose `turnId` is not the current turn are dropped. The interrupted tool process keeps running (ralph does not kill it); its late events carry the old `turnId` and are dropped.

Live check 2026-10-23, codex-cli 0.164.0 (`ralph chat` reply tool): `turn/start` replied `result.turn.id`. An interrupt during `sleep 60` sent one `turn/interrupt`, which got `{}`, then `turn/completed` `interrupted` in the same second, and reply said cancelled. The next `turn/start` followed at once, and its report was counted. The sleep kept running, and its `item/completed` came 8 s into the next turn with the old `turnId`. An idle interrupt sent no `turn/interrupt`, and reply said nothing was cancelled. No `-32600` or missing reply happened, so those paths were not tested live.

Permission live check 2026-10-23, codex-cli 0.164.0, a network `curl -sI` under `on-request`. Ask: `item/commandExecution/requestApproval` offered `[accept, acceptWithExecpolicyAmendment, cancel]`. `blocked/<id>` listed only `accept` and `cancel`, with one `blocked` inbox report. The reply `accept` sent `{"decision":"accept"}`, Codex returned `serverRequest/resolved`, and the command ran. Yolo: the same request got `{"decision":"accept"}` in the same second, with no marker and no `blocked` report. Interrupt while blocked: ralph sent no answer. Codex ended the turn `interrupted` and resolved the request itself, the marker cleared, reply said cancelled, and the next prompt ran. File-change, elicitation and permissions-grant requests did not come up, so they were not tested live.

A plain `reply` to a headless worker waits up to 5 s for uptake: the prompt entry file gone means taken, `activity/<id>` `running` means busy (see [reply confirmation](ralph-chat.md#mcp-tools)). Codex replies use the Cursor transport: `reply` writes `<store>/codex-prompt/<id>/<entry>`, `CodexHost` polls it and hands the text to the worker, whose pump thread holds it in the shared `PromptQueue` (`crates/core/src/worker/codex/turns.rs`). The next `turn/start` goes out only after `turn/completed`, because the GUZ-643 probe showed a `turn/start` during a running turn merges into it. `item/completed` of an `mcpToolCall` (`ralph-worker`, `report`, `completed`) emits `Reported`. A turn that ends without a report gets one `REPORT_REMINDER` turn; if that also ends unreported the worker writes the `unreported` and `waiting` markers, as Cursor does. A failed turn, or one that ends with a stop reason, posts a `blocked` prompt-failure report to the inbox as Cursor does; a turn ralph interrupted posts nothing, and one interrupted without a ralph request gets the reminder. Each turn end takes a snapshot first (unless closing), before any reminder or queued `turn/start`. Stdout EOF writes a `gone` marker unless the worker is closing. Close order and the trust override are in Codex resume and close.

### Codex resume and close

Record (GUZ-649): `<store>/codex-session/<id>` holds `session_id` (thread id), `cwd`, `inbox`, `store`, `model`, `effort` and `permissions`. It is written after the first ok turn, kept on chat shutdown, and removed by explicit close (a worker quit before its first ok turn has none). The rollout under `~/.codex/sessions` is never touched.

Resume runs on chat start (`CodexHost::resume_all` through `Resumed` in `crates/ralph/src/codex_worker/resume.rs`, decision `resume_decision_for` in `core/src/worker/codex/resume.rs`; claude-headless uses both with the agent `claude-headless`). It claims `<store>/codex/<id>` atomically (create-new); if another chat owns it, the id is skipped with `codex session <id> not resumed: a running chat owns it`. A skip or failure warns and writes `codex-error/<id>` (not for the owned case); the record stays. Strings, all prefixed `codex session <id> not resumed: `: `its record is unreadable`, `the record has no owner`, `it belongs to the chat store <a>, this chat uses <b>`, `its worktree <path> is gone`, `could not claim it: <e>`, `could not find the ralph executable`, then the start error. A resumed worker sends `thread/resume` with the record's model, effort and permissions, checks the returned thread id equals the record's (else `codex resumed thread <a> instead of <b>`), posts no replayed report, and on success removes `codex-error/<id>` and prints the green `✓` notice `codex session <id> resumed` (`warn::notice`). Resume of every harness runs on a background thread, so its warnings usually come while the chat prompt is open; they print above the prompt (see [ralph chat](ralph-chat.md)). `[codex] model` and `effort` are validated against `model/list` at spawn.

Close order (`codex_close_plan`): wind down (mark closing, drain pending permission requests and RPCs), wait up to 3 s (`CODEX_CLOSE_TURN_WAIT`) for a running turn to end after `turn/interrupt`, drop stdin, snapshot the descendant tree with each start time, TERM then KILL the app-server group, sweep the snapshot entries whose pid and start time still match, then check again after KILL and log any survivor to `acp-logs` with tag `sweep`, remove the owner file. Close then removes `ready/<id>`, the session record and the close marker.

`thread/start` writes a global `[projects."<repo>"] trust_level = "trusted"` entry to `~/.codex/config.toml` unless the project is already trusted. Ralph passes an in-memory `projects."<cwd>".trust_level = "trusted"` override on `thread/start` and `thread/resume`, so Codex writes no trust entry (GUZ-847). The /tmp and /private/tmp forms both matched.


### Permission request ids

Each pending request carries `request_id` in `BlockedContent`: the ACP JSON-RPC id from `Responder::id()` (Cursor), the app-server JSON-RPC id (Codex), the `control_request` `request_id` (claude-headless), or `PermissionAsked.id` (opencode). The id is an opaque string. Cursor, Codex and claude-headless publish `{pid}-{started_ms}.{raw}`: the token is made once per host spawn, so an id from an older host process never matches a new request, and the wire reply keeps the raw id (`worker::process_request_id`). Opencode ids are unchanged. An old unprefixed id fails as stale. `blocked/<worker id>` holds the front request (`request_id`, `tool`, `summary`, `options`) and `pending`, the ids of every queued request in order (`worker::pending_requests`). The id also shows in the `blocked` inbox alert (Cursor, Codex, claude-headless) and in reply errors. `reply` with `request` writes `<store>/<harness>-answer/<worker id>` as JSON `{request_id, option_id}` (`worker::PermissionAnswer`). The file is keyed by the worker, so one reply runs at a time: it holds an exclusive lock on `<store>/.answer-<id>.lock` (the answer is staged at `<store>/.answer-<id>` and renamed into place) from clearing the error file to reading it, waits for that lock for up to 30 s, and fails with `another reply to worker <id> is still in progress` when that passes. Once the lock is held there are two fresh 30 s deadlines: one for an earlier claim to clear, then one for the handoff, so a reply can take about 90 s with the lock wait. The host claims the answer by renaming it to `<store>/.claimed-<harness>-answer-<id>` before it acts and deletes the claim last, so a reply is done only when the answer and the claim are both gone, and the next reply first waits for any claim to clear. When the deadline passes, the reply removes the answer if it is still there (`ralph chat did not pick up the permission answer in time`), and otherwise reports `outcome unknown`. The host looks the id up with `worker::pending_position` and removes the request once answered. An unknown, settled or already answered id fails with `stale request <id>; pending: <ids>`. A `reply` without `request` to a blocked worker fails with `this worker is waiting on a permission request; pass request. pending: <ids>`. Opencode removes its request on `permission.replied`. Claude tmux workers have no request ids. Action digests and signed approvals are GUZ-1054.
## Claude headless hosting

`claude-headless` runs `claude -p --verbose --input-format stream-json --output-format stream-json --permission-mode <mode> --permission-prompt-tool stdio` in the worktree, where `<mode>` is `default` for `[claude] permissions = "ask"` and `auto` for `"yolo"`, with a config file passed through `--mcp-config` and `--strict-mcp-config` after it, so only servers in that file load, as in chat. The file is `<store>/workers/<id>.json` (mode `0600`, `worker::worker_config_path`). It holds the `[chat] mcp_servers` entries copied from `~/.claude.json` (`select_servers`, default `["mcptools"]`) and `ralph-worker`, inserted last so an import cannot shadow it (`worker::merged_mcp_config`). A file keeps copied tokens out of argv. The write refuses a symlink or a multi-link path (`private_file::check_path`) and opens with `O_NOFOLLOW`, so a symlink planted between the check and the open fails the open and its target is never truncated. A name missing from `~/.claude.json` warns `worker: MCP server "<name>" not found in ~/.claude.json; continuing without it` through the start warning, and the spawn goes on; a reserved name (`ralph-worker`, `ralph-chat`) warns `... is reserved by ralph; continuing without it` and is dropped before the merge, so `--allowedTools` never lists a copied `mcp__ralph-worker__*`. The version gate warning and every missing-name warning are collected and written once to `<id>.warning`, joined with `; ` (`worker::join_start_warnings`), so none overwrites another. The host rewrites the file on every start, resume included, so config changes apply at the next start. Close removes it, and so does every failure path of the host start (`worker::cleanup` lists `RemoveConfig` for a failed `claude` spawn, a failed owner or record write, a failed init, and a spawn that is not adopted). `--allowedTools` pre-allows the own tools (`mcp__ralph-worker__report`, `mcp__ralph-worker__set_status`) and `mcp__<name>__*` for each copied server, so they never ask, and the attachments dir through `--add-dir` (`worker::claude_headless_args`). A new spawn passes `--session-id <uuid>`, a v4 uuid ralph makes before spawn (`worker::uuid_v4` over 16 bytes read from `/dev/urandom`); a resume passes `--resume <session_id>` and never `--session-id`. `CLAUDE_CONFIG_DIR` follows `[claude] config_dir`. Before spawn, `claude --version` passes the shared version gate (`worker::check_agent_version`, `CLAUDE_GATE`): older than 2.1 fails, newer than the probed 2.1.314 warns.

The host writes the task as a stream-json user line, then waits up to 20 s for the `system`/`init` line; init fails when it has no `session_id` or when `mcp_servers` lists `ralph-worker` as not connected. Turns reuse Codex's `Turns`: a `tool_use` of `mcp__ralph-worker__report` counts as reported, a `result` line ends the turn (`is_error` posts a failure report), an unreported turn gets one reminder and is then marked waiting, and a reply during a turn waits for its `result` (`worker::decode_line`). The `init` session id must equal the id ralph passed (`worker::resumed_session`), else init fails. Every stdout line touches the heartbeat. EOF without a close writes `gone/<id>`. Close drops stdin, stops the process group, sweeps the tree and removes `claude-headless/<id>`; a new host sweeps stale owners.

Close cleans the worktree's `~/.claude/projects` folder as for tmux claude workers (`cleans_claude_leftovers`).

Usage (GUZ-1258): a claude-headless worker appends the same worker usage rows as a tmux claude worker (see ralph-chat.md), with `harness` `claude-headless` and no `turn_id` (headless takes no snapshots). It reads the session transcript at `<claude dir>/projects/<transcript_dir_name(worktree)>/<session_id>.jsonl` (`claude_leftovers::claude_transcript_path`) and its subagent transcripts through `worker_usage::record_session`, with the same `<store>/workers/<id>.usage-seen` file, so a row is written once. The claude dir is the one the spawned claude uses (`claude_leftovers::spawned_claude_dir`): `[claude] config_dir` when set (ralph passes it as `CLAUDE_CONFIG_DIR`), else a `CLAUDE_CONFIG_DIR` that claude inherits from the chat, else `~/.claude`. claude 2.1.317 builds the folder as `path.join(CLAUDE_CONFIG_DIR ?? ~/.claude, "projects")`: it does not resolve the value or expand `~`, and it keeps an empty value. So ralph joins the inherited value onto the worktree (claude's cwd): an absolute value stays, a relative one starts at the worktree, and an empty one gives `<worktree>/projects/...`. It records when a turn ends (each `result` line, failed and interrupted turns too), when claude exits, and when the worker stops (`release_owner`), before the host removes `claude-headless/<id>`. Close waits for that owner file before it removes the transcript folder, so the last turn is recorded first. A lock lets one record run at a time, and the record at close is the last one: a later record (for example the reader thread's record after claude exits) does nothing, because close then deletes the `.usage-seen` file and a new record would write every message again. It does not read the `result` line: its `modelUsage` and `total_cost_usd` are running totals for the process, and `modelUsage` has no 5m/1h cache-write split or prompt tier for each call. `cost_usd` is null and `/workers costs` prices the row from its tokens. A message that is not finished in the transcript when a turn ends is recorded at a later turn end, exit or close. Limit: a close with no live worker process in this host (for example after a chat crash that was not resumed) records nothing, so the rows of the last turn that were not yet recorded are lost.

Claude headless resume (GUZ-1114): `<store>/claude-headless-session/<id>` holds the same `SessionRecord` as Codex (`session_id` is the uuid ralph passed as `--session-id`, `cwd`, `inbox`, `store`, `model`, `permissions`). It is written in `start` before the first turn is sent, so a crash in turn 1 is resumable. It is rewritten in `adopt`, removed when init fails or the worker is not adopted, kept on chat shutdown, and removed by close. On chat start `ClaudeHeadlessHost::resume` runs the Codex resume flow and strings with the prefix `claude-headless session <id> not resumed: `, then starts `claude --resume <session_id>` in the record's `cwd` with the record's model and permission mode. claude prints no `system`/`init` until it reads a user line (probe on 2.1.316: with stdin closed at once it printed only `SessionStart` hook lines and exited 0), so a resumed worker is ready once the process starts and sends no task; the first `init`, at the next reply, must carry the recorded session id, else the worker posts a `blocked` report `claude resumed session <a> instead of <b>` (`worker::resumed_session`). A turn running when the chat exits is lost and not re-sent. On chat exit `shutdown` (`worker::shutdown_steps`) posts a `blocked` report that the turn in flight was lost and must be prompted again, removes the activity marker right away, then stops the worker (stdin closed, 500 ms, then group TERM, 3 s, KILL, then the process tree sweep), so an exit cut short after the report leaves no `running` marker and resume posts no second report. After a crash or `kill -9` that marker still says `running`; `resume` reads it before `start` clears it and, once the worker is adopted, posts the same report (`worker::turn_lost_at_resume`). The report does not say whether the transcript kept a partial turn. A spawn still starting at chat shutdown is in the host's `starting` list and its process group is stopped, as for Codex. `resume` is Partial: turn in flight reported, not re-sent; same cwd required. A moved or deleted worktree is skipped; a changed `[claude] config_dir` makes `--resume` miss the transcript.

Claude headless interrupts (GUZ-1113) use the Cursor transport: `reply` writes `<store>/claude-headless-interrupt/<id>/<entry>` and polls `<store>/claude-headless-interrupt-result/<id>/<entry>` (250 ms, 30 s). The stream has no turn id, so the host binds a synthetic one at each turn start. A running turn gets a `control_request` with subtype `interrupt` on stdin and each pending permission request id gets a `deny` `control_response` line before the interrupt line; the interrupt `control_response` is ignored. From the drain until the interrupted turn ends (`TurnEnded`), the queue refuses new `can_use_tool` requests and ralph answers each with `deny` at once, so a request that races the interrupt is never left unanswered. The error `result` that follows counts as interrupted when ralph sent the interrupt; on claude 2.1.316 (Haiku live run, GUZ-1113) it is `subtype: "error_during_execution"`, `is_error: true`, `terminal_reason: "aborted_tools"`, and claude stops the running tool itself. A `can_use_tool` request still pending at the interrupt gets a `control_cancel_request` from claude, and ralph's drain leaves nothing pending. When claude's stdout closes, `Turns::process_gone` writes `gone` for every pending interrupt, and any later interrupt to that worker gets `gone` at once; an interrupt entry for a worker the host does not hold also gets `gone` (GUZ-1124). `Workers::reply` words `gone` as the worker exited and the message was not delivered (`InterruptOutcome::Gone`; Cursor, Codex and opencode never write it). Only the Cursor print host writes `dropped` (through `Turns::interrupt_dropped`, which clears the sent flag and keeps the interrupt text queued) (`InterruptOutcome::Dropped`): the interrupt was not sent, and `Workers::reply` words it as the interrupt not sent and the message running next. `interrupt` is Partial: outcome unknown if claude ignores the interrupt for 30 s.

Claude headless permissions (GUZ-1112): `--permission-prompt-tool stdio` makes claude send a `control_request` with subtype `can_use_tool` on stdout when its permission mode would ask; `ask` spawns `--permission-mode default` so writes and shell calls ask, while `yolo` spawns `auto` and allows what still asks (`worker::decode_line` gives `ClaudeLine::Permission`). ralph synthesizes two options, `allow_once` and `deny`; the summary is the request `description`, else the input `command` or `file_path`, else the tool name. The answer is a `control_response` line on stdin with `{"behavior":"allow","updatedInput":<the request input>}` or `{"behavior":"deny","message":...}` and never `updatedPermissions`, so it covers that one request (`worker::permission_response`). `[claude] permissions` (`"ask"` default, `"yolo"`) is read when a worker spawns, so the mode is per spawn and a resumed worker keeps the mode in its session record; a wrong value warns and uses `ask`. `yolo` answers `allow_once` at once with no `blocked` marker (`worker::auto_answer`). Under `ask`, allow rules in the project or user `.claude/settings.json` (under `config_dir` when set) still skip the prompt, because claude sends no `can_use_tool` for them. A permission line with no `request_id` or no `input` object gives `ClaudeLine::Malformed`: the worker posts one `blocked` inbox report and queues nothing. A `control_cancel_request` without a `request_id` is ignored. `ask` uses the Cursor and Codex queue, `blocked` marker and one `blocked` inbox report (`crates/ralph/src/permission_queue.rs`); the person answers through `reply` with `request` and an exact `optionId` (`<store>/claude-headless-answer/<id>`), matched by request id (see [Permission request ids](#permission-request-ids)). A `control_cancel_request` drops that request; close drops all pending requests. In claude 2.1.316 an aborted `can_use_tool` request writes `control_cancel_request` before the turn's `result` line, so the worker does not drain the queue at turn end: draining would drop a live request from a background task. `reduce` already clears the `blocked` marker on `TurnEnded`. The wire shapes come from the CLI schema of 2.1.314; the GUZ-1113 live run on 2.1.316 saw `can_use_tool` and `control_cancel_request` arrive in that shape, while the allow and deny answers are not probed live yet.

## Cursor print fixtures

`crates/core/src/worker/cursor_print/fixtures/` holds four hand-built `agent -p --output-format stream-json` transcripts: `success`, `tool`, `interrupted` (no `result` line) and `crash` (init only). The shapes are inferred from the GUZ-1311 brief, not recorded from a real `agent` run. Core tests `include_str!` them (`fixtures_tests.rs` checks JSON validity, the `result` usage keys and one `session_id` per file).

`stub-agent.sh` replays a fixture for manual host runs and the paid verify, never for cargo tests. Pass the scenario as the first argument or set `STUB_AGENT_SCENARIO` (default `success`). It discards stdin to EOF, prints the fixture, then `interrupted` waits for a signal and exits 130 and `crash` exits 1.

Print-mode core (`crates/core/src/worker/cursor_print.rs`, pure; GUZ-1325):

- `print_args(&PrintArgs { workspace, model, resume })` builds `-p --output-format stream-json --trust --approve-mcps --workspace <wt> --model <variant>`, then `--resume <chatId>` when `resume` is set (the first turn has none), then `--force` (the print path only runs for yolo workers). The prompt goes on stdin, never in argv.
- `decode_print_line(line, model)` gives a `PrintEvent`: `Init(chat id)` from `system/init` `session_id`, `Activity` from `assistant` lines and from `tool_call` `started` and `completed`, `Result { end, usage }` from `result` (`TurnEnd::Succeeded`, or `Failed` when `is_error` is true), and `Ignored` for a malformed, unknown or id-less line. It never panics.
- `exit_outcome(saw_result, sigint_sent)` gives `ExitOutcome`: a `result` line means `Ended`; no `result` after ralph sent SIGINT means `Interrupted` (exit 130); no `result` otherwise means `ProcessGone`.
- `map_print_usage(&result["usage"], model)` maps `inputTokens` (already non-cached) to `input_uncached`, `cacheReadTokens` to `cache_read`, `cacheWriteTokens` to one `CacheTier::Unspecified` write (none when 0), and `outputTokens` to `output`, as a `ModelUsage`. The model is the configured variant, not the `init` model. A missing or non-numeric key gives `None`, not zeros.
- An interrupted turn writes no `result` line, so its tokens are lost (the same class as an opencode close).
- `turn_end_for(outcome, result)` gives the `TurnEnd`: `Interrupted` after an interrupted exit, else the `result` end, else `Failed` for an exit with no result. `next_chat(current, event)` takes the latest `Init` chat id. `print_model(model)` falls back to `auto`. `cursor_mcp_json(existing, entry)` merges the `ralph-worker` entry into `.cursor/mcp.json` and keeps other servers.

## Cursor print mode (yolo)

`CursorHost` picks the path when a worker starts. `[cursor] permissions = "yolo"` runs the print-mode host (`crates/ralph/src/acp_worker/print.rs`, `PrintWorker`). `"ask"` keeps the `agent acp` path and its permission flow unchanged. A resumed worker uses the path its session record names: a record with `permissions = "yolo"` is print mode.

- Per-turn process: no child lives between turns (the worker is idle, not dead). Each turn spawns `agent -p --output-format stream-json --force ...` in its own process group with the worktree as cwd, writes the prompt to stdin, closes stdin and reads stdout lines through `decode_print_line`. Expect a cold start of about 3 to 5 s per turn.
- The turn order is the shared `Turns` machine (queued prompts, interrupt, reminder), as for claude-headless. Every decoded line refreshes `activity/<id>`. The first `result` line fixes the turn end and the usage row. ralph then keeps reading stdout until EOF or a 1.5 s grace (`RESULT_GRACE`), so the agent can save its chat store before the group is stopped, and a later `result` line is ignored. An exit with no result fails the turn and writes `gone/<id>` with a `ProcessGone` event, which the next turn clears.
- Snapshots: when the spawn has snapshots, each turn that ends while the worker is not closing takes a worker snapshot turn, as for the ACP worker.
- Chat id: a new worker writes the session record (`cursor-session/<id>`, empty chat id) at start. The latest `system/init` `session_id` is written to the session record (`cursor-session/<id>`, `permissions = "yolo"`). Later turns pass `--resume <chatId>`. The first turn passes none.
- MCP: before the first spawn ralph merges the `ralph-worker` server into `<worktree>/.cursor/mcp.json` (other servers stay). Spawn adds `/.cursor/` to the repo's `.git/info/exclude`.
- Interrupt: SIGINT to the child's process group. TERM follows at 3 s only if the same turn is still Running (no `result` line yet), and KILL follows 500 ms later only if it is still the same Running turn. One mutex-guarded state (`TurnProc`: Idle, Starting, Running, Grace) decides each interrupt. An interrupt during start (from the start action until the child exists) is held and sent as soon as the child exists. An interrupt in Running goes to the group at once. One in the result grace (`RESULT_GRACE`, after the first `result` line) is dropped, so it cannot break the chat-store save the grace protects. One with no child and no start in progress is dropped, so it never hits the next turn. A dropped interrupt is not reported as sent: the shell calls `Turns::interrupt_dropped`, the interrupt result file says `dropped`, and the interrupt text stays queued and runs as the next prompt. A failed start, a close and every early exit return the state to Idle and discard a held interrupt. A turn with no `result` line after a SIGINT that ralph really sent to the group (`sigint_turn`, the spawn number of the signalled group, stored in `send_interrupt` before the signal goes out and compared with the turn's own spawn number, so a late signal for an earlier turn never counts) ends `Interrupted`; a dropped or discarded interrupt does not count; a `result` line wins and the turn ends normally. Close and chat exit stop a running child group.
- Stderr goes to the capped log `acp-logs/<id>.log`. The spawn version gate is the ACP one (`agent --version`).
- Worker-server sweep: `agent -p` leaves `node …/cursor-agent/versions/<v>/index.js worker-server` running in its own process group, which the child group kill misses, and reuses it between turns. Close and chat exit (`PrintWorker::terminate`) TERM, then KILL, the group of a process whose command contains `cursor-agent/versions/`, ends in `worker-server`, and holds the `worker.sock` of this worktree's socket project dir (found with `lsof`). The group must also hold only cursor install processes: a group with a root process outside `cursor-agent/versions/` is left alone (`cursor_group_reclaimable`). It never matches by name alone and never runs per turn. ACP workers leak the same server; their sweep runs in close cleanup (see [Worker leftovers](worker-leftovers.md)). The shell glue is untested.
- Permission requests do not exist in this mode: a permission answer for a print worker is refused.
- Usage: a `result` line with usable `usage` appends one worker usage row (see ralph-chat.md) through the shared ledger (`crates/ralph/src/cursor_usage.rs`, pure builder `print_usage_record`), with `harness` `cursor`, `model` the configured variant, `session_id` the chat id, `turn_id` the worker snapshot turn of that turn (absent without snapshots or when the worker is closing) and `cost_usd` null. The four counters map as in `map_print_usage`. A failed write only warns. `/workers costs` prices the row from its tokens, so the cost shows `n/a` (never 0) until `[wire.prices]` has an entry keyed on the exact Cursor model id. An interrupted or crashed turn writes no `result` line, so no row is written and its tokens are lost. The shell glue has no automated test; check it by hand.

## Verify an agent version

`ralph worker verify <cursor|codex|claude-headless|opencode|claude> [--live]` (`crates/ralph/src/worker_verify.rs`, `acp_worker/verify.rs`, `codex_worker/verify.rs`, `claude_headless_worker/verify.rs`, `opencode_worker/verify.rs`, `workers/verify.rs`) runs a local spec against the installed agent in a temporary directory and exits 0 only when every blocking check passes, the required protocol checks ran (`CURSOR_REQUIRED_CHECKS`: `initialize`, `session/new`; `CODEX_REQUIRED_CHECKS`: `initialize`, `initialized`, `thread/start`; `CLAUDE_HEADLESS_REQUIRED_CHECKS`: `version`, `spawn`, `argv`; `OPENCODE_REQUIRED_CHECKS`: `version`, `spawn`, `events`, `session/create`, `session/read`, `interrupt/idle`, `session/delete`; `claude_required_checks`: `version`, `tmux`, `flags`, and `session start` only with `--live`) and the agent version is known; an unknown version or a missing required check is a FAIL (`spec_passed`, `missing_checks`). Before the run, the Cursor `agent --version` probe has its own 10 s limit (`VERSION_PROBE_LIMIT`); for verify, a non-zero exit is a failed probe and output that is not UTF-8 is an unreadable version (`finished_probe`); a spawn stays silent on such a probe. A missing required check adds a `required` FAIL line only when no earlier check failed (`required_failure`). The whole run has a 90 s limit (540 s with `--live`, `verify_limit`). Cursor and Codex enforce it while they run: a codex timeout names that verify limit, not the 20 s spawn limit. opencode, claude-headless and claude check it before each step (`Budget::allows`, `limit_failure`): once the time is gone the next check fails with `the 90s verify limit passed before the <check> check ran`, and no later step starts. A step already running is not cut short, so those runs can pass the limit by up to the longest step after the last check that passed. opencode: about 235 s, the `permission` step (a 120 s `TURN_LIMIT` turn plus its 10 s requests, `REQUEST_TIMEOUT`, with up to 3 attempts each for the session create, the prompt and the permission reply, `TRANSIENT_RETRIES`); `session/delete` also always runs once the session exists, even after the limit, and adds one more 10 s request. claude-headless: 120 s for a live turn (`TURN_LIMIT`), and about 14 s for the `argv` spawn (`SETTLE` 2 s, `EXIT_LIMIT` 10 s, `STDERR_LIMIT` 2 s). claude (tmux): 240 s for `permission` (two `TURN_LIMIT` waits: one for the request, one for the stop), 120 s for `prompt/reply`, and about 21 s for `session start` (`STARTUP_TIMEOUT` 20 s plus the 1 s `INPUT_SETTLE`). The steps checked are opencode `spawn`, `events`, `session/create`, `session/read`, `interrupt/idle`, live `prompt/reply`, `permission`, `cancel`, and `session/delete`; claude-headless `spawn` and `live spawn`, and live `prompt/reply`, `report`, `permission`, `cancel`; claude `tmux`, `flags`, and live `session start`, `prompt/reply`, `permission`. Pure types, verdicts and rendering are in `crates/core/src/worker/verify.rs`. The command spawns its own child and stops only that child. It does not touch worker stores. The claude-headless spec starts a real `ralph worker-mcp` server, but its inbox and owner file live in the temporary directory.

The claude-headless, claude and opencode specs pick their model the way spawn does, with no spawn override: `resolve_claude_model` with `[claude] model` for claude-headless and claude (no model means claude's default model and no `--model` flag), `resolve_opencode_model` with `[opencode] model` for opencode (`DEFAULT_OPENCODE_MODEL` when unset). The config loads once per run in `worker_verify::run`. A resolve warning prints as an advisory `model` line that never fails the spec. The summary line names the model (`PASS: claude-headless 2.1.316 with model claude-haiku-5-5 (...)`, or `claude's default model`); cursor and codex summaries are unchanged, and the recorded version stays plain.

A full pass writes `{agent, version, live, verified_at}` to `verified-agents.json` in the config directory. All five harnesses gate at spawn through the one `check_agent_version` (`crates/ralph/src/version_drift.rs` loads `verified-agents.json`): Codex (`CODEX_GATE`) and claude-headless (`CLAUDE_GATE`) can refuse a version older than the minimum; Cursor (`CURSOR_GATE`), opencode (`OPENCODE_GATE`) and tmux claude (`CLAUDE_TMUX_GATE`, agent name `claude`) only warn (`soft_version_warning` turns every gate result, too old or unreadable included, into a warning, and a failed or timed-out probe stays silent). The opencode and tmux claude warnings join the spawn result text. Every spawn-time `--version` probe, claude-headless included, is bounded by `VERSION_PROBE_LIMIT` (10 s, `timed_output`). A free verify pass records the version, so it silences the warning for that version; the warning text ends with the verify command. The shared version gate (`VersionGate`, `check_agent_version`) and the drift decisions (`drift_action`, `record_outcome`, `drift_check_due`, `DriftRecord` stored as `drift.json` beside `verified-agents.json`) live in `crates/core/src/worker/version_gate.rs`; see [Version drift](#version-drift) for the drift file. A free pass records `live: false`; it never replaces a `live: true` record of the same version. For the version warnings a missing or unreadable file counts as empty. A pass never overwrites a file it cannot parse: `merge_verified` refuses, and the file stays as it was. Verify saves before it prints the summary, so it then prints FAIL with `passed but was not recorded` and exits non-zero. `write_json` writes through a unique temporary file in the same folder, so concurrent runs do not share one temporary name. It keeps the mode of an existing file and fails if it cannot copy it; a new file is 0600.

On a `spawn_worker` start the host writes the warning to `<id>.warning` beside the error file (`HandoffFiles::warning`) and `spawn_headless` appends it to the tool result instead of printing a terminal box; resume starts still print it.

A `beforeShellExecution` hook that returns `{"permission":"ask"}` skips that auto-approval in every approval mode, and prompts for a shell command. `agent acp` reads project hooks only from `~/.cursor/projects/<slug>/.cursor/hooks.json`, where `<slug>` is the session `cwd` with every run of non-alphanumeric characters made one `-` and the ends trimmed (a `.cursor/hooks.json` in the `cwd` itself is ignored). The spec writes the hook there for its own temporary directory, stops if that folder already exists, and removes the folder after the run on every exit path (`hooks cleanup` row). It touches no other `~/.cursor` file; a user hook in `~/.cursor/hooks.json` still runs too. If no request arrives, the failure names the hook path, because a changed slug or hook loader is the likely cause. Cursor also makes a hashed folder for the real path of the temporary directory (`/private/var/...` on macOS, the socket-dir rule in `cursor_leftovers.rs`); the spec removes it after the run only if it did not exist before (`cursor cleanup` row). The claude-headless permission check does not depend on user settings: its verify argv adds `--setting-sources project,local`, uses permission mode `default`, and `--allowedTools` lists only ralph MCP tools, so a file-writing shell command asks (`PermissionSetup::claude_headless`; a user `defaultMode` or `PreToolUse` hook in `~/.claude/settings.json` cannot approve it first, and the read-only `date` command was auto-allowed in a live run). The `--live` `mcp` check holds `system/init` to a connected `ralph-worker` server. `--strict-mcp-config` is set in both a real spawn and verify, and also in a tmux claude worker (`worker_launch`), so user, project `.mcp.json` and plugin MCP servers do not load. Only a paid `--live` run can confirm this in stream-json mode, and none has yet. The Codex spec is not affected: its `thread/start` sets `approvalPolicy: "on-request"`, `approvalsReviewer: "user"` and a read-only sandbox, which replace `~/.codex/config.toml` for that thread, and it starts without the ralph MCP server, so the file-creating prompt needs approval. `session/load` of a never-prompted Cursor session answers `Invalid params` (cursor-agent 2026.10.22), so the load itself runs after the live prompt. Cursor offers no way to delete a session, so each run leaves one Cursor chat behind. The opencode spec starts its own `opencode serve` (not the worker's `Server::launch`: no inbox environment variable, no server record) with the temporary directory as the working directory, and stops it with the worker's `Server::stop`, which also sweeps its process group. The `ask` rule effect and the `shell` action name come from the `permission.asked` fixtures and have not been run live. The claude spec runs the tmux worker, not the headless one, and its launch adds `--setting-sources project,local` before `--append-system-prompt` (`VerifyPaths::command` only; `worker_launch` and `worker_command` stay unchanged), so a user `defaultMode` or `PreToolUse` hook cannot approve the permission prompt first (`--settings` adds to user settings, it does not replace them): all state is in the verify temporary directory (store, settings, an empty `mcpServers` config, markers, the working folder), the settings hooks run this ralph binary against that store, and the tmux session `ralph-verify-<pid>-<ms>` is killed on every exit path. Answering the folder-trust prompt makes claude itself record trust for the temporary directory in its own config; the spec writes no `~/.claude` file. The free run passes no task prompt, so it makes no model call. `--live` pastes the prompt into the pane; its `reported` marker is pre-created so the Stop hook does not ask for a report. The `Enter` key that allows the permission request, and the 1 s wait before the first prompt, are not yet confirmed against a live claude. There is no cancel check for claude, and a claude pass silences the spawn version warning for that version. The permission and cancel prompts never ask the agent to stop, kill or signal anything.

### Version drift

When a spawn sees an installed version that its gate flags (newer than the probed one) and that is not in `verified-agents.json`, `drift_action` decides what happens (`crates/ralph/src/version_drift.rs`, pure parts in `crates/core/src/worker/drift_run.rs`). All five harnesses use it: tmux claude and opencode in `spawn_warning`, claude-headless in `check_installed_version`, Cursor in `agent_version_warning`, and Codex in `handshake` through `codex_gate`. Codex gets the trigger on a fresh launch only, because the inbox path comes from the handoff warning file, and a resume has none.

- `Verify`: the spawn starts `ralph worker verify <harness> --drift <version> --inbox <dir>` in a detached process group with null stdio. The two flags are hidden, never run `--live`, and are the only way to start a background run. `[workers] verify_on_drift = false` stops this start; the spawn warning stays.
- Lock: the spawn starts the background run without a lock; the run takes an exclusive OS file lock (`File::try_lock`) on `drift-<harness>.lock` beside `drift.json` and exits at once, doing nothing, when it does not get it. The file is opened or created with mode 0600 and without following a symlink, and it is never deleted or written. The run holds the lock for its whole life, and the kernel releases it when the process exits or is killed, so there is no stale lock and no takeover. Only a held lock (`WouldBlock`) counts as busy. Any other failure (symlink, hard link, directory, unwritable file, lock error) gives one inbox alert and a `drift.json` `Failed` entry with the `drift lock` check. The run does no verify, later spawns get `KnownFail` for that version, and a manual `ralph worker verify` clears it. The lock file stays in place.
- 120 s cap: the background run starts a watchdog thread. The free verify has its own 90 s budget (`FREE_VERIFY_LIMIT`), so a run that ends in time records its own outcome. At `drift_watchdog_limit` (`FREE_VERIFY_LIMIT` plus 30 s) the watchdog records a failed `time limit` check, posts the alert, then kills every child process group in the process-wide registry (`subprocess/groups.rs`: `spawn_piped`, the opencode verify server and `timed_output` each register their `process_group(0)` group at spawn and drop it when the child is stopped or its exit is reaped: the ACP worker's `reap_exit` unregisters the group when it reaps an agent that exited on its own), then its own process group (only when the process leads that group), and exits. Child agents die with it even though each runs in its own group.
- Pass: the version goes into `verified-agents.json` as for a manual run, and `drift.json` gets a `Passed` entry only when that save succeeded (`record_after_post`); after a failed save nothing is recorded, so a later spawn verifies again. Nothing else happens. The run and the watchdog share one claim (`DriftRun::plan`, `finish_plan`): the first to claim the outcome is the only writer of `verified-agents.json`, `drift.json` and the inbox, so a pass is never saved after a time-limit failure was alerted. A run that loses the claim waits up to 10 s for the watchdog to end the process, then exits and writes nothing; the exit frees the lock.
- Fail: one report goes to the inbox, and only after it posted does `drift.json` get a `Failed` entry with the failing check names (`drift_entry`, `record_after_post`); a failed post records nothing and the lock ends with the run, so a later spawn retries the alert. The post uses `Inbox::post` (worker `drift-<harness>`, status `warning`). The text names the harness, the last verified version (or `none`), the new version, the failing checks, and says that running workers keep the old binary until restart (`drift_alert`).
- Recorded pass: a `Passed` entry in `drift.json` for the same harness and version gives no action, even when `verified-agents.json` lacks that version (the file lost it some other way, for example it was removed or edited). This stops every spawn from starting a new verify. The spawn warning still shows, and a manual `ralph worker verify <harness>` repairs the file.
- No retry: a recorded failure for the same harness and version gives `KnownFail`. The spawn starts no run and no second alert, and its warning names the failed checks (`known_fail_warning`). Spawn is never blocked by drift.
- A manual `ralph worker verify <harness>` records its outcome in `drift.json` too (a pass only when its save succeeded), so a manual pass clears a recorded failure. A manual run posts no alert.
- Daily check: while `ralph chat` runs, the monitor tick (`DailyTick` in `version_drift.rs`) starts a detached `ralph worker drift-check --inbox <dir>` once per 24 h (`drift_check_due`). The hidden command stamps `last_check` in `drift.json` first, then probes `claude --version`, `opencode --version` and `agent --version` (10 s each, `daily_probe_plan`), and for each version that is drifted, unverified and not a known failure (`daily_verify_version`) starts the same background verify as a spawn. A missing binary or unreadable version is skipped silently. A watchdog ends the command and its process group after 45 s (`DAILY_CHECK_LIMIT`). Codex is skipped: its version comes only from the spawn handshake, and no sample of `codex --version` output exists to decode. claude-headless is skipped too, because it shares the `claude` binary with the tmux claude probe. `verify_on_drift = false` turns the daily check off. Nothing runs while chat is not running; the next chat start checks at once when `last_check` is missing or 24 h old.

`drift.json` lives beside `verified-agents.json` and is written through `write_json` (atomic, 0600). Two runs for different harnesses can overwrite each other's entry in a rare overlap; the next spawn then starts one more run.

## Worker lifecycle log

Each worker spawn, reply, report and close appends one line to `<store>/analytics/workers.jsonl`. The store is the canonical store path, the same string as `store` in `usage.jsonl` rows. The file holds no cost, tokens or session id; join on `store` and `worker_id` to read them from `usage.jsonl`. Every line is one JSON object written with one `write_all` on an `O_APPEND` file (`outcome_log::append`), with no lock. A reader must skip a torn last line. A write failure only warns and never fails the spawn or close. The pure builders and the encoder are `crates/core/src/worker/outcome_log.rs`. Unknown values are `null`, never `0`.

Common fields: `v` (`1`), `at` (RFC 3339, UTC, seconds), `store`, `worker_id`, `event`.

| event   | fields                                                                                           |
| ------- | ------------------------------------------------------------------------------------------------ |
| `spawn` | `ticket`, `tracker` (`linear`, `jira`), `harness`, `model`, `base_sha`, `scheduled`, `phase` (`plan`, `build`, `fix`, `live-check`) |
| `close` | `outcome`, `commit_count`, `dirty`, `duration_s`, `spawn_at`, `files`, `insertions`, `deletions`, `turns`, `merged_sha` (`null`), `ci` (`null`) |
| `reply` | `harness`, `interrupt`, `via_permission`, `text_bytes`                                           |
| `report` | `status` (`done`, `blocked`, `question`), `text_bytes`, `seq`                                   |

- `spawn` is written after the launch succeeds, so a spawn that fails and rolls back has no row. Rows are ordered by `at`, not by position in the file: a fast worker can append a report row before its own spawn row. The spawn record also keeps `harness`, read at close for `turns`. `base_sha` is the tip of the worker branch for a new branch. For a respawn on an existing branch it is the merge-base of the branch with the close base branch (`worker_base`, else origin HEAD, else `main`). It is `null` when git cannot find a merge-base, and never falls back to the tip.
- `phase` is the optional `phase` argument of `spawn_worker`, recorded at spawn and never inferred later. It is `null` when the argument is missing, and always `null` for a scheduled worker. Any other value is refused. Rows written before `phase` existed lack the field: read it as `null`. The close row has no `phase`: join on `store` and `worker_id`.
- `outcome` is `abandoned` when the close used the abandon flag, `forced` when the close used force on a worker of another chat, and `landed` otherwise.
- `commit_count` is the count of commits on the worker branch that are not on the base branch. It is `null` when the branch is gone.
- `dirty` is `null` when the worktree is gone.
- `turns` is the highest turn snapshot id of the worker at close. The spawn snapshot is turn 0, so the id equals the number of snapshots taken after spawn, one per turn boundary: the Stop hook of a claude worker (a Stop that the report check blocks counts again), the turn start of a codex worker. It is `0` for a worker that never finished a turn. It is `null` when snapshots are off or unreadable, and always `null` for a `claude-headless` worker, which takes no snapshots. The spawn snapshot (turn 0) is taken for every harness, so close picks the harness for this field with `worker::close_harness`: a live Cursor, Codex, claude-headless or opencode probe first, then the `harness` of the spawn record, then `Claude`. A claude-headless worker that is no longer running still logs `null`. A leftover live-probe marker (for example a stale cursor owner file) wins over the record, so such a worker can still log `0`. A record from an older release has no `harness`, so a dead claude-headless worker spawned by it logs `0`. A turn running at close may or may not be counted. If the spawn snapshot failed, the first turn snapshot gets id 0, so `turns` is one lower than the real count. The id survives pruning of old snapshots. Rows of an older release lack it: read it as `null`.
- `files`, `insertions` and `deletions` come from one `git diff --numstat <base_sha>..<branch>` run at close, before the branch is deleted. `base_sha` is the spawn row value, kept in the spawn record. After a respawn the range covers the whole branch and matches `commit_count`. This is the worker's own committed range, so it still shows the work after the branch merged into the base branch. The diff is two-dot: it compares the `base_sha` tree with the branch tip. If the worker branch was rebased onto a newer base, or the base branch was merged into it, the counts also include every commit that landed on the base in between, so they overcount. Uncommitted and untracked changes are not counted. A binary file counts as one file and 0 lines. All three are `null` when the spawn record or its `base_sha` is missing (a worker spawned by an older release), `base_sha` is not 7 to 40 or 64 hex characters, the branch is gone, or git fails. They are `0` only when the branch has no changed files. The close row of an older release lacks them: read them as `null`. There is no polling: the diff runs once per close.
- `duration_s` is the close time minus `spawn_at`, the time in the spawn record. Both are `null` when the record is missing or unreadable.
- `reply` is written after the send succeeds, by `Workers::reply` (`/reply`, `reply_worker`). A nudge writes no row. `harness` is the running harness, `claude` for a tmux worker. `via_permission` is true when the reply answered a permission request, by request id or because the worker awaited one; an interrupt is never a permission answer.
- `report` is written by the worker MCP server after it posts the report to the inbox. `seq` is the report number in that server process. A report posted by another program (`ralph inbox post`, a thread or version warning) writes no row.
- `text_bytes` is the UTF-8 byte length of the text. The row holds no text. For a report it counts the text as posted, with the attached change summary when there is one.
- A close that only removes leftover markers writes no row.

Each DuckDB query reads the whole file to infer its columns (`sample_size = -1`). Without it DuckDB infers from the first rows only, and a query on `phase`, `turns`, `files`, `insertions` or `deletions` fails with a binder error when the log starts with rows from an older release. To read several stores at once, pass a list of paths and add `union_by_name = true`.

Last close of each worker, with the cost of that run (DuckDB):

```sql
WITH last_close AS (
  SELECT *
  FROM read_json_auto('<store>/analytics/workers.jsonl', sample_size = -1)
  WHERE event = 'close'
  QUALIFY row_number() OVER (PARTITION BY store, worker_id ORDER BY at DESC) = 1
)
SELECT w.worker_id, w.outcome, w.duration_s, sum(u.cost_usd) AS cost_usd
FROM last_close w
LEFT JOIN read_json_auto('<config dir>/usage.jsonl') u
  ON u.store = w.store AND u.worker_id = w.worker_id AND u.kind = 'worker'
  AND CAST(u.at AS TIMESTAMPTZ) >= CAST(w.spawn_at AS TIMESTAMPTZ)
  AND CAST(u.at AS TIMESTAMPTZ) < CAST(w.at AS TIMESTAMPTZ) + INTERVAL 1 SECOND
GROUP BY ALL;
```

A worker id can run again after a close. The query keeps the latest close of each `store` and `worker_id`, and counts only usage rows from that close's `spawn_at` through the second of its `at`. Both are whole seconds and usage `at` keeps sub-seconds, so the upper bound is the next second. Limit: `cost_usd` is `NULL` when the close has no `spawn_at`. A usage row written after the close `at` is not counted.

Closes per outcome (jq):

```sh
jq -s '[.[] | select(.event == "close")] | group_by(.outcome) | map({outcome: .[0].outcome, n: length})' <store>/analytics/workers.jsonl
```

Spawn rows with the harness and model:

```sh
jq -c 'select(.event == "spawn") | [.worker_id, .harness, .model]' <store>/analytics/workers.jsonl
```

Spawn rows per phase (jq):

```sh
jq -s '[.[] | select(.event == "spawn")] | group_by(.phase) | map({phase: .[0].phase, n: length})' <store>/analytics/workers.jsonl
```

Diff size per phase of the last close of each worker (DuckDB):

```sql
WITH last_close AS (
  SELECT *
  FROM read_json_auto('<store>/analytics/workers.jsonl', sample_size = -1)
  WHERE event = 'close'
  QUALIFY row_number() OVER (PARTITION BY store, worker_id ORDER BY at DESC) = 1
),
spawns AS (
  SELECT *
  FROM read_json_auto('<store>/analytics/workers.jsonl', sample_size = -1)
  WHERE event = 'spawn'
  QUALIFY row_number() OVER (PARTITION BY store, worker_id ORDER BY at DESC) = 1
)
SELECT s.phase, count(*) AS closes, sum(c.files) AS files, sum(c.insertions) AS insertions, sum(c.deletions) AS deletions
FROM last_close c
JOIN spawns s ON s.store = c.store AND s.worker_id = c.worker_id
GROUP BY ALL;
```

The join takes the latest spawn of each worker id, so a reused id counts once. `phase` is `NULL` for a spawn row written before `phase` existed and for a scheduled worker.

Turns and diff size per close (DuckDB):

```sql
SELECT worker_id, turns, files, insertions, deletions
FROM read_json_auto('<store>/analytics/workers.jsonl', sample_size = -1)
WHERE event = 'close' AND turns IS NOT NULL
ORDER BY turns DESC;
```
