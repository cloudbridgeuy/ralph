# Headless workers

Worker hosting and chat-owned lifetimes are separate from the selected agent. For spawn, reply, reporting and close behavior, see [ralph chat](ralph-chat.md#mcp-tools); for home-directory cleanup, see [Worker leftovers](worker-leftovers.md).

## HarnessId and compatibility

`HarnessId` (`crates/core/src/worker/kind.rs`) selects the agent and describes how its worker is hosted:

| Harness | Name | Hosting |
| --- | --- | --- |
| `Claude` | `claude` (default) | One tmux session per worker |
| `Cursor` | `cursor` | One `agent acp` child per worker, owned by `CursorHost` |
| `Opencode` | `opencode` | One session per worker on the chat's shared `opencode serve`, owned by `OpencodeHost` |
| `Codex` | `codex` | One `codex app-server --listen stdio://` child per worker, owned by `CodexHost` (`crates/ralph/src/codex_worker.rs`) |

`HarnessId` replaces the old Cursor boolean in `RunningWorker`, `WorkerObservation` and `CloseState`, and spawn commands carry it. The separate `opencode` boolean remains as agent/session metadata, not the hosting discriminator. For example, `close_plan` can remove an old opencode session before closing a claude worker when that metadata is present.

`RunningWorker.kind` serializes as `"kind": "claude"`, `"cursor"`, `"opencode"` or `"codex"`. Its serde `alias = "cursor"` and `HarnessId`'s custom deserializer let old records with `"cursor": true` load as `Cursor`, `"cursor": false` as `Claude`, and the old `"tmux"` kind string as `Claude`. If neither field is present, the kind defaults to `Claude`; the `opencode` boolean does not infer a kind. Saving emits `kind`, not the old `cursor` key. Unknown kind strings are rejected. These are serialization compatibility rules, not a migration of the harness-specific owner/session files.

The shell discovers running kinds from tagged tmux sessions, this chat's Cursor owner files, Codex owner files and opencode owner files (`workers::running_workers`). Close separately derives the kind from a Cursor owner file first, then a Codex owner or session file, then an opencode owner or session file, otherwise `Claude`; a worktree's `opencode.json` supplies cleanup metadata but does not by itself select `Opencode`. The monitor captures panes only for `Claude`; checks for the headless harnesses use markers and omit tmux attach hints (`chat/monitor.rs`, `core/src/worker_check.rs`).

## One host per harness, owned by the chat

`HeadlessHost: Send + Sync` (`crates/ralph/src/workers/headless.rs`) is the shared lifecycle interface, not a per-worker interface:

| Method | Contract | Current implementations |
| --- | --- | --- |
| `resume(&self)` | Resume persisted workers or supervise shared resources on a dedicated thread | `CursorHost` calls `resume_all` to load eligible ACP session records; `OpencodeHost` runs its server/event supervision loop (its constructor loads session records) |
| `poll(&self) -> bool` | Process queued worker requests; return false after host shutdown to end the poller | Each host consumes its own handoff directories; opencode also handles preflight requests |
| `shutdown(&self)` | Stop this host's resources at chat exit, never on an individual close or report | Cursor terminates its owned worker groups, including starts in progress; opencode stops the shared server process group and sweeps tracked descendants |

`chat::monitor::watch_headless` constructs `HeadlessShutdown` with an `Arc<dyn HeadlessHost>` for each of `CursorHost`, `OpencodeHost` and `CodexHost`. Each host gets a separate resume thread and a separate poll thread, sleeping `HANDOFF_POLL` (250 ms) between polls. Blocking ACP or HTTP handoffs therefore do not hold up the other host or the status/check loop.

Cursor's `AcpWorker` and opencode's per-session `OpencodeSession` implement the core `HeadlessWorker` port (`capabilities`, `send`, `poll`). `send` runs `decide` first, then maps `Prompt`, `AnswerPermission` and `Close`; `Spawn`, `Resume` and `Interrupt` return an error because the host handles them (interrupt keeps the inherent `AcpWorker::interrupt`, which needs the result entry id). Turn start, turn end, permission changes and close push `WorkerEvent`s to a per-worker sink. Each 250 ms `CursorHost::poll` drains every worker, runs `reduce` and applies the effects: `blocked` and `waiting` markers are set and cleared there, and close clears `ready`, `blocked` and `waiting`. `unreported` and its `waiting` write stay direct; the `ready` write at spawn stays direct; `ReplyText` effects are ignored. `OpencodeSession` is a short-lived view built per request by `OpencodeHost::worker` (the API handle, the front pending permission and the session's shared event sink). Its `send` maps `Prompt`, `Interrupt` (full: a synchronous `POST /api/session/{id}/interrupt`, whose `{"interrupted":bool}` body becomes `WorkerEvent::Interrupted`; a failed call warns and yields outcome `None`), `AnswerPermission` and `Close` (`DELETE /api/session/{id}`, then `Closed`); `Spawn` and `Resume` return the host-handles-it error. `OpencodeHost::run` turns each `Effect` into events (`Ready`, `TurnStarted`, `PermissionAsked`, `PermissionSettled`) and `apply_events` polls them, runs `reduce` and applies the marker effects at once; `reported` clear, `unreported` and its `waiting` write, and the ready write at spawn stay direct. The interrupt outcome reaches chat through `<store>/opencode-interrupt-result/<id>/<entry>` (`cancelled` or `sent`), awaited by `Workers::reply` like Cursor's; a failed interrupt writes nothing, so chat reports the outcome unknown after 30 s. ACP `decode_update` emits `WorkerEvent::Activity { at }` for every `session/update` frame (plus `Reported` for the report tool call), and the notification handler writes it to the activity marker through `Heartbeat::touch_at`. opencode's `session_activity` does the same for every session-tagged SSE event; `OpencodeWorker::route` writes it through `touch_at` (turn start and end still call `set_running`).

The chat keeps the `HeadlessShutdown` guard alive across its input loop. Dropping it, including on an early error return, shuts down hosts in reverse construction order. `ExitCleanup` holds clones of the same hosts: on input loss it kills watches, calls each host's shutdown, then the input watcher exits the process. Shutdown must tolerate repeat calls. It is per host and chat-owned, not per worker: `close_worker` uses worker-specific close handoffs and never calls `HeadlessHost::shutdown`. Closing even the last opencode worker leaves the server available for the next spawn; a report does not stop either host.

## Adding the next headless harness

The shared trait unifies lifecycle orchestration only; it is not a plugin registry or a generic spawn/reply protocol. A future headless Claude or Codex adapter needs the following wiring, following the existing Cursor and opencode implementations:

1. Add the harness choice, argument validation and MCP schema in `crates/core/src/worker.rs`, and its preflight/spawn handoff in `crates/ralph/src/workers/spawn.rs`. Today `claude` still means tmux. `codex` is served by `CodexHost`; `spawn_headless` in `workers/spawn.rs` is shared by cursor and codex.
2. Add a `HarnessId` variant if it uses a new hosting mechanism. Update both `HarnessId`'s serialized variants and its compatible deserializer; preserve the old boolean mapping and default. Extend running-worker discovery, ownership, reply/nudge/permission routing and close-kind detection in `workers.rs`, plus pane/check handling in `chat/monitor.rs` and `core/src/worker_check.rs`. These paths still have explicit harness/kind branches.
3. Implement `HeadlessHost` for the adapter and register one host in `HeadlessShutdown::new`. Keep resume/supervision and request polling independent, honor the closed state and make shutdown safe to repeat. No new harness-specific lifecycle loop or exit guard belongs in chat orchestration.
4. Keep worker close separate from host shutdown. Extend the pure `close_plan`/`CloseStep` dispatch in `core/src/worker/ownership.rs` and the shell's step executor only as needed. Shared resources must survive another worker's close. Keep home-directory cleanup explicitly scoped by kind, rather than treating every non-tmux worker as Cursor.
5. Reuse the worktree, marker and `ralph-worker` report contracts. Add pure/unit coverage for serialization compatibility, close isolation, discovery/check behavior and lifecycle dispatch, following the existing tests; update the harness details and cleanup docs alongside the adapter.

## Codex hosting

`CodexHost` (`crates/ralph/src/codex_worker.rs`) mirrors `CursorHost`. Spawn writes `<store>/codex-spawn/<id>`; the host starts `codex app-server --listen stdio://` in the worktree and writes the owner file `<store>/codex/<id>` at once. Pure protocol lives in `crates/core/src/worker/codex/` (`rpc.rs`: framing and request ids; `protocol.rs`: params, version, login and model checks, MCP startup verdict).

Start order, all inside a 20 s deadline: `initialize` (`experimentalApi`), `initialized`, version check, `account/read`, `model/list` (always, paged; checks model and effort), `thread/start` or `thread/resume`, wait for `mcpServer/startupStatus/updated` of `ralph-worker` to reach `ready`, `turn/start` with the task as the first turn, then `ready/<id>`. The session record is written after the first turn ends ok, not before it. Version rule: older than 0.162 fails; 0.162.x passes; 0.163 or newer passes with a warning through `crate::warn::warn`, even 0.164.0 itself, because the check compares only major and minor against 0.162 (probed 0.164.0; 0.162.1 earlier).

`thread/start` sets `approvalPolicy: "on-request"`, `approvalsReviewer: "user"`, `sandbox: "workspace-write"` and a runtime `config.mcp_servers.ralph-worker` entry (`required: true`, `default_tools_approval_mode: "approve"`, so the `report` tool needs no elicitation). Server requests that are not approvals (and approvals of a stale `turnId`) are answered with JSON-RPC error -32601, so they fail closed. Approvals follow the permission flow below.

`resume` is Partial: needs saved history, worktree and codex login; `close` is Partial: global trust entry left in ~/.codex/config.toml (GUZ-649, see Codex resume and close). `heartbeat` is Partial: app-server frames count as activity, not progress; silent long tools can yield false Quiet; 300 s default (GUZ-648). Every app-server stdout line (handshake, deferred, hook and unmapped frames included) calls `Heartbeat::touch`. A notification that ralph does not map is logged once per method per worker to `acp-logs` with tag `unmapped`, never to the chat. `TurnStarted` and `TurnEnded` set the running flag. Child exit shows as stdout EOF in the pump thread or as `try_wait` in `CodexWorker::poll`; a shared flag lets the first one write `gone/<id>` and push `ProcessGone` once, and never after a close; `poll` always `try_wait`s a live child, so an EOF-first exit is still reaped. Live check (codex-cli 0.164.0, `worker_quiet_secs = 10`, `worker_check_secs = 2`): during `sleep 75` frames came at gaps of 31, 17 and 20 s, giving 3 Quiet episodes, 3 `quiet` alerts and 3 recoveries; an idle worker posted no Quiet; an unmapped `skills/changed` frame touched activity while idle; `kill -9` of an idle app-server posted one Dead message within 1 s, none in the next 25 s, and the child was reaped. `perm-ask` is Partial: protocol-raised requests only. `perm-yolo` is Partial: single-request accepts only (GUZ-647). `interrupt` is Partial: outcome unknown after 30 s.

Codex permissions (GUZ-647): `[codex] permissions` (`"ask"` default, `"yolo"`) is read when a worker starts; a wrong value warns and uses `ask`. Pure classification is in `crates/core/src/worker/codex/approvals.rs`; the queue, `blocked` marker and one `blocked` inbox report are the same host code Cursor uses (`crates/ralph/src/permission_queue.rs`, `PermissionOption`/`BlockedContent`/`PermissionMode` in `core/src/worker/permissions.rs`). Handled requests: `item/commandExecution/requestApproval` (options are the request's `availableDecisions` strings, or accept/decline/cancel when absent), `item/fileChange/requestApproval` (accept/decline/cancel), `mcpServer/elicitation/request` (accept/decline/cancel when `_meta.codex_approval_kind` is `mcp_tool_call`, else decline/cancel) and `item/permissions/requestApproval` (only `decline`, which grants nothing). `acceptForSession`, `*Amendment` decisions and persist options are never published or picked. Replies are `{decision}` for commands and file changes, `{action}` for elicitations (no `persist`, no `content`) and `{permissions: {}, scope: "turn"}` for a grant. `yolo` answers `accept` at once for commands, file changes and tool-call elicitations when `accept` is offered; everything else waits for the person. The person answers through `reply` (`<store>/codex-answer/<id>`, an exact `optionId`); the front request gets the answer. `serverRequest/resolved` drops the request and clears the marker when none remain; an interrupt drops all pending requests without answering, because Codex settles them itself. A later answer for a settled request is refused through `codex-error/<id>`. `item/permissions/requestApproval` never fired in the probes, so that path is untested live.

Codex interrupts use the Cursor transport: `reply` writes `<store>/codex-interrupt/<id>/<entry>` and polls `<store>/codex-interrupt-result/<id>/<entry>` (250 ms, 30 s). `Turns` reads the turn id from the `turn/start` reply (`result.turn.id`; `turn/started` is the fallback). A running turn gets `turn/interrupt {threadId, turnId}`, sent without waiting for its reply. The result file says `cancelled` only after `turn/completed` of that turn with `status: interrupted`; the interrupt prompt starts right after, before queued replies. An idle worker, or a `-32600` reply, writes `sent` (nothing cancelled) at once. A missing reply writes nothing, so chat reports the outcome unknown. Frames that arrive while a request waits for its reply are kept and handled in order afterwards, and events whose `turnId` is not the current turn are dropped. The interrupted tool process keeps running (ralph does not kill it); its late events carry the old `turnId` and are dropped.

Live check 2026-10-23, codex-cli 0.164.0 (`ralph chat` reply tool): `turn/start` replied `result.turn.id`. An interrupt during `sleep 60` sent one `turn/interrupt`, which got `{}`, then `turn/completed` `interrupted` in the same second, and reply said cancelled. The next `turn/start` followed at once, and its report was counted. The sleep kept running, and its `item/completed` came 8 s into the next turn with the old `turnId`. An idle interrupt sent no `turn/interrupt`, and reply said nothing was cancelled. No `-32600` or missing reply happened, so those paths were not tested live.

Permission live check 2026-10-23, codex-cli 0.164.0, a network `curl -sI` under `on-request`. Ask: `item/commandExecution/requestApproval` offered `[accept, acceptWithExecpolicyAmendment, cancel]`. `blocked/<id>` listed only `accept` and `cancel`, with one `blocked` inbox report. The reply `accept` sent `{"decision":"accept"}`, Codex returned `serverRequest/resolved`, and the command ran. Yolo: the same request got `{"decision":"accept"}` in the same second, with no marker and no `blocked` report. Interrupt while blocked: ralph sent no answer. Codex ended the turn `interrupted` and resolved the request itself, the marker cleared, reply said cancelled, and the next prompt ran. File-change, elicitation and permissions-grant requests did not come up, so they were not tested live.

Codex replies use the Cursor transport: `reply` writes `<store>/codex-prompt/<id>/<entry>`, `CodexHost` polls it and hands the text to the worker, whose pump thread holds it in the shared `PromptQueue` (`crates/core/src/worker/codex/turns.rs`). The next `turn/start` goes out only after `turn/completed`, because the GUZ-643 probe showed a `turn/start` during a running turn merges into it. `item/completed` of an `mcpToolCall` (`ralph-worker`, `report`, `completed`) emits `Reported`. A turn that ends without a report gets one `REPORT_REMINDER` turn; if that also ends unreported the worker writes the `unreported` and `waiting` markers, as Cursor does. A failed turn, or one that ends with a stop reason, posts a `blocked` prompt-failure report to the inbox as Cursor does; an interrupted turn posts nothing. Each turn end takes a snapshot first (unless closing), before any reminder or queued `turn/start`. Stdout EOF writes a `gone` marker unless the worker is closing. Close order and the leftover trust entry are in Codex resume and close.

### Codex resume and close

Record (GUZ-649): `<store>/codex-session/<id>` holds `session_id` (thread id), `cwd`, `inbox`, `store`, `model`, `effort` and `permissions`. It is written after the first ok turn, kept on chat shutdown, and removed by explicit close (a worker quit before its first ok turn has none). The rollout under `~/.codex/sessions` is never touched.

Resume runs on chat start (`CodexHost::resume_all`, `crates/ralph/src/codex_worker/resume.rs`, decision in `core/src/worker/codex/resume.rs`). It claims `<store>/codex/<id>` atomically (create-new); if another chat owns it, the id is skipped with `codex session <id> not resumed: a running chat owns it`. A skip or failure warns and writes `codex-error/<id>` (not for the owned case); the record stays. Strings, all prefixed `codex session <id> not resumed: `: `its record is unreadable`, `the record has no owner`, `it belongs to the chat store <a>, this chat uses <b>`, `its worktree <path> is gone`, `could not claim it: <e>`, `could not find the ralph executable`, then the start error. A resumed worker sends `thread/resume` with the record's model, effort and permissions, checks the returned thread id equals the record's (else `codex resumed thread <a> instead of <b>`), posts no replayed report, and on success removes `codex-error/<id>` and warns `codex session <id> resumed`. `[codex] model` and `effort` are validated against `model/list` at spawn.

Close order (`codex_close_plan`): wind down (mark closing, drain pending permission requests and RPCs), wait up to 3 s (`CODEX_CLOSE_TURN_WAIT`) for a running turn to end after `turn/interrupt`, drop stdin, snapshot the descendant tree with each start time, TERM then KILL the app-server group, sweep the snapshot entries whose pid and start time still match, then check again after KILL and log any survivor to `acp-logs` with tag `sweep`, remove the owner file. Close then removes `ready/<id>`, the session record and the close marker.

`thread/start` writes a global `[projects."<repo>"] trust_level = "trusted"` entry to `~/.codex/config.toml`. Ralph does not restore it (GUZ-585 class).
